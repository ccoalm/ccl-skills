# Product R&D Workflow

The top-level workflow for product development, feature delivery, refactoring, release preparation, and process improvement. It does not replace stack skills; it decides which skill owns each stage and what evidence each stage needs.

A stage's full text is in the reference at its firing point. Naming a reference is not loading it; a summary never narrows it. All references: `references/stage-classify-and-route.md` §Reference Loading.

| Firing point | Load |
| --- | --- |
| A class, owner, entry or Scope rule the summaries leave open | `references/stage-classify-and-route.md` |
| A multi-step plan, implementation task breakdown, or first implementation edit | `references/stage-plan-and-design.md` |
| The first implementation edit, a complete/fixed/passing claim, commit, push, or merge request | `references/stage-quality-and-landing.md` |
| Before finalizing after a slice lands or after a stated next action | Pre-Final Continuation Gate below |

**Entry precedence.** For any product idea, feature delivery, release, cross-cutting refactor, or a **restart/redo of an in-flight delivery**, invoke this workflow first to classify and route — naming a stack/execution skill (e.g. `web-react-dev`, `multi-agent-delegation`) does not by itself skip this workflow's lifecycle gates (design / test / release / acceptance); those still apply unless already covered.

**Continuation-proposal output contract (session-wide for product delivery).** Use `proposed-next: <action and scope>` to make a next action observable, or `proposed-next: none — status only` for a status-only handoff. A missing, repeated, or conflicting marker triggers intent recovery, not a stop. Follow the current explicit user request; bind short assent to one recoverable concrete proposal and its scope. Repair your own formatting without asking the user to repeat an already-clear instruction. Markers never grant authority. Recovery, ambiguity, and outcome rules: `references/pre-final-continuation-gate.md` (Continuation-proposal output contract).

- **Restart/redo of an in-flight delivery** (清除代码重新开发 / 推倒重来 / redo-from-scratch) is a fresh entry: re-classify and re-establish the plan; "重来" discards code, not the design/spec, unless the user opts out of the design (§Baseline Selection).
- **Implementation entry / re-entry gate (active plan/spec required by default).** "Start development" first establishes the current executable artifact set (specs, plans, task docs read back or just produced, checked for freshness, scope, owners, acceptance, tests, stop conditions, and landing state), then codes against it; requests sent elsewhere by *Go straight to the owning skill* use that owner's entry rules.
  - Only an unmerged plan/spec on the active delivery branch is the baseline; anything else needs recorded user selection. A bare "continue" is not a waiver: context summaries, compacted memory, and previous-response residue are not establishment; the **first implementation edit** is the gate.
  - Before that edit, record the implementation boundary (baseline, scope, implementation owner loaded in-session, `multi-agent-delegation` decision, visible-UI record with `product-ui-ux-design` loaded, `feature-risk-router` inventory, test-case-first status; each gate triggered or `not-applicable` with a reason). **Load `references/implementation-entry-reentry-gate.md` before recording the boundary**: every owner-naming field follows its invoke bar — delegation being plausible at all loads `multi-agent-delegation`, including when you record `local`. Reaching the first implementation edit without this boundary record is a process defect.
  - Closeout backstop: a slice reported done without loading a triggered owner stays process-incomplete until that owner's post-hoc audit is recorded (§Closeout Backstop).
- **Go straight to the owning skill instead** for a narrow stack fix or diff review, a security-only audit, a single-symptom defect (→ `defect-diagnosis`), a retro or skill-edit question (→ `skill-extraction-workflow`), or a process skill the user names as the primary action, returning here when it hands off to a delivery stage. Before implementing, a narrow fix that changes a shared deterministic gate/verifier or shared/cross-repo contract/status/version/release/compatibility semantics, wherever it lives (code, config, scripts, generated artifacts), re-enters the shared-gate classification below.
- A process skill suggested by a session-start prompt, optional package, or skills listing (brainstorm, plan-writing, TDD) does not replace this entry; only a host-authored preflight runs first. Call that skill inside the stage it serves. External skills never replace CCL ownership, become required gates, or block delivery when absent (`references/external-skill-augmentation.md`).
- `multi-agent-delegation` owns the delegated execution recipe and worker verification; this workflow owns the lifecycle gate. Resumed delegated agents receive or re-verify the current plan/spec before editing.
- A multi-repo delivery, or a change to remote branch, MR, pipeline, release, or deployable state, keeps a per-unit delivery-status ledger (`references/status-tracker-sync.md`) before a done or merge claim or the next slice; a required gate passes only at `success`, `not-applicable`, or `not-required`. Risk acceptance never authorizes merge, push to the default branch, or cleanup; those need the user's explicit merge instruction (`worktree-isolation`).
- **Precedence order:** explicit user instruction > this workflow's stage/gate ownership > optional-package defaults. Naming an executor is not a gate waiver; an opt-out must be stated as one.

## Scope

Each line summarizes a rule; full text: `references/stage-classify-and-route.md` §Scope.

- Product shaping builds a per-point **acceptance-coverage matrix** (one independently-failable behavior = one point, plus its risk points, each with an observable check; `references/delivery-lifecycle.md` §Product Shaping Checklist).
- **Implementation completeness/minimality gate.** For behavior-changing delivery, or one claiming the refactor/mechanical exemption — functional completeness and structural minimality are independent gates — and gaps block `complete`: load `references/implementation-completeness-and-minimality.md` before implementation and again before a completion claim.
- Product requirement artifacts: route clarification to `requirement-intent`, current-state evidence to `requirement-baseline`, scope to `requirement-scope`, and Ready-only PRD assembly to `requirement-doc-writer`; this workflow owns the `PRD Ready` / `PRD Not Ready` verdict, which "只写个 PRD / 不走流程" still needs; you must load `references/stage-classify-and-route.md` §Workflow step 1 before issuing it.
- Design routing: decide when interaction, information architecture, visual system, or UX acceptance work must happen before implementation.
- Architecture routing: a backend design must load `software-architecture` before drafting.
- Development routing: `app-cross-platform-dev` for Flutter/Android/iOS apps, `miniapp-product-dev` for mini-programs, `web-react-dev` for React web, `terminal-cli-dev` for terminal/TUI surfaces and the command/subcommand/flag/help contract, which it owns even when nothing is rendered; CLI/tooling without terminal-UI concerns must go to that language's dev skill when one owns it (`go-microservice-dev`, `python-service-dev`, `nodejs-service-dev`) and must not fall back to `terminal-cli-dev` merely because it is a command; a CLI in a language with no such dev owner stays with `terminal-cli-dev` as the default CLI owner, `go-microservice-dev`/`python-service-dev` for Go/Python services, and `nodejs-service-dev` for Node.js services; `typescript-dev` joins any of these for the TypeScript language and compiler layer.
- Research routing: For research groundwork behind a selection or assessment decision, this workflow must call `multi-perspective-research` for an evidence-grounded brief; the verdict stays here.
- Product R&D standards docs: you must use the R&D standards checklist in Workflow (`references/rd-standards-doc-family-checklist.md`); standalone wording requests go to `tighten-doc`.
- High-risk resilience gating: when a feature touches money, billing, quota, permissions, tenant/user data isolation, privacy, high-impact AI answers, write-finality risk, repeated submission, async job finality, or incident explanation, require an explicit resilience gate before implementation or launch (`references/high-risk-resilience-gates.md`); product defines the visible degradation/refusal before engineering ships fallback, retry, or downgrade.
- Surface-specific rules, full text in the reference: AI/algorithm launch, user-visible tips, nudges, release notes and update notices, developer-facing surfaces (`references/verify-developer-experience.md`), artifact egress across the trusted boundary (`references/artifact-egress-confidentiality.md`, before the write/send call), upstream decision propagation, standards-to-health-gate propagation, and §Generalization Discipline for shared artifacts.

## Workflow

At each stage boundary, walk the per-stage entry-state enumeration in [Stage-Entry State Checklist](references/delivery-lifecycle.md#stage-entry-state-checklist) — confirm every required state already exists before crossing into the next stage; it points to the owning gate for each criterion rather than restating it.

1. Classify the work.
   - **Diagnostic spec-match baseline gate** (before any current-state/spec-match judgment or change recommendation): when a request combines a diagnostic verb with a spec-match semantic, do NOT treat the user's single-utterance description as the authoritative spec — identify the evaluation baseline source first, and record it before the diff lands. Details live in `references/diagnostic-spec-match-gate.md`.
   - Classes, each with a rule in `references/stage-classify-and-route.md` §Workflow step 1: product feature, requirement artifact, project assessment, quality remediation program or quality baseline (load `references/quality-remediation-program.md` before any refactor), architecture change, workflow/skill change, implementation, bug, release, AI/algorithm launch (`references/algorithm-launch-sop.md` §9).
   - Unclear risk goes to `feature-risk-router`; it is required for permission/access, money/quota, write-finality, data migration, cross-service API contract, AI inference/evaluation, release-ops, or unclear verification scope. A failure in any High-risk resilience gating class loads `references/high-risk-resilience-gates.md`.

2. Route responsibilities. This workflow owns intent, acceptance, and sequencing; the named owner owns each stage's substance (owner list: `references/stage-classify-and-route.md` §Workflow step 2). When 2+ slices look independent, surface `multi-agent-delegation`; it decides serial or parallel.

3. Plan and design. Plan depth scales to risk (`references/delivery-lifecycle.md` §Plan Authoring).
   - You must load `references/stage-plan-and-design.md` at its firing point above; a design drafted under this entry applies the lines below.
   - Reuse a usable spec/plan/assessment/task-doc set as re-entry; create or supersede a missing or stale one before implementation. A multi-step assessment-fix-test request needs a reviewed plan before code.
   - **Optional Feishu requirement record:** only when requested. Create or reuse only the requested resource; do not provision unrelated tables or impose a repository-wide schema.
   - **Spec / repo-contract sync gate**: before implementation, name the active contract layer (product spec, technical design/ADR, repo-local `AGENTS.md`) and update it in the same slice when a stable boundary changes. **Whenever the slice touches any upstream-owned value set, asserts the upstream is silent, or updates the owning spec/ADR or nearest repo-local contract, load `references/sync-spec-repo-contract.md` first**; for any upstream the slice depends on, cite the access-controlled pointer + revision rather than the copied value.
   - **Technical design gate.** Work that is cross-repository, multi-client, touches a contract/API with an external consumer, or is high-risk per High-risk resilience gating (two or more accountable teams, deployable clients, or contract/API consumers count) gets a review-altitude technical design before the task breakdown or code: interface/contract, architecture and data flow, key decisions with rejected alternatives, failure modes, contract impact, and high-risk handling (idempotency, server-side quota/rate-limit enforcement, concurrency, abuse, rollback). Exemption needs a short risk inventory; unknown consumer or risk scope escalates to `feature-risk-router`. A product spec or code-level plan does not stand in for it.
     - Owner-skill ownership covers both design substance and the review gate. A deliverable spanning more than one owning skill loads the complete owner set during design; an external model is supplement-only (`references/dispatch-owner-skills.md`).
     - **Owner-dispatch firing gate (non-exempt multi-owner designs only):** the complete owner set is recorded as an owner-dispatch map that gates **the START of design-substance production, not only design completion** — build it BEFORE drafting any design doc / test plan / architecture decision — and re-confirm it before the first implementation edit; a partial dispatch does not satisfy it, and an all-`N-A` map means single-owner work.
     - **Owner-dispatch mechanical firing (opt-in, per product repo):** at closeout of a gated multi-owner delivery, `owner-dispatch.sh status` must read `opted-in: yes`, or install the gate or record why exempt (`scripts/owner-dispatch/README.md`).
     - **Mechanism-operability check** fires whenever the design proposes new mechanical enforcement or verification machinery, **and again when a landing withdraws or downgrades the evidentiary claim an existing mechanism rests on** — load `references/design-review-gate-mechanics.md` before proposing the machinery, and before landing the withdrawal.
     - The design review is recorded, not implied; load `references/design-review-gate-mechanics.md` before invoking the independent review, before merging a triggered diff, and whenever the candidate changes after a review. Its rules: a recorded adversarial review with objections, disposition, and reviewer identity; it binds to the implementation diff; any post-review change, tests/docs included, triggers a full-scope rerun; human/team sign-off applies to high-risk money/permission/data or breaking external APIs before merge/launch, never before implementation. Explicit stricter rules still bind. Reaching implementation with only spec plus plan on triggered work is a process defect.
   - **Cross-repo feature coordination** loads `references/cross-repo-coordination.md`; **concurrent sessions** each get their own worktree on a unique branch before editing (`worktree-isolation`).
   - For any code change, include a test-layer decision table before implementation (`unit`, `integration/contract`, `E2E/host smoke`, `manual/exploratory`), each row `run`, `add`, `not applicable`, or `blocked` with command and reason; behavior-neutral changes record `not applicable: behavior-neutral/docs/config-only`. Dormant-code activation is behavior-changing (`references/dormant-code-activation.md`).

4. Enforce quality gates.
   - You must load `references/stage-quality-and-landing.md` at its firing point above; the lines below are its hard stops, not the full text.
   - Never mark work complete because a workaround hides the issue; never delete, skip, or weaken a failing test to pass; never fabricate verification, review status, or links.
   - Never claim complete, fixed, or passing without fresh verification evidence from the current turn — load `references/delivery-lifecycle.md` §Completion Evidence Gate before that claim or any independent review; external review is the backstop for what the audit missed, never the substitute that makes it optional.
   - Before sharing, publishing, syncing, committing, or opening a merge request for a deliverable doc (any human-readable artifact for another reader), confirm `tighten-doc` ran on it this turn with a one-line evidence note, or record a user-directed or blocker waiver.
   - Before coding any visible UI change, load `references/design-routing-and-readiness.md` and its canonical `../product-ui-ux-design/references/delivery-contract.md`; create the full Design brief or valid low-risk copy-only record and obtain Test Phase 0. Non-rendered client changes record `visible surface: no` and the reason.
   - For behavior changes, test-case-first is the default gate: write the test case before implementation, map it to a layer and command, and run it RED before coding; if code changed first, stop, add the missing test-case register, and do not claim TDD. Every code change runs at least one relevant test layer before completion; closeout labels are `complete`, `pre-runtime-test-ready`, or `blocked`.
   - After code/test edits, deep self-review in the main agent, then invoke `code-review` automatically before completion. Timeout, empty, or inconclusive review stays pending, never passed.
   - For product/spec normalization, standards-to-health-gate work, or any change that edits a shared deterministic gate/verifier or a cross-repo contract/status/version/release/compatibility coordination surface, this workflow classifies the artifact before implementation (`spec/plan`, `gate design`, `gate implementation`, `status sync`, `runtime/code`), then routes it through `feature-risk-router`'s `shared-gate` decision before shared push or merge (`references/shared-gate-artifact-classification.md`).
   - Landing labels need matching evidence; a protected or unknown default branch lands through branch plus merge request, and MR creation is not merge authorization.

5. Close the loop. Route reusable lessons through `skill-extraction-workflow` before choosing the target skill, and run the Pre-Final Continuation Gate before the final response after any landed slice; a merge-and-sync checkpoint is a handoff point, not an end point.

### Pre-Final Continuation Gate

Run this gate before finalizing a product R&D turn after any delivery slice lands, on every user reply immediately following an assistant message that states or implies a next action, and on any explicit continuation request. Recover the intended action from the current request and relevant conversation; a malformed or absent marker alone never selects `blocked:`. Report, on its own line, `continuing: <action and scope>` for work you will execute, or `blocked: <action and scope> — <specific blocker>` when no authorized work can proceed; `proposed-next:` never replaces it. A blocked dependent action may remain pending while a different authorized action continues. Apply landing checks only to actual landing claims; an already-authorized local investigation does not require inventing a prior landing. Details: `references/pre-final-continuation-gate.md` (Gate triggers and outcome contract).

1. Confirm the landing state from real evidence (local branch, remote sync, MR/review artifact, CI/pipeline when applicable, review/challenge status when required, status-doc sync, dirty worktree), proving the landing before reading any document (for the remote-backed default, fetch/update the target ref from its remote immediately before classifying the slice landed) per `references/pre-final-continuation-gate.md` (Landing-state proof); content/tree/patch equivalence never by itself proves a slice landed.
2. Inspect the current product/status source of truth, issue list, repo-local next-step artifact, unresolved acceptance item, or direct user continuation instruction for the next implied slice. **Reconcile it against the current branch/MR/merge/CI/tag state from step 1 before deriving: contradicting reality means stale — stop, repair the status source first, and do NOT derive from the stale source or a git-log/grep scan** (`references/pre-final-continuation-gate.md` §Status-source reconciliation).
   - **Deferred-evidence continuation check (`DFE-CONT`).** When real/runtime evidence is due (named by an acceptance item, status source, landing-evidence row, required gate, user correction, or because it is the behavior's only meaningful proof) yet deferred, blocked after remediation, skipped at finalization, or replaced by local/mock verification. Report deferred real evidence as `interim`/outstanding; do NOT report the turn complete while it is outstanding. A local/mock substitution is terminal only when a cited **non-agent** anchor — **agent-authored or agent-co-edited status/router/gate/handoff text never satisfies this** — names the same evidence, declares the deferral terminal, and carries the outstanding command/source forward for the active slice/ref. Never add verifier/config/test hardening motivated only by missing deferred evidence; never auto-continue past the pending gate. **Load `references/pre-final-continuation-gate.md` before treating any deferral as terminal** — it owns the valid/invalid-anchor list and hardening boundary.
   - **Affirmative-assent binding rule** lives in `references/pre-final-continuation-gate.md` §Assent binding — load it when recovering a short reply. Bind to the current explicit request or one recoverable concrete proposal, including an unmarked proposal; preserve its scope and existing authority. Ask only if action, scope, or required authority remains unresolved after recovery. A status remark or output marker cannot substitute for a proposal or permission; self-classifying the reply or marker away is never an exit from carrying out an already-clear request.
3. Continue an owned, verifiable, low-risk slice from the active task/status/acceptance source or user continuation, within scope and authority; apply `references/pre-final-continuation-gate.md`. Necessary fixes, tests and review inherit task authorization. Reviewer-budget flags require a method checkpoint and cumulative history, not renewed permission. Small tests and routine development/test-environment operations use configured access directly: no per-run approval or invented cost cap. Developer-self-use metered accounts are not new purchases; explicit user limits and high-impact boundaries still govern.
4. Stop only for an explicit stop/pause instruction, a user-requested status-only answer, a concrete blocker for the affected action, or no safe authorized work remains. Block materially differing viable approaches (none dominant-and-reversible) and a fix lacking evidenced cause; load `references/pre-final-continuation-gate.md` for the full stop conditions. **Scope each blocker to its dependent action or claim.** An unproven cause blocks the speculative patch, not available diagnosis; a pending gate blocks dependent landing/completion, not authorized remediation or independent work. Before ending, perform in-scope diagnosis, owner discovery, remediation or independent work, and poll any finite step you started to its result, never reporting it as running. Quality-gate failures require diagnosis and available related behavior-preserving cleanup before escalation; preserve readability and compatibility, never game counters (`references/refactoring-discipline.md`). Never bypass the blocked gate, invent a pass, widen scope, or substitute unrelated hardening. With one dominant reversible approach and no applicable stop condition, do not stop at a recommendation: deliver a tested reviewable draft.
5. If stopping, state the concrete stop reason and the exact evidence checked; an assent-triggered `blocked:` outcome uses the action/scope-plus-blocker form and classifies the turn `interim`. Ask one concise in-turn question when ambiguity or missing authority blocks; explicit stop/pause needs no reconfirmation. A `continuing:` outcome proceeds with the named slice before finalizing. A silent/completion stop is invalid. Do not send a completion-only, solved, fixed, or fully-closed final response after a merge/sync while a required review/challenge is pending or inconclusive; report interim or blocked with the next unblock step.
6. **Assent-outcome closeout check.** Every user reply immediately following an assistant message that states or implies a next action requires a visible `continuing:` or `blocked:` outcome before finalizing, even if the reply is not classified as assent; every explicit continuation request does too. Missing markers never waive it. Reconcile the current request, original proposal, scope/authority changes, tool/output evidence, and remaining blockers. Respect a current explicit stop or status-only request; name that reason in the blocked outcome without executing the prior proposal. Otherwise `continuing:` must be followed by execution in the same turn; a promised next step is not execution. If part remains blocked, report its pending state and independent work performed. A status-only handoff cannot discharge an unexecuted accepted action. Repair marker formatting; for short assent, if the original proposal cannot be recovered verbatim, select `blocked:` and ask. Formatting never requires clarification. Do not silently drop an accepted action or claim a pending gate passed.

### Existing Project Assessment

Broad prompts such as "分析项目", "重新分析本项目", or "review this repository/codebase" keep this workflow as owner of the whole assessment matrix, even after a reset/setup step; a stack skill owns one row. Before deep reading, fixes, or conclusions, load `references/stage-classify-and-route.md` §Existing Project Assessment and create the assessment launch checklist (`references/existing-project-assessment-report.md`).

### Feature Deprecation

When a feature is sunset, downscoped, or replaced (功能下线、废弃旧能力), **load `references/feature-deprecation-cascade.md` before any TC/test/code deletion or `complete` label** and run its 7-step cascade in order; delete a test or symbol only when its code is removed or has no other callers. A deprecation slice is `complete` only when steps 2–7 each have evidence (full text: `references/stage-classify-and-route.md` §Feature Deprecation).
