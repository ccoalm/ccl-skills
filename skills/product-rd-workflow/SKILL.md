# Product R&D Workflow

Use this skill as the top-level workflow for new product development, feature delivery, bug handling, refactoring, release preparation, or repeated process improvement. It decides which skill owns each stage and what evidence is required before moving on; stack skills do the work.

**Entry precedence.** For any product idea, feature delivery, release, cross-cutting refactor, or a **restart/redo of an in-flight delivery**, invoke this workflow first to classify and route — naming a stack/execution skill (e.g. `web-react-dev`, `multi-agent-delegation`) does not by itself skip this workflow's lifecycle gates (design / test / release / acceptance); those still apply unless already covered. **Precedence order:** explicit user instruction > this workflow's stage/gate ownership > lower-priority default behavior from optional skill packages; a gate opt-out must be stated as such.

**Continuation-proposal output contract (session-wide for product delivery).** Use `proposed-next: <action and scope>` to make a next action observable, or `proposed-next: none — status only` for a status-only handoff. A missing, repeated, or conflicting marker triggers intent recovery, not a stop. Follow the current explicit user request; bind short assent to one recoverable concrete proposal and its scope. Repair your own formatting without asking the user to repeat an already-clear instruction. Markers never grant authority. Recovery, ambiguity, and outcome rules: `references/pre-final-continuation-gate.md` (Continuation-proposal output contract).

## Routing

| Request | Owner |
| --- | --- |
| Product idea, feature, multi-stage refactor, release, existing-project assessment | This workflow: classify, then route each stage below |
| Restart/redo of an in-flight delivery (清除代码重新开发 / 完全重新开始 / 推倒重来) | A fresh entry: re-establish the plan before coding; discarding code does not discard the design/spec unless the user says so (`references/implementation-entry-reentry-gate.md` §Baseline Selection) |
| Requirement clarification, current-state evidence, scope/version, PRD prose | Product requirement artifacts: route clarification to `requirement-intent`, current-state evidence to `requirement-baseline`, scope/version to `requirement-scope`, and Ready-only PRD assembly to `requirement-doc-writer`, all under `requirement-doc-writer/references/requirement-closure-contract.md`; in active delivery results return here (only a standalone non-PRD narrow artifact may return directly to the user), and this workflow issues the lifecycle `PRD Ready` / `PRD Not Ready` verdict |
| Risk tags and required gates | `feature-risk-router` (required for permission/access, money/quota, write-finality, data migration, cross-service API contract, AI inference/evaluation, release-ops, or unclear verification scope) |
| Design, interaction, visible UI | `product-ui-ux-design` |
| Architecture: boundaries, contracts, storage truth, reliability | `go-microservice-architecture`, `python-service-architecture` |
| LLM, agent, RAG, prompts, evaluation | `llm-inference-integration` |
| Defects, reproduction, root cause | `defect-diagnosis` |
| Test layers, fixtures, CI gates | `testing-strategy`; structured test cases and Bitable records: `test-artifact-management` |
| Review | `code-review` |
| Delegated or parallel agent work | `multi-agent-delegation` owns the execution recipe; this workflow owns the lifecycle gate and acceptance boundary |
| Reusable lessons, retros, skill edits, "why did you stop" challenges | `skill-extraction-workflow` first; only a resulting routing or gate policy change comes back here |
| Reader-facing documents | `tighten-doc` after the substance owner |
| Worktrees, isolation, merge execution | `worktree-isolation` |

- Development routing: invoke stack-specific skills, such as `app-cross-platform-dev` for Flutter/Android/iOS apps, `miniapp-product-dev` for WeChat/Alipay/Douyin/Baidu mini-programs, `web-react-dev` for React web, `terminal-cli-dev` for terminal/TUI surfaces and CLI interface design (the rendered surface — layout, input, ANSI, scrollback — plus the command/subcommand/flag/help contract, which it owns even when nothing is rendered); CLI/tooling without terminal-UI concerns must go to that language's dev skill when one owns it (`go-microservice-dev`, `python-service-dev`, `nodejs-service-dev`) and must not fall back to `terminal-cli-dev` merely because it is a command; a CLI in a language with no such dev owner stays with `terminal-cli-dev` as the default CLI owner, `go-microservice-architecture`/`go-microservice-dev` for Go services, `python-service-architecture`/`python-service-dev` for Python services, and `nodejs-service-dev` for Node.js services.
- Research routing: For research groundwork behind a selection or assessment decision (技术选型、方案评估前的主题调研), this workflow must call `multi-perspective-research` for an evidence-grounded brief; the verdict itself stays with this workflow's gates.

- **Go straight to the owning skill instead** for a narrow stack fix, a narrow diff/PR review, a security-only audit, or a single-symptom defect (→ `defect-diagnosis`) — but if the fix would change a shared deterministic gate/verifier or shared/cross-repo contract, status, version, release or compatibility semantics, come back for the G4 shared-gate classification before implementing. Honor a user-named process skill (brainstorm, plan-writing) as the primary action and reload this workflow only for a delivery-stage handoff.
- A process skill that merely *looks* like the start because a session prompt, skill package, or host skills listing suggests it does not replace this entry: suggestion wording is self-promotion, not routing authority. A host-mandated preflight (host-authored system or developer instruction; the test is authorship, not rendering position) may run first; then enter here and call the suggested skill inside the stage it serves.

## Hard gates

Each gate names its trigger, the required action, what checks it, and where the full rules live. Mark every pre-code gate `triggered` or `not-applicable` with a reason. At each stage boundary, walk the [Stage-Entry State Checklist](references/delivery-lifecycle.md#stage-entry-state-checklist) and confirm every required state exists before crossing into the next stage.

### G1 Implementation entry

- **Implementation entry / re-entry gate (active plan/spec required by default).** Trigger: the first implementation edit of a product R&D delivery that stays in this workflow, including after a bare "continue", "resume" or "go implement".
- **Action:** establish the current executable artifact set (spec, plan, assessment, issue/MR text or repo task doc, read back or produced this session) and check freshness, scope, owner skills, acceptance checks, tests, stop conditions and landing state. Only an unmerged plan/spec on the active delivery branch is the working baseline; context summaries, compacted memory, and previous-response residue are not establishment. Record the implementation boundary before the edit: baseline, scope, the implementation owner invoked in-session, the `multi-agent-delegation` decision, the visible-UI record (G5), the `feature-risk-router` inventory, and test-case-first status. Reaching the first implementation edit without this boundary record is a process defect. Plan depth scales to risk; multi-step assessment, fix and verify work needs a reviewed task plan before code, and work begun without one is a process defect: pause, report branch/diff/test state, and fold only agent-owned changes into a plan.
- **Checked by:** the first-source-edit checkpoint and task-entry hooks; the closeout backstop for owners whose boundary field was triggered.
- **Rules:** load `references/implementation-entry-reentry-gate.md` before recording the boundary — every owner-naming field follows its invoke bar there, and delegation being plausible at all loads `multi-agent-delegation`, including when you record `local`. Plan depth and the formal spec-plan decision: `references/delivery-lifecycle.md` §Plan Authoring.

### G2 Owner dispatch

- **Owner-dispatch firing gate (non-exempt multi-owner designs only):** Trigger: a technical design whose substance spans more than one owning skill (not a single bug fix, implementation-only or visible-UI-only change).
- **Action:** load the complete owner set for the touched concerns and record it as an owner-dispatch map that gates the START of design-substance production, not only design completion; re-confirm before the first implementation edit. The design is `interim` until every touched concern shows an owner with applied evidence. External models are supplement-only.
- **Checked by:** the `owner-dispatch` PreToolUse and Stop hooks and `scripts/owner-dispatch/owner-dispatch.sh ci` in repos that commit `.owner-dispatch.json`; at closeout of a gated delivery, `owner-dispatch.sh status` reads `opted-in: yes` or the exemption is recorded.
- **Rules:** `references/dispatch-owner-skills.md`, `scripts/owner-dispatch/README.md`.

### G3 Test first, verify by layer, close with a real label

- **Trigger:** any code or test change.
- **Action:** before implementation, record a test-layer decision table (`unit`, `integration/contract`, `E2E/host smoke`, `manual/exploratory`), each `run`, `add`, `not applicable` or `blocked` with command and reason; behavior changes link each applicable row to a written test case, and behavior-neutral changes record `not applicable: behavior-neutral/docs/config-only` with the reason. For behavior changes, test-case-first is the default gate: write the test case, map it to a layer and command, add a failing or changed assertion and run it RED before coding; if no harness supports a RED test after remediation, record the blocker and the strongest alternate check first. If code was already changed before this gap is noticed, stop further implementation, add the missing test-case register, and report regression coverage honestly; do not claim TDD. Verification matches risk through `testing-strategy`; build, lint, static checks and review are supporting evidence, never a substitute for a test. Runtime-dependent client changes need evidence from the affected host. Do not push to a shared branch or open an MR until the layers the risk requires are green on the final pushed state (local and RED-first commits are exempt). After code/test edits, deep self-review in the main agent, then invoke `code-review` automatically before completion. Inconclusive review stays pending.
- **Closeout labels:** only `complete` (every blocking gate passes), `pre-runtime-test-ready` (lower layers and build green, a named runtime/device owner, draft or not-MR-ready, never merged in this state), or `blocked` (no owner or environment can run the gate; a stop state, not an escape for pushing). Report verification by layer and never relabel a failed blocking layer as accepted risk.
- **Checked by:** the review-covers-head hook, the repository's CI and branch protection where present; prefer a tracked verify script plus blocking CI, or a tracked script plus an installed hook when no CI exists — never discipline alone.
- **Rules:** load `references/delivery-lifecycle.md` §Completion Evidence Gate before any complete/fixed/passing claim or independent-review handoff (deep self-audit, non-UI action binding, runtime evidence); external review is the backstop for what the audit missed, never the substitute that makes it optional.

### G4 Technical design review and shared gates

- **Trigger:** work that is cross-repository, multi-client, touches a contract/API with any external consumer, or is high-risk (two or more accountable teams, deployable clients or contract consumers count).
- **Action:** produce a review-altitude technical design (interface, data flow, decisions with rejected alternatives, failure modes, cross-repo impact, high-risk handling) before task breakdown or code, and get a recorded independent adversarial review that also covers the implementation diff before merge; green tests do not discharge it. Before claiming exemption, record a short risk inventory; unknown scope escalates to `feature-risk-router`. Human/team sign-off applies only to high-risk money/permission/data or breaking external APIs, before merge or launch, never before implementation. Explicit stricter rules still bind.
- **Shared gates** (a separate trigger; it does not by itself require the technical design above): any change to a shared deterministic gate/verifier or a cross-repo contract, status, version, release or compatibility surface. For shared gates, this workflow classifies the artifact before implementation (`spec/plan`, `gate design`, `gate implementation`, `status sync`, `runtime/code`), then applies `feature-risk-router`'s `shared-gate` decision before shared push or MR merge, with a recorded independent adversarial review; a `gate implementation` runs the plan/status verifiers before implementation, and a verifier gap or unavailable required review/challenge stays `interim`.
- **Checked by:** the recorded review artifact bound to the diff; any post-review change, tests/docs included, refreshes the self-review row and mechanically triggers a full-scope rerun.
- **Rules:** load `references/design-review-gate-mechanics.md` when triggered; `references/shared-gate-artifact-classification.md`.

### G5 Visible surface

- **Trigger:** any change a person sees or acts on, including admin, operations and settings surfaces.
- **Action:** invoke `product-ui-ux-design` and run its surface classification before the first implementation edit. Before coding any visible UI change, load `references/design-routing-and-readiness.md` and the canonical `../product-ui-ux-design/references/delivery-contract.md`, then create the design brief or low-risk copy-only record and obtain Test Phase 0. Non-rendered client changes record `visible surface: no` with the reason. A build or snapshot never implies design acceptance; a challenge to UI quality is a design defect, not a preference dispute.
- **Checked by:** the first-source-edit checkpoint names the owner; rendered evidence on the target (device, developer tool, browser, PTY) before completion.

### Pre-Final Continuation Gate

Run this gate before finalizing a product R&D turn after any delivery slice lands, on every user reply immediately following an assistant message that states or implies a next action, and on any explicit continuation request. Recover the intended action from the current request and relevant conversation; a malformed or absent marker alone never selects `blocked:`. Report, on its own line, `continuing: <action and scope>` for work you will execute, or `blocked: <action and scope> — <specific blocker>` when no authorized work can proceed; `proposed-next:` never replaces it. A blocked dependent action may remain pending while a different authorized action continues. Apply landing checks only to actual landing claims; an already-authorized local investigation does not require inventing a prior landing. Details: `references/pre-final-continuation-gate.md` (Gate triggers and outcome contract).

1. Confirm the landing state from real evidence (local branch, remote sync, MR/review artifact, CI/pipeline when applicable, review/challenge status when required, status-doc sync, dirty worktree), proving the landing before reading any document (for the remote-backed default, fetch/update the target ref from its remote immediately before classifying the slice landed) per `references/pre-final-continuation-gate.md` (Landing-state proof); content/tree/patch equivalence never by itself proves a slice landed.
2. Inspect the current product/status source of truth, issue list, repo-local next-step artifact, unresolved acceptance item, or direct user continuation instruction for the next implied slice. **Reconcile it against the current branch/MR/merge/CI/tag state from step 1 before deriving: contradicting reality means stale — stop, repair the status source first, and do NOT derive from the stale source or a git-log/grep scan** (`references/pre-final-continuation-gate.md` §Status-source reconciliation).
   - **Deferred-evidence continuation check (`DFE-CONT`).** When real/runtime evidence is due (named by an acceptance item, status source, landing-evidence row, required gate, user correction, or because it is the behavior's only meaningful proof) yet deferred, blocked after remediation, skipped at finalization, or replaced by local/mock verification. Report deferred real evidence as `interim`/outstanding; do NOT report the turn complete while it is outstanding. A local/mock substitution is terminal only when a cited **non-agent** anchor — **agent-authored or agent-co-edited status/router/gate/handoff text never satisfies this** — names the same evidence, declares the deferral terminal, and carries the outstanding command/source forward for the active slice/ref. Never add verifier/config/test hardening motivated only by missing deferred evidence; never auto-continue past the pending gate. **Load `references/pre-final-continuation-gate.md` before treating any deferral as terminal** — it owns the valid/invalid-anchor list and hardening boundary.
   - **Affirmative-assent binding rule** lives in `references/pre-final-continuation-gate.md` §Assent binding — load it when recovering a short reply. Bind to the current explicit request or one recoverable concrete proposal, including an unmarked proposal; preserve its scope and existing authority. Ask only if action, scope, or required authority remains unresolved after recovery. A status remark or output marker cannot substitute for a proposal or permission; self-classifying the reply or marker away is never an exit from carrying out an already-clear request.
3. Continue an owned, verifiable, low-risk slice from the active task/status/acceptance source or user continuation, within scope and authority; apply `references/pre-final-continuation-gate.md`. Necessary fixes, tests and review inherit task authorization. Reviewer-budget flags require a method checkpoint and cumulative history, not renewed permission. Small tests and routine development/test-environment operations use configured access directly: no per-run approval or invented cost cap. Developer-self-use metered accounts are not new purchases; explicit user limits and high-impact boundaries still govern.
4. Stop only for an explicit stop/pause instruction, a user-requested status-only answer, a concrete blocker for the affected action, or no safe authorized work remains. Block materially differing viable approaches (none dominant-and-reversible) and a fix lacking evidenced cause; load `references/pre-final-continuation-gate.md` for the full stop conditions. **Scope each blocker to its dependent action or claim.** An unproven cause blocks the speculative patch, not available diagnosis; a pending gate blocks dependent landing/completion, not authorized remediation or independent work. Before ending, perform in-scope diagnosis, owner discovery, remediation or independent work, and poll any finite step you started to its result, never reporting it as running. Quality-gate failures require diagnosis and available related behavior-preserving cleanup before escalation; preserve readability and compatibility, never game counters (`references/refactoring-discipline.md`). Never bypass the blocked gate, invent a pass, widen scope, or substitute unrelated hardening. With one dominant reversible approach and no applicable stop condition, do not stop at a recommendation: deliver a tested reviewable draft.
5. If stopping, state the concrete stop reason and the exact evidence checked; an assent-triggered `blocked:` outcome uses the action/scope-plus-blocker form and classifies the turn `interim`. Ask one concise in-turn question when ambiguity or missing authority blocks; explicit stop/pause needs no reconfirmation. A `continuing:` outcome proceeds with the named slice before finalizing. A silent/completion stop is invalid. Do not send a completion-only, solved, fixed, or fully-closed final response after a merge/sync while a required review/challenge is pending or inconclusive; report interim or blocked with the next unblock step.
6. **Assent-outcome closeout check.** Every user reply immediately following an assistant message that states or implies a next action requires a visible `continuing:` or `blocked:` outcome before finalizing, even if the reply is not classified as assent; every explicit continuation request does too. Missing markers never waive it. Reconcile the current request, original proposal, scope/authority changes, tool/output evidence, and remaining blockers. Respect a current explicit stop or status-only request; name that reason in the blocked outcome without executing the prior proposal. Otherwise `continuing:` must be followed by execution in the same turn; a promised next step is not execution. If part remains blocked, report its pending state and independent work performed. A status-only handoff cannot discharge an unexecuted accepted action. Repair marker formatting; for short assent, if the original proposal cannot be recovered verbatim, select `blocked:` and ask. Formatting never requires clarification. Do not silently drop an accepted action or claim a pending gate passed.

- **Checked by:** the proposed-next Stop hook.
- **Rules:** load `references/pre-final-continuation-gate.md` before treating a deferral as terminal or recovering short assent.

## Triggers for rare, high-impact work

Each line fires on its trigger and names the rules to load.

- **Artifact-egress confidentiality gate:** before a delivery artifact or text generated from it crosses the local trusted boundary (shared docs, trackers, MR/issue text, commit and release metadata, external models, delegated-worker prompts), run the confidentiality pass; a block stops the egress, never deletes the draft. `references/artifact-egress-confidentiality.md`.
- High-risk resilience gating: when a feature touches money, billing, quota, permissions, tenant/user isolation, privacy, high-impact AI output, write finality, repeated submission, async finality or incident explanation, require the resilience gate and a risk scenario matrix; happy-path tests do not accept it. `references/high-risk-resilience-gates.md`.
- **Implementation completeness/minimality gate:** behavior-changing delivery, and any implementation claiming the refactor/mechanical exemption (the exemption is classified at entry); functional completeness and structural minimality are independent gates, and gaps block `complete`. Load `references/implementation-completeness-and-minimality.md` before implementation and the mapping, and again before a completion claim.
- **Mechanism-operability check** fires whenever the design proposes new mechanical enforcement or verification machinery (a CI/merge gate, pre-commit hook, validator, evidence apparatus, migration guard), and again when a landing withdraws or downgrades the evidentiary claim an existing mechanism rests on, at any scope; load `references/design-review-gate-mechanics.md` before proposing the machinery and before landing the withdrawal.
- **Spec / repo-contract sync gate:** before implementation, name the active contract layers for the slice (product/requirements spec, technical design/ADR, repo-local agent contract). A change to a stable boundary, service, workflow, generated surface, directory-local rule or architecture decision updates the owning spec/ADR and nearest `AGENTS.md` in the same slice; load `references/sync-spec-repo-contract.md` for the sync mechanics. Never restate an upstream authority's value sets: whenever the slice touches an upstream-owned value set or asserts the upstream is silent, load `references/sync-spec-repo-contract.md` first and cite the access-controlled pointer + revision rather than the copied value.
- **Cross-repo feature coordination:** one feature spanning repositories. `references/cross-repo-coordination.md`.
- **Multi-repo delivery-status ledger:** delivery that changes remote branch, MR, pipeline, release or deployable-artifact state keeps a per-unit ledger; a required gate passes only as `success`, `not-applicable` or `not-required`. `references/status-tracker-sync.md`.
- **Delegation becomes plausible:** when a multi-stage delivery develops two or more slices that look independent, surface `multi-agent-delegation` as a candidate and record its decision; it decides serial or parallel.
- **Internal reference as a source:** a product artifact built from an internal checkout names only mechanisms, boundaries and acceptance gates; split observations into mechanism, business noun and source quality or age; scan changed files for source identity before commit; inspect nested repositories and other branches before declaring no evidence.
- **Existing-project assessment** (分析项目 / review this repository): this workflow owns the whole matrix; create the launch checklist first, keep findings cited and confidence-labeled, and turn findings into an accepted plan before edits. `references/existing-project-assessment-report.md`.
- **Quality remediation program:** a cross-cutting, multi-phase engineering-quality initiative or ongoing baseline. `references/quality-remediation-program.md`.
- **Diagnostic spec-match baseline gate:** when a request combines a diagnostic verb with a spec-match claim, do NOT treat the user's single-utterance description as the authoritative spec; identify and record the evaluation baseline first. `references/diagnostic-spec-match-gate.md`.
- **Dormant code activation:** wiring previously unused code into a live path. `references/dormant-code-activation.md`.
- **R&D standards doc family:** creating or updating team development standards, stack guidelines, testing standards, engineering norms or a multi-doc R&D handbook must use the R&D standards checklist: classify the layer, enumerate the family, record authority and sync gates, route testing/conformance owners, and finish only with `complete` evidence or `blocked: family enumeration unverified`. Norms meant to check compliance later split into deterministic checks and agent review checks. Standalone wording or polishing goes to `tighten-doc`. `references/rd-standards-doc-family-checklist.md`.
- **AI/algorithm launch:** product goal, business, offline and serving baselines, rollout/rollback, risk owner. `references/algorithm-launch-sop.md`.
- **Developer-facing surfaces** (CLI, SDK, library, public API, developer docs): for a new/public developer surface, or a change touching onboarding, install/setup, first-success, defaults, error surfaces or a breaking migration, prove DX by the measured onboarding journey; safety defaults stay fail-closed. `references/verify-developer-experience.md`.
- **User-visible tips, nudges and update notices:** define audience, eligibility, suppression, disable path, freshness and cooldown before launch. `references/design-routing-and-readiness.md`.
- **External skill augmentation:** installed external skills supplement a narrow discipline and never replace CCL ownership. `references/external-skill-augmentation.md`.
- **Feishu requirement record:** only when the user or an accepted delivery contract requests one; this workflow owns its content (`需求 ID`, title, status, version) and `lark-base` performs the write. Create or reuse only the requested resource, and confirm the write before declaring that deliverable complete.

### Feature Deprecation

When a feature is sunset, downscoped or replaced, treat it as a multi-skill delivery slice. Load `references/feature-deprecation-cascade.md` before any TC/test/code deletion or `complete` label, and run its seven steps in order; a test or business symbol is deleted only when the underlying code is removed or has no other product callers. A deprecation slice is `complete` only when steps 2–7 each have evidence; a missing step is a release defect, not a follow-up.

## Non-negotiables

- Never mark work complete because a workaround hides the issue; root-cause real defects first.
- Never delete, skip or weaken a failing test to pass; fix the code or correct an invalid test with evidence.
- Never claim complete, fixed or passing without fresh verification evidence from the current turn, and never fabricate verification output, review status, links or install state.
- Landing labels need matching evidence: `landed` needs the commit or persisted artifact; `MR-ready` needs branch, push, review artifact, known CI and mergeability when applicable, and real review status; `release-ready` needs release checks, rollback/mitigation and runtime verification; `shared-status-ready` needs the owning status document to match the real branch/MR/review/verification state. Local or exploratory slices report their actual uncommitted or unpushed state.
- Separate source-control transport from platform control-plane operations and verify platform authentication before trusting API errors. When the default branch is protected or its protection is unknown, land through branch plus MR; move an accidental local commit on it to a branch and MR. Creating an MR is not merge authorization (`worktree-isolation`).
