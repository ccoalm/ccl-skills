# 算法服务上线执行规范

配套 [算法能力上线门禁 SOP](algorithm-launch-sop.md)。

## 1. 基线与阈值设置

业务效果基线和上线阈值必须在方案评审前冻结。上线评审只能检查是否达标，不能现场临时改标准。

| 项 | 要求 |
|---|---|
| 提出 | 产品负责人提出业务指标、最低上线标准和目标值；算法、研发、测试、数据补充算法、工程、成本和风险阈值 |
| 确认 | 方案评审会上确认指标口径、数据来源、看板位置、统计方法和责任人 |
| 冻结 | 指标和阈值冻结后进入测评报告；后续变更必须记录原因、影响范围和批准人 |
| 例外 | 高风险事实错误、红线误答、严重错译、严重溯源错误等高风险指标原则上 0 容忍；如需例外，必须在上线前单独评审 |
| 存档 | 阈值、口径、变更记录和评审结论必须随测评报告存档 |

## 2. 多版本实验或灰度规格

| 场景 | 必须说明 |
|---|---|
| A/B 实验 | 实验目的、随机分组方式、样本量、观察周期、核心指标、护栏指标、停止规则、统计方法 |
| 灰度发布 | 起始比例、扩量步长、扩量间隔、暂停条件、回滚条件、兜底版本、关键用户或高风险场景隔离 |
| 共同要求 | 版本标识、日志埋点、看板分组、成本归因、异常告警和负责人 |

## 3. 组合算法链路变更

一个产品能力由多个算法、策略、工具或服务共同组成时，子模块变更不能只验收本模块。上线前必须补齐真实链路核查和端到端回归。

| 项 | 要求 |
|---|---|
| 真实链路 | 从产品文档、技术文档、代码、配置或日志确认真实链路；未确认的节点不得写成已存在链路 |
| 影响面 | 标明受影响入口、模块、数据源、工具、知识库、三方服务、前端展示、埋点、计费、监控和回滚路径 |
| 模块验收 | 被改模块必须有新旧版本对比、错误类型分析、耗时、成本、异常兜底 |
| 接口契约 | 上下游输入输出、版本标识、错误码、超时、重试、降级和日志字段必须可验证 |
| 端到端回归 | 覆盖用户入口到最终结果展示；链路长时，必须验收下游业务指标是否变差 |
| 版本归因 | 日志、埋点、测评报告和灰度看板必须能定位到具体模块版本 |

问答 QA 的检索 query 改写、知识库检索、混合检索、NL2SQL、Agent/工具规划、SSE/SSE V2 或前端流式渲染发生变更时，必须同时验收模块效果和问答链路结果。

### 3.1 问答 QA 组合链路验收逻辑

问答 QA 的具体实现会随版本变化。上线验收不写死模块名，先按当次版本核实真实链路，再按链路分层验收。

```mermaid
flowchart LR
  A["用户提问"] --> B["入口/会话/历史"]
  B --> C["问题理解"]
  C --> D["检索/数据查询/工具调用"]
  D --> E["引用/溯源"]
  E --> F["答案生成"]
  F --> G["流式展示/状态回写"]
```

| 链路层 | 必验内容 |
|---|---|
| 入口/会话/历史 | 入口可用，历史上下文正确，当前文件和历史文件不混淆 |
| 问题理解 | 多轮承接、指代消解、query 改写、意图判断不能引入错误问题 |
| 检索/查询/工具调用 | 检索命中、数据查询、工具选择、工具超时、空结果兜底不退化 |
| 引用/溯源 | 引用内容、来源、顺序、去重和前端展示正确 |
| 答案生成 | 答案准确、可信、不过度回答；无答案和高风险问题能拒答 |
| 流式展示/状态回写 | 首 token、完整响应、停止、失败、超时、断连恢复和状态终态正确 |

未核实的节点不能写成真实链路。发现不确定节点时，只标“待确认影响面”，不作为上线验收的固定环节。

## 4. 监控、漂移与回滚时限

上线前必须定义监控和回滚规格，并说明触发后多久处理完成。

| 项 | 必须说明 |
|---|---|
| 告警阈值 | 哪个指标、绝对阈值或相对变化、持续多久触发告警 |
| 响应时限 | 告警后多久确认，多久给出处置结论，谁负责 |
| 处置动作 | 暂停扩量、降级、切回老版本、切三方、关闭入口或人工兜底 |
| 回滚时限 | 从触发条件成立到完成回滚的目标时间 |
| 授权人 | 工作时间和非工作时间谁可以直接暂停、降级或回滚 |
| 验证动作 | 回滚后如何确认版本、成功率、延迟、成本和业务指标恢复 |

## 5. 评测集治理

| 项 | 必须说明 |
|---|---|
| 防污染 | 评测集是否用于训练、微调、提示词调优或人工规则开发；如使用过，不能作为固定基准集 |
| 版本控制 | 评测集版本号、生成时间、样本来源、标注规则、负责人和存储位置 |
| 变更流程 | 新增、删除或重标样本必须记录原因、提交人、审核人和影响范围 |
| 保留周期 | 老版本评测集和历史测评结果必须可追溯 |
| 职责隔离 | 高风险项目中，评测集负责人和模型优化负责人原则上分离 |

## 6. 投入产出与三方对比

自研与三方方案必须用同一时间窗口和同一数据集对比投入产出。

| 项 | 必须说明 |
|---|---|
| 成本 | 研发、标注、测评、推理资源、运维监控、三方调用、合规安全和机会成本 |
| 收益 | 业务指标提升、成本下降、体验改善、风险降低、数据积累和能力自主性 |
| 时间窗口 | 至少说明 6 个月或 12 个月口径，不允许只看单次调用成本 |
| 三方对比 | 效果、延迟、稳定性、价格、数据安全、可控性、迁移成本和退出方案 |
| 结论 | 自研、采购、混合方案或暂缓；结论必须说明关键假设 |

## 7. 全量后持续运营

全量上线后，以下情况必须重新评估或重跑核心测评：

- 模型、提示词、检索策略、索引、知识库、工具或三方服务配置发生变化。
- 线上输入分布、无答案比例、失败率、超时率、成本或坏例类型明显变化。
- 发现严重高风险事实错误、红线误答、严重错译、严重溯源错误。
- 供应商模型、价格、服务承诺、数据处理条款发生变化。
- 核心业务指标连续低于最低上线标准。
