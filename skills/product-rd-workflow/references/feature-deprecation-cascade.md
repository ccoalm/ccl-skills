# Feature Deprecation Cascade

Use this reference when a feature is sunset, downscoped, or replaced (需求变更导致功能下线、迭代废弃旧能力、产品方向收敛). Treat it as a multi-skill delivery slice, not a one-line status change. A deprecation that only updates the product doc but leaves test cases, automated tests, dead code, dashboards, alerts, or feature flags behind is incomplete and silently rots the codebase.

The cascade itself is the contract: external skills slot into individual steps without replacing the cascade structure. Coordinate the steps in this order; do not skip steps even when one seems harmless.

1. **Confirm scope and source of truth** — name the feature, the source decision (product doc / requirement change / launch retro), the effective date, and whether the deprecation is immediate or staged. If the source decision is missing, stop and route back to product/requirements before any code or test deletion.
2. **TC layer (`test-artifact-management`)** — mark every affected TC as `废弃` in Bitable (not `跳过`); append a 信息流转 entry with the deprecation reason and source link; sync the same change to the local md mirror (mark `[废弃]` in the 功能点 column, do not delete the row). 废弃 TCs are frozen — automation must not change their status afterwards.
3. **Test-code cascade (`testing-strategy`)** — for each 废弃 TC, locate linked tests via the sidecar (`test/results/tc-map.jsonl`) + source grep for `tc("<TC ID>")` / `tc.Mark(..., "<TC ID>")` / `tcTest([..."<TC ID>"]` calls; for each match, decide whether to delete the test using the per-stack import-graph commands documented in the relevant dev skill's "废弃级联：业务代码是否仍在用" subsection (Python `grep import` / Go `go list` / Web `madge` / 小程序 madge+app.json / Flutter+native `dart analyze`+grep). If the underlying business code has been removed or has no other product callers, delete the test in the same commit as the code removal; if the code is still actively imported by other product code, take no action by default (the TC may have been marked early). For tests covering multiple TCs where only some are 废弃, remove the deprecated IDs from the `tc(...)` argument list without deleting the whole test. Tests without `tc(...)` calls are handled separately — only prompt the user when the underlying code is also being removed.
4. **Code removal (stack dev skill)** — route the actual code deletion to the owning stack skill (`go-microservice-dev`, `python-service-dev`, `web-react-dev`, `miniapp-product-dev`, `app-cross-platform-dev`, `terminal-cli-dev`); the stack skill is responsible for removing handlers, routes, models, UI components, terminal commands/text UI surfaces, and any feature-specific assets that no longer have a caller.
5. **Operational follow-through** — explicitly check and close: dashboards/alerts that reference the removed surface, feature flags or kill switches, scheduled jobs/cron entries, generated SDK or contract artifacts, CI gates specific to the removed feature, customer-facing docs, and release notes. Record each as `removed`, `kept with reason`, or `not applicable`; do not skip silently.
6. **Orphan detection** — after code removal lands, run `python gen_report.py --detect-orphans` to surface tests whose TC IDs are now 废弃 or missing in Bitable, and tests without TC IDs whose underlying code has been removed; resolve per `testing-strategy` orphan rules before closing the slice.
7. **Status sync** — update the product/status source-of-truth document and any shared roadmap entry in the same delivery batch; cite the merged commit, removed surfaces, and the 废弃 TC IDs. Do not leave the product doc claiming the feature is active or "to be deprecated" after the code is gone.

A deprecation slice is `complete` only when steps 2–7 each have evidence; a missing step is a release defect, not a follow-up.
