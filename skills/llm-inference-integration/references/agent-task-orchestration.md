# Agent Task Orchestration

## Product/runtime agent tasks as a control plane

Treat product/runtime agent tasks as a control plane, not as ad hoc promises or UI-only state. Every foreground, background, worker, remote, or in-process task needs a stable task id, task type, parent/session identity, user intent summary, capability/permission scope, tool-use or request correlation id where applicable, start/end timestamps, terminal status, output location and read offset, notification state, cleanup owner, and resumability policy. A durable task list or checklist is part of the same model-visible state: bind its storage namespace to principal/session/team/workspace scope, sanitize storage keys, preserve monotonic task identity across deletion or reset, serialize create/update/delete/claim operations with list-level or task-level locks as appropriate, validate task schema before use, and distinguish missing, malformed, blocked, already-owned, already-completed, busy-owner, and deleted tasks instead of treating them as empty success. Output for backgrounded work must be isolated from the foreground transcript unless explicitly merged, and task result insertion must preserve ordering, provenance, and finality. Bind every model-visible task summary, suggestion, queued attachment, and speculative response to task id, output generation or digest, read cursor, progress/event id, notification generation, retention generation, session incarnation, and privacy/source-scope labels; invalidate or revalidate after any output append, truncation, eviction, progress movement, read-offset change, background state change, completion notification, stalled-prompt notification, checklist create/update/claim/delete, dependency change, owner change, watcher refresh, stop/kill event, or tuple drift.

## Task state transition safety

Task state transitions must be monotonic and race-safe. Only running or pending tasks may accept progress, injected messages, or shutdown requests; terminal tasks must reject late output, late approvals, late user messages, duplicate completion, duplicate notification, and stale poll results. Checklist/task-list transitions need the same finality: a task may be claimed only after unresolved blockers and existing owners are checked under the current list generation; dependency updates must reject cycles, dangling or deleted-task edges, cross-list or cross-namespace edges, and stale blocker snapshots before claim or completion; ownership assignment, dependency edges, creation hooks, and completion hooks must either commit atomically or surface a non-completion result without leaving half-created, falsely completed, wrongly assigned, or partially notified tasks. Watchers and polling loops must debounce file or storage events, avoid per-turn watch churn, fence hide/reset timers by the task-list generation they were scheduled for, release claims when prompt submission fails, and fall back to polling or explicit refresh when storage notifications are missed. A multi-step checklist that closes without any verification item should surface a bounded verification nudge rather than letting the final response become the only evidence of completion. Cancellation needs a typed result that distinguishes user stop, parent abort, dependency failure, timeout, and unsupported task type; parent task cancellation must abort child workers and cleanup their owned background processes, queued notifications, credentials, and output handles without killing unrelated tasks.

## Background and remote task recovery

Background and remote task recovery must fetch fresh authority before resurrection. Persist only the metadata needed to reconnect; on resume, re-check live status, session generation/incarnation, principal/workspace scope, command/request intent, and authorization policy before re-registering a task. Archived, missing, unauthorized, or terminal remote work must not be resurrected. Pollers must use cursors or event ids, delta append, stable-idle or heartbeat debouncing, bounded timeout, and fencing against in-flight stop/kill races so a stale poll cannot overwrite a terminal state or emit a second completion. Before a resumed, retried, or replacement worker performs any write, tool action, remote call, or other external side effect, bind it to a task id, execution-attempt id, effect id or idempotency key, and authorization tuple; record durable prepared/committed/failed/unknown finality. Resume must reconnect or reconcile committed and unknown effects, not re-execute them, unless there is durable proof that no side effect committed.
