# Agent Model-Visible Instruction Composition

## Model-visible instruction-layer composition

Treat model-visible instruction-layer composition as a control plane, not string concatenation. Build an explicit precedence lattice before rendering: non-overridable system, developer/product, managed-policy, safety, permission, privacy, data-residency, tool-finality, and truthful-reporting constraints form the floor; current user intent may refine the task only inside that floor; workspace/project/user/plugin/config files, agent prompts, mode instructions, output style text, tool and hook context, memory, retrieved content, and append/addendum layers are lower-precedence inputs unless an explicit policy grants a narrower authority. Current-user instructions and every lower-precedence layer must fail closed or be labeled as data when they conflict with higher-precedence constraints. Classify every instruction source by source type, principal/session/workspace scope, trust level, policy owner, install or file identity, content digest or snapshot generation, mode/output-style/agent identity, and static versus dynamic cache scope before it reaches the model. File-backed, markdown-configured, output-style, agent, mode, or config-file instruction sources need fresh read authorization, source-scope validation, canonical containment, source-scope labels, symlink/hardlink and time-of-check/time-of-use rejection, stale snapshot rejection, and lower-precedence untrusted labeling unless an explicit policy makes them authoritative. Managed policy, safety, permission, privacy, tool-finality, data-residency, and truthful-reporting instructions cannot be overridden or suppressed by current-user instructions or by lower-trust output styles, agents, plugins, project/user files, hooks, retrieved content, memory, or append prompts. Output styles, modes, or agent definitions that remove or replace base coding/task instructions require an allowlisted product policy and must preserve safety, authorization, privacy, tool-use, finality, and truthful-reporting constraints. Prompt-prefix and section caches must be partitioned or invalidated by source digests, trust tier, principal, workspace/root, privacy state, policy generation, capability/tool generation, model/prompt generation, mode, output-style, agent identity, and dynamic-section generation; late-changing sources must be explicitly uncached or cache-breaking with a reason. Diagnostics may expose bounded categories, counts, precedence classes, and non-reversible digests, but not raw prompt text, local paths, internal mode/style/agent identities (public tool-contract discriminators are governed by the next section), free-form file errors, branch names, credentials, or sensitive config values.

## Write model-facing text from the model's perspective; wording is behavior

Author every model-visible surface — system-prompt sections, tool names and schema descriptions, tool results, and diagnostics returned to the model — in the vocabulary of the model's task and of the tool contract it must invoke. Keep out **implementation-only** concepts: names of internal plugins, transports, renderers, or host mechanics that the model can neither act on nor needs to construct a valid call — those belong to the consumer/renderer that owns them, and exposing them degrades tool selection. Do keep every discriminator the model must understand to select the tool or build valid arguments, even when it is a UI mode, a plugin, or a wire/schema field name the tool legitimately takes as input: the test is "actionable through this tool's contract or part of the user's task", not "sounds like implementation". Reconcile this with the diagnostics rule above: a discriminator that is part of the **public, authorized tool contract** may appear in the schema and in a bounded repair diagnostic ("unknown value for `<field>`; allowed: …"), while internal mode/style/agent/plugin identities, local paths, and sensitive values stay out of diagnostics regardless — when a name is both actionable and identity-revealing, expose it only through the tool contract's declared enum/schema, never through free-form diagnostic text. Treat the wording of model-visible text as behavior, not copy: a change to a prompt section, a tool description, a result rendering, or a model-visible diagnostic is a behavior change and needs evidence proportional to what it can move — a snapshot/golden of the text is a review aid that catches unreviewed drift (pin it verbatim only for wording that passes `testing-strategy`'s documented-contract / past-defect keep test; otherwise it is a change-detector), and the behavioral claim ("selection/arguments/outcome unchanged or improved") is carried by a replay or eval that exercises the affected mode with behavioral assertions (see `model-prompt-evaluation.md`); a snapshot updated alongside a wording change proves nothing about behavior. "Reworded the description" without either is an unreviewed behavior change. Corollary for reviewers: inspect the exact prompts, tool schemas, results, and diagnostics the model receives across the affected modes, and flag implementation-only concepts — not legitimate contract discriminators — before checking anything else.

## Slash commands and skill invocation

Treat slash commands, local commands, prompt-backed skills, workflow commands, keybinding-triggered commands, and command-like remote or bridge invocations as a capability and action control plane, not a text alias list. Bind every command registry snapshot and invocation to principal/session/workspace, entrypoint mode, command source identity, source trust tier, registry/cache generation, availability and enablement generation, command name plus alias/user-facing-name resolution, user-invocable flag, model-invocable flag, hidden/help visibility, bridge-safe and remote-safe allowlists, immediate/queued execution mode, sensitive-argument policy, lazy-load module generation, tool-schema/capability generation, permission policy, allowed-tool scope, hook-set generation, and command completion generation. A command visible to users is not automatically visible to the model, bridge, remote client, keybinding, or sub-agent; each surface needs an explicit allow path, and disabled/hidden/user-only/model-disabled commands must fail closed after every registry refresh. Immediate commands that bypass queueing must be opt-in, side-effect bounded, and revalidate the finalized input snapshot, pasted-content expansion, prompt stash/restore state, loading state, command generation, and current policy before execution. Prompt-backed skills that inject model-visible content, hidden meta messages, scoped tools, hooks, forked agents, or model/effort overrides must label their source and generation, preserve lower-precedence untrusted content, and reauthorize before granting scoped tool rules or registering hooks. Command completion callbacks that append transcript entries, hidden model-visible messages, next input, or automatic query submission must bind to the original command invocation identity, args digest, session/incarnation, command generation, and current privacy/policy state; stale, duplicate, late, or post-abort completions must be ignored or surfaced as uncertainty. Sensitive command args, command bodies, plugin/source names, local paths, raw prompts, hidden meta-message bodies outside their intended model-visible channel, and free-form command errors must be redacted from user-visible transcript renderings, telemetry, logs, search indexes, and diagnostics unless explicit product policy requires a visible record.
