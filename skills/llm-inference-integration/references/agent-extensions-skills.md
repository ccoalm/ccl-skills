# Agent Dynamic Extensions And Skills

## Dynamic extensions and locally loaded skills

Treat dynamic extensions, locally loaded skills, connector-discovered skills, and extension-provided commands/hooks/tool servers as a model-visible capability control plane. Classify every contribution by source type, principal/workspace scope, manifest/schema version, trust level, enabled or disabled state, policy owner, install path, session-only versus persisted lifetime, and whether it can inject instructions, run code, alter settings, or expose tools. Disabled, unavailable, policy-blocked, dependency-demoted, plugin-only-restricted, or cache-missing sources must not contribute model-visible descriptions, tools, hooks, settings, or prompt content.

## Extension install, update, and reload

Extension install, update, and reload paths need explicit cache and trust semantics. Never let a cache-only startup path fetch or install fresh remote code; never let a full refresh satisfy a later cache-only caller with stale policy or settings state unless the refreshed result also cleared dependent prompt, tool, settings, and skill caches. Preserve a session snapshot for already-running agents when background updates write a new disk version; require an explicit reload, restart, or generation change before the model sees the new capability set. Path materialization must validate catalog/source-relative paths, reject traversal, sanitize cache path components, remove or ignore source-control metadata, and treat symlink, dangling symlink, hardlink, archive extraction, and preloaded-cache containment as security boundaries. Materialize updates in a staging location, validate containment and manifests before publication, publish by atomic generation swap, reject incomplete markers, keep the prior valid generation until the new one is proven loadable, and fail closed rather than booting from a damaged capability graph. User/session-supplied extension directories may override ordinary installed sources only within that session; managed or policy-locked sources win even when local paths collide.

## Extension manifests and skill bodies as untrusted

Treat extension manifests, skill frontmatter, and skill bodies as untrusted routing and instruction metadata unless their source has been reviewed under the active trust policy. Validate JSON/YAML shape, names, duplicate capability identifiers, path filters, allowed-tool declarations, model or effort selectors, shell settings, hooks, settings overlays, bundled tool-server definitions, and prompt-like instruction content before they enter routing or execution. Remote, connector-supplied, workspace-local, session-supplied, or otherwise unreviewed skills must not execute inline shell, hook commands, shell-capable command blocks, or bundled code unless they have an explicit reviewed execution policy; local bundled code still needs declared capabilities, short-lived credentials, sandboxing, and execution-time authorization. Skill/extension descriptions are routing inputs, not authority: they may affect model selection but must not grant permissions, widen tool scope, bypass human approval, or override system/developer/current-user policy.
