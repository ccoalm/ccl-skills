# Agent Ambient Context Freshness

How an agent keeps ambient "world state" — working directory, environment, project-contract files (e.g. `AGENTS.md`/`CLAUDE.md`), available tools/skills/plugins, network/filesystem posture — fresh in the model's context across a long multi-turn session, without re-injecting everything every turn and without leaving stale state the model still believes. This is a distinct concern from the durable event log (`agent-session-persistence.md`) and from instruction precedence/trust (`agent-instruction-composition.md`); it owns the *staleness-detection and refresh* layer that sits between them, and defers precedence, authority, and untrusted-data decisions to that instruction-composition owner rather than re-deciding them.

## Model context in three classes, not one

Split model-input context by *how it changes*, and treat each class differently:
- **One-shot fragments** — injected once and not tracked for change (a skills-usage preamble, a one-time notification). Push these into the initial context.
- **Diffable ambient sections** — cwd/environment, project-contract files, tool/skill/plugin availability. This is the only class with a persisted baseline and a change-detection lifecycle (below).
- **Volatile per-step signals** — values that change almost every turn (remaining-token count, a deadline, transient status). These are NOT one-shot (they go stale after one turn) and usually not worth diffing; emit them fresh each turn (or on a TTL/generation) and mark them ephemeral — in a prompt-reassembly runtime, drop the prior turn's volatile line when assembling; in an append-only transcript, emit the newest value as superseding — but older copies remain model-visible and potentially influential until compaction removes them, so make the fragment type self-recognizing (below) so compaction can drop them. The *static* budget contract can be one-shot; the *remaining* count is a per-step signal.

Rebuild the diffable ambient state **fresh from live runtime state every step**, reading as coherently as the sources allow — there is no truly atomic snapshot across process state, externally-edited files, plugin registries, and network posture, so use a generation/seqlock for runtime-owned state and a version-before/version-after check with bounded retry for external sources; render `unknown` when a coherent read can't be obtained rather than mixing values from different instants. Then reduce to a delta against the last model-visible baseline. Distinguish `unknown`/read-error from `absent`: a transient failure to read a contract file is not "the file was removed," and must not render a removal notice. Inject full state at window initialization and whenever the baseline is missing, invalid, or reset; steady-state turns with a valid baseline emit only what changed.

## Place load-bearing context where attention reaches it

Effective context is smaller than the nominal window: recall degrades non-uniformly as input grows, worse with distractors than with plain length (`research.trychroma.com/context-rot`), and models use the start and end of a long input better than the middle (`arxiv.org/abs/2307.03172`). Two placement rules follow for the assembled prompt: keep the current objective, binding constraints, and pending decisions near the end of the context (the recitation pattern — a re-rendered task list or plan each step — is the cheap way to do this in a long loop), and keep the stable instruction block at the start where it also serves the cache prefix; never rely on a rule buried mid-history. Evaluate long-context behavior with distractor-bearing tasks, not needle-in-a-haystack retrieval alone. This is placement guidance; the byte-stable prefix and append-only discipline that make it cacheable are in `llm-client-gateway.md` (prompt cache design).

## Detect staleness by a comparison-snapshot, not by re-reading the rendered text

Give each ambient section two halves: a compact serializable **snapshot** for equality comparison, and a separate **render-diff** that produces model-visible text when the snapshot differs. Persist and compare the snapshot; never diff rendered prose. Change detection is then cheap, deterministic, and small enough to persist per turn; a section that renders nothing when unchanged contributes no message that turn. The one constraint: **snapshot equality must imply equivalent model-visible semantics** — so a change to how a section *renders* (wording, a security label, an escaping fix) must bump a renderer/schema version that participates in the snapshot, or the model keeps the stale rendering forever because the comparison state never moved.

## Supersede stale ambient state in-band — but this is a freshness tool, not a security control

When an ambient source changes (contract file edited, a capability removed), do **not** rewrite or delete the earlier injection in place — model-visible history is effectively append-only within a window and may additionally be dropped or summarized by compaction, so an edit-in-place is unreliable. Emit a **new** fragment that supersedes — scoped to the specific source and section, not globally: "the previous <section> from <source id> is replaced by the following" / "… no longer applies", never an unscoped "replaces all previously provided instructions". The scoping matters twice over: an unscoped template lets one low-precedence source claim to displace unrelated material, and when the ambient source is attacker-editable (a contract file in a cloned repo), authority-claiming replacement framing around its content is a prompt-injection amplifier — the notice describes a *data* update, consistent with the trust boundary below. When the prior state is unknown (e.g. resume with no baseline), always emit a superseding render rather than assume continuity. Two boundaries keep this honest:
- **Supersession is prose refresh, not enforced revocation or precedence.** A fragment saying "replaces previously provided" carries no authority by itself — a lower-precedence source must not override higher-precedence material just by claiming to replace it. Key supersession to an immutable source id + authority class and let the precedence lattice in `agent-instruction-composition.md` decide what actually wins; the prose is informational.
- **In-band supersession does not remove exposure.** It hides *stale* state from the model's next step, but the superseded text is still in the transcript sent to the provider. Genuine confidentiality, data-retention, or legal-deletion requirements need real redaction / tombstoning / context rebuild — supersession is the default path for staleness only.

## Make machine-injected context self-recognizing — as a best-effort dedup aid over untrusted history, failing safe

Give every injected fragment a way to **recognize its own past injections in raw history** (a marker/envelope matcher keyed to the fragment type). This lets the runtime, reading back an opaque message list, treat a match as *probably its own re-derivable context* — enabling dedup, a history-scan fallback, and safe recompaction. But a text marker is not an integrity boundary: it can appear in escaped user/model content, so it can be forged — and what a match may *authorize* depends on the provenance backing it, per the rules below:
- Where the platform has **trusted typed metadata / authenticated provenance** for a message, use that to identify runtime injections; text-matching is only the fallback for opaque histories that carry nothing else.
- **Fail safe, and scope the fallback:** the history-scan fallback classifies already-rendered fragments as runtime-owned for **dedup and recompaction of that rendered content only** — it never *answers a freshness question*. Freshness decisions come solely from the persisted baseline or a full re-render: with no baseline, always full-render (do not let "a same-type marker is present in history" *suppress* a needed refresh — a planted marker-shaped string echoed into history would otherwise pass off attacker content as your own current injection). And because a text marker alone cannot prove provenance, **a marker-only match is never a license to suppress or destroy: it may only gate presentation** (grouping/labeling for display); *suppressing a render* (dedup) is decided only by the persisted baseline — never by a marker match, so a forged marker cannot silence current context — and *dropping or rewriting matched history content* during recompaction always requires authenticated per-message provenance (typed metadata, a MAC, or a runtime-reserved channel that user/model text cannot write); without it, preserve the content and over-render. A missing or forged marker must degrade to over-rendering, never to dropping content.

## Persist a derivable baseline and re-derive on resume — with durable ordering

Persist only what is needed to *rebuild* the comparison baseline: periodic full snapshots plus the merge patches between them (an RFC 7396-style JSON merge patch fits — a member set to `null` means delete, arrays are replaced wholesale rather than merged; see RFC 7396, which obsoletes RFC 7386). Because `null` is reserved for deletion, **snapshots must not carry literal `null` values — encode them** (a sentinel/wrapper that round-trips). Do not simply drop them: a dropped null is indistinguishable from absent, and a value→null transition would emit a *delete* patch — "set to empty/null" would render to the model as "removed", the same conflation the `unknown`-vs-`absent` rule above exists to prevent. The rendered fragment *text* rides along as ordinary history; the baseline is separate derived state. On resume, rebuild the baseline by replaying snapshot+patches **chronologically**, not by re-parsing rendered prose. Invariants:

- **Durability ordering under a single writer per session.** Context assembly for a session is single-writer (the same one-live-writer invariant `agent-session-persistence.md` establishes) — rely on that rather than reconciling concurrent baseline writers. Given it, the history item must be *durably committed* before the baseline advance is persisted (or both in one transaction / one derivable log event): rendering into memory first is not enough, because with an async writer a crash can ack the baseline while losing the history item, leaving a baseline that claims the model saw context it never did.
- **Bound the patch chain.** Force a fresh full snapshot on a count/byte budget so resume replay stays bounded (array-replacement patches can each re-persist a whole list); validate a sequence/checksum, and a patch with no preceding full snapshot is a corrupt/old record — drop it and full-render, never apply it to an empty baseline.
- **Key the baseline by context-window generation and reset it atomically on compaction.** Compaction / a new window forces a full re-inject; commit the compacted-history replacement, the generation bump, and the baseline reset as **one durable event** (or derive all three from a single compaction record) — a crash between "history replaced" and "baseline reset" otherwise leaves a valid-looking old baseline against replaced history, and the next turn emits nothing. Sessions persisted by older code with no baseline must full-render on resume rather than fail.

This is the ambient-context analogue of "restore derived accounting, not just messages" in `agent-session-persistence.md`; keep the durable-log ownership there and the staleness/merge-patch mechanics here.

## Keep budget *signaling* in this layer and budget *enforcement* in the compaction layer — with an aggregate backstop

Emitting window ids, remaining-token counts, and guidance is **signaling** — telling the model its headroom. It is not the **enforcement** that reclaims space (compaction, a new-window reset), and the two must not be conflated: don't let the context-assembly layer silently truncate or re-prioritize whole ambient sections as its normal behavior. But signaling alone is not a bound — when the *mandatory* ambient state at full render already approaches the window (many individually-bounded values still exceed it in aggregate), there must be an **aggregate token/byte/count budget with an explicit required-vs-optional priority and a visible omission/failure signal**, or you get an unresolvable compaction loop or a failed model call. So: enforce a per-value elision (e.g. fixed middle-elision on an oversized single blob) *and* an aggregate cap that sheds optional sections first and surfaces what it dropped, reserving space for that omission/error envelope; delegate reclamation of *conversational* history to the compaction layer. Elision is never silent: surface what a per-value elision cut just as the aggregate cap surfaces shed sections, and **policy/permission/security-bearing content is never elided at all** — an adversary who can pad a contract file must not be able to push its deny-rules into the elided middle while the turn proceeds; such a section that cannot fit whole takes the error branch. Define the required-overflow branch explicitly: when the mandatory sections alone still exceed the budget after their allowed bounded representation, fail the turn with a typed error — never call the model having silently dropped required context.

## Trust boundary: ambient content is data; markers and source labels are not authority

- Ambient sources — contract files, environment values, user-supplied context — are injected **as data**, not trusted instructions. The marker envelope is for self-recognition/supersession, **not** a trust boundary: escaping interpolated values prevents envelope forgery but does not grant the content authority. Route precedence and untrusted-data handling to `agent-instruction-composition.md`; do not re-decide it here.
- A **hidden/invisible model-steering channel** (context an extension injects with no user-facing surface) is an authority-escalation risk, and a validated source-label character set only makes abuse *auditable*, it does not *authenticate* the injector. Bind the label to an authenticated injector principal (a runtime-assigned label, not a self-declared string), scope the injection's content/destination/expiry, record it in durable auditable history ("hidden" must never mean "untracked"), and enforce "may not grant permissions or override policy" at the permission floor / precedence lattice — not as unenforced prose in the steering fragment itself.
