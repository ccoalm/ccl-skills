# Schema And Validation Patterns

Use this for Pydantic, OpenAPI, Django serializers/forms, generated clients, and validation tests.

## Rules

- Public API request and response models should be explicit.
- Keep persistence models separate from public schemas when fields, nullability, or exposure differ.
- Validate syntax at the boundary and business rules in service/domain code.
- Treat finite domain values as domain concepts, not scattered schema literals. Public schemas may expose `Enum`, `Literal`, or generated enum values, but handlers should convert them into the domain-owned symbol through one parser/canonicalization helper before service logic runs.
- If a finite value crosses Python services, packages, storage, or generated clients, keep the canonical type/constants in the smallest shared domain or platform package already allowed by the repo. Do not create parallel enum sets with different casing, defaults, or unknown-value behavior. If no eligible shared package exists or creating one needs architecture approval, obtain architecture approval before merge, keep the local constants for this slice, add a same-line `finite-value-debt: <task-ref> <owner> <deadline> <reason>` comment at every temporary duplicate/raw use outside boundary conversion, and record a consolidation task. A debt marker does not constitute architecture approval. If architecture approval is not obtained before merge, the PR must not be approved; treat absent approval as a blocking finding. A debt marker without task reference, owner, and deadline is non-compliant.
- When storage or existing domain models are string-based but OpenAPI/protobuf already has an enum, keep explicit enum/string conversion helpers and mark direct generated-enum or raw-string use outside boundary conversion with `finite-value-debt: <task-ref> <owner> <deadline> <reason>`. Do not depend on generated transport enums deep in domain code unless the whole layer is intentionally transport-coupled by a traceable architecture decision, recorded as an ADR path or inline usage-site comment formatted `architecture-approval: transport-coupled finite value <scope> <decision-ref> <reason>` where `<decision-ref>` is a full URL or numeric record id such as `ADR-123`; reviewers must confirm the referenced record exists and approves the specific value/scope before approval. A CI check, grep panel, or required review checklist item MUST exist and pass before any PR introducing `architecture-approval:` comments is merged; absence of that check is itself a blocking finding. The first PR that introduces `architecture-approval:` comments must include the enforcement check in the same PR or reference a prior merged check; "will add later" is not approval.
- Architecture owns cross-boundary semantic consistency for finite values: approve the shared package or contract location, approve any transport-coupled exception through a traceable decision, and make sure every `finite-value-debt` marker has an exit owner, deadline, and consolidation task.
- Do not return raw provider payloads directly from product APIs.
- For shipped or externally consumed schemas, preserve backward-compatible request/response behavior by default. Add optional fields or versioned behavior first; do not remove fields, make optional fields required, rename keys, change enum meanings, or reject previously valid requests without explicit human approval of a breaking-change risk assessment.
- Add tests for validation errors, default values, optional fields, enum handling, finite-value boundary conversion, unknown-value behavior, and compatibility-sensitive fields.
- **Model library choice by boundary, not by author preference**: Pydantic at API request/response, config (Pydantic Settings), and any other untrusted-input parsing surface where validation + JSON-schema export + error messages are core; **`dataclass(slots=True, frozen=True)`** for internal shallow-immutable value objects with no validation need (smaller memory, no Pydantic overhead, no schema export — note `frozen=True` only prevents attribute reassignment, mutable fields like lists/dicts are still mutable in-place); **`msgspec`** when profiled hot-path evidence (high-rate serialization, low-allocation parsing) or an existing service / platform standard justifies it — Pydantic v2 (powered by `pydantic-core` in Rust) has narrowed the gap, so reach for msgspec on measured need, not by default. Mixing all three in one service is acceptable when each is at its right boundary; using one library for everything is the smell — Pydantic for internal pure data is overhead, dataclass for API input loses validation, msgspec everywhere makes the codebase non-standard for new contributors.

## Generated Clients

- Treat generated clients as output from OpenAPI/protobuf tools.
- Update source contract first, regenerate, then test generated client behavior where the repo requires it.
- For compatible changes, test old-client/new-server and new-client/old-server behavior when the repo has generated clients or consumer fixtures. For approved breaking changes, test that the removed compatibility path fails in the intended way and that the documented migration/cutover path works.
