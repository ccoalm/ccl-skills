# Async And Worker Patterns

Use this for asyncio, async endpoints, workers, blocking work, and cancellation.

## Async Rules

- Bound `asyncio.gather` with semaphores, pools, or queue limits.
- Use `asyncio.timeout`, client timeouts, or framework timeout controls where available.
- Use `asyncio.to_thread` only for bounded blocking calls that are safe to run in a thread.
- Do not run CPU-heavy work in the event loop.
- Clean up async clients through lifespan, context managers, or explicit close hooks.
- **`asyncio.TaskGroup` (Python 3.11+) is the default structured-concurrency primitive for fan-out work; prefer it over `asyncio.gather`** for any code where partial failure should cancel siblings. Per Python docs: when a child task raises, TaskGroup cancels remaining scheduled tasks; `gather(return_exceptions=False)` does not — sibling tasks keep running to completion, which is the wrong default for most fan-out (each leak burns a request budget or external rate-limit). Use `gather` only when partial success with independent siblings is the intended contract (and even then, pair with bounded concurrency + per-task timeout). Wrap TaskGroup with `async with asyncio.timeout(...):` for deadline enforcement, NOT per-task timeouts when the whole batch shares a deadline. **Exception-shape gotcha when outer timeout fires concurrently with a sibling failure**: the outer `asyncio.timeout()` cancels the TaskGroup scope; `TaskGroup.__aexit__` drains children and propagates failures as an `ExceptionGroup`. If a sibling raised an application error before the timeout cancellation completed, you do NOT receive a clean `TimeoutError` — you receive an `ExceptionGroup` containing both the application error AND a `CancelledError` (or `TimeoutError`) from the cancellation. Handle both shapes with `except* asyncio.TimeoutError` AND `except* DomainError` AND a fallback `except* BaseException`; do not assume `except TimeoutError` will catch the deadline case, because in this race it does not.
- **Handle TaskGroup failures with `try / except*` (PEP 654 ExceptionGroup, Python 3.11+) rather than `except Exception`** — when multiple sibling tasks fail, TaskGroup raises an `ExceptionGroup` (or `BaseExceptionGroup` for cancellation cases) that bundles all errors; a bare `except` strips the multi-error structure and discards diagnostics. Pattern: `try: async with asyncio.TaskGroup() as tg: ... except* SomeTransientError as eg: ... except* SomeFatalError as eg: ...`. Each `except*` handler receives an ExceptionGroup containing only the matching subset, and unmatched exceptions re-raise as a residual group. Document in API contracts that operations using TaskGroup may raise ExceptionGroup so consumers wrap with `except*`, not `except`.
- **Never swallow `asyncio.CancelledError` inside async code that runs under TaskGroup or `asyncio.timeout`** — Python docs warn that those structured-concurrency primitives are implemented via cancellation internally; a `try/except Exception` that catches CancelledError (because CancelledError is a `BaseException` in 3.8+ but some code still catches it as a transient) prevents the cancellation from completing and leaves the task group / timeout in an inconsistent state. Re-raise CancelledError explicitly after any cleanup, or use `except Exception:` (which excludes BaseException) so CancelledError propagates naturally.

## Worker Rules

- Use workers for long-running or retryable work.
- Store progress and terminal status when user-visible work outlives a request.
- Separate the setup lifetime from the spawned-worker lifetime: work that must outlive the request must not be a child of the request's structured-concurrency scope — do not put it in a request-owned `TaskGroup`, and do not `await` it under the request's `asyncio.timeout` — or it is cancelled when the request ends. But "outside the request scope" is not fire-and-forget: register it with an application-lifetime supervisor / durable queue / tracked task registry that keeps a strong reference (a bare `asyncio.create_task` can be garbage-collected and lose its exception), observes failures, and gives the worker its own bounded deadline. The request handler's own setup still honors request cancellation; cancelling the request after the task is registered must not cancel it, and cancelling setup must not orphan an already-registered task.
- An exception inside a detached execution never reaches framework/request exception handlers: a bare `asyncio.create_task` failure surfaces only via the loop exception handler when the task is garbage-collected, a `threading.Thread` dies silently, an executor future swallows the exception until awaited, and a queue-job body gets only what the worker runner is configured to record. Route every production detached spawn (task, thread, executor submit, job body) through one shared firewall wrapper that catches, logs the traceback with the trace/correlation id, and increments a failure metric; enforce coverage with a checklist or lint, not memory. The only rigorous regression proof for "the process/worker survives this exception" is a subprocess exit code: a test runs a child process that triggers the exception inside the detached execution and asserts it exits cleanly — an in-process assertion cannot prove process survival. Scope that proof to per-item/per-request work where catch-and-continue is the policy; for a supervisor or global-invariant task (scheduler loop, registry owner), the test asserts the opposite — the worker goes non-serving/unready or exits nonzero on purpose rather than continuing on corrupted state.
- For any async side-path that outlives the request (audit, ledger, usage reporting, notifications), the working posture is four pieces together: detach the lifecycle but keep only correlation — re-attach the correlation/trace fields of the contextvars snapshot per `redis-cache-lock-patterns.md` rather than dropping the correlation id, but never a wholesale snapshot replay that smuggles request auth/session/secrets into work outliving the request (whitelist correlation + durable work-item identity; the worker runs under service identity), detaching only at the accept boundary for an already-accepted work item with its own bounded deadline; for the service's own rollbackable mutations the accept boundary is durable commit success — or a same-transaction/outbox row that commits and rolls back atomically with the mutation: before that, caller cancellation suppresses side-path work and nothing detached may be enqueued against an in-flight commit (a commit that fails, rolls back, or returns unknown must never leave a fired detached record — and idempotent reconciliation of an unknown outcome requires a durable intent/reconciliation key written with or before the mutation, the outbox row being exactly that key; post-commit async capture without such a durable key is a blocked design for audit/billing-relevant records unless unknown outcomes are impossible or reconciliation is provable from durable authoritative state); after it, capture is mandatory and not gated on the caller still being connected; records of NON-rollbackable external side effects (a provider call that already consumed quota) invert the order — book a per-attempt reservation/outbox row independently of the local outcome, with idempotent reconciliation; a bounded queue or semaphore; shutdown ordering where accepting new submissions and draining are serialized so no submit can race the drain — mark closed, stop accepting, then drain with a deadline without holding the accept lock through the drain wait (drain/flush paths must not need it, or shutdown deadlocks); and a loss policy matched to the data class: explicitly accepted bounded loss + a reconciliation/repair job only when a tested idempotent reconstruction source exists — for billing/ledger/usage data with no such source, use a same-transaction outbox or backpressure instead of drop.
- Make retries idempotent.
- Include exception handling, logs, metrics, and retry-vs-drop behavior.
