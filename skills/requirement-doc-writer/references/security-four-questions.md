# 安全 4 问（canonical）

四个产品需求技能（`requirement-intent` / `requirement-baseline` / `requirement-scope` / `requirement-doc-writer`）共用同一份问题本体。改动先改本文件；各技能 `## 安全 4 问` 节只定义该技能的产物落点与交接，不复述、不改写问题本体。always-on 层（agent-context/session-start.md「设计期安全 4 问」）保留常驻反射全文——那是每会话注入的反射本体（实测区分度项），不是本文件的副本；bootstrap 的 Q2/Q4 是压缩常驻式（动词表为其子集：伪造/篡改、伪造/越权），完整谓词集以本文件为准——改动本文件动词表时同步核对 bootstrap 常驻式仍为其子集。

## 触发

设计、方案、需求澄清、现状盘点、范围界定或 PRD 触及：身份、计费、配额、租户/用户隔离、权限、删除、覆盖。always-on 层的走时点是交付路由之后、产出设计/方案 substance 之前。命不中（纯内部无关输入）显式记"无安全敏感输入"。

## 问题本体（逐条走；散文里带一句"注意安全"不算）

1. 哪些输入由调用方或用户可控。
2. 伪造、篡改、重放、越权、重复提交、误删或覆盖这些输入的爆炸半径。
3. 每个安全敏感值（身份、租户、金额、配额、权限）的信任根：安全敏感值必须从认证主体或服务端状态推导，绝不信请求体自带。
4. 至少一条伪造/越权/误删/覆盖的负向用例。

## 各产物落点

- **澄清记录（`requirement-intent`）**：逐项包含四项答案；第 4 条写作负向验收用例。
- **现状盘点（`requirement-baseline`，as-is 应用）**：Q1 问"当前哪些输入由调用方或用户可控"；Q3 照实记录当前信任根来自认证主体、服务端状态、配置、人工运营规则还是请求体——现状若就是请求体自报，照实记录并标注为风险，安全敏感值不得以请求体自报为权威（命中即记为必修风险）；Q4 是一个能证明现状是否防住伪造/越权/误删/覆盖的负向用例。
- **改动范围（`requirement-scope`）**：范围表逐项记录四项答案；负向用例写入验收范围（如伪造租户、越权改配额、重复删除、覆盖他人数据）。
- **PRD（`requirement-doc-writer`）**：文档必须有"安全与滥用"小节，逐条写四项答案；负向验收用例覆盖伪造身份/租户、越权、重复提交、误删/覆盖等。

## 命中后的交接

命中上述触发任一项时，风险标签与 gate 选择 → `feature-risk-router`；进入研发交付/生命周期 → `product-rd-workflow`。本文件只做安全反射与产物落点，不替代 `feature-risk-router` 的风险定级。
