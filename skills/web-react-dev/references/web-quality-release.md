# Web Quality And Release

## API Integration

- Use typed API clients or schema validation when available.
- Test URL, method, headers, request body, response envelope, empty body, invalid JSON, non-2xx, timeout/abort, network failure, permission denied, and feature-closed responses where relevant.
- Map backend errors to user-readable state and developer-observable diagnostics.
- Keep request cancellation and stale response handling explicit for search, filters, autosave, and rapidly changing inputs.

## API Client Recipe

For API-backed pages, centralize these mechanics in the client or the narrowest shared request wrapper the repo already uses:

| Concern | Required behavior | Test evidence |
| --- | --- | --- |
| Request metadata | Attach or preserve request id, trace id, operation name, app/client version, auth context, and upload/long-running classification where available | Assert headers/body/query metadata and redaction behavior |
| Response parsing | Accept the repo's canonical envelope; classify empty body, invalid JSON, non-2xx envelope, backend error envelope, and malformed success separately | Contract tests for each response shape |
| Cancellation | Distinguish user/navigation/rapid-input cancellation from network failure and timeout | Test abort/cancel path without user error toast |
| Auth and permission | Convert expired auth, forbidden, feature-closed, and scope-mismatch responses into route guard, disabled state, or permission state | Component/API tests for 401/403/closed responses |
| User error mapping | Show readable state near the affected region; keep raw transport details for logs/devtools, not UI copy | Component test asserts visible message and retry/next action |
| Long work | Expose task id/status, polling/retry/backoff, stale result protection, refresh recovery, and final status | API-client test plus browser smoke for one pending-to-final flow |

## Streaming Client Mechanics (SSE / WebSocket Chat, Live Logs, Progressive Results)

For AI-chat, live-log, or progressive-result surfaces consuming SSE/WebSocket streams, centralize these behaviors in the stream client wrapper (visible streaming *states* are enumerated in `references/complex-workspace-patterns.md`; provider-call retry/continuation semantics are owned by `llm-inference-integration/references/llm-client-gateway.md`):

- **Retry asymmetry**: automatic connection retry (bounded exponential backoff plus a connect timeout) is safe only when establishing the connection cannot re-trigger the operation — i.e. when subscribing/reconnecting to an existing server-issued operation or stream id, or when the send carries an idempotency key with an acknowledged dispatch boundary. Once a stream has consumed ANY event whose handler has a non-idempotent effect — a start/processing event that fired analytics or stateful handlers counts, not only visible deltas or dispatched tool events — automatic resubscription additionally requires a resume position — a resume cursor / SSE `Last-Event-ID` whose delivery semantics are verified strictly-after (an inclusive cursor or ambiguous-disconnect boundary replay re-delivers the boundary event), or paired with stable per-event ids plus client-side deduplication and idempotent side-effect handling — because a server that replays history or delivers at-least-once around the disconnect hands the new attempt events the stale-attempt guard reads as current, double-applying text, analytics, or tool side effects; without a resume mechanism, terminate for explicit user retry instead, and cover the overlapping-replay-after-disconnect case with a regression test. Per-tab attempt tokens, latches, and dedup state do not span browsing contexts: when two tabs can subscribe to the same operation, side-effectful handlers (tool dispatch, analytics, mutations) need server-side idempotency keyed by operation/event id as the primary control; a client-side single-executor election is an acceptable supplement ONLY with an atomic exclusive mechanism — the Web Locks API, or a lease with expiry and a fencing token the server validates — because two tabs reading ordinary shared state can both observe "no executor" and both claim it; without one of these, both tabs will independently execute the same replayed events. A POST-style send that starts billed generation or dispatches work server-side before the first delta arrives must NOT be auto-resubmitted on connect timeout or lost response — and a lost acknowledgement is an UNKNOWN dispatch, not a failure: the server may have accepted the operation, so the user-driven retry must reuse the original idempotency key or first reconcile the operation's server-side status before a new send is allowed, or the "safe" manual retry double-charges and repeats tool side effects; and never blind-retry a stream that already emitted visible deltas or dispatched tool calls — a replay duplicates them (the partial-stream discipline on the provider side owns when continuation is safe; ambiguous provider-call retry policy routes to `llm-inference-integration`). When no eligible resume/deduplication mechanism exists — or its retry budget is exhausted — mid-stream failure becomes a terminal error state with an explicit user-driven retry/regenerate, never an automatic reconnect-and-replay.
- **Guaranteed terminal state**: when the current attempt's transport closes — mid-stream error, abnormal close, or a NORMAL close — without an already-latched recognized terminal event, and the close is not eligible for automatic resubscription (per the retry-asymmetry rule above) or the reconnect budget is exhausted, synthesize a local terminal event and push it through the same message pipeline, so every streamed message provably reaches done/error/canceled (cover the clean-close-after-unknown-status case in a regression: a newer server emitting an unrecognized terminal status then closing normally must not leave the operation pending forever). While an eligible resubscription is still in budget, supersede the closed attempt first, suppress its terminal callback, and keep the operation visibly pending until the final transport attempt resolves — latching failure on a transient disconnect fires terminal side effects that a successful reconnect then cannot cleanly undo. A spinner that can never resolve on mid-stream drop is the recurring production bug this prevents. Terminal state is a per-attempt latch: the first end/error/canceled transition for an attempt wins, closes/aborts that attempt's transport, and every later callback for that attempt token — later terminal, close, and error callbacks AND ordinary data/tool events from a late open or buffered delivery on the same transport — is rejected; one failing connection can fire error then abnormal-close, or deliver a buffered delta after the UI went terminal, and without the full-coverage latch those double-fire state transitions, analytics, or tool-result handling.
- **Stale-stream guard covers synthesized events too**: tag each connection attempt with a monotonic token; every consumer — incoming stream events AND the locally synthesized terminal/close/error callbacks above — checks the token and drops anything from a superseded attempt, and abort the previous `AbortController` before opening a successor. Aborting the predecessor fires its own close/error handler, so an unguarded synthesized terminal event from the dead attempt overwrites the successor's UI state; an intentional abort of a superseded attempt emits nothing, and user cancellation of the *current* attempt is modeled as `cancel-requested` until the transport confirms teardown — if a buffered server `end` arrives first, resolve the operation as completed (the work may already be done and billed) and surface that instead of a `canceled` state whose retry would repeat the charge; only an unconfirmed teardown synthesizes `canceled` (branch on the abort reason, not just on "closed abnormally").
- **Reconnect policy is declared data, not scattered constants**: `{enabled, maxRetries, initialDelayMs, maxDelayMs, connectTimeoutMs, idleTimeoutMs}` on the transport wrapper; connect-timeout fires its own event so the UI distinguishes "still connecting" from "failed", and the idle/heartbeat timeout catches the proxy-buffered stall where the connection opened successfully but no event, close, or error ever arrives — without it the terminal-state guarantee (which triggers on closure) never fires and the UI stays pending forever.
- **Transport behind one interface, with declared degradation**: WS/SSE/polling behind a single event-surface interface so SSE-hostile networks (buffering proxies, restrictive gateways) degrade to polling without changing consumers — degradation is conditional on the server actually exposing the fallback protocol; when no polling/read endpoint exists (a WebSocket-only backend), a blocked transport resolves to the explicit unsupported/network-error terminal state rather than emitting semantically incompatible requests. Fetch-based SSE libraries need deliberate settings: background-tab behavior, abort wiring, and suppressing the library's built-in auto-retry when the wrapper owns retry policy.
- **Status enum → UI state via one lookup table**: map the wire message-status enum (e.g. start/processing/executed/end/error/canceled) to loading/disabled/retry UI in one table — not scattered conditionals per component. An unknown status maps to an explicit unsupported/error presentation with telemetry, keeping send/retry controls conservatively disabled until a recognized terminal event resolves the operation; treating unknown as "not loading" re-enables actions while the server may still be working and double-fires them.
- **Reload recovery is server-replayed history** through the same message pipeline with an `isHistory` flag that suppresses side effects (no tool re-execution, no analytics double-fire); add client-side partial-message persistence only when the product genuinely needs offline drafts.
- **Client-executed tool/action failures report back into the agent loop** as a terminal tool result; a console-only error leaves the backend agent waiting forever — that is a hang, not an error state.
- **Trace propagation applies mid-stream**: read the trace id from the stream response headers or first event and attach it to the message state, so a broken stream is supportable like any failed request.

## Test Layers

- Unit tests: pure mapping, validation, reducers, derived data, error translation, and utility behavior.
- Component tests: loading/empty/error/success states, forms, validation, permissions, emitted request intent, keyboard interaction, and visible state.
- API-client/contract tests: request/response and failure parsing.
- Browser/E2E smoke: critical route opens, primary action succeeds, one realistic failure path is readable, console has no new serious errors, and visible result is asserted.
- Scenario tests: build the scenario matrix in `testing-strategy`; for web surfaces, map each scenario to component state, API-client contract, and only the necessary browser smoke instead of duplicating every branch in E2E.

## Performance And Deployment

- Check bundle growth, code splitting, image optimization, caching headers, long tasks, unnecessary rerenders, list rendering, hydration/runtime errors, and Core Web Vitals risk.
- Build-time environment variables must be explicit; do not hide production behavior behind local-only defaults.
- Release checks should include build, smoke route, error monitoring, analytics event sanity, rollback or feature flag path, and cache invalidation/CDN implications when relevant.
- **Request waterfalls are a top-priority review category** (Vercel's impact-ranked React guidance grades sequential-to-parallel fixes as the 2-10× class): start independent async work before awaiting and join with `Promise.all`, defer an `await` into the branch that actually consumes it, avoid chained sequential awaits in route handlers / server components / effects, and place Suspense boundaries so the shell streams while slow regions resolve.
- **Bundle-size discipline**: import concrete module paths instead of barrel files (a barrel import can pull the whole package into the graph), keep import paths statically analyzable for tree-shaking, dynamic-import heavy or below-the-fold components, and preload on user intent (hover/focus) rather than eagerly.

## SEO And Discoverability (Public-Facing Pages)

Applies to marketing, content, docs, landing, and any page meant to be found via search or unfurled in social/chat previews. Auth-gated consoles and internal workbenches are exempt, but their public shells (landing, login, share/preview pages) are not. Grounded in Google Search Central, `schema.org`, and `ogp.me` (verified 2026-08); when in doubt those docs are authoritative, not memory.

- **Indexable pages need a unique, descriptive `<title>` and meta description per page** — no boilerplate duplicated across routes, no keyword stuffing. For SPAs this means route-level title/description management (framework metadata API or a head manager), not one static `index.html` title.
- **Variants whose primary content is duplicate or substantially equivalent declare `rel=canonical`** to pick the representative URL and consolidate signals; the canonical page carries a self-referential one. A parameterized URL is NOT automatically a duplicate — a filter/category landing page with distinct indexable content keeps its own canonical (canonicalizing it away tells the crawler it is non-representative and can drop it from results); decide indexability per parameterized route family, not by the presence of query parameters.
- **Keep-out uses `noindex` (meta tag or `X-Robots-Tag`), and the page must NOT be blocked by robots.txt** — a robots.txt block hides the `noindex` from the crawler; robots.txt manages crawl traffic, it does not remove pages from the index. Blocking a should-be-indexed page's JS/CSS in robots.txt also breaks rendering-based indexing.
- **XML sitemap when the site is large, new, or weakly interlinked**; a small (~<500 well-linked pages) site usually doesn't need one.
- **Structured data as JSON-LD** (Google's recommended format) with `schema.org` vocabulary for surfaces that qualify for rich results (articles, products, FAQs, breadcrumbs); validate with the Rich Results Test rather than eyeballing.
- **Social preview: the Open Graph required set is `og:title`, `og:type`, `og:image`, `og:url`** (add `og:image:alt` with any `og:image`); with incomplete Open Graph metadata the preview becomes incomplete or platform-dependent (platforms may fall back to ordinary HTML metadata or their own tags). Verify the unfurl with the target platforms' debuggers when share traffic matters.
- **Multilingual pages use bidirectional `hreflang`** (every variant lists itself plus all others — non-reciprocal tags are ignored), absolute URLs, and `x-default` for unmatched languages. Localized variants with distinct content (different languages, or regional pages with real differences) keep their own self-referential canonical — canonicalizing translations to the default-language URL marks them non-representative and removes them from localized results, defeating the hreflang set; same-language regional near-duplicates may share a canonical representative per the duplicate rule above, and hreflang then annotates the canonical set.
- **Client-rendered React has JS-SEO constraints**: Google renders JS in a deferred headless-Chromium queue, so (1) navigation must be real `<a href>` links (router `<Link>` components render one; click-handler-only navigation is invisible to crawling), (2) no fragment-based routing for indexable content — use History API paths, (3) soft-404s need a real 404/410 status (or a JS-injected `noindex` when the server can't), (4) primary content must not require user interaction to load, and (5) Google itself still recommends SSR/pre-rendering for critical content ("not all bots can run JavaScript"). For content-heavy public surfaces this is an SSR/SSG/Islands adoption signal per `Framework-Era Patterns` below.
- **Core Web Vitals are used by Google's ranking systems** (good thresholds: LCP ≤ 2.5 s, INP ≤ 200 ms, CLS ≤ 0.1, at the 75th percentile of field data) and mobile-first indexing is fully rolled out — the mobile rendering is the indexed one, so mobile CWV and mobile-rendered content parity are the release-gate numbers for public pages.
- **Verify deterministically**: Lighthouse SEO category, the Rich Results Test, or a fetch-and-parse check beats hand review; for changed public routes assert title/description/canonical/OG in a component test or the browser smoke — asserting canonical VALUE per route class, not mere presence: distinct indexable pages self-canonicalize, duplicate variants resolve to their intended representative, and the canonical target is a successful indexable URL (not a redirect or error) — a presence-only check stays green while every route canonicalizes to the home page and drops out of results; keep the check in CI for the marketing/content app rather than re-auditing by hand each release.
- Primary pages per rule cluster (all under `developers.google.com/search/docs` unless noted): titles/descriptions → `appearance/title-link`, `appearance/snippet`; canonical → `crawling-indexing/consolidate-duplicate-urls`; noindex vs robots → `crawling-indexing/block-indexing`, `crawling-indexing/robots/intro`; sitemap → `crawling-indexing/sitemaps/overview`; structured data → `appearance/structured-data/intro-structured-data`; social preview → `ogp.me`; hreflang → `specialty/international/localized-versions`; JS SEO → `crawling-indexing/javascript/javascript-seo-basics` and `.../lazy-loading`; CWV/mobile-first → `appearance/page-experience`, `appearance/core-web-vitals`, `crawling-indexing/mobile/mobile-sites-mobile-first-indexing`.

## Build Tooling Currency

- **Vite 8 (released 2026-03) is the current stable**, shipping Rolldown as the default Rust-based bundler (10-30x faster builds, full plugin compatibility per Vite's own announcement). **Vite 7** (Node.js 20.19+/22.12+ required, Node 18 dropped; ESM-only distribution) remains the previous stable line for teams not yet ready for the Rolldown migration trade-off (Rust-toolchain debugging, plugin compat audit). Migration cadence: upgrade Node first if pinned to Node 18; then plan Vite 7 → 8 with a build-perf + plugin-compat smoke before flipping defaults. The historical `rolldown-vite` opt-in package is no longer the path forward — Vite 8 ships Rolldown directly.
- **Tailwind CSS v4 (stable Jan 2025) uses CSS-first configuration**: no `tailwind.config.js` for new projects; configure via `@theme { --color-brand: ... }` directives in the same CSS file that imports Tailwind. The first-party Vite plugin + automatic content detection eliminates most config; full builds 5x faster, incremental 100x faster than v3. Migration from v3 to v4 is not free (config shape, plugin API, some utility-class differences) — the migration guide is authoritative; do not infer migration steps from training-data memory.
- **Biome v2 (June 2025, "Biotype") for formatter + linter** when the team wants ESLint + Prettier collapsed into one Rust tool. Type-aware linting without TypeScript compiler dependency (Biome implements its own type inference for lint rules — this does NOT replace `tsc --noEmit` in CI for full type-check); 520+ lint rules (many inspired by other linters — verified 526 as of 2026-08); CSS formatting/linting stable since v1.9; `biome migrate eslint` automates most config porting. Trade-off: smaller plugin ecosystem than ESLint; if the project depends on niche ESLint plugins (custom org rules, framework-specific lint), audit those before migrating. ESLint flat config + Prettier remains valid for teams with deep ESLint plugin investment.
- **React Compiler ESLint plugin**: when React Compiler is enabled (per `react-architecture.md`), keep `eslint-plugin-react-hooks` at the version that ships the compiler-aware preset; the recommended preset enforces the rules Compiler relies on (no mutating props, deterministic render, etc.). Without it the compiler may silently skip components that violate its assumptions.

## Framework-Era Patterns (When To Adopt, When To Defer)

Several React-adjacent architectures became visible in industry conversation (RSC / Server Actions / Islands / Module Federation / Suspense data fetching). They are real and useful in narrow contexts; they are not the new default for every React app. Rules below define when to opt in.

### React Server Components / Server Actions / Streaming SSR

- **Adoption condition**: the app is on a framework/runtime with **production-supported RSC and Server Functions enabled for this app path** — Next.js App Router in RSC mode is the canonical example; other frameworks ship RSC as opt-in or experimental on specific paths. Framework-native loaders / actions (Remix / React Router framework mode, Modern.js, RedwoodJS) are valid server data patterns but are NOT automatically RSC / Server Actions — `loader` / `action` / `useFetcher` are their own primitive. Mixing hand-rolled RSC into a Vite + React Router v6 SPA is a research project, not a delivery path.
- **Where RSC pays off**: content-heavy pages with mostly read traffic and small mutation surface (marketing, docs, dashboards with a stable read shape, list/detail screens). The data dependency moves to the server; the client bundle shrinks; first-load latency drops.
- **Where it does not**: highly-interactive workbench surfaces (the chart/table workbenches in `react-architecture.md`'s heavy-dashboard pattern), live-collaboration editors, anything whose interactivity-to-content ratio is high. The "use server" / "use client" boundary becomes a maintenance tax that outweighs the SSR win.
- **Server Actions / Server Functions** (`'use server'`) are async network calls with serializable args, designed for mutations / form POST paths where the framework owns revalidation. They can replace some fetch-based form submissions on RSC frameworks (progressive enhancement: form works without JS). They are NOT a general data-fetching replacement and they are not meant for retrofitting the API surface on a non-RSC framework. **Every Server Action is a publicly reachable HTTP endpoint regardless of where it sits in the component tree — authenticate and authorize inside each action body**; UI-level gating or "the button is only rendered for admins" is not access control. On Next App Router, declare fetch caching semantics explicitly (`cache` / `next.revalidate` per the pinned major's docs) rather than relying on implicit defaults, which have changed across majors.
- **Streaming SSR with `<Suspense>` boundaries** is independent of RSC and works in plain React 18+: choose Suspense boundaries that match user-visible regions (header / nav / primary content / secondary panel) so the slowest region does not block the rest. Boundary placement is design — every fallback geometry must match the resolved region or layout jumps when the fallback resolves. Pair with `ErrorBoundary` at the same node — Suspense alone catches loading, not failure.
- **Don't pick the framework for the buzz; pick it for the deploy story.** Many SaaS / admin / data-console apps already work on Vite + React Router + TanStack Query and would gain little from migrating to App Router; the migration cost (auth, middleware, build pipeline, hosting, third-party SSR compatibility) is real.

### Suspense Data Fetching And `use()` Hook (React 19+)

- **`use(promise)` requires a Suspense-compatible data source**: a framework loader (Next App Router, React Router data APIs, Relay) or a cache library that throws promises (TanStack Query with `suspense: true`, React Query's `useSuspenseQuery`). Calling `use(fetch(...))` directly in a component creates a new promise on every render and falls into an infinite-suspense loop.
- **Suspense boundary placement is part of the page contract**: each boundary represents a user-visible region with its own loading geometry and its own error boundary. A single top-level boundary turns the whole page into a spinner; a boundary per micro-component turns the page into a flicker fest. Match boundaries to design regions.
- **Fallback geometry MUST match resolved geometry.** A skeleton row that's 40px tall when the loaded row is 80px causes layout jump on resolve. Reserve space in the skeleton; check rendered behavior in the browser.

### Islands Architecture / Partial Hydration

- **Adoption condition**: the surface is content-dominant with sparse interactivity (marketing, docs, blog, knowledge base, public help center, status page). Astro / Fresh / Marko / Eleventy + islands are the appropriate stack.
- **Not for**: data consoles, admin workbenches, editors, dashboards. The "island" concept assumes most of the page is static; SaaS workbench pages are >90% interactive — turning them into islands fragments the state model.
- **Within React: `astro:react` or similar lets a Vite/Astro static site host React islands.** This is a legitimate pattern for content sites that need occasional interactive widgets; it is not a SaaS app architecture.

### Module Federation / Micro-Frontends

- **Adoption condition** (all must hold, not any): (1) multiple independent teams deploy independently to the same shell, (2) shell + remote runtime version compatibility is a contractual concern with maintained governance, (3) the shared runtime overhead (shared React, shared design system, shared auth, shared analytics) is non-trivial AND can survive cross-team version skew, (4) a monorepo + code-splitting alternative was evaluated and rejected with reasons.
- **Default for SaaS portfolios is NOT micro-frontends**: a monorepo + meta-framework + per-feature code splitting (`React.lazy` / route-based splits) gets you per-feature lazy loading and per-team ownership without the runtime composition tax. Module Federation 2.0 / `single-spa` are real tools, but they introduce shared-dependency version contracts, runtime-error-class issues, type-sharing problems, and CSP / origin / CORS concerns that monorepo splits do not.
- **If adopted**: pin shared singletons (`react`, `react-dom`, the design-system runtime) via the federation config; document the version-compatibility window; gate cross-remote breaking changes through a contract test; never let a remote inject global side effects (analytics, error boundaries, route registration) without the shell's awareness.

## Lane-Aware Static Deployment On Object Storage

When the front-end build output (HTML, JS, CSS, assets) is served from object storage (S3 / OSS / TOS / GCS) instead of a stateful web server, and the portfolio runs multiple environments / canary lanes / preview lanes side by side, a thin server-side router sits between the user and the bucket to select the right lane's artifacts. The pattern is mature but security-sensitive; the rules below are necessary, not optional.

### Storage And Bucket Posture

- **Storage layout**: the build artifacts of each lane live under a stable prefix; the lane prefix is the unit of isolation. The standard lane (production baseline) has its own well-known prefix. The router resolves an inbound request to a `(lane, prefix, path)` tuple and serves the matching object.
- **Bucket separation by trust**: protected lanes (canary, preview, tenant-isolated, internal) and the public production baseline MUST live in separate buckets — the production baseline can be public-readable for CDN performance; protected lanes MUST be in a private bucket with identity-bound or network-bound origin access control. Mixing public and protected lanes in one bucket is a finding, because any per-prefix policy is easy to misconfigure into a public exposure.
- **Origin access control choice depends on the topology, but the lane-resolution contract is the same**: when a managed CDN fetches directly from object storage, use the provider's CDN-bound origin-access mechanism (S3 OAC bound to CloudFront, OSS-CDN equivalent) — but direct CDN-to-bucket is valid only for immutable public baseline assets that need no lane resolution, token exchange, manifest verification, or response-header control. Any path that needs lane resolution / preview-token validation / response-header policy / structured logging MUST go through the router; routing it directly via CDN bypasses the entire trust model. When a custom router proxies bytes from object storage, the router authenticates with its own IAM / service-account identity that has the minimum required permissions, and the bucket policy restricts access to that identity (and to the CDN-bound identity if a CDN sits in front). Do not rely on `Referer`-based bucket policies — `Referer` is client-set and trivially spoofable by non-browser clients (curl, scripts, native apps). The "TOS equivalent" or any other provider's equivalent must be identity-bound or network-bound and resistant to client-supplied header spoofing.
- **Immutable artifact prefixes**: each deployment writes to a fresh content-addressed prefix (e.g. `<commit-sha>/`); existing prefixes are never overwritten. The deploy step uploads all artifacts, verifies them against a generated build manifest (per-file expected size + content checksum via the provider's authoritative checksum API — `x-amz-checksum-*` on S3, equivalents on OSS / GCS / TOS; for multipart uploads use the full-object checksum type where the algorithm/provider supports it; when only a parts-composite checksum is available, do not compare it against the manifest's whole-file digest — verify by independently reading back the completed object and hashing it with the manifest's algorithm), and only then flips the active manifest to the new prefix. ETag is not a reliable content checksum for multipart uploads — do not equate ETag match with content match.
- **Artifact retention and GC**: old immutable prefixes are kept for at least `max(CDN cache TTL, browser cache TTL, service-worker cache TTL, rollback window)` after they stop being active. Premature GC orphans live clients still holding old HTML that references old chunks → blank screens and chunk-load errors. Retention policy is part of the deployment contract, not an afterthought; GC is a separate scheduled job with explicit safety margins, never tied to "deploy succeeded" timing.

### Trust Model For Lane Selection

- **Router origin lockdown**: the router MUST NOT be reachable directly from the public internet or from any caller that bypasses the trusted edge. Enforce by private networking (internal load balancer, VPC-internal listener, no public DNS), mTLS / shared internal auth between edge and router, or an explicit trusted-proxy chain plus a router-side check that rejects any request not carrying the proxy's authenticated identity. If an attacker can reach the router directly with their chosen lane header, "edge strips and re-injects" provides nothing.
- **Lane signal trust**: client-controllable signals (request headers, query strings, host names when DNS is shared) MUST be validated and re-asserted at the edge before they reach the router. The edge (CDN, ingress controller, reverse proxy, or auth gateway) strips client-supplied lane headers and re-injects the authorized value based on authenticated session, signed token, or platform identity. The router treats the edge-rewritten value as authoritative; raw inbound lane headers are rejected.
- **Signed preview tokens**: for shareable preview links, the query token MUST bind {lane, app, route or prefix, target commit / build, tenant or audience, allowed host(s), expiry, key id, nonce} with HMAC or asymmetric signature, and be replay-bounded (server-side nonce store or jti deny-list within the expiry window). Short expiry (minutes). Because query tokens leak into web-server logs, browser history, `Referer`, and CDN cache keys, **the safe pattern is single-use exchange, not long-lived URL auth**: the first request validates the token, sets a short-lived `HttpOnly; Secure; SameSite=Lax` cookie or signed session for the lane, then redirects to a clean URL without the token. The cookie itself is scoped tightly: **host-only** (no `Domain=` attribute, so it never widens to `*.example.com`), `Path=/` for the lane's path scope only, and the session payload itself binds the allowed host(s). `SameSite=Lax` is the right choice here because cross-site top-level navigations from chat / email / external links are exactly the preview-link use case; `SameSite=Strict` would drop the session on the initial cross-site navigation. The token-exchange landing page is the only entry that needs cross-site cookie acceptance; deeper navigation within the preview is same-site. Subsequent requests use the cookie/session; the original token is consumed and cannot be replayed. Server-side: the router MUST verify the session's lane is permitted for the inbound canonical host and reject mismatch (a preview session presented on a production-only host fails closed) so a broad-cookie or replayed-session attempt cannot serve preview/canary artifacts on the production surface. Strip the token from the URL before logging, set `Referrer-Policy: no-referrer` on the preview shell so outbound links cannot leak the token, redact tokens from access logs and traces.
- **Host-based lane selection** uses a canonical host value the edge asserts after enforcing a host allowlist; raw `Host` / `X-Forwarded-Host` headers and substring matching on host are findings.
- Inside the trust boundary, the router consults inputs in a fixed priority and records which one decided the lane. **Authenticated session takes precedence over edge defaults**: a valid preview-lane session (set by single-use token exchange) wins over a canonical-host or edge-injected default; otherwise a user holding a preview session on a shared production host would be silently served production. Effective order: signed session/cookie (authoritative once established) > canonical-host (only when the host is dedicated to one lane) > edge-injected header (only when no session is set) > signed query (one-shot, exchanged immediately).

### Prefix Resolution And Pre-Check Semantics

- **Per-lane prefix resolution**: avoid bucket prefix LIST as the control plane — it does not scale across many router instances and rate-limits under traffic. Instead, the deploy step publishes a small active-lanes manifest (`active-lanes.json` or equivalent), the router fetches it with conditional GET / ETag and stale-while-revalidate, jittered refresh interval, single-flight on miss, and a bounded stale-fallback policy when the manifest is unreachable. A "list all prefixes every 5-30 s" loop is acceptable only for tiny portfolios; document the cutover threshold.
- **`active-lanes.json` is the highest-risk pointer**: a wrong value here serves wrong lane/commit globally. Treat it with the same rigor as `routes.json` — signed by the deploy identity (HMAC or asymmetric), integrity verified on each fetch, write access restricted to the deploy identity, read access restricted to the router identity (not publicly readable). On signature failure or read failure, the router fails closed (uses last known-good with a bounded max-staleness, then 503) rather than reverting to bucket LIST. **Replay protection is stateful, not timestamp-only**: the router stores the highest generation id seen per (app, lane) and rejects any signed manifest with a generation ≤ that high-water mark. A timestamp inside the payload without router-side state lets an attacker replay an older valid manifest. The high-water store is durable across router restarts (shared cache / consensus store) so a fresh router instance does not accept stale-but-valid manifests.
- **Cache miss policy**: canary, stress, shadow, tenant-isolated, and preview lanes fail closed (return 404 / 503) on cache miss. Fallback eligibility is determined by the route's lane-isolation policy plus downstream-capability policy, not by HTTP verb — almost all static HTML routes are GET but the HTML they boot can mutate state, so "read-only route" is not a safe gate. Only routes explicitly tagged as fallback-safe (no tenant binding, no downstream API audience binding, no preview/canary semantics) may fall back to the standard baseline.
- **Pre-check before serve**: HEAD against the resolved object key tells you whether the artifact exists *only* when you can distinguish "missing" from "denied" / "service error" / "throttled". S3 `HeadObject` returns generic errors and is permission-dependent: a 403 can mean "object missing without ListBucket" or "access denied"; a 503 can mean throttle. The router MUST classify HEAD result before deciding fallback: 200 → serve; explicit not-found (404 with ListBucket permission) → consider fallback per lane-isolation policy; anything else (5xx, 403 with ambiguous semantics, network error) → surface as service error, NEVER silently fall back to standard (silent fallback turns IAM / KMS / config errors into cross-lane data leaks).
- **Path normalization**: a catch-all router plus object-key suffix mapping needs explicit rules for URL decoding, `%2f` handling, dot-segment removal, duplicate-slash collapse, case sensitivity, query stripping, and an allowlist of accepted route keys. Without normalization, a route table bug can become arbitrary object-key fetch within the lane prefix.
- **Route-table suffix rules**: even with a signed `routes.json`, the suffix values must be relative (no absolute object keys), pass a strict character allowlist (no `..`, no leading `/`, no `%2e%2e`, no double-decoded traversal), and confine the final resolved key to the active lane prefix. Validate the route value AFTER URL decode AND any application-level decode pass; do not trust the signed payload's structure alone. A route mapping to another lane's prefix or to an absolute key is a router-level bug, not a contract decision the route table can authorize.

### Routing Table And Atomic Rollback

- **Routing table as versioned artifact**: the router reads `routes.json` (or equivalent) from the bucket; the table maps URL paths to object-key suffixes. The table is a deployment artifact, signed/versioned with the app, never hand-edited.
- **Atomic flip is partial atomicity, not full**: object-storage versioning + manifest write is atomic only for the one manifest object; router cache, CDN cache, browser cache, service worker cache, and HTML-to-JS-chunk version compatibility are not. To approach end-to-end atomicity: (1) every deployment uses immutable content-addressed prefixes; (2) the router pins one manifest version per request (read once at request entry, use throughout) so a mid-request flip cannot mix old HTML with new chunks; (3) conditional writes / generation IDs / pre-conditions on the manifest write prevent concurrent deploy races; (4) CDN TTL on the manifest is short (seconds), TTL on immutable content prefixes is long (hours-days, with versioning); (5) document the partial-atomicity boundary so operators know what a "rollback" actually rolls back.
- **Cache key includes lane (and many CDNs ignore raw `Vary`)**: CDN cache key MUST include the resolved lane signal and any auth-derived identity that influences the served artifact. Many CDN cache policies ignore arbitrary `Vary` headers unless the CDN's own configuration explicitly lists the header as a cache-key dimension — relying on `Vary` alone is insufficient. Configure the CDN cache key explicitly through the provider's mechanism (CloudFront cache policy, Cloudflare cache rules, fastly VCL, etc.) to include the lane dimension. Protected and tenant-specific HTML should be served with `Cache-Control: private, no-store` (or `private, max-age=0, must-revalidate`) so neither shared CDN nor browser back/forward cache can leak it cross-user. Public baseline HTML can be cached normally but the cache key still includes the resolved lane to avoid cross-lane leakage at the edge.
- **Signed-URL redirect policy**: the router SHOULD proxy bytes from object storage rather than 302-redirect to a signed object-storage URL. Redirects leak bucket keys / lane prefixes into client logs and `Referer`, weaken response-header control (CSP, X-Frame-Options, cache headers cannot be set on a signed-URL hop), can outlive the user's lane assignment or a rollback, and get cached independently by browsers and CDNs. If a redirect is unavoidable (very large file), the signed URL must be short-lived (minutes), single-use where the storage supports it, scoped to the exact key, and marked non-cacheable; protected lanes never redirect.

### Lane Binding Extends Beyond Static Artifacts

A "lane-aware deployment" that only routes static artifacts is **incomplete and dangerous** — a preview / canary HTML shell still talks to API endpoints, reads runtime config, sets cookies, and uses auth tokens. Without lane binding on the downstream calls, the preview shell mutates production data while looking like preview. Architecture extends lane binding all the way down:

- The HTML shell receives a per-request runtime-config injection (or fetches a per-lane runtime-config endpoint) so it knows the lane it was served from. The shell does not infer the lane from URL or guess.
- Outbound API calls from the shell may carry a lane hint, but the API gateway / service mesh does NOT trust a client-supplied lane signal. The gateway derives the authoritative lane from the authenticated session / signed token / canonical host (the same trust model as the static router) and rejects any request whose client-claimed lane does not match the derived value. A browser-set header / query param alone is attacker-controlled; treating it as routing input is a cross-lane routing hole.
- The API gateway / service mesh enforces the same lane policy on the downstream calls: a request whose authenticated lane is preview cannot land on production API instances, and vice versa.
- Auth tokens issued for a preview / canary lane are audience-scoped to that lane; production tokens are not accepted by the preview-lane downstream, and vice versa.
- Cookies set by the preview shell are scoped (`Path`, `Domain`, `SameSite`) so they cannot bleed into production app loads in the same browser.
- Cross-lane writes are blocked at the data layer too: tenant id + lane signal both validated before a write commits, so a misconfigured shell cannot mutate the wrong tenant.

### Service Worker Scope And Cache Isolation

Service Workers can poison lanes across deploys if not constrained, because they intercept all requests within their scope and survive page reloads:

- **No Service Worker for protected lanes** unless each lane has its own origin (e.g. a per-lane subdomain) — same-origin lanes share a SW registry and a preview lane's SW can intercept production traffic in the same browser (and vice versa).
- **Scope ceiling**: by default a SW's scope is its script directory, but the response header `Service-Worker-Allowed` CAN widen scope within the same origin beyond the script's path. For shared-origin lane deployments, the SW-serving response MUST NOT emit a wider-than-script-path `Service-Worker-Allowed`, and the registration code MUST NOT request a wider `scope` option. A SW served from `/sw.js` (no widening header) controls `/` already; a widening header would let a sub-path SW control `/` too. Enforce by inspecting the response header at delivery time, not only by where the script lives.
- **Cache name includes lane + manifest version** so a SW for production cannot serve cached production HTML to a preview lane (or vice versa).
- **On lane transition, unregister + clear caches**: when the user moves from preview back to production (or between tenants), the previous lane's SW is unregistered and its caches cleared explicitly. Stale SW survival is a top source of "rolled back but still seeing old version" incidents.
- **Protected HTML is not SW-cached**: the SW's fetch handler explicitly excludes protected-lane HTML paths from offline caching; only public baseline assets are cacheable.

### Observability And Error Contract

- Every request records the resolved `(lane, prefix, path, manifest_version)` plus a request id and structured log fields. A 5xx-class error in the router surfaces the resolved tuple to the operator (in the logged record, not in the user-facing body — see XSS / info-leak rules). Generic error strings like "environment incorrect" without the resolved tuple make on-call triage impossible.
- **Logs are a credential sink unless redacted**: the logging pipeline strips signed preview tokens, signed object-storage URLs, auth-derived identity, and sensitive tenant/lane labels before persistence. Field-level redaction at the logger, not in ad-hoc per-call code. Combined with the single-use-exchange rule for query tokens, this prevents long-term log exposure of preview credentials.

### Security Headers

- **Content-Security-Policy**: set deliberately for HTML served by the router; do not default to permissive. CSP rules live in middleware, but middleware must be route-aware (or declaratively configured per route family) when different routes need different CSPs. When the HTML shell needs per-request runtime-config injection (lane id, tenant, feature flags, auth audience), do NOT relax CSP with `unsafe-inline` — generate a per-response nonce and serve the inlined config as `<script nonce="...">` with CSP `script-src 'self' 'nonce-...'`, or fetch the config from a same-origin lane-aware endpoint immediately on shell load. `unsafe-inline` defeats the entire CSP injection-defense surface and is a finding.
- **Clickjacking**: use `Content-Security-Policy: frame-ancestors <origin-list>` for origin-specific embedding policy — the only mechanism modern browsers support for allowlist-style control. `frame-ancestors` does not fall back to `default-src`, is not valid in `<meta>` (must be sent as a response header), and applies to every ancestor in nested-frame chains. `X-Frame-Options` is limited to `DENY` / `SAMEORIGIN` (`ALLOW-FROM` is obsolete and ignored by current browsers); use it only as a legacy fallback for `DENY` / `SAMEORIGIN`.
- **Host pinning**: the router pins the trusted host set in config and rejects requests with unexpected `Host` values that survived the edge.
- **No request echo**: never echo request paths, header values, or query strings into the response body or error messages; they may carry attacker-controlled content.
- **Client-side XSS — untrusted-HTML and URL sinks**: React escapes text children by default, so the risk is the raw sinks. Any `dangerouslySetInnerHTML` (or direct `innerHTML`, inline-`<svg>`, or other raw-HTML sink) fed backend-supplied, user-supplied, or otherwise untrusted content MUST be sanitized at the sink — through the shared sanitizer (`shared/security/sanitizeHtml` per the sanitization-library policy in `react-architecture.md`) or DOMPurify / Trusted Types; the CSP above is defense-in-depth, not the primary control (OWASP Top 10 2021 A03:2021-Injection, which folds in Cross-Site Scripting). Likewise treat a `href` / `src` / `window.location` / router-redirect target taken from user input (`?returnTo=` / `?next=`, `<a href={userValue}>`) as untrusted, and scope the allowlist to the sink: a link **`href`** may allow `http`/`https`/`mailto` plus same-origin relative paths; a resource **`src`** splits by class — an image/media `src` allows `http`/`https` from trusted origins (not `mailto`), but an **executable or embed `src`** (`<script>`, `<iframe>`/`<object>`/`<embed>`, active-SVG context) is never constructed from a user-supplied value at all — even a same-origin path can be attacker-chosen — use a fixed static asset path or a closed per-sink allowlist, enforced with a per-sink CSP (`script-src` / `frame-src`, and `object-src 'none'` unless a closed allowlist is truly required), SRI for any remote script, and `sandbox` on untrusted iframes; a **redirect / `window.location` / router navigation** target is strictest — allow only same-origin relative paths or an explicitly allowlisted origin set, never an arbitrary user-supplied absolute URL (that is the open-redirect). Reject `javascript:` / `data:` and other active schemes at every sink.

### Storage Consistency vs Cache Propagation

- Modern S3 and GCS are strongly consistent for read-after-write and list-after-write of objects; older provider docs and other providers may differ — record the chosen provider's actual guarantees in architecture. The dominant propagation risk is not storage consistency but CDN cache, browser cache, and service-worker cache; deployment design should target those layers.

### Anti-Pattern Guardrails (Recurring In Prototype-Grown Routers)

- Debug `console.log` statements in the request hot path. Replace with structured logging at info/warn/error levels and a sampling policy for high-volume routes.
- Mixed environment-detection sources (host substring check vs `process.env` flag) that can disagree. Pick one canonical signal and derive everything from it.
- Catch-all `try { ... } catch { ctx.body = 'error' }` that swallows the original error class. Log the cause with the resolved tuple; return a stable error code.
- Empty controller / service / model files committed as scaffold. Either implement or remove them; the linter should flag.

## Cross-Stack Contract (Front-End Side Of The Back-End Envelope)

The front-end API client is one half of the front-end-back-end contract. The other half is owned by the architecture-layer back-end skills (`python-service-architecture/references/api-contract-and-schema.md` and `go-microservice-architecture/references/protobuf-contract-architecture.md`); these rules apply to the front-end consumer side and must stay symmetric with the producer side.

- **Response envelope consumption**: when the portfolio uses HTTP-200-always + JSON envelope (`{code, message, data}` with optional `{success}`), the front-end client classifies `code === success-code` as domain success, any other code as a typed domain error keyed by `code`, and HTTP-level non-2xx as a transport error. Domain error → user-readable mapping happens in the API client or in the narrowest shared error helper, not scattered in every page. When the portfolio uses HTTP-status-as-semantic instead, the client maps status families to the same internal classification. Mixing both styles across apps in the same portfolio is a portfolio-level finding.
- **Trace propagation surface**: every outbound request attaches `X-Request-ID` (client-generated UUID) and propagates `X-Trace-ID` when the runtime carries one. Every response surfaces the trace id back (header or envelope field). The client exposes the trace id to user-facing error UI so support flows can map a screenshot to a back-end log. Skipping client-side trace id injection breaks end-to-end correlation regardless of how good the back-end tracing is.
- **Auth header contract**: front end attaches the agreed auth header (`x-token` / `Authorization` / equivalent) and the agreed app identity header (`x-app-id` / equivalent). Header names, value format, and expiry semantics are portfolio contracts; the front end does not invent its own. For refresh-token flow when the portfolio supports it: a 401 response with a refresh-eligible signal triggers one silent refresh + retry; without that signal the client clears auth and routes to login.
- **Timeout layering**: outer caller budget is always longer than inner callee budget so an inner failure can return a structured error before the outer caller gives up. For a normal request path that is `browser/client → gateway → downstream RPC`, the relationship is `client timeout > gateway timeout > downstream RPC timeout` (typical: client ~30 s, gateway ~20 s, downstream RPC ~10 s, tuned per endpoint risk). If the client times out before the gateway can return, the user sees a network error when the back end could have returned a typed code with the trace id — that loses both the error class and the trace. Long-running operations (export, batch, large-file upload) use an explicit per-request override on every layer of the chain; SSE/WebSocket use a heartbeat rather than a single timeout. A single global 10 s timeout applied to every operation is a finding for export-heavy or upload-heavy apps.
- **Object-storage client-signed upload**: large-file upload goes through the platform's signed-upload path — the front end calls a back-end token endpoint (e.g., `/kms/get-tos-token` or equivalent) to receive an STS credential, then writes directly to object storage with the client-side SDK. The auth header / main API channel never carries the file body. Failure modes (token expiry mid-upload, partial multi-part failure, network drop, deduplicated retry) are part of the client wrapper, not the calling page.
- **Network vs business error classification**: AbortError / timeout / `navigator.onLine === false` map to "network error" with a retry affordance; envelope errors with a known code map to typed domain errors; unknown envelope shapes map to "unknown error" and surface the trace id. The client does not silently swallow any of these.

## Multi-App CI/CD And Quality Gates

For portfolios with multiple React apps sharing a back-end:

- PR gate must run remotely (GitLab CI / GitHub Actions / equivalent), not only as a local pre-commit hook. Pre-commit catches obvious lint/format problems; PR-level gates catch what locally was skipped, what dirty branches drag in, and what the merge introduces.
- Required PR gate stages, in this order: install (frozen lockfile) → type check (`tsc --noEmit`) → lint → unit/component tests → build. Skipping any of these because "the local hook ran" is a recurring source of broken main branches.
- Husky + lint-staged + `verify-commit` are the local layer; they enforce style and message format. They are not a substitute for the PR gate — local hooks vanish under `--no-verify`, and correctness lint rules downgraded to `warn` severity gate nothing anywhere; rules that matter are `error` in the remote gate.
- Lane / environment separation in CI (online vs offline lanes, canary vs production deploy targets) belongs at the deploy stage, not at the build stage. Build artifacts should be lane-independent where possible; lane choice is a deploy-time variable.
- A portfolio without remote PR gates is a deliberate trade-off (fast iteration, small team, single owner) or an oversight; document which. Adding PR gates retroactively to ten apps is expensive — start one app at a time with the lightest gate (type check + lint + build) and expand.

## Test Coverage Floor

A portfolio with **zero unit tests, zero component tests, and zero E2E** across every app is a structural finding, not an app-level oversight. The minimum bar that catches the most common regressions cheaply:

- One unit-test framework chosen at the portfolio level (Vitest, Jest, or Bun test); even a small initial suite gates the most-imported utilities (env-aware config, API client, error mapping).
- One component-test runner (`@testing-library/react` + the unit-test framework) for the per-app top-five risky components: forms with validation, the API-error fallback, the auth/permission gate, the long-running task UI, and the error boundary.
- One E2E framework (Playwright or Cypress) for one golden path per app: login → main screen → primary action → logout. Adding more flows is cheap once the framework is wired; the wiring is the expensive step.
- A coverage floor (e.g., 30% on shared utilities, 50% on API client, golden-path E2E green) gated in PR catches regressions before they hit users; aiming for high coverage on day one is not the goal.

## Cross-App Quality Hygiene

- Dead dependencies (declared in package.json with zero imports) are a recurring finding when multiple authors edit shared starter templates. Lint or a per-CI step (e.g., `depcheck`) catches them.
- Per-app `@umijs/max` / `next` / `vite` major-version skew (`4.0.x` to `4.4.x` across apps in the same portfolio) is a finding; cap the skew and run a periodic bump pass on the lowest-pinned app.
- Generated outputs (OneAPI clients, Hertz/Kitex stubs, OpenAPI clients) check into the repo and run formatter-skip rules; CI should fail when generated output is stale relative to the IDL/schema source.
- Optional deterministic React health scan: `react-doctor` (npm; by the react-scan/Million authors; young 0.x line — verified real and maintained 2026-08) scans correctness/performance/security/accessibility and outputs a 0–100 score; `--scope changed` restricts findings to files changed vs the base branch, which makes a cheap "score must not regress" PR ratchet. Supplement to — not replacement for — the ecosystem ESLint/typed-lint executors in `testing-strategy/references/fitness-functions.md` §4.1.3; pin the version in CI rather than `@latest`, and never wire any scanner mode that fetches and obeys remote playbook prompts at run time (remote-instruction execution is an untrusted-content hole, per `llm-inference-integration` trust rules).
