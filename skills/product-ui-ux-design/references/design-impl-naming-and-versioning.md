# Design-Implementation Naming And Versioning

Load this reference when a task crosses the Figma↔code boundary and depends on **finding the matching pair** — e.g. "which code module implements this Figma frame?" or "is this V2 component the active one?". It defines how to detect naming drift between design and code, and how to detect in-flight version stacks that look stable but aren't.

## Triggers

- A task asks "find the implementation of <Figma surface>" and the obvious `grep` returns nothing.
- A code tree contains both `Foo` and `FooV2` (or `Foo` and `Foo.v2.tsx`, etc.) and you must decide which is active.
- A Figma frame name carries a date stamp / version suffix / "use this one" parenthetical.
- A design-system refresh ships and the implementer can't tell which code locations still reference the old version.

## Rules

- **Name a glossary, do not improvise the translation**: when the team uses one set of terms in Figma (often in the working language, e.g. Chinese: review/scan/exam/etc.) and a different set in code (often English equivalents, sometimes translated freely as `Correct` / `Process` / `Inspect`), maintain an explicit bidirectional glossary in the private provenance archive. Future agents that try to grep without the glossary will silently miss matches.
- **Glossary is part of onboarding**, not a per-task artifact: a new contributor or agent learning the project must encounter the glossary as part of the source-classification step. Hidden glossaries fail in proportion to how busy the project is.
- **In-flight versioning is a smell, not a feature**: a code module named `FooV2` that coexists with the unsuffixed `Foo`, a Figma frame stamp such as a current-marker suffix / version-N suffix / date-stamp suffix / designer-added disambiguation parenthetical, and a folder name like `module.new` are all evidence that the team is mid-migration. None of them is wrong, but a *long-lived* coexistence is anti-pattern: it forces every reader to do extra work to find the active version.
- **The active version must be discoverable from the runtime entry**: do not rely on intuition. To decide which of `Foo` / `FooV2` is active, follow the route table / router config / app entry import — whichever the runtime actually mounts. The unmounted sibling is dead weight even if it has more recent commits.
- **Old versions should be retired on a date, not on vibes**: when introducing `FooV2`, write down the date or release that retires `Foo`. Same in Figma: when promoting `_ver1`, tag the old frame as deprecated rather than leaving siblings competing.
- **Date stamps in design file names do not propagate to code**: never name a code module `Foo_0904.tsx` because the corresponding Figma page carries a date stamp. Translate the design version stamp into a clean code name plus a top-of-file comment that records the design-source revision.
- **Verify business-axis frame labels by structural diff before treating the label as a product axis**: when paired figma frames carry business-axis vocabulary in the form "X / non-X" (tenant tier / customer segment / plan tier / region / vertical / industry / org type), structurally diff the two frames before code, tests, backend enums, or analytics dimensions branch on the named axis. **Diff unit** (specify it so two reviewers reach the same verdict): node path + node id + component/variant props + text content + bounds + layer visibility + interactive/prototype links. A changed component INSTANCE with changed variant props or overridden internal children counts as multiple deltas, not a single-element presence delta. **Procedure**: read both frames at matching depth, enumerate every node at the diff unit, list every delta. **If the only delta is presence/absence of a single permission-gated or state-driven element** (one quick-action cluster, one CTA button, one config row): UI evidence alone proves a permission/state-rendering delta — it does **NOT** alone prove the business axis is fake. The named axis may still be a real product/analytics/backend dimension that happens to surface through entitlement gating (plan tiers and regions often manifest exactly this way: one entitlement-controlled action toggles, with the axis itself living in product schema/PM intent). Confirm whether the gating permission is **derived from** an independent business axis (PM/PRD, product enum, backend schema, entitlement matrix) before deciding. Two outcomes: (i) gating is **not** derived from any business axis → label is misleading, the real axis is permission/state, raise rename to designer; (ii) gating **is** derived from the named axis → label is accurate, the axis is real even though UI manifests as one gated control, code/enums/analytics should keep the named axis (with the permission as its rendering mechanism). **Design-side judgment** (this skill's lane): record in the private glossary with source file, frame node ids, revision/version marker, observed delta summary, resolved axis (misleading / entitlement-derived from <axis>), and the entitlement-source evidence (PM/PRD doc, product enum file, etc.); the entry is **not a permanent cache** — re-diff when either frame changes revision or when a current-marker/version stamp appears. When outcome (i) holds, raise the label as a hygiene defect for designer rename (e.g. "with-<permission-name>" / "without-<permission-name>", "in-<state>" / "out-of-<state>"). **Routing for enforcement**: code gating → `web-react-dev` / `app-cross-platform-dev` / `miniapp-product-dev`; test coverage → `testing-strategy`; backend enum and analytics dimension changes → owning backend / data skill or human owner. This file's role ends at recording the judgment and routing. **If the diff returns a multi-element substantive delta** (multiple node-path differences, distinct INSTANCE trees with different variant props, different navigation patterns), the named axis is a **candidate** real axis — confirm against product / runtime / source-of-truth evidence (PM/PRD, route table, backend enum, data dictionary) before introducing axis-aware code, tests, enums, or analytics; multi-element delta alone is insufficient because it can still be state, permission combo, experiment, locale, or responsive variant.
- **Designer-side dating is acceptable but needs a current-discriminator**: Figma lacks a git-like branch/version-history mechanism, so designers commonly suffix the active page with a date stamp (e.g. a `_YYYY.MM/DD` or `_MMDD` suffix) and keep older dated pages in the same file as informal version history. This is acceptable, *provided* one page is unambiguously identifiable as the current source — any of: only one page in the file carries the latest date stamp and no other page carries a later one; a `(current)` / "use this one" / `(active)` annotation on the current page; or older dated pages renamed to start with `archive/`. Without such a discriminator, a file with two or more dated pages becomes a graveyard where the maintainer cannot tell which is the source of truth. **Conflict precedence when signals contradict**: when two discriminators point at different pages — for example, an older page is annotated `(current)` but a newer dated page exists without annotation, or a page carries both a `(current)` label and an `archive/` prefix — none of the automatic signals can be trusted. Treat the file as `freshness: candidate-needs-inspection`, hold rule extraction, and confirm with the file's designer/owner which page is the live source before proceeding. Do not pick a "winning" discriminator silently. The code-side rule above (date stamps do not propagate into module names) still holds independently.

## Decision Checklist

When you hit a Figma↔code naming mystery:

1. Open the private glossary (or ask the maintainer to create one if it doesn't exist). Translate the Figma label into all known code-side equivalents.
2. Re-grep using each equivalent. If still no match, the implementation may not exist yet (`not-observed` per maturity gate) — flag it as a gap, do not invent a mapping.
3. If you find `Foo` and `FooV2`: read the router/app-entry first, see which one mounts. Treat the other as legacy; do not edit the legacy version unless explicitly cleaning up.
4. If a Figma frame has version/date stamps: read the page's other frames to see if a "current/latest" sibling exists (a sibling stamped as the chosen version or as "use this one" in the team's working language). If yes, the un-stamped sibling is stale.
5. After resolving the mapping, add it to the glossary (one line: design label → code module → status). Future agents skip the search.
6. If two figma frames carry business-axis "X / non-X" labels (tier / segment / region / industry / org type): structurally diff at the diff-unit granularity (node path + id + component/variant props + text + bounds + visibility + prototype links). Single-element permission/state delta → run the entitlement-source check (PM/PRD, product enum, entitlement matrix). Gating not derived from any business axis → label is misleading, raise rename, route enforcement to implementation owner. Gating derived from the named axis → axis is real, route axis-aware code/enums/analytics changes to implementation owner. Multi-element substantive delta → candidate real axis; confirm against product / runtime / source-of-truth evidence before introducing axis-aware code, tests, enums, or analytics; do not treat the figma delta alone as authorization. Glossary entry records source file, node ids, revision, resolved axis, and entitlement evidence; re-diff when frame revisions change.

## Anti-Patterns

- **Coexistence beyond one release**: `Foo` and `FooV2` both in `pages/`, both reachable, neither documented as legacy. Every reader pays the cost.
- **Naming the active version by date stamp**: a Figma frame with a `MMDD` stamp and a code module copying that stamp into the filename. The stamp ages; the relationship becomes meaningless in a month.
- **Translating without a glossary**: agent A grep's "review", agent B grep's "Correct", agent C grep's "mark". All three miss the actual code, which uses `Exam`.
- **"use this one" siblings**: a frame the designer has stamped as the chosen version only signals that the wrong siblings have not been deleted yet. Do not assume the un-stamped frames are also current.
- **V1/V2 dual-track on both sides with no retire plan**: when one product surface has V1 + V2 routes in code (e.g. `pages/Foo/` plus `pages/FooV2/`), V1 + V2 components on the mobile side (e.g. legacy `pages/Foo/` directly + new `pages/FooV2/*/page.tsx` re-exporting from `features/foo/`), AND multiple dated pages in the design source (e.g. `<surface>-<date1>` + `<surface>-<date2>` + `<surface>-backup`), the team is in indefinite migration. Cost compounds: type duplication, route ambiguity, dead code in tests, contradictory designer guidance to engineers. The retire-date discipline is necessary but not sufficient: a recorded date alone, without a migration checklist, creates deletion pressure that ships its own incident class — saved deep links 404, exports/QA fixtures/analytics events/persisted user state reference V1 paths after V1 is deleted, rollback becomes destructive. The retire commitment must include: an explicit migration checklist (V1→V2 redirect / compatibility adapter / data backfill); telemetry that proves residual V1 usage has dropped below a stated threshold before deletion; a rollback path; and a sunset validation step that exercises old deep links, exports, and persisted state on the post-retire build before V1 code is removed. If a retire date is recorded but the migration plan is missing, treat that as a worse state than no retire date — pressure to delete with no safety story. **What stops vs what continues**: net-new V2 feature expansion (a new module, a new tab, a new endpoint shape, a new surface area) stops until both the date AND the migration plan exist. What does NOT stop, regardless of plan status: security fixes, rollback wiring, compatibility adapters, telemetry to measure residual V1 usage, bug fixes that reduce risk in V1 or V2, and the migration work itself. Refusing to ship a security fix because the retire plan is incomplete makes the situation worse, not better — the goal of the rule is to prevent scope expansion in a half-migrated state, not to freeze risk reduction.
- **Cross-stack naming style drift on the same field**: same semantic field rendered three different ways across web, mobile, and design — e.g. `is_xxx_checked` (web React) / `showXxxCheck` (mobile React) / a local-language label that translates to "toggle Xxx" (Figma). Each side individually defensible; together they break grep, glossary, and engineering↔design discussion. Pick one naming style per cross-cutting concept and treat it as part of the glossary, not a per-side stylistic choice. Typos that leak into the active path (e.g. `useShcool…` shipped instead of `useSchool…`) are part of this pattern, not a separate one — they reach the glossary the same way.
- **Frame-per-state ≠ frame-per-version**: when a Figma file shows the same module name repeated N times (e.g. `<module-name> ×6`), the default extraction reading is "N coexisting versions." That reading is wrong about half the time — on mobile design files especially, frame repetition is the designer's way of expressing state variants (default / hover / selected / Modal-overlay / single-mode / all-mode / different permission combos). Inspect each repeated frame's bounding box and any state-name suffix before treating the cluster as a version graveyard. The dual-track coexistence rule applies to genuine version siblings, not to state cardinality. (Genuine version siblings carry date stamps, version suffixes, or explicit deprecation markers; state variants do not.)
- **In-file deprecation marker vs in-file design-system tag library — read the content, not the name**: a section literally named with a local-language phrase that translates to "use this as canonical" (or "source of truth", "official version") looks like a version-marker section. Open it before drawing conclusions. If the content is a set of category/state/modality `Tag` instances (e.g. enum-style chips for type, source, status), the section is a **tag library**, not a version marker — the section name is misleading-but-internal. Real version markers tag a specific page or frame as canonical; tag libraries enumerate values used across the file. Misclassifying a tag library as a version marker corrupts the dual-track-coexistence audit.
- **Same-name V1/V2 coexistence breaks bare "X is deprecated" deprecation markers — discriminator is mandatory**: when the user-facing label "X" exists in both an old V1 route (often a sub-page embedded under a legacy section) and a new V2 route (often a standalone top-level route), a figma annotation that says only "X is deprecated, ignore" (in any language) is **ambiguous by construction**. A literal reader will conclude the entire X capability is deprecated and either (a) wrongly retire V2 or (b) skip both and miss V2's active feature surface. The deprecation marker MUST carry a version, path, or source-route discriminator — e.g. "the OLD `<legacy-section>/X` is deprecated; the new standalone `X` route is active" — or it is an audit failure on the design side. The audit path when you hit such an ambiguous marker: (1) resolve the user-facing label X through the private glossary so you have its known code-side synonyms across languages and renames; (2) inspect the route table / router config / app-entry imports — the authoritative signal for which of V1/V2 actually mounts at runtime is the route table, not grep counts; (3) only after the glossary + runtime-entry pass, use grep on each synonym as discovery support. Escalate to the file owner when the marker lacks a discriminator AND the runtime + glossary evidence cannot identify which side is being deprecated — not merely when grep returns more than one file (tests, stories, and dead files inflate that count; multilingual route names deflate it).
- **Implicit retire-without-delete (intra-file commented-out alternative components)**: same anti-pattern as V1/V2 dual-track, expressed at intra-file granularity. A page that renders `<Foo />` and carries `{/* <FooV1 /> */}` / `{/* <FooV2 /> */}` block-comments alongside is the same debt: the source reader cannot tell whether the commented siblings are "removed", "paused for rollback safety", or "in-flight before re-enable". The default resolution is **delete with rationale recorded in the removing commit message**, OR attach a dated `TODO(YYYY-MM-DD, owner):` comment naming the condition under which the sibling re-enables. **Re-enabling the commented sibling is NOT a routine cleanup response** — it requires the runtime owner to confirm the sibling is the actual intended active path, plus test coverage / feature-flag gating / a recorded rollback rationale; without that confirmation, re-enabling silently reintroduces duplicate UI, stale side effects, or stale permission behavior. Bare `{/* <X /> */}` blocks grow because every future reader has to decide whether to delete or restore, with no signal — the same propagation that the V1/V2 file-level rule prevents.
- **Business-axis frame label resolved without the entitlement-source check (symmetric anti-pattern, both directions)**: paired figma frames labeled with a business axis ("X / non-X" by tier / segment / region / industry / org type) whose only structural delta is one permission-gated or state-driven UI element, resolved without checking whether the gating permission is derived from an independent business axis. Two failure shapes, both expensive: (a) reader trusts the label, introduces code branches / test fixtures / backend enums / analytics dimensions for an axis the design never actually meant (false axis ships into the contract; removing it later is expensive — consumers, dashboards, persisted records); (b) reader treats single-delta UI as definitely misleading and strips a real product axis from code / enums / analytics because the UI happened to surface through one entitlement-gated control (plan tier, region, or industry that legitimately gates one action — re-introducing the axis later is equally expensive). The fix is **structural diff PLUS entitlement-source check** (PM/PRD, product enum, entitlement matrix) before trusting **or** rejecting the label; glossary entry stores source file + node ids + revision + resolved axis + entitlement evidence so the next reader can verify rather than re-decide.
- **Shared-API + diverged-frontend V2 rewrite is the lowest-risk dual-track shape (positive pattern)**: when V1 and V2 share the same backend API, same permission code, and same shared components — diverging only in the page shell (filters, layout, pagination, integration) — the V2 retire migration plan is correspondingly small *on the backend / permission / cross-service axis*. There is no DB migration, no permission re-grant, no cross-service contract change. But "small backend plan" is NOT "no checklist": even pure-frontend V2 rewrites routinely change route shape, query-param schemas, local-storage / persistence keys, default filter values, pagination cursor shape, analytics event names, and export entry-point URLs. The dual-track rule's compatibility checklist still applies to all of those — saved deep links, persisted user state, exports/QA fixtures, and analytics events must continue to work or have an explicit redirect/migration. The right framing: skip the DB/API/permission migration items **only after verifying those contracts are actually unchanged**; never skip the route / query / persistence / export / analytics compatibility items, and always run the post-retire sunset validation (open old deep links, check persisted state, check exports) before V1 file deletion. Size the migration to the divergence; do not skip the checklist when V2 forks the API, and do not bloat the checklist when V2 only forks the page shell — but the frontend-only checklist is still a checklist, not a single-line redirect.

## Routing

- Code-side enforcement of "no `FooV2` coexists with `Foo` after release N" → `web-react-dev` and `app-cross-platform-dev`.
- Test coverage of both `V1` and `V2` paths while coexistence persists → `testing-strategy`.
- Glossary maintenance and design-side cleanup of `_verN` / current-marker / date-stamp siblings → stays here (design discipline) plus owner update in the private archive.
