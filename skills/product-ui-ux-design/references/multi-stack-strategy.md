# Multi-Stack Strategy

Load this reference when a product spans **more than one client stack** — for example, a React workbench plus an H5 plus a native Android app plus an iOS app plus a mini-app plus a legacy Vue subproject. It defines how to decide which stack owns which surface, how to treat stack outliers, and how to keep design intent consistent when the stacks cannot share code.

## Triggers

- Auditing a product whose subprojects span multiple client stack families (React + Vue + Taro + RN + native iOS + native Android is one common shape; the stack names here are illustrative, not exhaustive).
- **Same-framework cross-end products** (e.g. React desktop + React H5 + React Native, all sharing one brand and one core toolchain): load this reference together with `multi-project-token-consistency.md`. The framework-shared theme module is governed by multi-project-token-consistency; per-end UI-kit choice, surface differences, and accessibility variation are governed here. Both apply, not one.
- A new feature must ship on web + H5 + native; deciding which surface implements which slice.
- A subproject uses a stack different from the rest of the product (e.g. one Vue island in a React organization).
- A design system was extracted from a Figma file targeting only one stack and the team is about to extend it to other stacks.

## Rules

- **Map the product's stack landscape before drawing rules**: list every subproject and tag it `web-desktop` / `web-h5` / `mobile-rn` / `mobile-native-android` / `mobile-native-ios` / `mini-app` / `legacy`. A product is "multi-stack" the moment two of these coexist on the same brand.
- **One stack = one UI-kit family**: within each stack, pick one UI-kit family (see multi-project-token-consistency). Mixing two UI-kit families inside the same end without a stated migration plan is anti-pattern. The specific families a team uses are a project-level decision and live in the project's design-system file or architecture doc, not here.
- **Feature-domain capability-library isolation may be acceptable when the design source requires capabilities beyond the stack's canonical UI-kit/design-system**: the one-UI-kit-family rule is the unification baseline, not an absolute. This exception applies **only** to feature-local capability add-ons — specialized notification / toast / alert / modal / overlay / editor / chart / scanner-bridge / canvas / annotation / media-player libraries layered alongside the canonical UI-kit. It never authorizes a second UI-kit family for canonical surface area: tokens, theme, layout primitives, forms, tables, navigation, and page shell remain under the unify-stack audit. Within that scope, isolation is design-driven only when **all** of the following hold: (a) the **active team-authored A1** design-system source (classified per `design-system-source-of-truth.md` — a file labeled "design system" may be a third-party mirror; mirrors don't count) contains zero components of the relevant capability class; (b) the feature-area design file contains explicit extended forms (multi-size variants, in-domain teaching/help patterns, multi-step modal flows, hardware-aware states, or other concrete capability extensions visible as separate frames) that the canonical library **cannot express without one-off local reimplementation or unacceptable UX loss** — verify against the canonical runtime UI-kit's component docs, not Figma alone; (c) the exception is recorded with all required fields below. Missing any of (a)/(b)/(c) → treat as accidental drift and apply the unify-stack rule. **Required exception-record fields** (in the project alias map or private provenance archive, optionally mirrored to the subproject README — pick the location appropriate for project confidentiality, but recording is mandatory, not optional). The field set is shaped by which branch fired: **A1-present branch** — capability class; exact package and feature-path boundary that is exempt (everything outside the boundary stays under unify-stack audit); owner + exception date; design-source node id and revision/version marker for both the A1 file and the feature file; recheck trigger (re-evaluate when the canonical design system adds the capability class, or when either source frame's revision/version stamp changes). **Green-field/provisional branch** (when no A1 Figma design system exists yet per `design-system-source-of-truth.md` provisional path) — capability class; exact package and feature-path boundary; owner + exception date; `A1 source: absent (provisional)`; canonical runtime UI-kit version + docs link verified to lack the capability; shared primitives audited (list what was checked); feature design file node id and revision; provisional status flag; recheck trigger fires when A1 lands or when the feature file's revision changes. In either branch, missing any required field for that branch's field set → the exception does not exist and the unify-stack rule applies.
- **Design system should split by stack, not by product feature**: a single Figma "design system" covering desktop + H5 + native usually under-serves at least one stack. Split desktop and mobile design-system files; for mini-app or native-platform-specific tokens, split further only if there is real divergence (HIG/Material guidance, system fonts, touch targets).
- **Outlier stacks need a documented retire/isolate/coexist plan**: if exactly one subproject runs an off-stack family inside an otherwise unified organization (a single Vue island in a React organization is one illustrative shape), decide explicitly: retire (set a date), isolate (declare it permanently independent and exclude from brand drift checks), or coexist (write down the shared layer). A silent outlier silently leaks brand inconsistency.
- **No-dominant-stack early phase**: if the portfolio has no dominant stack yet (every subproject picked its own framework + UI-kit, no consolidation pressure has been applied), the retire/isolate/coexist framing does not apply — there is nothing to be an outlier *of*. The prior decision is "which stack(s) does the organization commit to long-term?", which is a product/business call, not a design call. Route to `product-rd-workflow` for the stack-commitment decision. If the consuming organization has external strategy or ideation support installed, `product-rd-workflow` may use it through local skill discovery; otherwise escalate the stack-commitment question to the human owner or record it as `unresolved` in the active audit's notes, and do not apply the retire/isolate/coexist framing in this file until that prior decision is landed.
- **Native + WebView + H5 hybrid is a contract, not a coincidence**: when a product ships as a native shell wrapping an H5 module, the shell owns chrome/storage/safe-area/orientation/upload-bridge/back-gesture; the H5 owns content/state/business logic. Crossing the line — H5 controlling status bar, shell rendering business UI — is the cause of most "the iPhone version looks weird" bugs. Document the contract; do not rely on each engineer's intuition.
- **Mini-app and RN have stack-specific design constraints**: mini-app platform variants (`weapp` / `alipay` / `jd`) have platform-locked components; RN cannot use web-only animations. The design source must signal which surfaces are supported and which fall back; the implementation skill must reject "just use the web design" guidance for these stacks.

## Code Monorepo Subproject Classification

A frontend monorepo with multiple packages is its own mini-source-set. Classify each package by role, not by directory name, before applying rules:

| Class | Definition | Routing |
|---|---|---|
| **web** | Browser-targeted application (consumer web, admin console, ops dashboard, marketing site, H5) | `web-react-dev` (or the language-specific web skill) |
| **native** | Mobile / desktop / TV client (Flutter, native iOS, native Android, RN, Electron) | `app-cross-platform-dev` |
| **mini-app** | Host-platform mini-program client (WeChat, Alipay, Douyin, Baidu, Taro/uni-app mini-program target) | `miniapp-product-dev` |
| **pkg-shared** | Reusable library / SDK consumed by app packages (shared components, hooks, types, design tokens, business primitives) | Routes per platform: web-facing rules → `web-react-dev`, app-facing rules → `app-cross-platform-dev`, design-system rules → `product-ui-ux-design` |
| **infra** | Build / tooling / dev infrastructure (CI scripts, codegen, lint config, monorepo manager, deploy/release pipelines, server-side renderers, edge config) | Mostly routing-internal; concrete rules live in the relevant implementation skill's "release/build" section |
| **legacy** | Archived or deprecated package, kept for reference (pre-migration, retired surface, abandoned experiment) | Excluded as a positive baseline; provenance only |

Map every package before mining. A `pkg-shared` package treated as a `web` application produces wrong-owner skill content; an `infra` package treated as `pkg-shared` produces wrong-routing rules. The retire/isolate/coexist framing in this reference operates over these classes — outliers are identified by class mismatch, not by directory name.

## Decision Checklist

When starting a multi-stack task:

1. List every subproject and tag its stack family. Identify which are `current` and which are `legacy` / `outlier`.
2. For each stack, confirm the canonical UI-kit family is set. Outliers raise an explicit retire/isolate/coexist decision (record in private archive).
3. For each end-platform stack (desktop, mobile H5, mobile native, mini-app), confirm one design-system file owns its tokens (see design-system-source-of-truth).
4. For native-shell + H5 / RN + H5 / mini-app + H5 hybrids: locate the chrome/business-logic contract. If it is not written down, write it down before adding new features.
5. For any feature spanning multiple stacks: decide per-surface ownership (desktop = X, H5 = Y, native = Z, mini-app = W). Do not assume one design satisfies all surfaces.
6. If one feature area inside an otherwise unified stack uses a non-canonical UI-library family: branch on whether an active team-authored A1 Figma design-system exists for that stack (classify per `design-system-source-of-truth.md`). **A1 exists** → open the A1 file AND the feature-area design file; both criteria met (zero canonical abstraction class in A1 + extended forms in feature file the canonical runtime UI-kit cannot express without one-off reimplementation or unacceptable UX loss) AND the A1-present exception-record field set from rule 2 (capability class, package/feature-path boundary, owner+date, A1+feature node ids and revisions, recheck trigger) is recorded → design-driven exception. Any criterion fails → raise the unify decision per rule 2. **No A1 yet (green-field/provisional)** → use the Green-field fallback: evaluate against the canonical runtime UI-kit's component docs + existing shared primitives + provisional token taxonomy, and record the exception with the **green-field/provisional field set from rule 2** (capability class, package/feature-path boundary, owner+date, `A1 source: absent (provisional)`, runtime UI-kit version + docs link, shared-primitives audit list, feature design node id and revision, provisional status flag, recheck trigger fires when A1 lands or feature file revision changes). Never authorize a second UI-kit family for canonical surface area regardless of branch.

## Anti-Patterns

- **Single design system, multi-stack assumption**: one Figma file expected to drive desktop + H5 + native — accessibility, density, safe area, and gesture coverage will be wrong somewhere.
- **Silent outlier**: a Vue 2 / legacy subproject that nobody is retiring and nobody is brand-checking. It will drift further over time until the only "fix" is rebuild.
- **Web-only design feeding RN/native**: motion, layout, modals built for web don't translate. Animations break, modals look like web alerts, gestures feel wrong.
- **Mini-app treated as H5**: mini-app platform components (Tab, Picker, Image) have platform-specific behavior; ignoring this leaves the surface visually correct but UX-wrong on some platforms.
- **Undocumented native-H5 contract**: every native engineer and every H5 engineer has their own mental model of "who owns the status bar / orientation / safe area / back button". A single shipping cycle reveals dozens of edge bugs.
- **Mechanically applying the unify rule without opening the design source**: flagging a single-feature capability-library divergence as anti-pattern using only code-side grep evidence. Accidental drift and design-driven exception look identical at the code level — the design-system file and the feature-area design file are the only authorities that distinguish them. Forcing convergence on a design-driven exception regresses the feature; tolerating accidental drift leaks brand inconsistency. The judgment lives in design, not in code grep. Note: this exception covers feature-local capability add-ons only, never a second UI-kit family for canonical surface area (layout, forms, tables, navigation, theme, page shell).

## Routing

- Web-react-dev: enforces the canonical web UI-kit and tests the desktop / H5 surfaces.
- App-cross-platform-dev: enforces the native / RN design-system mapping and owns the native-H5 contract document.
- Miniapp-product-dev: enforces mini-app platform mapping, host-platform capability boundaries, and mini-app release evidence.
- Testing-strategy: verifies per-platform smoke for shared features (one platform passing ≠ all platforms passing).
- Product-rd-workflow: if a new feature appears that should span multiple stacks, raise the decision early instead of building web-only first and "porting" later. Optional external strategy or ideation support may supplement this through local skill discovery, but the portable ccl-owned route is `product-rd-workflow`.
