# Flutter Dev

## Architecture

- Start from the existing repo pattern. If no pattern exists, use feature-first structure with presentation/widgets, state/controller/view model, data/repository, API client, models, and platform adapters.
- Keep widgets declarative and thin. Heavy mapping, validation, side effects, and command handling belong outside `build`.
- Pick state management deliberately. Riverpod, Bloc, Provider/ChangeNotifier, ValueNotifier, or built-in state can all be valid; do not introduce a new framework when the repo already has a consistent one.
- Separate ephemeral widget state from app/domain state. Durable state needs a clear owner and lifecycle.
- Use explicit navigation and deep-link handling. Treat route params as typed contracts and verify back behavior.
- **Widget mental model**: `StatelessWidget` for pure render-from-props; `StatefulWidget` only when the widget itself owns ephemeral interaction state that does not belong in a state container. For dependency injection across the tree, prefer `InheritedWidget` (broadcast change) / `InheritedModel` (selective subtree rebuild by aspect) over global singletons. App / domain state lives in the chosen state container (Riverpod / Bloc / etc.), not in `StatefulWidget`.
- **Hooks and DI carve-outs**: `flutter_hooks` is a legitimate alternative composition style — adopt project-wide if the team chose it, not as a sprinkle. `get_it` / `GetIt` is acceptable as a service locator at app composition root, but treat it as a controlled trade-off — global mutable locators erode testability and hide dependency graphs; prefer constructor injection or Riverpod providers for new code. Both default to "not introduced if absent" per the existing state-management rule.
- **Riverpod 3 migration breaks several API shapes**: automatic retry of failing providers is on by default; provider failures rethrow as `ProviderException` (not the original error); `StateProvider` / `StateNotifierProvider` / `ChangeNotifierProvider` are LEGACY and moved to `package:riverpod/legacy.dart` (new code uses `NotifierProvider` / `AsyncNotifierProvider`); `AsyncValue` is now `sealed` (enables exhaustive `switch` pattern matching); `valueOrNull` renamed to `value`. Offline persistence and mutation support are experimental. Verify before upgrading existing Riverpod 2 projects.
- **App lifecycle observation**: `AppLifecycleListener` (`flutter/widgets`) is the newer, preferred API over `WidgetsBindingObserver` for observing app lifecycle state — callback-based, no class inheritance required, supports `onExitRequested` for desktop close-window negotiation. `AppLifecycleState.hidden` (added Flutter 3.13) is part of the standard state set across both APIs. `WidgetsBindingObserver` remains valid for existing code and for combined observation needs (metrics + accessibility + focus + lifecycle in one observer).

## Codegen And Toolchain

- **Codegen stack**: `freezed` (immutable data classes + unions/sealed classes) + `json_serializable` (typed JSON) + `build_runner` (build orchestrator) is the canonical pattern for typed models and serialization. Generated files (`*.g.dart`, `*.freezed.dart`) are checked into the repo or regenerated in CI; do not depend on developers running `build_runner` ad-hoc. When using Riverpod, `riverpod_generator` + `riverpod_annotation` is the canonical codegen path — only adopt if the project already uses Riverpod.
- **Flutter SDK version pinning**: pin the Flutter SDK version per repo via FVM (`.fvmrc` / `.fvm/`) or the equivalent toolchain manager; CI uses the same pinned version. An unpinned project drifts across developer machines; build-vs-runtime mismatch is a class of bugs unique to cross-platform SDKs.
- **Dart Macros are indefinitely paused (Dart team Jan 2025)** — do NOT bet on macros for production code generation. The Dart team paused implementation work to focus on improving `build_runner` and shipping **augmentations** (one feature prototyped as part of macros) as a standalone language feature. `build_runner` + `freezed` + `json_serializable` remains the canonical codegen path; `freezed 3.0` and successor codegen tools target the post-macros world.

## Platform Integration

- Keep platform channels, plugins, and native SDK calls behind adapters.
- Represent permission and capability failures in UI state, not only logs.
- For add-to-app, define ownership of the host app, Flutter module, build pipeline, route handoff, and lifecycle events.
- **Pigeon vs MethodChannel vs FFI** — pick by surface, not preference: **Pigeon** (codegen) for typed, evolving, multi-platform contracts where long-term type safety across Flutter / Android / iOS / future targets matters — prefer Pigeon when the contract will change over time or carries structured types. **MethodChannel** (manual) for small, stable, one-off capabilities, dynamic payloads, or bridge debugging where the codegen overhead is not worth it. **FFI** for C-ABI native libraries and measured perf paths (image / crypto / parsing) — NOT for routine Kotlin/Swift business APIs (FFI does not target Kotlin/Swift directly and does not cover Web).

## Cross-Platform Target Matrix

- **Cross-platform is not "one UI fits everywhere"**: each target (mobile iOS / mobile Android / web / desktop macOS / desktop Windows / desktop Linux) has its own input model (touch / pointer + keyboard / mouse + keyboard), window model, navigation conventions, accessibility APIs, plugin support matrix, and performance profile. Maintain a platform capability matrix per project: which targets are in scope, which plugins are verified on each, which screens have target-specific layout overrides, which capabilities are stubbed / disabled on each.
- **Material / Cupertino / Adaptive**: Material for explicit Material-system apps; Cupertino for explicit iOS-native look; **adaptive widgets** (e.g. `Switch.adaptive`, `Slider.adaptive`, `CircularProgressIndicator.adaptive`) when the surface should follow platform conventions automatically. Mixing without a portfolio rule produces inconsistent feel; record the choice in the project's design contract.
- **Flutter Web renderers**: per current Flutter docs, only two renderers exist: **CanvasKit** (default for normal builds — Skia compiled to WebAssembly, ~1.5MB) and **skwasm** (selected when building with `--wasm` if the browser supports WasmGC, falls back to CanvasKit otherwise — more compact ~1.1MB, multi-threaded rendering). The **HTML renderer is no longer documented in current Flutter docs** — projects pinned to old SDK versions using HTML renderer need an explicit migration plan to CanvasKit (default) or `--wasm` / skwasm before SDK upgrade. Web targets also need SEO / document-heavy considerations Flutter does not natively address — for content-dominant pages, a static / SSR-rendered web surface alongside the Flutter app is usually the right architecture.
- **Web interop migration**: `dart:js_interop` (released with Dart 3.3, Feb 2024) replaces `package:js` / `dart:js`; `package:web` replaces `dart:html` and the other browser libraries. Legacy JS interop is deprecated as of Dart 3.7 (Feb 2025). New Web code uses `dart:js_interop` + `package:web`; existing Web code on `dart:html` has migration debt — required for Wasm compilation (Wasm only works with the new interop). Migration guide is at `dart.dev/interop/js-interop/package-web`.
- **Federated plugin architecture** for multi-platform plugins: split into platform-interface package (`<plugin>_platform_interface`) + per-platform implementation packages (`<plugin>_android`, `<plugin>_ios`, `<plugin>_web`, etc.) + app-facing package (`<plugin>`). Per Flutter docs, federated is **optional** — recommended / expected for shared multi-platform plugins where independent platform implementations or endorsed third-party additions matter, optional for single-package plugins. The structure makes per-platform contribution and version skew explicit; adopt when those concerns are real, not as ceremony.
- **Multi-package Flutter repo**: when a Flutter project grows into multiple packages (app + shared libs + plugins), Melos / Dart workspaces is a common monorepo orchestration choice. Deep monorepo governance routes to the team's repo / tooling owner; Flutter-side responsibility is keeping per-package `pubspec.yaml` resolvable and CI building each package.

## Theme And Brand Color

Shared design discipline lives in `product-ui-ux-design/references/multi-project-token-consistency.md`; consult it before applying the Flutter-specific implementation rules below.

- **`MaterialApp(theme: ThemeData(...))` must reference a brand theme, not the default**: an app whose entry is `MaterialApp(theme: ThemeData())` / `MaterialApp(theme: ThemeData.light())` / `MaterialApp()` with no `theme` arg renders the Material default palette. This is the Flutter equivalent of the empty framework-wrapper anti-pattern in `multi-project-token-consistency.md`. Audit signal: `MaterialApp.theme` must reach a brand `ThemeData` built from the project's design tokens (not the framework default); `CupertinoApp.theme` must reach a brand `CupertinoThemeData` (NOT `ThemeData`); a `MaterialApp` wrapping `CupertinoApp`-style screens still needs `MaterialApp.theme` populated since Material widgets read from it.
- **Flutter scaffold colors left as dead-code declarations**: `flutter create` ships sample colors (`Colors.blue`, `Colors.deepPurple` as the seed in `MaterialApp.theme: ThemeData(colorScheme: ColorScheme.fromSeed(seedColor: Colors.deepPurple))`). When the team replaces the seed with a brand value but leaves the original scaffold-color constants declared elsewhere in `theme.dart` / `colors.dart`, those become onboarding noise — same shape as the Android Compose `Purple40/Pink40` dead-code anti-pattern in `android-dev.md`. Delete unreferenced scaffold colors once the brand value is wired.
- **Vendor-default literal leak in custom theme** (cross-stack rule): `Color(0xFFD93025)` / `Color(0xFF6750A4)` / `Colors.deepPurple` / Material 3 default tonal palette values typed into the brand layer fall under the shared anti-pattern in `multi-project-token-consistency.md`. Detection: grep `theme.dart` / `colors.dart` / `ThemeData` builder for known Material default literals. A hit resolves to one of three classes per the shared rule: **leak** (replace with brand token), **deliberate documented reuse** (keep with rationale comment), or **legitimate convergence** (brand role independently resolves to the same hex — keep but reference the brand token, not the literal).
- **Algorithmic secondary / tertiary derived without designer sign-off** — applies to **custom** derivation patterns; standards-based Material You has a carve-out: Flutter's `ColorScheme.fromSeed(seedColor: brandColor)` algorithmically derives the entire tonal palette from one seed. This IS the Material You design intent. Acceptable as the design policy when the project records (a) the Material You variant in use (M3 default vs `DynamicSchemeVariant.tonalSpot` / `vibrant` / `expressive` / etc.), (b) accessibility/contrast checks against the brand seed, (c) visual QA on canonical screens at the seed value. Designer sign-off applies to the policy adoption + the seed/canonical-screen pass, NOT to every runtime-generated secondary/tertiary value. Silent reliance on `fromSeed` without ANY of (a)/(b)/(c) is the failure mode. Custom HSV-shift / alpha-tint / complementary derivations have stricter sign-off requirements per the shared anti-pattern in `multi-project-token-consistency.md`.
- **`ThemeExtension<T>` for brand-specific additions beyond `ThemeData`'s fixed fields**: subclass `ThemeExtension<T>`, define brand-specific fields (extra colors, spacing tokens, custom typography roles), implement `copyWith` + `lerp` for smooth transitions; register via `ThemeData(extensions: [<MyExtension>(...)])`; read via `Theme.of(context).extension<MyExtension>()`. This is the official path for "Material doesn't cover this brand-specific token". Do not create a parallel `BrandTheme` `InheritedWidget` SOLELY to host Material / brand tokens that `ThemeExtension` would carry — that path breaks `Theme.of(context).extension` lookups and animation interpolation. A separate app-domain `InheritedWidget` for non-theme runtime config (feature flags, user role, environment) is still valid.
- **Material 3 Expressive (Google I/O 2025): watch, do not adopt as Flutter default yet**. Material 3 Expressive is currently shipping for Wear OS via dedicated Jetpack libraries (Wear Compose Material 3 + Wear ProtoLayout Material 3) and Android handheld surfaces; Flutter Material widget set has not yet adopted Expressive as a production-ready default. Track Flutter docs `docs.flutter.dev/ui/design/material` and Flutter release notes for adoption; until then, current `ColorScheme.fromSeed` + Material 3 remains the production guidance.

## Tests And Verification

- Unit test pure mapping, validators, state reducers/controllers, repository behavior, error translation, cache policy, and retry decisions.
- Widget test loading/empty/error/success states, gestures, forms, validation, route entry, and permission-denied UI.
- Use golden or screenshot tests when the repo already supports them or when the UI surface is visually risky.
- Integration test critical device flows, plugin paths, deep links, auth/session behavior, and offline/retry flows.
- Run analyzer/format/build for the changed target and inspect a rendered screen before delivery.
- **Mocking**: prefer `mocktail` for Flutter (null-safety friendly, no codegen / `build_runner` dependency, simpler stub API). `mockito` remains valid for projects already using it, but new code in the codegen + null-safety era leans `mocktail`.
- **Golden / screenshot testing** (`golden_toolkit` / `alchemist`): apply when the surface is visually high-risk (design-system primitives, financial / data-dense forms, complex layouts the design team reviews). Do NOT golden every screen — golden suites are maintenance debt, baselines drift across font / OS / renderer, and per-developer flakiness is real. Scope per-project to the screens whose visual regression cost is high.

## Errors And Diagnostics

- **Three-layer error capture for public / staged-rollout / high-risk shipping apps**: (1) `FlutterError.onError` catches errors thrown during widget build / framework callbacks; (2) `PlatformDispatcher.instance.onError` (or `runZonedGuarded` in older patterns) catches errors outside the Flutter framework — uncaught async, isolate errors, native bridge errors propagating up; (3) the `ErrorWidget.builder` controls what users see when build itself fails (default red error screen is for debug, never for production). Wire all three to the crash backend (per `mobile-quality-release.md` symbolication gate); missing any layer drops a real class of crashes from the dashboard. Internal / closed-test builds may downgrade by risk acceptance.
- **DevTools is non-optional for debugging non-trivial behavior**: per Flutter docs, the top-level views are Flutter Inspector (widget tree + layout boundaries) for rebuild / overflow / constraint debugging; Performance view (with Timeline Events tab inside) for jank / frame-rate investigation; CPU Profiler view for CPU-bound work analysis; Memory view (heap + leak detection) for image / cache / list memory issues; Network view for HTTP / WebSocket inspection; plus Debugger, Logging view, Debug console, App size tool. Reaching for `print` instead of DevTools is the recurring habit that masks the actual cause.
- **Hot reload vs hot restart**: `hot reload` re-runs `build` and preserves widget state — fast iteration on UI / business logic. `hot restart` resets the app state and re-runs `main()` — required after changing `main()`, top-level state, `const` constructors, `enum` / generic type signatures, or DI graph; reload silently keeping stale state from these classes is the recurring "but it worked locally" cause. When in doubt, hot restart.
- **DevTools extensions** (`package:devtools_extensions`): for products where repeated domain-debugging cost exceeds extension maintenance, ship a DevTools extension as a custom panel embedded in DevTools (iframe-based, Flutter web app). Extension consumes shared DevTools APIs (VM service connection, theming, shared widgets); user enables by adding the providing package as a `dev_dependency`. Recent integration with the Dart Tooling Daemon allows access to IDE-registered methods and a minimal file-system API. Not for every in-house framework — the threshold is "we keep instrumenting print-debugging for the same domain over and over"; if it's one-off debugging, scattered `print` + DevTools' built-in panels still win.

## Internationalization

- **`gen_l10n + intl` (official) is the default** for any Flutter app that might ship in more than one language. Configure via `l10n.yaml` + `.arb` files; `flutter gen-l10n` (or the build runner) emits typed `AppLocalizations` accessed via `BuildContext`. Hard-coded user-facing strings in `Text(...)` are migration debt the day a second language is added.
- Alternatives (`easy_localization`, `slang`) are acceptable if the project already uses them; do not introduce them in greenfield work without a specific reason to skip the official path. Plural / gender / select forms, locale-aware date / number formatting, RTL layout, and font fallback for non-Latin scripts are part of i18n acceptance — not a string-replace exercise.

## Performance

- Watch startup work, large rebuilds, image decoding, long lists, jank during animation/scroll, synchronous parsing, and app size.
- Move CPU-heavy parsing or transforms off the UI path when needed. On **native** targets, `compute()` (or `Isolate.run()`, Flutter 3.7+) runs the callback in a separate isolate so it does not block the UI isolate. On **Web**, `compute()` runs the callback on the current event loop — there is no isolate to offload to, so it does NOT prevent UI jank for CPU-bound work; Web CPU-bound work needs Web Workers via JS interop or algorithmic chunking, not `compute()`.
- **Repaint boundary discipline**: wrap subtrees that repaint frequently (animations, scrollable lists with their own animation, custom-painted overlays) in `RepaintBoundary` so their repaints don't invalidate the parent's raster. `CustomPainter` is the right primitive for one-off visuals that don't compose from existing widgets — pair with `shouldRepaint` returning `false` when inputs are unchanged. For long scrollable lists / grids, use `Sliver*` widgets (`SliverList`, `SliverGrid`, `CustomScrollView`) instead of nesting fixed-extent widgets in a `ListView` — Slivers participate in the scroll geometry directly, avoid forced relayouts, and support sticky / collapsing headers naturally.
- Prefer measured profiling for suspected performance issues; do not tune blindly.
- **Impeller renderer is default on iOS (since 3.10) and on Android API 29+ (since 3.27)**. Two separate verification surfaces: **iOS** — Flutter docs current state is Impeller-only on iOS, no Skia switch; verify first-frame and animation smoothness on supported iPhone floor. **Android** — Impeller is default on API 29+; the `--no-enable-impeller` debug flag still toggles to Skia for diagnosis. Verify on real low-end Android devices the project supports, watch for shader-compile-on-demand jank on rare surfaces, and confirm Skia fallback still ships acceptably for the targeted Android API floor before treating Impeller as the only path.

## Release Patterns

- **OTA / code push (Shorebird) is the production path for Flutter** when the team needs faster-than-app-store-review updates. Shorebird is in active production at scale (hundreds of millions of patches deployed in 2025 across Android / iOS / macOS / Windows / Linux per the vendor's year-in-review). **Platform constraint discipline**: Apple's App Review Guideline **2.5.2** (executable code) plus Apple Developer Program License Agreement **3.3.1(b)** (which Shorebird itself cites) constrain what can be patched without re-review — interpreter compliance, no deceptive primary-purpose change, and major / native-surface changes continue through normal store releases. Document the patch policy with legal/release-engineering before adopting, not after a patch is rejected. Android has fewer constraints but still subject to Play Store policy. OTA is niche-but-recommendable for products with: (a) high cost of waiting for review, (b) critical bug-fix windows, or (c) feature-flag governance the team will actually use; not a substitute for normal release discipline.
