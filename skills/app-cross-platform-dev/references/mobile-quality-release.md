# Mobile Quality And Release

## API Client Recipe

For mobile and cross-platform apps, centralize these mechanics in the shared API client or platform adapter:

| Concern | Required behavior | Test evidence |
| --- | --- | --- |
| Request metadata | Attach or preserve request id, trace id, operation name, app version/build, platform, auth context, and upload/long-running classification where available | Fast client tests assert metadata and redaction |
| Response parsing | Classify canonical envelope, empty body, invalid JSON, non-2xx envelope, backend error envelope, and malformed success separately | Fast API-client tests for each response shape |
| Cancellation and lifecycle | Distinguish user cancel, route dispose, app background, timeout, and network failure | Unit/widget tests plus device smoke for an interrupted flow when risky |
| Auth and permission | Convert expired auth, forbidden, feature-closed, and scope mismatch into route/session/permission state without losing recovery context | Widget or integration tests for session and permission states |
| Offline/weak network | Preserve pending intent only when safe; expose retry/final status and avoid duplicate irreversible actions | State-machine tests and one device smoke for recovery |
| Long work | Expose task id/status, polling/backoff, refresh or foreground recovery, terminal success/failure, and support identifier where needed | Client test plus installable-device smoke for one pending-to-final path |

## Test Layers

- Fast tests: pure logic, state transitions, mapping, validation, API client parsing, retry decisions, cache policy, and permission state mapping.
- UI/widget/component tests: loading, empty, partial, success, error, retry, disabled, permission-denied, offline, and optimistic states.
- Integration/device tests: native plugins, deep links, push opens, auth redirects, camera/files/media, background work, local database, and installable build smoke.
- Manual or screenshot verification: required for nontrivial UI layout, gesture, animation, visual hierarchy, and platform-specific fit.
- Scenario tests: build the scenario matrix in `testing-strategy`; for app surfaces, map each scenario to fast state/API tests, widget tests, device integration, and only the necessary installable-device smoke.
- **E2E / UI tests benefit from Robot pattern for non-trivial flow suites**: regardless of the underlying runner (Maestro for declarative cross-platform flows, Detox / Patrol for React Native + Flutter, XCUITest for iOS, UIAutomator / Espresso for Android), wrapping selectors + actions in per-screen Robot objects (`loginScreen.enterEmail(...).tapNext()`) means a UI structural change touches one file, not every test. Apply when the suite has ≥5 tests touching the same screen or when test churn from UI refactors is the visible pain — for a single smoke or one-off, the wrapper is overhead. Tool choice routes to repo / platform owner; the pattern survives the tool.

## UI/UX Judgment Checks

- Aesthetic: verify hierarchy, density, rhythm, contrast, motion, and material treatment on real target devices or screenshots. The screen should not become cramped, bland, or visually noisy after implementation.
- Interaction: verify navigation stack, back/close, bottom sheet/dialog return, gesture conflict, keyboard path, and orientation-specific toolbar/preview behavior.
- Behavioral: verify disabled reasons, duplicate tap protection, pending/final state, retry/cancel, offline/weak-network behavior, foreground/background recovery, and app restart recovery where relevant.
- Psychology: verify the screen reduces uncertainty and perceived risk. Users should know what is happening, whether it is safe to wait or retry, and how to recover if the app is interrupted.
- Adaptation: check safe-area insets, keyboard-covered inputs/actions, text scale, landscape where supported, narrow/large phones, and tablet/foldable layouts when in scope.
- Native capability and device tasks: verify missing host/permission/device, wait state, success continuation, raw status-code mapping, retry/report path, callback cleanup, and production debug gating.

## Mobile Client STS Upload Lifecycle

When the mobile client uploads directly to object storage (TOS / S3 / GCS) using short-lived STS credentials minted by the backend, the client-side lifecycle has rules distinct from the server-side STS broker contract (which lives in `platform-release-engineering/references/secret-and-config-management.md` Pattern C-adjacent — Cloud Session Token Brokering):

- **STS-version / bucket selection is a remote-config decision with a security-incident-grade TTL, not a build-time constant**: the client asks the backend for the current `(bucket, sts_version, region)` tuple at upload time. Cache TTL is bounded by the incident-response budget — typical: low single-digit minutes for the security-sensitive fields (bucket, sts_version, region, kill-switch), longer is acceptable only for non-security fields. Hardcoding the bucket in `BuildConfig` / `Info.plist` constants forces a store-cadence release every time ops switch bucket, region, or STS major version. The build-time constant remains as the degraded-mode fallback when remote config is unreachable.
- **Backend kill-switch and revocation handling**: the remote-config response includes an explicit kill-switch flag per upload class; when set, the client fails closed (no upload, structured error to caller) until the next config fetch clears it. When the backend revokes a bucket / region / STS version, every still-cached client config must converge within the TTL above; clients receiving "bucket revoked" / "sts version retired" from the upload API fail-close immediately and force a config refresh, never retry against the revoked target.
- **Degraded-mode fallback is explicit and logged**: when the remote-config fetch fails (network down, bad response, parse error), the client falls back to the build-time bucket + a fixed STS version (typically v1 / oldest-supported). The fallback is logged as a degraded path (warning level, with the failure cause); silent fallback hides incidents where the remote config has been wrong for weeks. Fallback is itself subject to the kill-switch: if the backend has revoked the fallback target, no upload happens until config is refreshed.
- **Token request is per-upload-session, not per-app-launch**: short-lived STS tokens (typical 15-60 min) are fetched at the start of an upload session and re-fetched on token expiry within a long session, NOT cached across app launches. App-launch caching produces "first upload after launch tries with an expired token from yesterday" failures.
- **Log redaction at the boundary, including DEBUG paths**: the upload-coordinator logger emits `ak_prefix=<first-8-chars>`, `token_len=<int>`, `bucket=<bucket>`, `sts_version=<enum>` — NEVER the full access key, secret key, session token, or signed URL. The redaction lives in the client SDK and applies in DEBUG builds too — `#if DEBUG` / `BuildConfig.DEBUG` blocks logging the raw STS response is a real leak class because (a) DEBUG-flagged builds reach beta/internal users on real STS credentials, (b) developer devices that log raw tokens upload them via crash report attachments / diagnostic export / log-share buttons. The same redaction applies to HTTP interceptors (OkHttp logging interceptor, URLSession metrics observer), crash-breadcrumb collectors, analytics body capture, and any third-party SDK that records request/response bodies — disable body capture on the upload path or scrub credentials before the third-party SDK sees them. Mobile logs leave the device through too many channels to leave any one uncovered.
- **Multi-version STS coexistence**: when the backend supports more than one STS version (v1 legacy, v2 new), the client picks the version from remote config, not from local logic. The version selector wires into the upload SDK as the request shape (header / query param), so backend rollout of v2 does not require a client release.
- **Upload-coordinator is the single seam — enforced by lint, not by convention**: bucket selection + STS fetch + retry on credential expiry + upload progress + cancellation all live in one coordinator class; callers (camera flow, document picker, log-export, etc.) call `coordinator.upload(file, metadata)` and never touch credentials. Enforcement: a build/CI lint rule (gradle / xcodebuild custom check, or grep gate) fails the build when any file outside the coordinator imports the TOS SDK directly, calls the STS token-fetch API, or constructs an upload signing header. Per-feature upload helpers that fetch credentials independently are a real recurring drift class, not a hypothetical — the lint catches it before review.

## TLS Trust And Certificate Pinning

When the mobile app must talk to internal-CA / enterprise-CA / self-signed hosts (typical: a development environment, a corporate intranet, a partner integration with a private CA), the trust override rules:

- **The override gates by distribution channel + data sensitivity, not just an environment enum**: a check like `Environment.Current != .Production` is too coarse — staging, preview, canary, TestFlight, internal-distribution, and dogfood builds routinely carry real user sessions, real auth tokens, and real (or partially-real) PII. A trust override that fires on those builds is the same MITM vector as a production override. The correct gate combines (a) the distribution channel / signing identity (debug-keystore / development-provisioning-profile only, never any distribution channel that touches real users including TestFlight and staged-rollout), (b) the build flavor's data sensitivity (no real auth tokens, no real PII), and (c) the hostname allowlist below. All three must be satisfied; production hosts on a dev build still get system-default validation.
- **Hostname allowlist with suffix-match boundary**: the override accepts the server trust only when the request's hostname matches an explicit allowlist with a strict suffix-match: `host == allowed || host.hasSuffix("." + allowed)`. The leading-dot boundary is mandatory — without it, a host like `<allowed>.<attacker>.tld` matches and accepts a hostile cert. Blanket accept-any-cert in non-prod is still a leak vector when the device joins a hostile network — the dev build a developer carries through public Wi-Fi accepts forged certs for any host.
- **Production hosts use public-CA certificates**: the production hostname MUST use a publicly-trusted CA. Falling back to the internal-CA override path on a production hostname is a deployment / ops bug to fix, not a client-side trust-override extension.
- **Trust handler is delegate-scoped at the right TLS layer, not at an interceptor layer**: implement the override as a custom `URLSessionDelegate` (iOS, hooking `urlSession(_:didReceive:completionHandler:)` for `NSURLAuthenticationMethodServerTrust`) or as a custom `X509TrustManager` + `SSLSocketFactory` (and where pinning is wanted, a `CertificatePinner`) attached to the dedicated `OkHttpClient` for internal hosts. Android `OkHttp` interceptors run AFTER the TLS handshake and cannot affect certificate validation — implementing the override as an OkHttp interceptor is a no-op that looks like it works and silently leaves system-default validation in place (or worse, gives a false sense of security). The handler is attached only to the dedicated client that targets the internal hosts; the global default (`URLSession.shared`, system OkHttp default) keeps system-default validation so a third-party SDK using shared session is never weakened.
- **Pinning for high-trust endpoints, when used, pins to the public key (SPKI) not the leaf cert**: leaf certificates rotate (every 90 days for many public CAs); pinning to the leaf bricks the app on next rotation. Pin to the issuing CA's SPKI or the project's long-lived intermediate. Ship at least one backup pin (the next-issuing CA's SPKI) so a CA-rotation incident does not require a store release; when both pinned CAs are revoked simultaneously the only recovery is a forced app update, so the backup-pin set is reviewed at every release to track the active rotation horizon. Audit the pin set every release; a pin set that never updates will eventually brick.
- **Pin-failure UX**: when a pin fails (network MITM detected, expired pin, CA rotation outpaced the app), the app surfaces a structured "secure connection failed" message with a support code, NOT silently retries or falls back to unpinned. Silent fallback is the bug pinning was meant to prevent.

## Accessibility

- Check labels, hints, focus order, keyboard/switch control where relevant, dynamic type/text scale, contrast, touch target size, and readable error messages.
- Do not add icon-only actions without accessible names.

## Performance And Reliability

- Watch app startup, frame/render stability, scroll performance, memory, image loading, network retry behavior, offline handling, crash-free path, and app size.
- Add observability for critical flows: crash breadcrumbs, analytics events, performance traces, and meaningful client-side errors.
- **Crash report symbolication is a release gate for public / staged-rollout traffic**: every release going to public traffic MUST upload Android R8 / ProGuard mapping (`mapping.txt` + per-ABI native debug symbols / `*.so` symbols) AND iOS dSYM bundles to the crash backend (Crashlytics / Sentry / Bugsnag / equivalent) before traffic — without them obfuscated stack traces are unreadable and "crash-free path" is unverifiable. Wire the upload into the release pipeline; do not rely on manual upload. Internal / closed-test builds may downgrade this gate by risk acceptance. Note: bitcode is deprecated since Xcode 14 and App Store no longer accepts bitcode submissions from Xcode 14, so dSYM upload is the only practical iOS symbolication path.
- **Image loading verdict is by capability surface, not by library name**: regardless of which library is in use (Coil / Glide / Picasso / SDWebImage / Kingfisher / Nuke / cached_network_image / FastImage), audit the same surface: decode happens off the main thread, memory + disk cache configured with bounded size, placeholder + error + retry states defined, network failure modeled in UI state, large-image / thumbnail strategy for lists, memory peak under realistic list scroll measured.

## Release Readiness

- Verify build variants/flavors/schemes, signing, environment config, app version/build number, feature flags, rollback path, store policy implications, and install smoke.
- Store release notes and screenshots are release artifacts; keep them consistent with shipped behavior.
- For staged rollout, define the monitored metrics and stop/rollback condition before release.
- **Debug-only instrumentation must be structurally excluded from every real-user build, and the exclusion verified on the exact shipped artifact — a runtime flag is not the guard.** The class is broad: debug bridges, in-app state/inspection servers, dev overlays/menus, network inspectors, remote WebView debugging, verbose token/PII logging, mock-auth or auth-bypass hooks, and any QA state-export or runtime-introspection surface — including ones with no visible UI that are still reachable via deep link, push action, JS bridge message, or custom URL scheme. Any of these is an attack surface and data-exposure risk (an in-app state server can bind a port and dump app state on a real user's device) if it reaches a build that can touch real users, real auth, or real PII. **Scope by distribution channel + data sensitivity, not a single `isProduction`/`isDebug` enum**: the gate covers App Store / Play production AND TestFlight, enterprise / ad-hoc, dogfood, Play internal/closed testing, and staged rollout — all carry real users (same channel-not-enum boundary as **TLS Trust And Certificate Pinning** above).
  - **Exclude at the dependency/target level, per real-user variant — not just a runtime flag, and not just the variant named `release`.** An `if (isDebug)` check still compiles the code — and any bound port/server — into the binary; even `kDebugMode` / `__DEV__` only strip the Dart/JS call path while a native plugin/module/platform-channel stays linked. The primary guarantee is that the debug dependency/target is absent from the release classpath / target membership / build flavor of *every variant that reaches real users*, verified per variant: iOS `#if DEBUG` plus Debug-only target membership — CocoaPods can scope a pod to Debug configurations (`:configurations => ['Debug']`), but SwiftPM has no build-configuration-scoped *package dependency*, so a debug package must be confined to a debug-only target/scheme and left unlinked by every real-user target rather than gated by a `Package.swift` condition; also confirm no real-user scheme (TestFlight / enterprise / staging) inherits `DEBUG` in `SWIFT_ACTIVE_COMPILATION_CONDITIONS` / `GCC_PREPROCESSOR_DEFINITIONS`, or `#if DEBUG` code compiles straight into it; Android a `debugImplementation` / debug source-set dependency, NOT `implementation` plus a runtime check (a manifest `ContentProvider`/initializer or reflection keep-rule runs it anyway) — and note a `debug` / `qaDebug` buildType shipped to dogfood/internal testing IS a real-user build that includes those deps, so real-user channels must use release-class variants with debug deps excluded; Flutter/RN remove the package from the release flavor at the platform level (a native plugin autolinks/registers into the binary via podspec/Gradle/manifest unless excluded from the release target, even when the Dart/JS guard is stripped).
  - **Verify on the exact final signed/packaged upload artifact per channel and variant, and treat a symbol/string grep as a backstop, not proof.** A single `nm -j` / `strings` / dexdump / grep is defeated by R8 / Hermes / LTO renaming (`DevInspector` → `a.b.C`), dynamic loading (`dlopen`, Android dynamic feature, RN/Flutter OTA bundle, remote WebView JS), and non-code surfaces (debug assets, URL schemes, manifest providers/services, plist keys, debug entitlements). *Discover* the inventory from the dependency graph, manifest/plist, entitlements, and route/deep-link/bridge registries — not a remembered list, since an unlisted transitive SDK initializer or debug bridge handler is exactly the gap — then for each assert absence across binary, dex/native libs, assets/resources, manifest/plist, entitlements (`get-task-allow` is debug-only; Local Network / ATS / cleartext exceptions are security-sensitive plist/capability config that need production justification, not necessarily debug), and the OTA/dynamic-load channels reachable by that release (a passing artifact digest does NOT bind a debug bundle pushed later via CodePush/Expo/remote WebView JS, so real-user OTA/remote channels must not serve debug payloads). Run it on the post-signing artifact you actually upload (record its digest), across every shipped platform / scheme / flavor / extension, never on an intermediate `assembleRelease`. (`__DEV__` / `kDebugMode` elimination is also minifier-dependent and has silently regressed historically, so the source guard alone is never proof.)
  - **Make it a release-blocking evidence row, not MR prose** (otherwise the gate is decorative — a team ships from local Xcode/Fastlane, self-marks "checked", or never adds the CI job). The row is machine-generated, tied to the uploaded artifact digest + variant, and verified by someone other than the author; it records the digest, distribution channel, variant matrix, and check-command output, and the release/upload lane fails closed on a missing row. **Risk acceptance cannot waive structural exclusion** of debug-only instrumentation in any real-user / real-auth / real-PII build: an exception may only reclassify the channel as non-real-user / no-real-data, or apply to a production-intended diagnostic that ships its own auth + redaction controls (at which point it is no longer debug-only instrumentation) — otherwise the release stays blocked, an unbounded "accepted" is not a valid disposition. Guidance cannot force a given repo's pipeline to fail closed — that mechanical enforcement is the release-pipeline owner's job (route to `platform-release-engineering`); absent the row the status is not release-ready, the same way missing device smoke leaves a slice `pre-runtime-test-ready`. A manual removal/teardown flow is a convenience path for a one-off exit, never the mechanism that keeps debug code out of real-user builds.

## Component-Library Version Discipline

- Write third-party UI/component-library APIs against the exact **resolved installed version** — the package-manager lockfile (pubspec.lock / Podfile.lock / package-lock.json / yarn.lock / pnpm-lock.yaml / Gradle dependency-locking or `dependencies` report) or the package manager's installed-package query — never a manifest's semver range (package.json / a catalog alias with dynamic constraints declares a range, not what is installed) and never memory of "current" APIs — prop names and defaults shift across majors.
- When the library ships its own lint/codemod or migration checklist, close changes and major-version migrations with it on the changed files (deprecated-usage and a11y rules a generic lint config does not know).
