# Android Dev

## Architecture

- Follow Android's common layer split: UI layer for rendering and user events, data layer for repositories/data sources, optional domain layer when use cases are reused or complex.
- Keep screen state in ViewModel or a repo-approved state holder. Compose functions should render state and emit events rather than own durable business state.
- Hoist Compose state to the lowest common owner that needs to read or write it.
- Collect flows lifecycle-aware. Avoid leaking work across stopped screens.
- Keep repositories as data boundaries for network, database, cache, and sync decisions.
- **MVVM / MVI naming is rebrand, not contract** — the audit looks at: single source of truth (ViewModel / state holder owns durable state, no shadow copies), unidirectional flow (UI emits Intent / event → ViewModel produces new State → UI renders), side effects (navigation, toast, snackbar) routed through a one-shot event channel rather than re-emitted state. A repo that says "MVI" but mutates state directly from `@Composable` callbacks is closer to "scattered state with extra ceremony".
- **Modularization is a tool, not a goal**: split into feature / API / platform-adapter Gradle modules when build-time / team-ownership / variant-isolation evidence justifies it. Module boundary's job is to prevent cross-feature direct dependency, duplicated network clients, and duplicated state holders — not to maximize module count. A monolithic `:app` is fine for small teams; a 40-module graph with two engineers is overhead.
- **Coroutines + Flow are the default async substrate**: scope work to `viewModelScope` / `lifecycleScope` / `repositoryScope` (custom + `SupervisorJob`) — never `GlobalScope` in app code; expose state as cold `Flow` and convert to `StateFlow` / `SharedFlow` at the boundary that needs replay / sticky value; collect with `flowWithLifecycle(...)` / `collectAsStateWithLifecycle()` in UI so collection cancels off-screen. `LiveData` remains valid for older Java/Kotlin codebases but new code defaults to `StateFlow`. RxJava is acceptable in projects with deep Rx investment, not for new code.
- **Compose strong skipping mode**: introduced experimental in Compose Compiler 1.5.4; non-experimental in 1.5.13; **enabled by default starting Kotlin 2.0.20**. When enabled, all restartable composables become skippable regardless of parameter stability, and lambdas are auto-`remember`-wrapped — the optimization "greatly increases the number of composables that the runtime skips during recomposition" per Android docs (docs do NOT publish a specific recomposition % win; APK size impact is +4kB on the Now In Android sample). For projects on Kotlin <2.0.20, opt in via `composeCompiler { enableStrongSkippingMode = true }`; for projects on 2.0.20+, verify lambda capture semantics did not change before assuming default-on is safe.

## Platform Capabilities

- Use platform components for background work, notifications, permissions, camera/media/files, and app links when the feature needs OS-level behavior.
- Model permission denied, permanently denied, unavailable hardware, interrupted background work, and app restore as explicit states.
- Keep build variants, flavors, signing, min/target SDK, ProGuard/R8, and manifest changes reviewable.
- **Android 14+ Foreground Service strictness**: every started foreground service MUST declare a `foregroundServiceType` in the manifest (missing → `MissingForegroundServiceTypeException`) AND declare the matching FGS permission in the manifest (`FOREGROUND_SERVICE_LOCATION` / `_CAMERA` / `_MICROPHONE` / `_DATA_SYNC` etc — these are NORMAL manifest permissions, auto-granted, not runtime-revocable). Per-type runtime prerequisites must ALSO be satisfied (e.g., `camera` FGS requires `CAMERA` runtime permission already granted; `location` requires `ACCESS_FINE_LOCATION` / `_COARSE`; `microphone` requires `RECORD_AUDIO`; `dataSync` has no extra runtime prerequisite). Missing prerequisites → `SecurityException`, not deprecation warning. Audit FGS start sites whenever permission, media, or sync code is touched.
- **Android 15 (targetSdk 35) edge-to-edge default**: apps targeting API 35 render edge-to-edge by default; insets handling (system bar / nav bar / IME) becomes mandatory for every screen — windows no longer auto-pad. Run edge-to-edge / insets visual check on every screen with status-bar / nav-bar overlap before bumping targetSdk to 35.
- **Baseline Profile + Macrobenchmark for startup-critical surfaces**: generate a Baseline Profile (Android Studio / `androidx.benchmark.macro` library) for launch + first-interaction paths; install it with the AAB so the included code paths are AOT-compiled at install time and avoid interpretation / JIT on first launch. Verify startup gains via Macrobenchmark, not by stopwatch.
- **Splash Screen API (Android 12+, `androidx.core:core-splashscreen` backport to API 23+)**: stop hand-rolling a `SplashActivity` — the system splash is constructed from the app launcher icon + `windowBackground`. Migrate any custom splash to `SplashScreen` API; the compat library provides a consistent look across all supported Android versions. Use `setKeepOnScreenCondition` for the "wait for first data" pattern instead of an extra screen.
- **Predictive Back enforcement timeline**: Android 14 (API 34) introduced predictive back as opt-in via manifest `android:enableOnBackInvokedCallback="true"`. Android 15 (API 35) removed the developer option — opt-in apps see system back-to-home / cross-task / cross-activity animations, but opting in remains required. **Android 16 (API 36): predictive back is default and enforced** for apps targeting API 36 — `onBackPressed()` is no longer called and `KeyEvent.KEYCODE_BACK` is no longer dispatched; migrate to `OnBackPressedDispatcher` / `OnBackPressedCallback` (View system) or `BackHandler` / `PredictiveBackHandler` (Compose). Temporary opt-out via `android:enableOnBackInvokedCallback="false"` exists but is announced to stop working at targetSdk 37.

## Data Persistence

- **DataStore (Preferences DataStore for key-value, Proto DataStore for typed schema) replaces SharedPreferences for new code**. SharedPreferences has a sync API that's unsafe to call on the UI thread, no error signal, no transactional API; DataStore is async (Coroutines + Flow), handles migration / corruption explicitly. Preferences DataStore is the SharedPreferences shape without the bugs; Proto DataStore adds schema + type safety via protobuf. For complex data with partial updates or referential integrity, use Room — DataStore is for small / simple datasets only.
- **Sensitive credentials use the Android Keystore directly (or existing platform crypto APIs)** — Keystore manages keys in hardware-backed secure storage when available; never store raw tokens in regular SharedPreferences / files. The Jetpack wrapper `androidx.security:security-crypto` (`EncryptedSharedPreferences` / `EncryptedFile` / `MasterKey`) deprecated all APIs in 1.1.0-beta01 on 2025-06-04 (stable 1.1.0 on 2025-07-30); official direction is platform APIs + direct Android Keystore use — no Jetpack-wrapper successor. Existing projects on `security-crypto` migrate to direct Keystore + a project-owned crypto wrapper.

## Dependencies And Toolchain

- **KSP (Kotlin Symbol Processing) over KAPT**: Kapt is in maintenance mode and incompatible with the built-in Kotlin compiler plugin; the recommendation is to migrate. KSP is up to 2x faster on Kotlin-aware processors (no Java-stub generation step); for most libraries the migration is just renaming `kapt(...)` to `ksp(...)` in dependency declarations because the processor ships in the same artifact. Hilt, Room, Moshi, and most modern Android codegen libs support KSP. Stay on KAPT only for processors that have not shipped a KSP variant.
- **`libs.versions.toml` (Gradle Version Catalog) for dependency declarations**: single source of truth for versions across multi-module builds; type-safe accessor generated by Gradle; dependency-update tooling reads the catalog directly. New modules should consume from the catalog, not declare versions inline.
- **`androidx.startup` (App Startup library) for SDK initializer order**: replace ad-hoc `Application.onCreate` blocks with explicit `Initializer<T>` classes; declare dependencies between initializers so order is explicit; CI / build can verify the graph. Critical when multiple SDKs (analytics, crash, push, feature-flag) need init order.

## Theme And Brand Color

The shared design discipline (token sourcing, multi-platform alignment, source-vs-export rules, three-layer evidence) is owned by `product-ui-ux-design/references/multi-project-token-consistency.md` and `design-system-source-of-truth.md` — consult those before writing or auditing this section's implementation rules.

Android-specific anti-patterns observed across native Compose subprojects:

- **IDE / Material You scaffold colors left as dead-code declarations in `Color.kt` / `Theme.kt`**: new Compose modules generated by Android Studio ship with `Purple40 / Purple80 / PurpleGrey40 / PurpleGrey80 / Pink40 / Pink80` plus matching `lightColorScheme(primary = Purple40, ...)` / `darkColorScheme(primary = Purple80, ...)` blocks. When the team adds a brand `primaryColor = Color(0xFF<brand>)` and routes it through a separate `generateColorScheme(primaryColor, ...)` builder, the original Purple/Pink declarations and the scaffold `ColorScheme` vals usually stay in the file unreferenced. They are inert at runtime, BUT they confuse onboarding ("which is the real brand color?") and make later regex / search-and-replace refreshes ambiguous. Delete the unreferenced scaffold declarations once the brand color is wired; do not keep them "for reference".
- **`AppTheme(dynamicColor: Boolean = true, ...)`-style dead parameter**: scaffold `@Composable` themes accept a `dynamicColor` flag intended to switch to `dynamicLightColorScheme(LocalContext.current)` on Android 12+. When the team overrides the body to call its own `generateColorScheme(brandColor, ...)` unconditionally and never reads the flag, the parameter becomes a footgun — callers think Material You is opt-in. Either honor the flag (branch on `Build.VERSION.SDK_INT >= S` and dispatch dynamic vs brand scheme) or remove the parameter; do not ship a no-op flag.
- **Vendor-default literal leak in custom theme**: a brand theme that still contains literals identifiable as Google Material defaults — `Color(0xFFD93025)` (Google red), `Color(0xFF6750A4)` (Material You purple), `Color(0xFF03DAC5)` (Material teal), `Color(0xFF1976D2)` (MUI blue), `Color(0xFFBB86FC)` (Material light purple), etc — inside `errorColor`, `secondaryColor`, fallback values, or per-component overrides. Same pattern as the cross-stack rule in `multi-project-token-consistency.md` "Vendor-default literal leaked into a custom theme": the value looks deliberate because someone typed it, so generic literal-detection passes; but brand refresh skips it. Detection: grep the theme module for the per-version Material / MUI default palette values. A hit resolves to one of three classes per the shared rule: **leak** (replace with brand token), **deliberate documented reuse** (keep with rationale comment), or **legitimate convergence** (brand role independently resolves to the same hex — keep but reference the brand token, not the literal).
- **Algorithmic secondary / tertiary derived from primary without designer sign-off** — applies to **custom** algorithmic derivation, NOT to standards-based Material You: patterns like `secondaryColor = Color.hsv(hue = (primaryColor.hue + 30) % 360, saturation = 0.8f, value = 0.9f)` or `SecondaryColor = primary.copy(alpha = 0.2f)` are custom derivations that skip the designer for every derived state. See the shared rule in `multi-project-token-consistency.md` Anti-Patterns. Acceptable IF the file carries a one-line provenance comment naming the algorithm and the designer sign-off date, AND brand-refresh QA includes a derived-color visual check. **Material You carve-out**: `dynamicLightColorScheme(LocalContext.current)` / `dynamicDarkColorScheme(...)` (Android 12+ wallpaper-derived) and standards-based `ColorScheme.fromSeed(seedColor = brandColor)` are acceptable as the design policy when documented with library/version, `DynamicSchemeVariant` if set, accessibility/contrast checks against the brand seed, and visual QA on canonical screens. Designer sign-off applies to the policy adoption + the seed/canonical-screen pass, NOT to every runtime-generated secondary/tertiary value (incoherent for wallpaper-derived schemes).
- **Per-app duplicated brand literal vs shared design-token module**: when N native Android apps in one product each declare `val PrimaryColor = Color(0xFF<brand>)` in their own `Color.kt`, a brand refresh becomes an N-place edit and apps silently fall out of sync. The fix is a shared design-token Gradle module (or published artifact) consumed by every app — same pattern as the shared theme-package rule on the web side.

### WebView-wrapper Android shells

A native Android app whose main product flows are hosted in a `WebView` plus a thin shell of native helper screens (network error, photo upload, auth bridge, splash, settings) is a **hybrid WebView shell**. The audit verdict is per-surface, not per-app: WebView-hosted product flows route their brand audit to the loaded web app; native-owned shell screens (splash, login, settings, offline / network-error fallback, permission prompts, native modal flows, status-bar / safe-area chrome, deep-link landing) are audited as native surfaces with normal three-layer evidence.

- Detection signals: small native source count relative to the app's apparent feature surface, `WebView` / `WKWebView` plus a JS bridge as the primary UI component, no Compose / View-system screens for the main product flows, vendor pods or AARs for JS bridging (`WebViewJavascriptBridge` and equivalents).
- Reporting rule: the verdict is **per-surface, not per-app**. WebView-hosted product flows → `native-theme: not-applicable (webview-hosted, brand audited via loaded URL)`; native-owned surfaces in the SAME app (splash, login, settings, offline / network-error fallback, permission prompts, native modal flows, status bar / safe-area chrome, deep-link landing, updater dialogs) → `audit native brand tokens normally`. A whole-app `not-applicable` verdict is wrong whenever the app ships ANY native screen with brand-relevant chrome; that wording lets auditors skip visible surfaces blindly. Confirm the loaded web URL's brand alignment separately for the WebView portion.
- Wrapper-specific risks that DO belong to native: WebView JS-bridge auth, file-upload / camera permissions plumbed through the WebView, status-bar / safe-area / system-back integration, deep-link handoff into the WebView URL, offline / network-error native fallback screen branding. Those still need native attention even when the visual brand lives in the web app.

## Vendor AIDL Hardware Service Binding

When the app runs on a dedicated / kiosk / vendor-supplied Android device and needs hardware capabilities exposed by a vendor-installed system service (printer driver, scanner, payment terminal, scale, RFID reader, OEM firmware control like timed power-on/off, silent install, status-bar display), the integration is via AIDL service binding to the vendor's service — not via root, not via `Runtime.exec`, not via fragile reflection on hidden APIs:

- **AIDL interface is a contract artifact owned by the vendor, copied into the app under a documented license**: the vendor publishes the `.aidl` files (or an SDK that includes them); the app copies them into `app/src/main/aidl/<vendor-package>/` preserving the vendor's package path. Before the copy lands, confirm the vendor SDK's license permits source redistribution / inclusion (some vendor SDKs ship `.aidl` under a license that allows binary linking only; copying source into the app repo can be a license violation). Record per-binding: vendor name, SDK / AIDL source version, license, the vendor doc URL that authoritatively describes the methods. Vendor SDK updates rev the AIDL file; the contract version is a per-vendor track, not the app's version.
- **One `ServiceConnection` per vendor service, with explicit handlers for ALL Binder lifecycle callbacks AND a circuit-breaker terminal state**: `<Iface>.Stub.asInterface(service)` runs on `onServiceConnected`. All four Binder lifecycle callbacks must be handled, each for a distinct failure mode: `onServiceDisconnected` (process killed by framework / OOM / firmware reboot) → reconnect; `onBindingDied` (the binding itself died, typical for vendor-service package update / OTA replace) → unbind + rebind, NOT just reconnect, because the dead binding never recovers without re-binding; `onNullBinding` (`bindService` returned non-null but the service returned `null` from `onBind` — the service is installed but refuses our identity, typical for signature-protected services) → fail-closed terminal "vendor service refused binding" state; explicit `false` return from `bindService` (component not present at all) → fail-closed terminal "vendor service not installed" state. Reconnect uses bounded exponential backoff AND a maximum-attempts / maximum-window circuit breaker (typical: stop after N attempts over T minutes); when the circuit opens, the binding enters a stable "vendor service unavailable" state until a package-replace broadcast (`ACTION_PACKAGE_ADDED` / `_REPLACED` for the vendor package) or explicit user action retries — silent infinite reconnect spams logs and battery without ever recovering.
- **Wrap every AIDL call in `RemoteException` handling**: AIDL calls cross a Binder boundary and can throw `RemoteException` (vendor service died, transaction failed, parcel too large). Bubble these as typed errors with the vendor + capability name in the message (`<vendor>.<method> failed: <cause>`) so logs identify which vendor service was unreachable. Returning `null` silently from a vendor-service wrapper is the bug class that lets the hardware feature degrade unnoticed for weeks.
- **Capability detection happens at binding time, not at call time**: when the binding succeeds, probe the vendor service's `getManufacturer()` / `getVersion()` / capability-discovery method once, cache the result, and expose `isAvailable(capability)` to callers. Callers gate UI affordances on `isAvailable`; they do not catch `RemoteException` per call as the availability check. Vendor services with no version probe are wrapped in a per-method capability map updated on each known-vendor revision.
- **AIDL service binding is a `<service>` declaration in the vendor app, not in our app**: the binding target is a `ComponentName(<vendor-package>, <vendor-service-class>)` — verify the package + class in vendor docs before shipping. A `bindService` to a non-existent component returns `false` silently; check the return value and fail closed with a "vendor service not installed" state, NOT a generic "hardware unavailable" toast.
- **USB-attached peripherals (printer, scanner) go through `UsbManager` + permission broadcast, not AIDL**: AIDL-bound vendor services are for OEM-firmware capabilities (timed boot, status bar, silent install). Plug-in USB hardware uses `UsbManager.requestPermission()` + a `BroadcastReceiver` for `ACTION_USB_PERMISSION` / `ACTION_USB_DEVICE_ATTACHED` / `ACTION_USB_DEVICE_DETACHED`. Mixing the two paths in one class is acceptable; conflating them in the rule is not — the auth model and the failure mode are different.
- **Privileged AIDL methods (silent install, reboot, shutdown) require the device's vendor signature or platform permission**: confirm the privilege model with the vendor before the feature ships; an app distributed via Play Store generally cannot exercise `installPackage` / `reboot` against vendor services from third-party APKs. Ship the privileged path only when the device is vendor-flashed with the app pre-installed under the vendor's signature.

## Shared-Device Inactivity (Compose)

When the Android app runs on a shared device (kiosk terminal, counter staff terminal, intake tablet) and needs inactivity-driven session handoff: the **full cross-platform shared-device contract** lives in `web-react-dev/references/web-ui-quality.md` (Shared Device And Inactivity Session) — full input event set, throttled reset, durable shared timestamp, cross-tab/window coordination, terminal-to-neutral, deployment-context timeout split, server-side independent session expiry. A Compose implementation MUST satisfy the full contract, not only the local-timer subset; a `LaunchedEffect` + `remember` timer that ignores the durable-timestamp / cross-process coordination rules is the source-observed shorthand, NOT the rule. Compose-specific implementation guidance for satisfying the full contract:

- The inactivity handler is a top-level `@Composable` that wraps the route content and exposes a `resetTimeout: () -> Unit` slot to children that need to register additional activity sources.
- The countdown loop runs inside a `LaunchedEffect` keyed on the dialog-visible state; on dialog dismissal the effect cancels via standard coroutine cancellation — no manual cleanup needed.
- Input event observation: pointer/touch events are observed via `Modifier.pointerInput` on the wrapping `Box`. Key events (hardware keyboard, DPAD, barcode scanner that emulates keypresses, remote control) need a focus-bearing root — `Modifier.onKeyEvent` only fires when the node or a focused descendant is focused, so the root must be `Modifier.focusRequester(focusRequester).focusable()` with a `LaunchedEffect { focusRequester.requestFocus() }` AND/OR the activity-level `dispatchKeyEvent` override forwards keys into the inactivity handler. The modifier order is significant: `focusRequester` must be applied BEFORE `focusable` in the chain — `.focusable().focusRequester(...)` reverses the wiring and `requestFocus()` silently no-ops, leaving the key-event capture broken. Without one of these, key-only activity (a user paging via DPAD on a kiosk remote) does NOT reset the timer and the app misfires the terminal action.
- The shared-monotonic-timestamp cross-tab rule from the web side translates on Android to a durable shared store (`DataStore` / `SharedPreferences` / Room with `lastActivityAt` / `expiresAt`), updated by activity and re-read immediately before the terminal action. `BroadcastChannel` on web maps to a `BroadcastReceiver` (cross-process) or a process-level `Flow` (in-process multi-Activity / multi-Fragment). The durable store is authoritative; broadcasts are notification only — process restart, framework recreation, or backgrounded-Activity resumption all rely on re-reading the durable store, never on in-memory state.
- Compose composition lifecycle differs from React unmount: a `LaunchedEffect` cancels on key change OR on the composition leaving — but Activity / Fragment lifecycle (foreground/background) and process death are separate dimensions. The terminal-to-neutral rule applies on process-resume (read durable `expiresAt`, terminate if exceeded), not only on composition recomposition.

## Tests And Verification

- Unit test state holders, use cases, repositories with fakes, mappers, validators, and error translation.
- Compose/UI tests should assert visible states and interactions, not just launch screens.
- Instrumented tests belong to flows requiring real Android framework behavior.
- Verify app links, notification opens, permission prompts, process death/state restore, and offline/cache behavior when touched.
- **Test tooling stack**: JUnit 5 (`useJUnitPlatform()` in Gradle) for new **local JVM** unit tests; instrumented (`androidTest`) tests still run on the JUnit 4 runner by default unless extra setup is added (e.g., `de.mannodermaus.junit5`). MockK for mocking (Kotlin-native, supports coroutines + extension functions / final classes that Mockito needs special config for); Robolectric for JVM-side Android-context tests (faster than instrumented but not a substitute when real Android framework behavior matters); Turbine for `Flow` / `SharedFlow` testing (manages collection lifecycle + assertion-on-emission). Screenshot regression goes through Roborazzi (JVM-based, Robolectric-style) or Paparazzi (LayoutLib-based, no emulator) — scope to design-system primitives and visually-risky surfaces, not every screen.

## Quality

- Check startup time, frame stability, list performance, memory, image loading, network failures, accessibility labels, touch targets, contrast, and font scaling.
- Prefer existing Gradle wrappers and CI tasks over raw commands.
- **StrictMode + LeakCanary as dev/staging guardrails**: enable `StrictMode.setThreadPolicy` (detect disk / network on main thread) and `setVmPolicy` (leaked closables / cursors / activities) in debug builds — Strict findings are violation-class evidence of bugs that ship unnoticed. Add LeakCanary to debug / staging variants; activity / fragment leaks surface immediately in dev rather than via support tickets in production. Both stay out of release builds.
- **WorkManager / CoroutineWorker for deferrable background work**: any task that should survive process death / app close / device reboot (sync, upload, scheduled refresh, deferred notification) goes through WorkManager, not raw `JobScheduler` / `AlarmManager` — WorkManager handles backoff, constraints (network / charging / idle), chained work, and Doze-mode compatibility. Use `CoroutineWorker` for Kotlin code; `RxWorker` for Rx codebases. Foreground services (per Android 14+ FGS rule above) are for actively-running visible work, not deferrable.
