# Mobile Platform Boundaries

## Platform Choice

- Choose Flutter when shared product behavior, speed of delivery, and consistent UI are more important than heavy native specialization.
- Choose native Android or iOS when the feature depends on deep platform APIs, strict platform conventions, mature native modules, store policy nuance, or existing repo ownership.
- Use mixed architecture only with a clear ownership split: shared UI/module boundary, native host boundary, build ownership, release ownership, and fallback plan.

## Boundary Checklist

- Route model: tabs, stacks, modal flows, back behavior, deep links, universal/app links, and unauthenticated entry.
- State model: transient screen state, session state, cached data, optimistic changes, sync state, and invalidation trigger.
- API model: typed request/response, auth/session refresh, cancellation, retry, timeout, pagination, upload/download, streaming or websocket if used.
- Local model: key-value storage, database, file cache, encryption needs, migration, cleanup, and offline source of truth.
- Platform model: permissions, background work, notifications, camera/media/files, clipboard/share, payments, biometrics, widgets/extensions, and OS policy.
- Native bridge model: initialization, capability detection, callback id generation, callback cleanup, fallback to old bridge or degraded mode, timeout/failure mapping, and visible recovery when the host bridge is missing or stale.
- Delivery model: build flavors/schemes, environment config, signing, app versioning, store review risk, telemetry, and rollback flags.
- UI/UX model: define the visual focus, entry/current/next/return path, interruption recovery, safe retry/cancel behavior, and user confidence cues for each mobile task. Cross-platform consistency is not enough if the screen feels cramped, ambiguous, or unrecoverable on a real device.

## Cross-Platform Rules

- Keep shared behavior explicit. Document intentional differences by platform instead of letting them emerge from implementation drift.
- Treat deep links, push opens, auth redirects, and app restore as first-class flows.
- Model every async feature with loading, empty, partial, success, failure, retry, permission-denied, and offline states where applicable.
- Keep platform adapters narrow and testable. UI code should not directly know transport, permission, or native SDK details unless the repo pattern requires it.
- **Kotlin Multiplatform (KMP) / Compose Multiplatform are evidence-driven, not defaults**: KMP is appropriate for shared domain / data / API-client logic across an existing Kotlin Android codebase and a native iOS app (mature production pattern: shared logic + native UI). Compose Multiplatform iOS reached Stable in 1.8.0 (2025-05) — UI-sharing is a narrower Kotlin-first team bet that needs explicit native-feel parity evidence, native escape hatch, and iOS team acceptance. For products where the iOS team owns SwiftUI, Flutter / React Native is already the cross-platform path, do not introduce KMP "while we're at it". For adoption decision matrix, expect/actual + source-set discipline, iOS framework integration paths (direct / CocoaPods / SPM), Kotlin/Native runtime, Compose MP iOS scope, code-reuse tiering by layer, build/test matrix, and platform stability table, read `references/kotlin-multiplatform.md`.

## Cross-Platform Brand Color Boundary

The shared rule on brand-color divergence across platforms (web, native mobile, mini-program) is owned by `product-ui-ux-design/references/multi-project-token-consistency.md` "Cross-platform brand divergence — a recurring sub-case" and `design-system-source-of-truth.md` Anti-Patterns. Mobile-side implementation responsibilities:

- **Audit each mobile shell for its actual rendered brand primary**, then compare against the web brand primary for the same product. Two different values are NOT automatically drift — first run the Migration-State Classification in `multi-project-token-consistency.md` (`current` / `target` / `in-flight` / `drift`); a documented staged brand refresh with named migration signals (upgrade-plan artifact, deprecation marker, parallel-runs switch, tracked work item, deliberate partial rollout) is a planned rollout, not a per-platform-role failure. After that classification: when the divergence is **permanent intentional** cross-platform branding, the design source must use explicit per-platform role naming (`colorPrimary-web` / `colorPrimary-native` / per-platform variable collection); when the divergence is **drift** (no migration signal, no per-platform role), escalate the fix.
- **When the divergence IS permanent intentional**, the mobile theme module must comment-link to the design-source variable name and the product-decision owner (PM / brand owner) — e.g. `// brand: colorPrimary-native per <design-system file> Variables panel, owner: <role>`. Implicit "we just always used this color" is the same risk as no decision record.
- **Algorithmic secondary / tertiary derivation** falls into two paths per the shared rule in `multi-project-token-consistency.md` Anti-Patterns: **custom derivation** (HSV shift, alpha tint, complementary, lightness step) requires a one-line designer/date sign-off in the theme file AND a brand-refresh derived-color visual check; **standards-based platform schemes** (Material You's `ColorScheme.fromSeed` / `dynamicLightColorScheme`, antd's automatic palette from `colorPrimary`, MUI's `createTheme` tonal palette) require recording the variant/version in use, accessibility/contrast checks against the brand seed, and visual QA on canonical screens — designer sign-off applies to the policy adoption + seed/canonical pass, not to every runtime-generated tonal value. The two paths are distinct; do not collapse them.

## WebView-Wrapper App Recognition

A mobile app whose main product flows are hosted in a `WebView` (Android) / `WKWebView` (iOS) plus a thin shell of native helper screens (network error, photo upload, auth bridge, splash, settings) is a **hybrid WebView shell**. The audit verdict is per-surface, not per-app: WebView-hosted product flows route their brand audit to the loaded web app; native-owned shell screens are audited as native surfaces with normal three-layer evidence. Recognition rule below applies to both Android and iOS shells:

- **Native-source-count signal**: typical wrapper has very few native UI screen classes (no Compose `@Composable` screens, no SwiftUI `View` for product flows). The native source is dominated by infrastructure (AppDelegate / MainActivity, network, file/image helpers, JS bridge).
- **JS-bridge signal**: dependency on `WebViewJavascriptBridge`, `WKScriptMessageHandler` patterns, or equivalent web-to-native bridging libraries.
- **Audit verdict is per-surface, not per-app**: WebView-hosted product flows → `native-theme: not-applicable (webview-hosted, brand audited via loaded URL)`; native-owned surfaces in the SAME app (splash, login, settings, offline / network-error fallback, permission prompts, deep-link landing, native modal flows, status bar / safe-area chrome) → `audit native brand tokens normally`. A whole-app `not-applicable` verdict is the failure mode — auditors then skip visible native surfaces in a "wrapper" app.
- **Wrapper-specific native concerns still apply**: status bar / safe area styling under the WebView, the native fallback / network-error screen's branding (since users see it when the WebView fails), permission-prompt chrome (camera, photos, location), deep-link handoff into the WebView URL, login bridge modal chrome, and any native modal flows whose visual chrome is owned by the native app. These must still align with the product brand even when the main UI is web-rendered.
- **Desktop wrappers (Electron / Tauri / Wails / .NET MAUI Blazor Hybrid) are NOT automatically covered by this mobile-side rule**. Per `multi-stack-strategy.md`, Electron classifies as `native`. Desktop wrappers carry their own per-surface split — web-rendered content vs native shell chrome (window chrome, menu bar, system tray, native dialogs, updater UI, app icon, splash) — and the desktop shell chrome IS brand-relevant. Route desktop wrapper audits through the desktop platform skill that owns them; do not analogize the mobile WebView-wrapper verdict to Electron.
- See per-platform implementation in `android-dev.md` and `ios-dev.md` Theme And Brand Color sections.
- Gate debug consoles, mock login, and local bypasses to development or explicit test builds. Production app/H5 surfaces must not expose debug entry points through query strings, default accounts, or visible console tooling.
- Device or native-capability flows need explicit status taxonomies. Convert raw native codes into user-facing states, retry safety, support evidence, and terminal failure paths instead of showing generic bridge errors.
- Mobile layouts must be validated through the same four layers as design: aesthetic focus and density, interaction path, behavioral recovery, and psychology of certainty/control. Safe-area, keyboard, orientation, permission, background/foreground restore, and host-bridge absence are part of the product experience, not only platform plumbing.

## Bridge Protocol Contract Discipline

Hybrid apps that expose native capabilities to a hosted H5 layer almost always grow two parallel bridge implementations (iOS WKWebView + Android WebView) plus the H5 caller. Without an explicit contract, the three sides drift.

- **The bridge surface is a typed contract, not a coincidence.** Enumerate every handler/method name, request payload shape, callback response shape, status taxonomy, and timeout in one place that both native sides and the H5 side consume. Free-form `callHandler("openCamera", anyJSON)` calls are how silent drift accumulates.
- **Status semantics must be uniform.** Pick one numeric or string enum (e.g. `Success / Cancel / Fail`) and apply it across every bridge call on every platform. Mixing `0/1/-1` on one side and `"ok"/"cancelled"/"error"` on the other forces every caller to write platform-aware branches.
- **Payload encoding must be uniform.** If one platform passes a JSON object and the other passes a JSON string in a single `data` field, every H5 caller pays a `JSON.parse + typeof` cost on every callback. Pick one and codify it.
- **Capability asymmetry must be enumerated, not silent.** If one platform supports `exportLogs` and the other does not, the H5 caller must detect this and degrade gracefully — never crash the page on a missing handler. Maintain a capability map keyed on platform.
- **Long-lived `window.<callbackId>` injection patterns must clean up — and namespacing alone is not enough.** Android-style bridges that attach the resolve/reject to `window[callbackId]` and rely on the native side to fire it leak globals and fire into unmounted React trees. Moving the slot under a namespaced object (e.g. `window.NativeBridge.callbacks[id]`) is a step but not the answer — the registry is still enumerable, the dispatcher is still monkey-patchable by any script that loads before the bridge, and a co-running script does not need to *guess* an id when it can enumerate the map. The complete pattern is: (a) install one locked, immutable dispatcher *value* before any third-party script loads — `Object.defineProperty(window, '__nativeBridge', { value: dispatcher, writable: false, configurable: false })` is necessary but NOT sufficient on its own, because the dispatcher object's *methods* are still mutable; harden the value itself by defining each public method as a non-writable / non-configurable property, calling `Object.freeze` on the dispatcher (and any nested objects it exposes), and preferring a `Object.create(null)` prototype so prototype-chain pollution cannot replace methods. The acceptance test is: a third-party script that loads after the dispatcher must not be able to replace `dispatch`, `settle`, or any registered handler. (b) Hold the callback map inside a closure private to the dispatcher rather than as a property of the bridge object — the map must not be reachable via `window.__nativeBridge.callbacks` or any other enumerable path. (c) Generate ids from a cryptographic source as defence-in-depth. (d) Wrap the registry in a one-shot settle (the callback is removed in a finally block before it resolves). (e) Attach a timeout that rejects + cleans up if the native side never fires. (f) Validate `(callbackId, op, generation)` triple on every fire so a stale or wrong-op response cannot resolve a different pending call. Each of (a)–(f) is necessary; none alone is sufficient.
- **Bridge initialization handshake is a separate state, and the queue must be session-scoped.** WKWebView's bridge loads via a one-shot iframe ping; before that fires, `window.WebViewJavascriptBridge` is undefined. Every page that calls the bridge during mount must either wait on the handshake or queue the call — not assume the bridge is ready. The queue must carry a session/route generation token, must drop entries when the user logs out / navigates / unmounts before the handshake completes, must enforce a maximum queue depth and TTL, and must explicitly re-prompt the user for privileged calls (payment, secure storage write, biometric auth) rather than auto-replaying them. A bridge queue that fires `purchase` or `writeSecureStorage` after a logout/navigation is a real incident class, not a theoretical one.
- **Two-side codegen beats handwriting — and codegen alone is not version negotiation.** When a portfolio has more than one bridge handler and more than one platform, hand-rolling each native handler + each H5 caller is anti-pattern. Generate from a shared IDL (TypeScript types, protobuf, JSON Schema, or framework-specific) so the contract cannot drift unobserved. The IDL must also carry a version number: H5 is updated from CDN/route at any time, native apps update at store cadence, so the H5 caller routinely runs against an older native handler set. Encode min/max compatible bridge versions on both sides, capability-probe the native version on handshake, and degrade gracefully when a method or field the H5 expects is unavailable. A capability map that is only updated when the H5 ships, never when native ships, will go stale silently.
- **Cross-platform storage is three abstractions.** Native Android key-value, native iOS key-value, and H5 `localStorage` / IndexedDB / framework persistence stores are not interchangeable. If the same business value must round-trip across all three, define one canonical encoding and one ownership rule (which side writes the source of truth) before code lands.

## Native ↔ H5 Data Channel Decision Rule

When choosing whether business data flows over native bridge or over HTTP, follow this rule. Native-exclusive capability goes through the bridge; everything else stays on HTTP.

- **Bridge channel is for native-exclusive capability**: camera, secure storage, biometric auth, file system, deep link consumption, lifecycle events, native UI dialogs, background tasks, in-app updates, share/permission sheets. The bridge is the only path to these — and they are the only things that justify the bridge cost.
- **Payment is not a single bucket — split by authority, not by surface.** Decide per payment phase, with the authority always sitting on the side that owns the secret, the contract, or the truth:
  - **Server-owned**: payment intent creation (the intent ID and secret are minted server-side), PSP webhook reception and verification, receipt verification against the PSP/store, entitlement grant (the source-of-truth flip that says "this user now has X"). These never live on the client — neither native nor H5. The mobile app receives results, it does not produce them.
  - **Native-owned (via bridge)**: opening the native pay sheet (Apple Pay / Google Pay / PSP pay sheet) so card data never enters the merchant app; in-app purchase / store-policy-bound subscription confirmation (App Store IAP, Google Play Billing); SDK confirmation callbacks where the SDK requires a native context; 3DS / SCA challenge surfaces that must render in a native webview controlled by the PSP. The bridge surfaces these to H5 as opaque "ask native to take payment, here's the result token" calls — never as raw card data.
  - **H5-owned (via HTTP)**: payment metadata UI only — order history, invoice list, billing settings labels, statement download, refund request submission (which goes to server, not the PSP directly), payment-method labels (not card data). The H5 caller never sees an intent secret, a card number, or a webhook payload.
  - **Either side, but pick one and own it**: payment status polling (UI display) and receipt reconciliation rendering can sit on either side, but cannot sit on both — pick the owner, document it, and have the other side read through that owner.
  - PCI scope, store policy, regulator scope, and PSP contract take precedence over what is convenient. PCI scope reduction depends on whether card data ever touches the merchant-controlled app: a native pay sheet that hands the merchant a token (rather than a PAN) typically reduces scope to SAQ-A class, but this MUST be confirmed against the specific PSP contract, store policy, and regulator before relying on it — none of this rule can be a substitute for the PCI/store/regulator review.
- **HTTP channel is for business data**: reports, analytics, user profile, content lists, comments, settings, search results, **plus the payment metadata listed above**. H5 is a capable HTTP client and the native side does not need to be on this path. Routing business data through the bridge to use native auth headers, native HTTP stack, or native caching is almost always premature optimisation that costs more in contract surface than it saves in network.
- **Hybrid is fine, mixed-channel is not**: a feature where the photo comes from native (bridge) and the AI analysis comes from server (HTTP) is healthy hybrid. A feature where some of the report data is bridged from a cached native blob and the rest is fetched from server is mixed-channel — the H5 caller has to reconcile two sources, and the cache invalidation story is not actually free.
- **The bridge contract should shrink over time, not grow.** When a capability moves from "native-only" to "available in browser" (new web API ships, framework adds a JS shim), the bridge handler retires. A bridge surface that only grows is a smell.
- **Failure isolation**: a native bridge failure should not blank the entire H5 surface. Wrap every bridge call with timeout + fallback + explicit user-facing state, so a stuck native side does not stall the page.
