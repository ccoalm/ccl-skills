# 会话视角泄漏（session-vantage leakage）

agent 写进**持久文档**（README、设计/架构文档、注释与 docstring、决策记录、技能文本、交付报告）的一类废话：句子的立足点是**写作时的那次会话**，而不是仓库/文档本身——它引用只有那次会话看得见的东西，叙述"改了什么"而不是"现在是什么"，或在跟一个已经离场的评审者辩论。这些句子在 HEAD 处的读者眼里要么解析不了，要么是噪音。它是 tighten-doc DELETE #1（元语自证）的近亲，但形态更隐蔽：内容像在传递信息，实际传递的是作者的工作过程。

## 唯一判据

对每个可疑句问：**一个只有 HEAD 处仓库/文档、没有任何会话记录、PR 讨论串或未提交草稿的读者，能否解析这句里的每个引用、核验其中每个断言？**

- 不能 → 先把句中**仍然为真的事实**改写成能独立站住的现在时陈述，再删掉围绕它的过程叙述；只有一个事实都不含的句子（审计编号、控制流复述）才整句删。
- 能 → 不算泄漏，哪怕它听起来"有历史感"。但在**现状类**页面（README、文档、docstring）里，一段能解析的"变更故事"仍是变更叙事——按第 3 类处理，搬到它的家（commit / PR / 决策记录 / postmortem）。

## 分类（8 类）

1. **死的设计会话引用**：`(decision 7)`、`(audit C2)`、`design §4.7`、`plan §1.4`、阶段代号（`T4` / `W3` / `P-I`）、"the design ledger"、"(B ruling)"。有已提交的 owner 就按名字+路径引用；没有就删引用、把它的事实句改写成能独立站住的话。
2. **stack / PR 视角**："a later PR in this stack"、"this PR adds"、"the previous commit"、"上一个 MR"。写已交付的机制或扩展点；未完成的工作进 `TODO` 标记或 issue 引用。
3. **变更叙事与指示性时间戳**："used to"、"no longer"、"the old X"、"以前 / 现在 / 不再"，以及在**现状类页面**里无锚点、只在写作那一刻有意义的指代（"this cut"、"本次改动"、"today"、与过去对比的"now"）——同样措辞出现在已点明版本/事故的变更史体裁里不算。写现在的行为；一个已修复的回归写成**现在时反事实**（"没有 X 时会 Y"），不写仓库史（"以前会 Y"）。**稳定的版本标识不在此列**：API / schema / 协议 / 产品版本号（`v1` 端点、`apiVersion: v2`、wire 版本、包版本）在 HEAD 可解析且决定客户端该用哪份契约——它们是现状事实，必须保留；本类删的是**把版本当叙事**的用法（"v1 时我们是这么做的，现在改了"）。
4. **评审编排**："Rejected in review:"、"the reviewer confirmed"、草稿序号（"v5 of this note"）、轮次归因（"r3 accepted"）。留下决定与理由本身，删掉"谁在什么时候说的"。
5. **对评审者辩护的注释**："the cast is safe — it simply…"、"this is correct because…"、"这里不会越界，因为…"。一条为自己正确性辩护的注释面向的是评审者，不是维护者：写出让代码安全的那个不变量；代码自己已能说明的就删。
6. **复述与推导流水账**：控制流叙述（"first we X, then we Y"）、测试走查、显然分支的证明。删；只保留非显然的契约或不变量。
7. **hedge 与规划残留**："probably fine for now"、"should be enough"、没有标记的"以后再说"。升级为 `TODO`/`FIXME` 并写实际界限，或直接写成那个界限；删掉 hedge。
8. **工作语言碎片**：在整体是一种语言的段落里残留另一种工作语言的片段、分隔符（如私有分节线、未翻译的术语），或反向。翻译或删除。

## 同族：现状类页面里的三种"会烂"的写法

第 3 类的推广，用于 README / 架构文档 / 包说明这类**描述现状**的页面（决策记录、postmortem、changelog 除外——变更故事是它们的家）：

- **变更史代替现状**："previously / now / no longer / renamed / was moved"、PR 号、commit、stack 位置。写现在的机制；变更故事放 commit / PR / 决策记录 / postmortem，需要时链过去。
- **实现状态注记**：散文或图里的 "implemented!"、"future: …"、"TODO: 上线后…"。状态会烂；仓库布局与清单文件才是状态的家。要么写成事实，要么变成有 owner 的 `TODO`/issue。
- **强调通胀**：到处加粗、大写、"critically / 务必 / 极其重要"。什么都强调等于什么都不强调——只给**改变行为的那个从句**保留强调。

## 不是泄漏（过矫正陷阱）

无辅助的引用清扫会朝两个方向犯错：删掉了耐久引用，留着死引用。以下必须保留：

- **issue / ticket 引用**：`#1470`、`TODO(name):`、"issue #N owns the follow-up" 在 HEAD 可解析——任何页面都留，不搬家。
- **决策记录与 postmortem 里对已合并 PR / issue 的引用**：这两类文档的家就是变更故事，是被允许的证据引用。
- **抑制说明**：lint-disable 的理由、coverage-ignore 的理由、空 catch 的解释——是必需散文；理由写错要改，不能删。
- **现在时反事实的回归钉**："没有 X 时会 Y"、"一个 naive 的 X 会…"。
- **实测数值**："(measured: 512 nests ≈ 0.15s)" 校准常量——"measured" 这个出处词是承重的。
- **运行时的新旧状态**："旧连接排空后新连接才接受"是运行时生命周期，不是变更史。
- **决策记录变更故事节里的阶段名**："第一版交付了 X"在该节里是安全的。指示性指代（"this cut" / "本次改动"）在**现状类页面**里禁——那里没有锚点，读者无从知道指的是哪一次；在变更史体裁（决策记录、postmortem、changelog、发布说明）里，只要所在文档或小节已点明它指哪个版本 / 发布 / 事故 / 决定，这就是正常行文，不要删。
- **稳定版本标识**：`v1` 路由前缀、`apiVersion`、schema/wire 版本、包版本、迁移目标版本——现状事实，任何页面都留。
- **按设计就在仓外解析的外部引用**：标准章节号（RFC 9110 §10.1.5）、设计稿的 frame 名——§ 禁令针对未提交内部草稿，不针对外部标准或自持章节编号的已提交文档。
- **项目口吻与体裁形式**："我们"作为项目声音；决策记录的 Alternatives considered 节。

## 修法与顺序

1. 要求明确 scope；不推断为全仓。冻结的历史（归档记录、录制的 fixture / snapshot、被测输出）不动——它们保留原始口吻。
2. 先只读审计：用批量 grep（含隐藏目录）找候选，再**逐条语义判断**——批量模式只是探针不是定义；每一轮人工复核都能找到 grep 漏掉的实例，所以还要读 scope 内最密的散文（模块 docstring、README、决策记录）。
3. 先改 owner 再改派生物：生成的目录/表 → 改源 JSDoc / 模板再重生成；模型可见的字符串 → 措辞即行为，标记为需 snapshot/eval 支撑的改动而不是顺手改词。
4. 删任何一句之前，先枚举这句的全部命题（tighten-doc "保留完整命题"纪律），再核对上面的过矫正陷阱：把义务改成了背书、把假设写成了已交付、删了真事实、丢了出处——都是错误的清扫。
5. 验证：重跑批量探针，只允许上面的例外与本节自身命中；确认剩余引用都能在 HEAD 解析；对触及的面跑相应文档 gate。

## 与本仓其他规则的关系
