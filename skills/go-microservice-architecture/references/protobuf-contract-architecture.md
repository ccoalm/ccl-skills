# Protobuf Contract Architecture

Use this when designing protobuf IDL for HTTP APIs, internal RPC, events, generated clients, or gateway routes.

## Contract Boundary

- Treat `.proto` files as source contracts; generated files are outputs.
- Separate public API contracts from internal RPC contracts when stability or security requirements differ.
- Keep shared envelopes, annotation extensions, and common enums in small dedicated protos; keep resource messages in owning package protos.
- Avoid monolithic service protos; split by capability, ownership, lifecycle, or client stability.
- Design request/response pairs per method unless streaming, batch, or shared shapes are intentionally stable.
- Put pagination, filtering, sorting, and idempotency fields in v1 for list and write APIs that need them.
- Transport metadata such as trace id, auth subject, lane/environment, and service identity should travel via metadata or middleware unless it is part of the contract.

## Package And Import Policy

- Every proto needs `syntax`, `package`, and a language package option such as `go_package`.
- Package names should be stable and independent of repo-local paths.
- Imports should point to source protos, not generated Go packages.
- Custom HTTP/gateway annotations belong in a dedicated annotation proto; normal contracts should import it rather than redefine options.
- `proto2` is acceptable for descriptor extension files; product contracts should use `proto3` unless there is a specific compatibility reason.

## Evolution

- Never reuse field numbers or enum numbers.
- Reserve deleted field numbers and names.
- Prefer additive fields, new methods, and new enum values over semantic changes.
- Do not change the meaning, type, cardinality, or units of an existing field.
- Keep public API messages more stable than internal RPC messages.
- Use explicit versioned messages or methods when compatibility cannot be preserved.
- **Protobuf Edition 2024 (released in protoc 32.x, Q3 2025) is the current evolution baseline** — supersedes the "proto2 vs proto3" syntax dichotomy with the editions model (per `protobuf.dev/editions/overview/`). Key feature changes Edition 2024 introduced over Edition 2023: (a) `string_type` feature default changes from `STRING` to `VIEW` (more efficient string handling at the generated-code layer; verify generated Go output behavior on the migration); (b) `EXPORT_TOP_LEVEL` default ensures top-level symbols are exported and nested symbols are local by default, with explicit `export` / `local` keywords for annotation — this is a visibility model previously not available in proto syntax; (c) `import option` syntax imports only custom options from a `.proto` file without pulling in other symbols, reducing dependency graph noise. Migration strategy: do NOT mass-migrate existing proto2/proto3 files to Edition 2024 in one commit — convert per file as that file is touched for other reasons, run `buf breaking` against every conversion, and verify each generated language target (Go via protobuf-go, plus any other consumer language) re-renders identically. Buf supports Editions 2024 in current buf-cli (v1.x as of writing); BSR-managed plugins continue updating per the BSR release notes — pin specific plugin versions in `buf.gen.yaml` so a managed-plugin auto-bump doesn't silently change generated code. Edition 2024 does NOT change the wire format — old binaries can still parse messages from Edition 2024 sources; the changes are at the IDL syntax + generated-code-shape layer.

## Message Modeling

- Leave numeric gaps for expected growth.
- Group field numbers by purpose only when it improves readability; do not depend on order semantically.
- Use nested messages only for substructures that are scoped to a parent and unlikely to be reused.
- Use `optional` when zero/empty and absent have different meanings.
- Use `repeated` for collections; define ordering, max size, and dedupe rules in comments or validation.
- Use `map` only for open-ended key/value metadata; use repeated typed entries when keys or values need validation or evolution.
- Use `oneof` for mutually exclusive payloads and document unknown or empty behavior.

## Enum And Status Policy

- The zero enum value should be `UNKNOWN` or `UNSPECIFIED`.
- Prefix enum values consistently to avoid generated-name collisions.
- Status enums should include initial, in-progress, terminal success, terminal failure, and cancellation states only when the workflow needs them.
- New enum values must be tolerated by old clients; clients should handle unknown values safely.
- A protobuf enum is a transport contract, not automatically the domain source of truth. Architecture decides whether generated enum types may be used beyond transport/adapters; if storage, clients, analytics, or existing domain models use another representation, define explicit conversion helpers and a migration plan. Any transport-coupled exception must be traceable through an ADR or an inline usage-site comment formatted `architecture-approval: transport-coupled finite value <scope> <decision-ref> <reason>` where `<decision-ref>` is a full URL or numeric record id such as `ADR-123`; reviewers must confirm the referenced record exists and approves the specific value/scope before approval. A CI check, grep panel, or required review checklist item MUST exist and pass before any PR introducing `architecture-approval:` comments is merged; absence of that check is itself a blocking finding. The first PR that introduces `architecture-approval:` comments must include the enforcement check in the same PR or reference a prior merged check; "will add later" is not approval.
- Shared enum placement is an architecture decision. Put cross-service finite values in the smallest shared IDL or domain/platform package that has real ownership; if none exists, approve a local fallback and track consolidation with `finite-value-debt: <task-ref> <owner> <deadline> <reason>`.

## Error And Envelope Policy

- Use one response envelope or canonical error contract consistently.
- Common code/message fields should not replace typed resource data.
- Shared error code ranges should be governed; local codes should not be added to global enums unless multiple clients depend on them.
- Do not inherit a framework's reserved envelope/base field number as a contract convention. New products should choose an explicit envelope field and document it.
- Keep request metadata minimal. Trace id, lane, caller identity, and auth context should normally be middleware metadata; put them in protobuf messages only when cross-language clients or async payload persistence require a typed contract.

## Streaming And Surface-Shape Validation

These tier/streaming/shape rules are cross-stack; the mirror lives in `python-service-architecture/references/api-contract-and-schema.md` (Contract Tiers, Streaming, And Shape Validation) — keep both in sync.

- **A server-streaming RPC's streamed message is a separate shape decision — not automatically the unary response envelope.** A per-item business envelope (SSE / NDJSON / SDK-compatible styles do this) or a discriminated event stream both work; just don't force the unary request/response envelope by default. Define completion and error semantics explicitly, and decide whether termination/errors travel in-band or via transport status/trailers (gRPC). For a fatal terminal error on a transport that can still signal it (e.g. gRPC trailers), surface a non-success status so monitoring/retry/circuit-breaking aren't misled; where the status header is already committed (SSE / NDJSON after a 200), carry the error in-band and ensure observability classifies it as a failure rather than trusting the 200. A stream that already emitted client-visible data or dispatched side effects is not freely retryable, so don't assume the unary retry rule. Per-domain event payloads (e.g. token usage on an inference stream) are that service's contract, not a universal field set. Ensure any envelope-shape check exempts the streamed message rather than misfiring on a `*Response`-style name.
- **Distinct contract tiers are distinct shapes — do not force one envelope across all.** Internal RPC (shared base + typed data), the public HTTP JSON business envelope (per the canonical HTTP-response-envelope contract), streaming events, and **externally-dictated standard protocols** (a provider-compatible API, a webhook spec, an industry wire format) each carry their own shape. An externally-dictated protocol follows that protocol's wire, mapped from the contract source — it is NOT the internal RPC or HTTP envelope. But a compatible wire is **not an exemption from internal controls**: authz, tenant isolation, quota, audit, and error-code governance still apply behind it — "we're just being standard-compatible" must not become a bypass. For a surface with no consumer yet, don't default it to another tier's envelope; define its own contract when a consumer or stability requirement appears.
- **Make the conventions machine-checkable and multi-service, scaled to repo maturity.** The contract conventions (per-tier shapes, shared base, naming, base-field placement) belong in an agent-readable spec that a contract health check enforces. The check should iterate every service rather than hardcode one, validate each unary tier's envelope, and exempt streaming events and the shared-base definitions themselves. Scale enforcement to risk — a hard CI gate for production multi-consumer IDL, a lighter check plus recorded gaps for early/migration/prototype repos. A service it cannot yet validate is recorded as a gap with an owner and severity, not silently skipped; a single-service-hardcoded or unary-only check lets agents infer the shape from whatever materialized example they find, which drifts when that example itself diverged.

## IDL Repo Organization

- For portfolios with more than a handful of services, architecture decides whether IDL lives in dedicated repos (one per IDL family — proto, thrift, http-thrift) or inline with business code. Dedicated IDL repos make codegen, breaking-change checks, and multi-language publishing cheaper, but require explicit consumer/publisher contracts and a release cadence.
- Inside one IDL set, organize sources by intent, not by team: a shared tier (`base`) for the canonical error/code enum and reusable structs, a gateway-facing tier (`api`) for contracts that cross the trust boundary, and per-domain tiers (`<domain>`) for internal RPC. The tiering is what makes Code range allocation, schema review, and downstream consumer rules tractable. Within one IDL set, the shared `base` is **defined once and imported** by every service, never redeclared per service within that set (a deliberate compatibility fork with owner, version, and deprecation plan is the documented exception — e.g. an open-source SDK or a cross-trust-domain boundary); a service that diverged unintentionally is recorded as a known divergence with an explicit migration target, not silently tolerated as a parallel convention.
- Reserve numeric Code range explicitly (e.g., `[0, 11999]` in `base.proto`) and sub-allocate per tier so services cannot accidentally collide. Architecture owns the allocation table.
- Multi-language codegen needs an explicit per-language script (Go, Python, TypeScript, etc.) driven by the IDL repo's CI. Architecture decides which languages are canonical (have integration tests) versus generated-only (clients without independent test coverage).
- Breaking-change governance is required for any IDL surface that has more than one consumer team or external clients. `buf breaking`, `kitex check`, or equivalent runs in CI; intentional breaks route through an explicit approval path.

## Runtime IDL Loading For Generic Call

When a service needs to call another service whose IDL is not known at build time — typical use cases: gateways routing to many backends, admin/management consoles that proxy arbitrary service methods, debug/inspection tooling, dynamic test harnesses — the runtime fetches and parses IDL on demand and invokes the target via the framework's generic-call mechanism (Kitex `generic.Call`, gRPC reflection + descriptor pool, Thrift skeleton-less call).

The pattern is real and useful but adds an authority + safety surface beyond static IDL:

- **IDL source authority**: the runtime resolves an IDL fetch through an explicit registry — an IDL repo with a stable URL, a centralized descriptor service, or an internal package index. The IDL source identity is part of the call: a generic call against an IDL fetched from a user-supplied URL is unauthenticated code injection through schema. Reject IDL sources outside the allowlist.
- **Recursive include / import resolution**: thrift `include` and proto `import` chains can pull in dozens of transitive files. The fetcher must (1) follow includes to a documented depth limit (typical 10) — refuse deeper, that is usually a misconfigured loop, (2) **deduplicate by canonical source identity + content digest, not by fully-qualified name alone** — FQN-only dedup hides alias / path loops, descriptor shadowing, and dependency-confusion cases where two sources claim the same FQN with different bodies; the fetcher rejects duplicate FQNs with non-matching digests at parse/link time, (3) record every fetched file's source identity in the call audit log, (4) bound total bytes fetched per resolution so a malicious or buggy IDL cannot exhaust memory.
- **IDL parse cache with version pinning**: the parsed descriptor for `(idl_source, version)` is cached so repeated calls do not re-fetch / re-parse. Cache key includes version; cache invalidation triggers on registry signal, not on TTL alone (a TTL miss while the IDL is in transition picks up a half-published version).
- **Call surface authorization**: generic call is broader than the caller's normal scope. The dispatcher checks (a) caller is allowed to use generic-call at all (most callers are not), (b) caller is allowed to invoke the target service + method, (c) the method is on the target service's published surface (not an internal/admin method exposed accidentally by reflection).
- **Request shape validation on the fly**: since the request is not a compiled type, the dispatcher must validate the request body against the parsed descriptor before forwarding — required-field presence, oneof exclusivity, recursion depth on nested messages, total message size. Enum validation follows proto3 forward-compatibility: unknown enum numeric values are accepted (the backend may have added them in a newer rollout), not rejected; rejecting unknown enum values breaks rolling upgrades where descriptor and backend release independently.
- **Audit per call**: generic call records caller identity, target service, target method, IDL source + version, request id, and outcome. The audit log is the only forensic surface when an attacker pivots through a generic-call gateway.
- **Failure modes worth naming**:
  - **IDL fetch failure for an uncached version** (registry down, network partition, requested version never been fetched): fail closed; never fall back to a stale, default, or sibling-version schema.
  - **IDL fetch failure when a verified pinned descriptor is already cached**: serve from cache, but only while the cached descriptor's revocation-status lease is still valid. Cached descriptors carry a `last_known_not_revoked_at` timestamp refreshed by the registry on each successful poll; serving from cache during a registry outage is allowed up to a documented lease window (typical: minutes to a small number of hours, set by the security policy), after which the dispatcher fails closed even though the descriptor itself is still parsed in memory. A descriptor version whose revocation signal has been received (registry marked the version revoked / disabled, or the lease expired) MUST fail closed immediately and is purged from cache; never serve a known-revoked or lease-expired descriptor. The distinction is "no verified descriptor available for the requested version" (fail closed) vs "verified, not-revoked, lease-valid descriptor for this version is already cached" (serve).
  - **Partial fetch** (some includes resolved, others timed out): reject the whole call; do not invoke with a partial descriptor.
  - **Descriptor version drift between fetch and call**: re-fetch under single-flight; do not mix two descriptor versions in one call chain.

## Runtime Frame Proxy (Generic Call Without Descriptors)

Sibling pattern to Runtime IDL Loading: instead of fetching+parsing descriptors and reconstructing typed calls, the proxy intercepts the raw RPC frame at the unknown-service handler (Kitex `WithGRPCUnknownServiceHandler`, gRPC's `UnknownServiceHandler`, equivalent) and forwards opaque payload bytes to a routed target. The proxy never parses the message body. Use cases: mesh-style routing for arbitrary methods, cross-lane traffic mirroring, blue/green frame replay, debug capture. Distinct trade-offs from descriptor-based proxying:

- **Caller identity comes from authenticated transport context, never from inbound metadata**: the proxy derives caller identity exclusively from the authenticated server context (mTLS client cert, signed session/JWT verified by middleware, SPIFFE id, k8s SA TokenReview) — not from inbound gRPC metadata headers, not from the payload. Any caller-identity-like metadata in the inbound frame (`x-caller-*`, `x-user-*`, claimed `from-service`) is stripped or overwritten with the authenticated value before any logic runs and before forwarding. Trusting metadata-claimed identity lets a caller impersonate an allowed principal and pivot through the proxy.
- **Routing source is an explicit metadata header on the inbound frame**, not the message body: e.g. a `destination-service` header carrying the target PSM/identity. The proxy MUST NOT trust caller-claimed identity embedded inside the payload (it would require parsing the body, which defeats the frame-level design and opens authorization gaps).
- **Routing header is canonicalized and validated BEFORE SD lookup**: reject non-canonical service ids, raw FQDN / IP / URL values (SD must be the only resolver), namespace or lane-escape syntax inside the header, duplicate or multi-value headers, and any value not in the authenticated caller's per-target allowlist. Without pre-SD validation, SD becomes a routing oracle and depending on the resolver implementation can become an internal-SSRF path. Authorization runs AFTER canonical target resolution and on the authenticated caller identity, not the claimed one.
- **Target address resolution goes through the same service-discovery layer as typed clients**: DNS/FQDN construction for in-cluster, explicit timeout. The lane-routing default for a frame proxy is **fail-closed on lane miss**: a request bound for lane `canary` that does not resolve in `canary` is rejected (audit + structured error), NOT silently forwarded to base. Lane fallback is opt-in per route policy and applies only to routes where cross-lane delivery is explicitly safe; the default protects blue/green replay, mirror, debug-capture, and any tenant-scoped lane from silent wrong-recipient delivery. SD lookup empty must fail fast — never retry against a last-known address.
- **Admission control is mandatory in addition to per-stream backpressure**: cap (a) max concurrent proxied streams globally and per route, (b) max inbound frame / message size, (c) per-caller and per-target-service concurrency. "Single goroutine pair, no full-stream buffer" prevents per-stream OOM but does not prevent many-streams OOM or oversized-frame OOM. Excess admission returns a structured `RESOURCE_EXHAUSTED` / 429 and is metered.
- **Context propagation MUST cross all three surfaces** simultaneously: framework `appctx` value (for in-process middleware), outgoing gRPC `metadata` (for the wire), and persistent metainfo (`kitex_metainfo.WithPersistentValue` or equivalent, for in-cluster persistent values that survive through hops). Trace id, lane, tenant, and (authenticated) caller identity must each appear on all three; missing one breaks downstream observability or routing. Test this with end-to-end trace correlation, not by inspecting the proxy alone.
- **Authorization is mandatory at the proxy boundary**: the proxy is broader than a typed client — any caller able to send a frame to the proxy can address any backend reachable from it. Apply (authenticated-caller) × target-service × method allowlist after the routing header is canonicalized, before forwarding. Same posture as Runtime IDL Loading's call-surface authorization. The proxy is a privilege boundary; treat its exposure surface like an API gateway, not like an internal RPC.
- **Payload codec coercion via framework-internal reflection is fragile**: code that reaches into the framework's internal `RPCInfo` / `Stream` types via `reflect.FieldByName(...)` to coerce payload codec or extract the underlying server stream pins the proxy to a specific framework version and breaks on minor upgrades. Acceptable when no public API exists, but: (a) pin the framework version explicitly, (b) document the reflective access in a comment naming the version, (c) add a build-time or startup-time assertion that the expected fields exist, fail closed on absence.
- **Server-stream forwarding preserves backpressure**: the proxy reads from the inbound stream and writes to the outbound stream in a single goroutine pair; do not buffer the entire stream in memory. Close propagation must work both directions (client cancel → upstream cancel; upstream error → client error frame).
- **Observability**: log per-call records {authenticated_caller, target_psm, target_method, route_decision, lane, admission_decision, latency, error}. The proxy is often the only place where cross-service call patterns are visible at this granularity; this log is forensic evidence for routing or auth incidents.
- **Failure modes worth naming**: routing header missing / non-canonical → reject with explicit error (do not silently forward); routing header valid but caller lacks authorization → reject and audit; lane miss without explicit fallback policy → reject and audit (do not fall back to base); SD lookup empty → reject (do not retry against last-known address); admission cap hit → structured exhaustion error, do not queue indefinitely; framework reflective access fails (post-upgrade) → fail closed and alert, do not fall back to typed default that may not exist.

## Front-End Consumer Contract

The HTTP/RPC contract that Go services publish is consumed by front-end clients (React Web, mobile web, mobile-native). The same envelope/header/timeout rules that the server owns appear on the consumer side; architecture documents both sides so they cannot drift independently.

- **Envelope direction**: the response envelope shape the server emits is the same shape every front-end client parses. Mixing HTTP-200-always with HTTP-status-as-semantic across services in the same portfolio forces the front-end client to special-case per endpoint; the choice is a portfolio-level architecture decision recorded once. See the consumer-side rules in `web-react-dev/references/web-quality-release.md` (Cross-Stack Contract section) and the server-side decision in `error-contract-architecture.md`.
- **Trace propagation**: the server reads `X-Request-ID` from inbound HTTP requests when present and otherwise generates one; it propagates the request id and the runtime trace id on the response so the front end can surface them in error UI. A server that drops the inbound `X-Request-ID` because middleware did not register the read is a finding — end-to-end correlation depends on this header surviving from client to log line.
- **Auth header contract**: the server agrees with the front end on the auth header name (e.g. `Authorization` or a platform-specific token header), the app-identity header, and any tenant / lane / shadow-traffic headers that the front end injects. The server validates them through middleware once and exposes the result on the request context using a tiered context-keys convention.
- **Timeout layering**: outer caller budget is always longer than inner callee budget. For the path `front-end client → gateway → downstream RPC`, the relationship is `client timeout > gateway timeout > downstream RPC timeout`. A gateway longer than the client lets the client time out before the gateway can return a structured error with the trace id; a gateway shorter than the downstream RPC budget the gateway itself initiates lets the gateway give up while the inner call is still running, leaving the work in an undefined state. Per-endpoint risk tunes the specific values; the ordering is invariant.
- **Client-signed object-storage upload**: when the architecture supports direct front-end → object-storage upload, the server exposes a narrow `signed-token` / `STS` endpoint that returns a short-lived credential plus the upload target (bucket, key prefix, expiry). The credential is scoped, the expiry is short, and the server logs token issuance for audit. The main API path never carries the file body.
- **SDK/codegen for the front end**: when the contract is exposed via OpenAPI / IDL annotation, the front-end TS client is generated from the same IDL the server compiles; architecture owns the generator command and the publishing cadence so the front-end client never lags the server contract by more than one release.
