# Artifact Generation Architecture

Use this when designing generated spreadsheets, PDFs, CSVs, reports, exports, or downloadable files.

## Contract

- Treat generated files as artifacts with owner, type, source query, version, generation time, retention, access control, and size limit.
- Large or slow artifacts should be generated by jobs rather than request handlers.
- Define output formats, templates, fonts/assets, localization, and schema/version compatibility before implementation.
- Generated artifacts must apply the same authorization and resource-scope filters as the underlying read path.
- Decide whether artifacts are regenerated, cached, or immutable after creation.

## Storage

- Prefer object storage for generated files and store only object keys or short-lived signed references in relational records.
- Artifact keys should be deterministic enough for traceability but should not expose private data.
- Define cleanup policy for source files, temporary files, and generated outputs.
- Local filesystem output is acceptable for tests and CLI tools, not server runtime durability.

## Quality Checks

- Validate that generated files open in common clients and preserve expected rows/pages.
- Define behavior for empty datasets, partial data, oversized output, unsupported characters, missing fonts/assets, and upload failure.

## Server-Side Document Rendering

When the artifact is a print-quality document (PDF, image batches, report packets, certificates, structured forms) rendered server-side from rich content (HTML + math + embedded media):

- **Print-vs-design DPI separation is explicit constants AND coordinate-domain-named**: declare `CSS_LAYOUT_PX_PER_INCH` (typical 96, the browser CSS px coordinate space the renderer lays out in), `PDF_POINTS_PER_INCH` (constant 72, the PDF coordinate space points map into), `OUTPUT_RASTER_DPI` (typical 300, the target raster density on final output), and the page dimension constants in mm. Name the coordinate domain on each constant explicitly — `LAYOUT_DPI` vs `PRINT_DPI` alone is the classic footgun: a renderer that computes browser-layout pixels with 72 thinking it's "print dpi" produces a half-size layout before rasterizing at 300 DPI, and the bug only appears on paper. Compute pixel dimensions from these named constants, not hand-tuned literals; document one conversion table for the three coordinate spaces in the renderer.
- **Font embedding is part of the deployment artifact, not "system font"**: for non-ASCII typesetting (CJK, Cyrillic, Devanagari, IPA) the renderer ships the chosen font files (typically variable fonts to avoid weight/width explosion) alongside the binary. Relying on the host OS's font set means tests pass on dev-machines that happen to have the font installed and renders fall back to a glyph-substitution box in production. Architecture names the font set, the license, and the cache-busting strategy for font upgrades.
- **Math / formula typesetting is configured once at the service**, not per-request: server-side MathJax / KaTeX is loaded once at module init with the explicit package set (mhchem, extpfeil, siunitx, unicode, boldsymbol — list only those needed), the explicit macro set (degree, parallel, unit aliases, project-specific shorthand), and inline-vs-display delimiter pairs. Per-request math config is a P1 latency surface: the engine warmup is slow and serializing it across requests serializes the renderer.
- **Batch rendering chunks with per-chunk concurrency**: when the request asks for N items rendered (e.g. 200 question images, a paper sheet with M questions), the handler splits into chunks (typical: low double-digits) and `Promise.all` within the chunk; chunks run sequentially. Naive `Promise.all(allItems.map(render))` peaks heap to N parallel rendering contexts and OOMs the renderer. Naive sequential single-item loops waste cores. The chunk size is a function of the per-render memory cost, not a guessed magic number.
- **Output goes direct to object storage from the renderer**, not via local FS: write the rendered buffer to the configured bucket key in the same handler; emit `{key, format, dimensions, density, quality}` as the response. Local FS as a staging layer fails on container restart and complicates horizontal scale-out. Local FS is acceptable only for unit tests and CLI tools.
- **Credentials for the upload come from the platform credential surface, scoped to the upload operation**: object-storage access uses the platform's STS / role-broker per the full contract in `platform-release-engineering/references/secret-and-config-management.md` Pattern C-adjacent — Cloud Session Token Brokering (caller authn/authz before mint, full credential-scope cache key, refresh-ahead-of-expiry, single-flight refresh, fail-closed on STS failure, per-issuance audit). The renderer's credential is scoped narrowly: `(tenant, bucket, key-prefix, put-only)` — not a broad "renderer can write any bucket" role; a renderer role with broad write surface is a privilege-escalation pivot through any RCE in the renderer. A raw `accessKeyId / accessKeySecret` pair in config is the anti-pattern this replaces. Single static bucket name passed via env is acceptable when the bucket is the same for the whole tenancy; multi-tenant artifacts need a per-tenant bucket / prefix scheme.
- **Missing-config fails closed, not config-or-empty**: `bucket = config.get('TOS_BUCKET') ?? ''` silently uploads to bucket "" (which most SDKs accept as "default" or "first bucket the credential can see") instead of failing fast. Required config is asserted at startup; the renderer refuses to serve traffic when any required value is missing.
- **Snake-case vs camel-case at the consumer boundary** applies ONLY to non-IDL JSON endpoints: when the renderer is exposed via a hand-written controller that returns plain JSON to a FE caller and the contract is snake_case while the service uses camelCase internally, the conversion lives at the controller response. For endpoints that ARE defined by an authoritative IDL (proto / OpenAPI) and consumed via generated clients, the casing comes from the IDL — applying a blanket `snakeDumpResultCase` at the controller desyncs server output from the generated client and is a contract violation (see `http-gateway-architecture.md` Generated HTTP Client Policy and `protobuf-contract-architecture.md` Front-End Consumer Contract). The rule: one casing convention per endpoint surface, decided by whichever side owns the authoritative contract; never apply blanket case-conversion to a generated-client endpoint.
- **Anti-pattern observed**: a hardcoded vendor / bucket URL in the renderer's source (for example, `<project-dev-vendor-bucket-url>/...`) bakes the project's identity into the deployable artifact, leaks the bucket address into anyone who decompiles the binary or reads the source, and breaks every cross-region / cross-tenant deployment. Asset URLs are config inputs, never literals.
