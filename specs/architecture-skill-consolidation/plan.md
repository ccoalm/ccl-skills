# 架构技能合并与效果优化方案

状态：步骤 0、1、2、3a 已实施，步骤 3b 未开始；3a 的基线不支持 3b 原定的领域模型步骤，3b 的范围待重新确定，见 10.5。方案做过一轮独立评审，11 条发现逐条对仓库核实后全部采纳。方案基线 `origin/main` 55c3ce5，2026-11-11；步骤 2 相对方案的调整见第 9 节，步骤 3a 的记录见第 10 节。

**结论：把 `go-microservice-architecture` 和 `python-service-architecture` 合成一个 `software-architecture`，入口直接承载领域建模、共同架构方法和三套后端栈默认值；其它方向靠路由表和已有的 owner-dispatch 闸接入，不新建专题资料，不新增 `typescript-dev`。`feat/product-rd-redesign` 的代码改动废弃，它的调查与试验记录先落到 `main` 再删分支。**

要改善的真实任务结果有三个：架构任务加载的入口文本更少而约束不丢；Node 和跨栈设计有明确的架构 owner；领域模型在设计阶段被写出来并变成可检查的断言。能否改善由第 6 节的对照决定，本文件不预先声称。

## 1. 现状证据

数据的取证方式见第 8 节。

| 观察 | 数据 |
| --- | --- |
| 两个架构入口骨架相同 | 六个二级标题一致，核心流程都是五步；逐行相似度 0.31，19 条长句完全相同；各约 31 KB |
| 重复集中在少数资料 | 12 对同名资料里，3 对受字节一致性闸保护（相似度 0.88–0.92，约 750 行/侧）；5 对中等（0.57–0.75，每个不到 40 行）；4 对基本是不同内容（0.09–0.40） |

| 引用面 | 活跃文件里约 45 个文件引用旧名（技能 26、docs 10、脚本 5 等）；路由题库 159 条里 10 条预期指向旧名 |

`feat/product-rd-redesign` 留下了与本方案直接相关的三条结论（记录在该分支的 `specs/product-rd-redesign/validation.md` 和 `specs/product-rd-usage-audit/proposal.md`）：

1. 把入口文字搬进资料后，行为指标在两个同期对照下都变差，被搬走的文字在试验期一次都没被打开。
2. 往入口里加说明文字，在每组 32 次运行的实验里没有改变行为；确实生效的规则都有 hook、校验器或钉住的测试。
3. 日常试用的样本量区分不出差异（每组需约 200 个有代码编辑的会话），应改用可重复运行的评估套件。

## 2. 设计决定

### 2.1 一个入口，行为相关内容留在入口

`skills/software-architecture/SKILL.md` 由四部分组成，目标不超过 20 KB（两个旧入口合计 62 KB）：

| 部分 | 内容 | 来源 |
| --- | --- | --- |
| 路由 | 何时用、何时不用（局部 DTO 字段、组件临时状态、既定方案内的实现不进入）；涉及其它方向时同时加载哪个 owner | 新写，替代两份 Skill Routing |
| 共同方法 | 领域模型 → 边界与依赖方向 → 契约 → 数据与状态归属 → 质量取舍 → 决定记录，写成逐项走查的清单 | 两份核心流程里的栈无关条目合并，加领域模型一步 |
| 栈默认值 | Go、Python、Node 三段，每段只留真正随栈变化的默认值和前提 | 两份入口的栈相关条目；Node 段来自 `nodejs-service-dev` 现有约束，需补核 |
| 资料索引 | 按主题分组的一张表 | 两份 Reference Loading 合并 |

栈默认值留在入口而不下沉为"按栈必读资料"，依据是第 1 节的结论 1：下沉的文字实际不会被读到。代价是 Go 任务会带上约 5 KB 无关的 Python/Node 默认值，仍比现在的 31 KB 少。

### 2.2 领域模型是共同方法的第一步

触发条件是业务概念、对象关系、持久状态或跨模块规则发生变化；简单模型用字段加规则说明即可，不要求分层或完整 DDD。产出一张小表：概念与所属上下文、关系、状态与合法迁移、不变量、权威数据来源。每条不变量写成可观察结果（例如"相同幂等键重试后只有一个预约"），交 `testing-strategy` 选验证层。业务规则有矛盾时带着技术后果退回需求 owner，架构不自行改写承诺。

只加这段文字不足以改变行为（第 1 节结论 2）。配两处指向：

- 在每次用户输入都会注入的入口路由块里加一行架构去向（架构、服务边界、领域模型 → `software-architecture`）。这个块现在没有架构这一行，它是唯一对所有会话都触发的位置，受注入字节闸约束。
- 在 `product-rd-workflow` 技术设计闸的必备内容里加一项"领域模型（满足触发条件时）"。

两处都仍是文字。owner-dispatch hook 只在仓库提交并启用了自己的配置、且发生了受管的代码编辑时才触发，只做设计的会话不会被它拦到。所以领域模型步骤没有机械保证，是否生效由步骤 3a 的评估判定，评估里要包含只做设计的会话。

### 2.3 其它五个方向不新建专题

前端、客户端、LLM、终端、平台的架构知识继续由现有技能持有。`software-architecture` 入口只放一张七行以内的对照表（决定涉及什么 → 同时加载谁），并在 owner-dispatch 映射里登记为所有栈的架构 owner。不新建专题资料的理由：它们会是第二份真值，而且不会被读。

### 2.4 资料迁移从简

| 资料 | 处理 |
| --- | --- |
| 3 对受闸保护的镜像资料 | 各合成一个文件：共享区域保留一份，后接 Go、Python 两段栈实现。共享区域字节一致由现有闸保证，零丢失可用脚本证明 |
| 其余 9 对同名资料 | 加栈前缀原样迁入（`go-…`、`python-…`），本轮不手工合并 |
| 25 个栈独有资料 | 原样迁入，同名冲突加前缀 |
| Go 依赖方向图 | 迁移前单独修正：图只表达代码依赖，另用一句说明运行时调用方向 |

手工合并中等相似的资料收益低（没人读）而零丢失核对成本高，延后到有读取证据时再做。

### 2.5 让资料被读到

资料不是天然没人读，取决于入口怎么指向它。同一批 780 个会话里（排除维护本仓的会话）：

| 指向方式 | 例子 | 读取 |
| --- | --- | --- |
| 在具体动作点点名一个文件并要求先读，多数还有 hook 在该动作触发 | `worktree-isolation` 的合并收尾资料、`code-review` 的分阶段评审契约、`product-rd-workflow` 的实现入口闸、`tighten-doc` 的会话视角清单 | 单个文件 77–571 次 |
| 入口末尾一张"按情况加载"的目录，二三十项 | 两个架构技能、各栈开发技能 | 整个技能 0–9 个会话 |

`software-architecture` 按第一种方式写指针：

- 共同方法的每一步最多点名一个资料，写成"涉及 X 时，先读 `<文件>` 再给结论"，放在该步骤里，不放在入口末尾。
- 首批只给读了会改变设计结论的资料配这种指针：事件驱动、多租户隔离、数据平台三份合并后的资料，以及数据建模与迁移。
- 其余资料只留在索引里，不承诺会被读。
- 合入后用仓库已有的 `reference-access-census.sh` 统计读取：配了指针的资料若仍无人读，改写指针或把要点并入入口；索引里的资料连续两个统计窗口无人读，列入退役候选，退役前逐个判断是否属于罕见但关键的路径。

这种指针对架构任务是否同样有效尚未验证，读取次数作为步骤 2 之后的观测指标，不作为合入条件。

### 2.6 随合并退役或改写的机制

- `check-parallel-stack-parity.sh`、它的测试、`check-ccl-skills.sh` 里的调用、`test_check_ccl_regressions.sh` 里对该测试的登记：镜像资料变成单文件后失去对象，同批删除。
- 三份镜像资料尾部各有一段可执行的"Mirrored-section grep gate"，按"共享区域里不得出现本栈专有词"检查。合成单文件后改写为只扫共享区域（从起始标记到第一个栈小节之前），否则任一栈的小节都会让另一栈的检查误报。
- `source-register.md` 里有 14 处定位符指向两个旧技能目录或一致性闸脚本，`register-firing-path-resolution.rb` 会检查整本账并要求原文件存在。只追加新行不够：需要给该脚本加一个经测试的"文件已迁移到新路径"的解析方式，并显式登记一致性闸命令的退役。这是步骤 2 里唯一要改闸逻辑的地方，单独做先红后绿的测试。
- 改 10 条题库预期会触发 `test_frozen_case_sanctity.sh`：每条要在 `source-register.md` 追加一行 `case-rescoped: <id>` 并写明理由。本地必须带 `CCL_SKILL_BASE_REF` 跑，否则该检查只会跳过而 CI 会拒绝。
- `parallel-stack-references-pattern.md`：模式本身仍适用于其它栈对，保留；把举例从这两个架构技能换成中性示例，并补一种形态：调用方不按栈进入时，用一个文件承载共享正文加各栈小节，不再需要一致性闸。
- "Node 无架构同级入口"的条款（`product-rd-workflow`、`defect-diagnosis`、`llm-inference-integration`，以及 `nodejs-service-dev` 的 `description` 和正文）和 `test_routing_pointer_integrity.sh` 的对应断言：改为指向 `software-architecture`，断言同批更新，不能只删。题库里已有的 `route-nodejs-architecture-not-go-python` 问的正是 Node 架构、预期是 `product-rd-workflow`，要改预期并登记 `case-rescoped`，不能另加一条相互矛盾的新题。
- `impact-chain-gate.rb` 按 `-architecture/SKILL.md` 后缀选择上游 owner，新名字自动命中，无需改列表。

## 5. 交付顺序

每一步是一个可独立评审的 PR，目标分支 `main`；回退顺序见第 7 节。

| 步骤 | 内容 | 出口 |
| --- | --- | --- |
| 0 | 把 redesign 记录落 `main`，删分支和工作树 | 记录可在 `main` 读到；分支不存在 |
| 1 | 修 Go 依赖方向图 | 图与正文一致；独立评审与挑战通过 |
| 2 | 建 `software-architecture`、迁资料、删两个旧技能、改全部活跃引用、退役一致性闸、改路由题库 | 零丢失映射完整；`make test`、heavy 回归、公共文本检查、评审证据检查全绿；路由静态分析无阻断项 |
| 3a | 建架构任务的行为评估：任务集、评分器、阴性对照、重复次数和通过线，先在 `main` 上跑出基线 | 评估能区分"写了不变量"和"没写"的两份人工样例；基线已记录 |
| 3b | 领域模型步骤与入口路由行、Node 栈默认值 | 3a 的对照有改善才合入；不达标则收窄或撤回这一步，步骤 2 不受影响 |

步骤 2 是纯组织变更，要求专业规则语义等价；步骤 3 是新增行为。分开是为了让对照结果能归因。

先验证的两个假设（答案会改变方案，在步骤 2 动手前确认）：

1. 新入口在约 20 KB 时能通过入口体量闸；新增面超预算是直接阻断，没有豁免。若不能，先把栈默认值压到能过，仍不够再改为"核心入口加栈默认值资料"并接受读取风险。
2. 一条不超过 800 字符的 `description` 能覆盖 Go、Python、Node 和通用架构触发词而不丢现有 10 条题库用例。若不能，优先保留现有用例覆盖的触发词，其余放正文入口判定。

## 6. 验证

| 层 | 检查 | 阶段 |
| --- | --- | --- |
| 零丢失 | 两个旧入口逐条义务映射到新入口或资料的位置；被钉住的短语逐条跟随。3 对镜像资料按整文件核对：起始标记之前的前言（含脱敏边界说明）、共享区域、各栈小节、待办清单逐段对应。原样迁入的资料用改名前后的内容哈希核对 | 步骤 2，本地 |
| 路由 | `make eval-routing` 无阻断；题库 11 条改预期后通过并带 `CCL_SKILL_BASE_REF` 过改判检查；新增三类题：跨栈领域模型、局部 DTO 改动（不应进入）、既有链路补 trace（不应进入） | 步骤 2，本地 |
| 仓库闸 | `make test`、`test_check_ccl_regressions.sh --heavy-only`、`check-public-sanitization.py`、fetch 目标分支后的 `check_review_evidence_present.py`、`shared_git_surface_gate.py` | 每步，本地；CI 另验 |
| 评审 | 每个 PR 一次独立评审加一次对抗挑战，挑战后的改动做一次增量复查 | 每步 |

## 7. 风险与回退

| 风险 | 应对 |
| --- | --- |
| 单一入口对某一栈触发变弱 | 题库保留全部现有用例并补 Node；路由退化则步骤 2 不合入 |
| 栈默认值压缩时丢约束 | 零丢失映射逐条核对；压不下去的条目进资料并在映射里标明"已下沉"，对照里专门测这些条目 |

回退按依赖逆序：步骤 3b 改了新入口和上游清单，要先回退 3b 才能回退步骤 2，否则会出现修改与删除冲突或新旧两代入口并存。步骤 2 回退即恢复两个旧技能、一致性闸和安装脚本的旧行为，回退后同样回读宿主目录。步骤 3a 的评估、步骤 1 的知识修正与步骤 0 的记录不随之回退。

## 10. 步骤 3a 实施记录

基线 `origin/main` b2a6fa3。本步只新增评估，不改任何技能文本，所以不改变 agent 的行为。

### 10.1 评估由什么组成

| 部分 | 位置 | 作用 |
| --- | --- | --- |
| 六个设计任务 | `eval/paired-tasks/arch-design-*.json` | 每个任务给一份需求和一个最小的服务骨架，要求只出设计、写到 `docs/design.md`。由现有的配对评测工具运行，它只检查设计文档存在 |
| 评分表 | `eval/design-rubrics/<任务>.json` | 列出该任务的业务不变量、栈约束和依赖方向，共三类评分项 |
| 已知答案样例 | `eval/design-rubrics/<任务>.*.md` | 每个评分表配 2 到 3 份人工写的设计：全写且给出机制、只陈述规则不给机制、只列接口和表、只把话题列为风险 |
| 判分器 | `eval/design-judge.py` | 运行结束后读取保存下来的运行。改了任务建好的文件、或在 `docs/` 之外新增了文件的运行先剔除；其余的按评分表逐项判定「已陈述」和「已对应到机制或检查」 |

六个任务分两档。四个「显式」任务的需求直接写出业务规则：Go 和 Python 各做一次同一份部分退款需求、Go 的会议室预约、Node.js/TypeScript 的通知服务拆分。两个「隐式」任务的需求只列功能，规则要自己推出来：Python 的退款和 Go 的预约。加隐式一档的原因见 10.5。

评分项和第 6 节的判据对应：不变量是否写出并对应到检查、栈约束遗漏数、依赖方向是否写明、加载字节。依赖方向这一项只判文档有没有写明方向，不判设计里有没有方向错误的依赖，后者本评估测不了。

### 10.2 判分器为什么可信，以及它不能说明什么

判分靠语言模型读自由文本，所以判分器自己要先被证明能分辨好坏。做法有三条：

1. 每个肯定判定必须附一句原文引用，引用在文档里找不到就改判为否。
2. 每份文档问 3 次，取多数。
3. 先在已知答案样例上校准：只有判分器在该评分表的全部样例上都复现了预期判定的评分项才计入结果，未通过的项从所有数字里剔除并在报告里列出。评分项、样例、提示词、解析和表决的代码、判分模型或投票数任何一个变了，之前的校准和判分全部作废；调用模型、缓存和出报告的代码不在其内。

校准结果：六个评分表共 42 个评分项，全部通过。这满足第 5 节的出口条件，即评估能区分「写了不变量」和「没写」的人工样例。其中「只陈述规则不给机制」和「只把话题列为风险」两类样例也被正确区分。

首次校准时有一项不一致，原因在样例而不在判分器：通知任务的「只列接口和表」样例写了「订单服务通过消息队列把事件发给它」，这句话本身就意味着异步交接，判分器判为已陈述是合理的。样例改成同步调用后通过，判分器没有改。

确定性部分有 43 条单元测试，不调用模型。对判分器的 35 处保护逐个做了删除或放宽的变异，每个变异都让测试转红。

这套评估不能说明的事写在 `eval/design-judge.py` 文件头。最要紧的三条：它不是设计质量分；校准只覆盖那十几份样例，换一种写法的文档可能判错；判分模型和被测模型同属一个家族，两者一致不算独立证据。

### 10.3 运行条件

被测 agent 和判分器都用 `claude-opus-5-5`，被测 agent 用 CLI 默认 effort，每个任务每个臂 5 个样本，判分 3 票。基线两个臂：`off`（不加载插件）和 `base`（加载 `origin/main` b2a6fa3 的插件）。运行输出在仓库之外的私有目录，不入库。

评分表和样例在仓库里，带插件的臂导出的插件目录也会包含它们。工具输入里出现这些路径的运行按污染剔除；本次基线的 `base` 臂导出自尚未包含这些文件的提交，不存在这个问题，步骤 3b 的候选臂会有。

### 10.4 基线结果

60 次运行里 57 次有效。无效的 3 次都在隐式任务的 `base` 臂，由配对评测工具按自己的隔离规则判定：2 次注入的路由块和导出不一致，1 次读到了工作区的指令文件。判分只计有效运行。表中分母是该项在有效运行里出现的次数。

| 评分项 | `off` | `base` |
| --- | --- | --- |
| 不变量已陈述且对应到机制或检查 | 118/120 | 105/109 |
| 一次运行里全部不变量都做到 | 28/30 | 23/27 |
| 依赖方向写明 | 0/30 | 3/27 |
| Go：外部调用带截止时间，经 `context.Context` 传递 | 0/15 | 2/13 |
| Go：存储访问在 DAL 边界之后，依赖注入 | 14/15 | 9/13 |
| Node.js：边界上做运行时 schema 校验 | 1/5 | 5/5 |
| Node.js：出站调用有超时和并发上限 | 5/5 | 5/5 |
| Python：阻塞工作不进 async 请求路径 | 8/10 | 9/9 |
| Python：客户端在启动时装配，导入时无网络访问 | 0/10 | 1/9 |
| 每次运行的成本，各任务中位数 | 0.30 至 0.36 美元 | 0.88 至 1.19 美元 |
| 加载的技能文本，各任务中位数 | 0 | 100,135 至 146,877 字节 |

没做到的不变量只有两项：预约任务的「提醒至多一次」（`off` 3/5，`base` 2/5）和通知任务的「偏好只有一个写入方」（`base` 4/5）。两个隐式任务的不变量在两个臂都是全部做到。

`base` 臂的 27 次有效运行里，15 次调用了 `software-architecture`，25 次调用了 `product-rd-workflow`。

### 10.5 这些结果说明什么

1. **不变量这一项没有改善空间。** 不加载任何插件时已经做到 118/120，需求不写规则的两个任务也全部做到。加隐式一档就是为了排除「需求把答案写出来了」这个解释，结果相同。抽查了一份 `off` 臂隐式退款任务的文档原文：它自己写出了退款总额上限，并给了订单行锁加汇总校验、幂等键唯一索引和终态条件更新。所以第 5 节步骤 3b 的「领域模型步骤」在这个模型和这类任务上测不出收益，按第 7 节「领域模型步骤没有改变行为」的应对，不应照原样实施。
2. **插件的可见收益在栈约束上，而且只在一部分上。** Node.js 运行时校验从 1/5 到 5/5；两个 Python 任务里写明依赖方向的从 0/10 到 3/9（显式任务 3/5，隐式任务 0/4）。Go 的截止时间、Python 的启动装配和依赖方向这三项，加载插件后仍然很少被写出来。
3. **`base` 臂的不变量数字略低于 `off`（105/109 对 118/120），差在上面那两项。** 每臂每任务只有 3 到 5 个样本，这个差距不足以说插件让它变差，只能说没有让它变好。
4. **成本约为 3 倍。** 每次设计会话多加载 10 万字节以上的技能文本，而架构技能自己只在 27 次里被调用了 15 次。

据此，步骤 3b 若继续做，值得测的是两件事：让架构类请求稳定加载 `software-architecture`；把三条很少被写出的栈约束提到入口里能被读到的位置。这改变了第 5 节对 3b 的定义，需要先确定范围再动手。

### 10.6 步骤 3b 的预登记

下面的条件在看到任何 3b 候选之前写下。起草时已经知道本节的基线，所以它们约束的是候选，不是基线。

- 运行条件同 10.3，臂为 `base`（当时的 `main`）和 `candidate`（3b 分支），六个任务全跑。
- 候选臂的导出包含评分表，按 10.3 的规则剔除污染的运行，并在结果里报告剔除数。
- 判定只用校准通过的评分项。评分表或样例有任何改动，先重新校准并重跑 `base`。
- 通过线：3b 声称要改善的每个评分项，`candidate` 做到的次数比 `base` 至少多 2，且分母不小于 4；同时没有任何评分项比 `base` 少 2 次或更多；加载字节的中位数不高于 `base`。
- 不变量各项在基线已接近满分，不能作为 3b 的收益依据，只用作不退化的检查。
- 达不到通过线就收窄或撤回，不靠增加入口文字补救。每臂 5 个样本只能分辨大的差异，结果按这个限度表述。
