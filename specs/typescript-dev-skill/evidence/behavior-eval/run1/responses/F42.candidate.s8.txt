# TS 大仓库打开 `strict` + `noUncheckedIndexedAccess`：一周迁移方案

这是方案，没有在你的仓库里跑过。下面的命令和数字都要以你们实测为准。

## 先说结论

3000 多个错误，一周内用改代码的方式真正改完是有可能的，但前提是 6 到 8 个人并行，而且不能靠加 `!` 或 `as` 糊过去。我建议把"打开"分成两个承诺：

1. **第 1 天：两个开关在主 tsconfig 里全局打开，CI 开始卡新错误。** 新代码和新文件从当天起必须完全符合 strict。旧错误记进一份基线文件。基线只能变少，不能变多。
2. **第 2 到 7 天：按错误类型分人清基线，目标是清零后删掉基线机制。** 到第 7 天还没清完的部分，每一条都要有负责人和截止日期，不能一直挂着。

不要用批量插入 `// @ts-ignore`（或批量插 `@ts-expect-error`）的方式来"打开"。那样一周后错误只是看不见了，问题还在。

## Day 0（半天）：盘点和测量

先弄清楚现在的检查链路：
- `npx tsc -v` 看编译器版本。再列出所有依赖编译器 API 的工具：typescript-eslint、vue-tsc 之类、测试框架里的类型检查。
- 列出所有 `tsconfig*.json`，以及它们的 `extends`、`references` 关系。确认 CI 里跑的类型检查是否覆盖了全部 tsconfig，包括测试、脚本和配置文件。只查 `src/` 的话，测试代码就没人检查。
- 确认到底是谁在做类型检查。Vite、esbuild、SWC、Babel 编译通过不代表类型通过。如果 CI 里没有 `tsc --noEmit` 或 `tsc -b`，要先补上这一步。

然后分开测量两个开关各自引入多少错误：

```bash
# 每个 tsconfig 都跑一遍；分两次测：
npx tsc -p tsconfig.json --noEmit --pretty false --strict                              > strict.out
npx tsc -p tsconfig.json --noEmit --pretty false --strict --noUncheckedIndexedAccess   > all.out
```

把输出按"目录 × 错误码"统计。常见错误码：TS7006/7031 是隐式 any，TS2531/2532/18047/18048 是可能为 null 或 undefined，TS2564 是属性没有初始化，TS18046 是 catch 变量为 unknown。`noUncheckedIndexedAccess` 引入的错误单独统计（两次结果的差集）。

**验证**：
- 两种测法的总数和你们说的"三千多"对得上。
- 每个 tsconfig 都有自己的统计结果。
- 找出被很多处引用的共享类型或工具函数。一个签名修对，往往能消掉几百个下游错误，这类要排在最前面改。

## Day 1：全局打开 + 只减不增的基线门禁

**1. 改配置。** 在根 tsconfig 写明 `"strict": true, "noUncheckedIndexedAccess": true`。不要依赖编译器默认值：TS 6.0 起默认就开 strict，写明了可以避免升级时出现意外。不要用 `skipLibCheck` 去盖住第一方 `.d.ts` 里的错误。

**2. 生成基线并接入 CI。** 解析 `tsc --pretty false` 的输出，以 `文件 + 错误码 + 去掉行号的消息` 作为键，记录每个键出现的次数，写进 `strict-baseline.json` 并提交。不用行号做键，是因为行号一改代码就变。CI 脚本的规则如下：
- 出现基线里没有的键，或某个键的次数增加：**失败**。
- 新增文件里有任何错误：**失败**。
- 实际错误比基线少，但基线文件没有同步更新：**失败**，要求把基线一起改小。这样基线只会单向下降。
- 不想自己写脚本的话，可以用 betterer。按文件逐步打开的方式也可以考虑 `typescript-strict-plugin`。

**3. 防止"假修"。** 把 `@typescript-eslint/no-non-null-assertion` 设成 error，对断言 `as` 也加类似的限制。保证错误数是靠收窄类型降下来的，而不是靠 `!` 换来的。确实需要的地方，用 `// @ts-expect-error <原因>` 并逐条说明。

**Day 1 的验证**：

| 检查项 | 怎么验证 |
|---|---|
| 门禁真的能卡住新错误 | 在测试分支里故意写一个 `arr[0].x`，CI 必须失败 |
| 基线只能变小 | 修掉一个基线里的错误但不更新基线文件，CI 必须失败 |
| 覆盖完整 | 每个 tsconfig 都在门禁里，CI 日志能看到逐个执行 |
| 产物没有变化 | 改配置前后各构建一次，对比产物，应该完全一致。strict 系列基本只影响类型检查；唯一会改变输出的是 `alwaysStrict`，它会给非模块文件加 `"use strict"`。如果产物有差异，逐个排查原因 |
| 测试正常 | 单测和 E2E 结果和改动前一致 |

## Day 2–6：按类型分人清基线

**改的顺序**：先改共享类型和公共工具函数，再改叶子模块。同一个目录尽量交给同一个人，减少冲突。每个 PR 只处理一类错误，或者一个目录，方便评审。

各类错误的改法：
- **隐式 any（TS7006/7031）**：补上真实的类型。不要写 `any`。实在不知道类型的，用 `unknown` 再收窄。
- **可能为 null/undefined**：用提前 return、条件判断或者直接改类型，让这个值不可能为空。默认值（`?? x`）会改变运行时行为，要单独标出来，由评审确认。
- **`noUncheckedIndexedAccess`**：
  - 按下标遍历的循环改成 `for...of`。
  - `arr[0]` 改成先检查长度或解构后判断。
  - `Record<string, T>` 的查找改成 `Map` 或 `in` 检查。
  - 定长的元组本身不受这个开关影响。如果某个数组长度本来就固定，把类型改成元组。
- **属性未初始化（TS2564）**：在构造函数里初始化。只有当框架负责注入值时（比如装饰器注入），才用 `!:`，并写注释说明原因。
- **catch 变量为 unknown（TS18046）**：用 `err instanceof Error` 收窄，不要写 `as Error`。

**把 PR 分成两类，验证强度不同**：
- **纯类型改动**（只改类型标注，没有可执行代码变化）：跑 tsc 全部配置、typed lint、单测、构建，并确认基线变小了。
- **会改变运行时行为的改动**（新增分支、默认值、提前 return 等）：除上面这些外，还要补针对这段逻辑的单测，覆盖为空和越界的情况；评审时要专门确认行为变化是有意的。

**每天的验证**：
- 看板上更新基线剩余条数（按目录、按错误码），以及代码里 `!` 和 `as` 的总数。后者不应该上升。
- 主干每天跑一次完整回归，包括 E2E。

**第 5 天做一次判断**：如果剩余条数按目前速度到第 7 天清不完，剩下的每一条都指定负责人和截止日期，基线机制继续保留。不要为了按时完成而转成批量 suppress。

## Day 7：收尾

1. 基线清零后，删除基线脚本和配置，CI 只保留普通的 `tsc --noEmit` / `tsc -b`，有任何错误就失败。
2. 如果是 monorepo，确认所有子 tsconfig 都继承这两个开关，没有哪个子项目单独关掉。
3. 上线：会改变运行时行为的修复要灰度或分批发布。观察前端错误监控（比如 Sentry），重点看 `Cannot read properties of undefined` 一类的报错，以及新出现的错误类型。正常情况下前者应该下降；出现新的错误类型，通常说明某处修复改变了行为。

## 主要风险

- **"修类型"其实改了行为**：主要来自默认值和提前 return。靠上面的 PR 分类、单测和灰度来控制。
- **用 `!` 刷数字**：靠 lint 规则和 `!`/`as` 数量指标兜底。
- **CI 变慢**：typed lint 要分析整个项目，会慢一些。可以用 `tsc -b` 增量构建，并利用 CI 缓存。
- **IDE 里旧文件大量报红**：属于预期现象，在团队里提前说明。
