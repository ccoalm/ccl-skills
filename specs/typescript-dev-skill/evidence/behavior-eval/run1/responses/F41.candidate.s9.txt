## 结论

继续用 tsc，编译两次：
- **ESM 版**：`module: nodenext`，输出到 `dist/esm`
- **CJS 版**：`module: commonjs`，输出到 `dist/cjs`，并在 `dist/cjs` 里放一个 `{"type":"commonjs"}` 的 `package.json`

两套 `.d.ts` 各放在自己目录里，`exports` 按 `import` 和 `require` 分别指过去，两边就能拿到各自正确的类型。

现在的 `moduleResolution: bundler` 不适合直接发布的库。它假定用户一定有打包器来解析不带扩展名的导入，但 Node 直接加载产物时会找不到文件。

## 1. 源码要改的地方

- **相对导入补上 `.js` 扩展名**。比如 `import { x } from './utils'` 改成 `'./utils.js'`，导入目录要写成 `'./utils/index.js'`。`nodenext` 会报出所有漏掉的地方，按报错逐个改就行。
- **公开 API 只用具名导出，不用 `export default`**。否则 CJS 用户要写 `require('pkg').default`。
- **不要用 `import.meta` 和顶层 await**。它们在 CJS 版里没法编译，会直接报错。

## 2. tsconfig 拆成三个

`tsconfig.json`：基础配置，编辑器和类型检查都用它。

```jsonc
{
  "compilerOptions": {
    "target": "es2022",
    "module": "nodenext",
    "moduleResolution": "nodenext",
    "strict": true,
    "declaration": true,
    "declarationMap": true,
    "sourceMap": true,
    "rootDir": "src",
    "outDir": "dist/esm",
    "skipLibCheck": true
    // 不要开 verbatimModuleSyntax：开了以后 CJS 版不允许 ESM 导入语法
  },
  "include": ["src"],
  "exclude": ["src/**/*.test.ts"]
}
```

`tsconfig.esm.json`：

```jsonc
{ "extends": "./tsconfig.json", "compilerOptions": { "outDir": "dist/esm" } }
```

`tsconfig.cjs.json`：

```jsonc
{
  "extends": "./tsconfig.json",
  "compilerOptions": {
    "outDir": "dist/cjs",
    "module": "commonjs",
    "moduleResolution": "bundler"
  }
}
```

**`tsconfig.cjs.json` 有一处要按 TypeScript 版本调整。** TS 6.x 允许 `commonjs` 配 `bundler`，这点我没实际验证过。TS 5.x 会报错，那就把 `moduleResolution` 改成 `"node10"`；TS 6 里 `node10` 已废弃，同时还要加 `"ignoreDeprecations": "6.0"`。

**ESM 版靠 `type: "module"` 决定格式。** 根 `package.json` 声明了 `"type": "module"`，`nodenext` 才会把 `src` 当 ESM 编译。CJS 版用的是固定的 `module: commonjs`，不受 `type` 影响。

## 3. package.json

```jsonc
{
  "type": "module",
  "main": "./dist/cjs/index.js",
  "types": "./dist/cjs/index.d.ts",
  "exports": {
    ".": {
      "import":  { "types": "./dist/esm/index.d.ts", "default": "./dist/esm/index.js" },
      "require": { "types": "./dist/cjs/index.d.ts", "default": "./dist/cjs/index.js" }
    },
    "./package.json": "./package.json"
  },
  "files": ["dist"],
  "sideEffects": false,
  "scripts": {
    "clean": "node -e \"require('fs').rmSync('dist',{recursive:true,force:true})\" --input-type=commonjs",
    "build": "npm run clean && tsc -p tsconfig.esm.json && tsc -p tsconfig.cjs.json && node scripts/mark-cjs.mjs",
    "typecheck": "tsc -p tsconfig.json --noEmit && tsc -p tsconfig.cjs.json --noEmit",
    "check:pack": "attw --pack . && publint",
    "prepublishOnly": "npm run build && npm run check:pack"
  },
  "devDependencies": {
    "typescript": "…",
    "@arethetypeswrong/cli": "…",
    "publint": "…"
  }
}
```

`scripts/mark-cjs.mjs`：

```js
import { writeFileSync } from 'node:fs';
writeFileSync('dist/cjs/package.json', JSON.stringify({ type: 'commonjs' }) + '\n');
```

为什么这样写：
- **`types` 嵌在 `import` 和 `require` 里，而且排在第一位。** TypeScript 按书写顺序取第一个匹配的条件，排在后面就永远读不到。
- **`dist/cjs/package.json` 不能省。** 根目录是 `type: module`，没有这个文件的话，Node 会把 `dist/cjs/*.js` 当 ESM 加载，TypeScript 也会把 `dist/cjs/*.d.ts` 当 ESM 类型。用户那边的表现就是运行时报错，或者类型和实际格式对不上。
- **顶层的 `main` 和 `types` 是给老环境用的。** 不认识 `exports` 的环境（TS `moduleResolution: node10`、旧版 Node）会读这两个字段。
- **加 `"type": "module"` 会影响仓库里其他 `.js` 文件**，比如 `eslint.config.js` 和各种脚本，它们都会变成按 ESM 加载。需要保持 CJS 的文件请改名为 `.cjs`。

## 4. 两个取舍

- **同一个包会有两份实例。** ESM 用户和 CJS 用户在同一个进程里会各加载一份代码。如果库里有模块级状态、单例，或者依赖 `instanceof` 判断自己的类，两边的结果会对不上。纯函数工具库一般不受影响。
- **可以考虑只发 ESM。** 如果用户都在 Node 20.19+ 或 22.12+，这些版本里 `require()` 可以直接加载不含顶层 await 的 ESM，只发 ESM 就够了，构建和类型都只需要一套。你明确要两边都支持，所以上面给的是双格式方案。

最后用打好的 tarball 在一个临时目录里模拟真实用户。这一步检查的是真正要发布的包，而不是本地源码：

```bash
npm pack                          # 生成 your-lib-x.y.z.tgz
mkdir -p /tmp/consumer && cd /tmp/consumer
npm init -y >/dev/null && npm i typescript /path/to/your-lib-x.y.z.tgz

# 运行时
echo "import * as m from 'your-lib'; console.log(Object.keys(m))" > a.mjs && node a.mjs
echo "const m = require('your-lib'); console.log(Object.keys(m))" > b.cjs && node b.cjs

# 类型：nodenext 下 ESM 和 CJS 各检查一次，再用 bundler 模式检查一次
echo "import { someExport } from 'your-lib'; someExport;" > t.mts
echo "import { someExport } from 'your-lib'; someExport;" > t.cts
npx tsc --noEmit --strict --module nodenext --moduleResolution nodenext t.mts t.cts
echo "import { someExport } from 'your-lib'; someExport;" > u.ts
npx tsc --noEmit --strict --module esnext --moduleResolution bundler u.ts
```

通过标准：
- 两条 `node` 命令打印出相同的导出列表
- 三次 `tsc` 都没有报错
- attw 没有任何红色或黄色项

把 `your-lib` 和 `someExport` 换成你实际的包名和一个导出名。如果包有子路径入口（比如 `your-lib/foo`），每个入口都要在 `exports` 里写一组同样结构的条件，并重复上面的检查。
