## 一、tsconfig 结构：用项目引用 + `tsc -b` 做增量检查

现在每次全量检查，是因为整个仓库被当成一次编译。改成每个包是一个独立的 composite 项目后，`tsc -b` 会为每个包记录构建状态（`.tsbuildinfo`）。改一个包时，它只重新检查这个包；如果这个包对外的类型声明（`.d.ts`）变了，再检查依赖它的包。其他包直接跳过。

```
tsconfig.base.json          # 公共选项
tsconfig.json               # 根 "solution"：只做引用，自己不编译文件
packages/core/tsconfig.json         # src，composite
packages/core/tsconfig.test.json    # 测试，引用 ./tsconfig.json
packages/api/tsconfig.json          # references: core
...
```

**tsconfig.base.json**（选项全部写明。TS 6 改了不少默认值，不要依赖默认值）

```jsonc
{
  "compilerOptions": {
    "target": "es2022",              // 按你支持的最老运行时来定
    "lib": ["es2023"],               // 浏览器包在自己的 tsconfig 里加 "dom"
    "module": "nodenext",            // 由 Node 直接加载的包；交给打包器处理的包改成 esnext + bundler
    "moduleResolution": "nodenext",
    "strict": true,                  // 保持你现有的严格程度，不要借升级顺手改
    "verbatimModuleSyntax": true,
    "isolatedModules": true,
    "noUncheckedSideEffectImports": true,
    "composite": true,               // 隐含 declaration 和 incremental
    "declarationMap": true,
    "sourceMap": true,
    "skipLibCheck": true,
    "types": []                      // 每个包自己列出用到的全局类型（如 node、测试框架）
  }
}
```

**packages/api/tsconfig.json**

```jsonc
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "rootDir": "src",
    "outDir": "dist",
    "tsBuildInfoFile": "dist/.tsbuildinfo",
    "types": ["node"]
  },
  "include": ["src"],
  "references": [{ "path": "../core" }]   // 必须和 package.json 里的 workspace 依赖一致
}
```

**packages/api/tsconfig.test.json**（测试单独一个项目，确保测试代码也被检查）

```jsonc
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "rootDir": ".",
    "outDir": ".tsbuild/test",
    "emitDeclarationOnly": true,
    "types": ["node", "vitest/globals"]
  },
  "include": ["test"],
  "references": [{ "path": "./tsconfig.json" }]
}
```

**根 tsconfig.json**

```jsonc
{
  "files": [],
  "references": [
    { "path": "packages/core" }, { "path": "packages/core/tsconfig.test.json" },
    { "path": "packages/api" },  { "path": "packages/api/tsconfig.test.json" }
    // 其余三个包同理
  ]
}
```

**每个包的 package.json**

```jsonc
{
  "type": "module",
  "exports": { ".": { "types": "./dist/index.d.ts", "default": "./dist/index.js" } },  // types 必须放在最前面
  "dependencies": { "@scope/core": "workspace:*" }
}
```

几个需要注意的点：
- 包之间统一走构建产物：`exports` 指向 `dist`，类型来自 `tsc -b` 生成的 `.d.ts`。不要一部分包直接引源码、一部分引构建产物，否则编辑器、CI 和运行时看到的类型会不一致。如果确实想直接引源码，就用 `customConditions`，并且打包器和测试运行器也必须配置同样的条件。
- 不要用 `paths` 加 `baseUrl` 做跨包别名。`baseUrl` 在 TS 6 已废弃，TS 7 会直接报错。跨包靠 workspace 依赖加 `exports`；包内别名用 `package.json#imports`（`#internal/*`）。
- 引用之间不能有循环。如果出现循环，说明包的划分有问题，需要调整包边界，而不是在配置上绕过去。

常用命令：
- `tsc -b`：检查全部，跳过没变的包。
- `tsc -b packages/api`：只检查 api 和它依赖的包。
- `tsc -b -w`：开发时持续监听。
- CI 可以缓存 `**/dist/.tsbuildinfo`、`dist` 和 `.tsbuild`。

## 二、升级步骤（5.x → 6.0 → 7.x，每一步单独一个 PR）

0. **先确认版本和依赖情况。**
   - 用 `npm view typescript dist-tags` 和官方发布说明确认当前最新的稳定大版本。如果 7.x 还不是 `latest`，就先升到 6.0，再加一个不阻塞合并的 CI 任务试跑 7。
   - 用 `pnpm why -r typescript` 找出所有用到 `typescript` 的地方。
   - 列出所有调用编译器 API 的工具，比如 typescript-eslint、ts-jest、ts-node、vue-tsc，以及用 api-extractor、rollup-plugin-dts、tsup 生成类型声明的流程。原生的 TS 7 **不提供编译器 API**，这些工具都会受影响。
1. **在当前 5.x 上先做结构改造。** 统一升到最新的 5.x（用 pnpm catalog 或根目录的 `pnpm.overrides`，保证全仓只有一个 `typescript` 版本），再按第一节改成项目引用。这一步不改任何类型行为，先让 `tsc -b` 全绿，同时记录全量和增量检查的耗时，作为对比基准。
2. **升到 6.0。**
   - 运行 `tsc -b`，逐个处理新出现的错误：
     - `moduleResolution: node`/`node10` 改成 `nodenext` 或 `bundler`；
     - 去掉 `baseUrl`；
     - 补上 `types`；
     - 补上 `rootDir`。
   - 第一节的配置已经把受新默认值影响的选项都写明了。
   - 实在来不及修的，用带原因说明的 `// @ts-expect-error`，不要用 `@ts-ignore`。
   - 这一步结束时，配置里**不能**再有 `ignoreDeprecations`。
3. **升到 7.x。**
   - 用 7 的 `tsc` 作为类型检查的 CI 关卡。
   - 需要编译器 API 的工具继续用 6.0 的 API。TypeScript 团队发布了 `@typescript/typescript6`（包含 `tsc6` 和 6.0 的 API），具体用什么 pnpm 别名，请按官方发布说明来配，这里不凭记忆写。
   - 在 typescript-eslint 的支持范围里确认它支持哪个版本。
   - 确认你那个版本的 7 支持 `--build` 和项目引用。
   - 这种两个版本并存的情况，要在仓库文档里写明原因和以后的退出条件。
4. 每个 PR 只做升级本身，不顺手做其他类型重构。
