## 先把"一周内全部打开"拆成两个目标

3000 多个错误里，大部分是补个类型就能解决的，但有一部分要加空值判断或默认值，这会改变运行时行为。一周内把这些改完，最大的风险不在类型上：为了赶进度，大家会用 `!`、`as any` 这类写法把错误压掉，或者顺手改出线上 bug。

所以建议分成两个目标：

| 目标 | 一周内能否做到 | 做法 |
|---|---|---|
| **A. 开关全开，CI 卡住新增错误** | 能，第 2 天就能做到 | 打开开关，把现存错误逐行压制并登记成债务，CI 只允许债务减少 |
| **B. 现存错误全部修完** | 取决于人力，要逐日看进度 | 按目录分给负责人修；只改类型的 PR 和改行为的 PR 分开，验证方法不同 |

A 一周内一定能完成。B 定一个清零目标，按每天的数字判断能不能按时完成。不要为了赶 B 把错误压成 `!` 或 `as any`。

## 第 1 天：盘点和准备工具（不改业务代码）

**1. 锁定 TypeScript 版本。** 迁移期间不升级 TS，否则错误数会因为升级而变化，不知道是谁造成的。

**2. 把错误按开关分开统计。** `strict` 其实是一组开关。每次只打开一个，跑 `tsc --noEmit`，按开关、错误码和目录分别计数：
- `noImplicitAny`、`strictNullChecks`、`strictFunctionTypes`、`strictBindCallApply`、`strictPropertyInitialization`、`noImplicitThis`、`useUnknownInCatchVariables`、`alwaysStrict`
- 再加上 `noUncheckedIndexedAccess`

  看一下各项数量之和和全部打开时的总数差多少，这能说明有多少错误是连锁产生的。按目录的统计结果直接用来分配负责人。

**3. 查三项会影响运行时的配置：**
- `alwaysStrict` 会在产物里加 `"use strict"`。如果代码全是 ES module，这没有影响；如果有非模块脚本，要单独确认。
- 如果用了 `emitDecoratorMetadata`（Angular、TypeORM、inversify 等），给带装饰器的成员补类型会改变产物里的 metadata，所以这类改动不能当作只改类型。
- 自动生成的 API 客户端和类型文件要改生成器的配置，不要手改生成出来的文件。

**4. 准备产物对比检查，这是整个迁移最主要的验证手段。** 准备一份专门用来对比产物的 tsconfig，设置 `removeComments: true` 和 `noEmitOnError: false`。分别在 base 和 head 上运行：
```bash
tsc -p tsconfig.emit-check.json --outDir /tmp/emit-base   # base 上
tsc -p tsconfig.emit-check.json --outDir /tmp/emit-head   # head 上
diff -r /tmp/emit-base /tmp/emit-head
```
类型标注、`as`、`!` 在编译后都会消失。所以**声明为"只改类型"的 PR，前后产物必须完全一样**。只要有差异，这个 PR 就按改了行为处理。

**5. 准备压制脚本。** 可以用 `ts-migrate` 的 ts-ignore 插件（配置成生成 `@ts-expect-error`），也可以用 `suppress-ts-errors`。注释统一加上标记，例如 `// @ts-expect-error strict-migration`。要处理好三种情况：JSX 里的注释要写成 `{/* */}`；多行表达式里错误报在哪一行；注释不能插进模板字符串里。

**第 1 天的验证：**
- 每个开关的错误数都记录下来，作为基线。
- 在 main 上用产物对比检查对比同一个提交，`diff` 结果为空。这能证明检查本身是确定的。
- 在一个副本上跑压制脚本，再跑 `tsc`，结果为 0 个错误。

## 第 2 天：打开开关并压制现存错误（目标 A 完成）

只开一个 PR，只做两件事：改 tsconfig，插入压制注释。合并时短暂冻结代码，避免和其他 PR 大面积冲突。

选 `@ts-expect-error` 而不是基线文件，原因有三个：
- tsc 和编辑器看到的结果一致。
- 某一行的问题修好后，留在那里的 `@ts-expect-error` 会自己报错，过时的压制能被发现并删除。
- 用 grep 就能统计剩下多少。

代价是：同一行以后出现的新错误也会被压住。这类压制存在时间应该很短，可以接受。如果团队不想在代码里加注释，可以改用 betterer 或 `typescript-strict-plugin`，代价是编辑器里会一直显示一片红。

同时在 CI 里加三个计数检查，数字只能减少，不能增加：
- `strict-migration` 压制注释的数量
- 新加的非空断言（`!`）数量，由 ESLint 的 `no-non-null-assertion` 规则统计
- 新加的 `as any` 和显式 `any` 数量

另外，新增文件里不允许出现 `strict-migration` 压制。

**第 2 天的验证：**
- `tsc --noEmit` 退出码为 0，并且是在全部开关打开的情况下。
- 产物对比结果为空。这证明这个 PR 只加了注释和配置，运行时行为完全没变。
- 单元测试和 E2E 冒烟测试全部通过。
- 压制注释的数量和第 1 天统计的错误行数对得上。
- 故意写一个新的空值错误，确认 CI 会失败。这一步证明卡口真的生效。

回滚很简单：把 tsconfig 改回去即可。压制注释对运行时没有影响。

## 第 3–6 天：按目录修复（推进目标 B）

**修复顺序：** 先修共享类型、工具函数和 API 类型层，再修业务目录。共享类型修好后，下游很多错误会自动消失，也可能冒出新的错误。所以压制数要每天重新统计，不能用第 1 天的数字推算进度。

**PR 分两类，验证方法不同：**

| 类型 | 典型改动 | 验证门槛 |
|---|---|---|
| **只改类型** | 补参数和返回值类型、`catch (e: unknown)` 加上类型收窄、修正类型定义、删除过时的压制 | 产物对比结果为空，测试通过，评审只看类型 |
| **改行为** | 空值判断、`??` 默认值、提前 return、补上缺少 key 时的处理、`for (i)` 改成 `for…of` | 一个 PR 只改一小块并对应一个模块；要加覆盖空值或缺失 key 路径的测试；评审要确认这条分支在线上可能被走到时的行为是对的 |

**`noUncheckedIndexedAccess` 的常见情况：**
- 循环里写 `arr[i]`：改成 `for…of` 或 `.entries()`，不要写 `arr[i]!`。
- 从 `Record<string, T>` 或字典里取值：确实可能取不到，要明确写出取不到时怎么处理。
- 解构 `const [first] = arr`：先判断数组长度，或者改用 `arr.at(0)` 再显式处理取不到的情况。
- 只有在不变量能证明一定有值时才用 `!`，旁边要写注释说明原因，而且受上面的计数检查约束。

**每天的验证：**
- 压制数、`!` 数、`any` 数的趋势。看每天能减少多少，判断第 7 天能不能清零。到第 4 天如果按趋势明显清不完，就公开调整目标 B 的截止日期，不要降低修复标准。
- 所有"只改类型"的 PR 产物对比都为空。
- "改行为"的 PR 都附带测试。合并后观察前端错误监控（例如 Sentry），按发布版本对比错误率。

## 第 7 天：留作缓冲和收尾

**验证：**
- `tsc` 结果为 0 个错误，并且 `strict-migration` 压制为 0。如果没清零，就把剩余清单分到各负责人，CI 卡口保持不动。
- 全量测试和 E2E 测试通过。
- 第 3–6 天里改了行为的部分，按正常节奏灰度发布，并观察错误率。
- 删掉产物对比检查等临时工具。不过建议保留计数检查，防止以后 `any` 和 `!` 又回来。
