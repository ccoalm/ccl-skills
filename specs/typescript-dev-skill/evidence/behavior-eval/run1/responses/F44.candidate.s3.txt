## 一、为什么改一个包要整仓重查

常见原因有三个：

- **只有一个根 tsconfig，或用 `paths` 指向其他包的 `src`。** 编译器把五个包当成一个程序，所以每次都全部重新检查。
- **每个包各自跑 `tsc --noEmit`，但没有 project references。** 每个包都要把依赖包的源码再检查一遍。
- **没有 `.tsbuildinfo`。** 没有增量缓存，每次都从零开始。

解决办法是用 `composite` + `references` + `tsc -b`。`tsc -b` 只重建过期的项目。如果某个包改了内部实现，但对外的 `.d.ts` 没变，依赖它的包不用重新检查。

## 二、tsconfig 结构

```
tsconfig.base.json          # 共享编译选项，只放这一份
tsconfig.json               # 根 solution：files: []，引用所有包
packages/
  core/
    tsconfig.json           # 包级 solution：引用 lib + test
    tsconfig.lib.json       # src，composite，输出 dist
    tsconfig.test.json      # 测试，引用 lib
  utils/ api/ web/ cli/     # 同样结构
```

**`tsconfig.base.json`**：把 6.0 改了默认值的选项都显式写出来，这样升级时不会悄悄变化。

```jsonc
{
  "compilerOptions": {
    "strict": true,
    "target": "es2022",               // 按最老的运行环境定
    "lib": ["es2022"],
    "module": "nodenext",
    "moduleResolution": "nodenext",
    "types": [],                      // 每个包按需列出 node / 测试全局类型
    "noUncheckedSideEffectImports": true,
    "verbatimModuleSyntax": true,
    "isolatedModules": true,
    "composite": true,
    "declaration": true,
    "declarationMap": true,
    "skipLibCheck": true              // 如有手写 .d.ts，另加一个 skipLibCheck:false 的检查
  }
}
```
现有的严格度选项原样保留。这次不加新的 strict 类 flag，否则会和升级的报错混在一起。

**`packages/core/tsconfig.lib.json`**
```jsonc
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": { "rootDir": "src", "outDir": "dist", "types": ["node"] },
  "include": ["src"],
  "exclude": ["src/**/*.test.ts"],
  "references": [{ "path": "../utils/tsconfig.lib.json" }]   // 必须和 package.json 依赖一致
}
```

**`packages/core/tsconfig.test.json`**
```jsonc
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": { "rootDir": ".", "outDir": ".tsbuild/test", "emitDeclarationOnly": true, "types": ["node", "vitest/globals"] },
  "include": ["src/**/*.test.ts", "test"],
  "references": [{ "path": "./tsconfig.lib.json" }]
}
```

**`packages/core/tsconfig.json`**：`{ "files": [], "references": [{ "path": "./tsconfig.lib.json" }, { "path": "./tsconfig.test.json" }] }`

**根 `tsconfig.json`**：`{ "files": [], "references": [{ "path": "packages/core" }, …五个包] }`

**几条规则：**
- **包之间通过 `dist` 引用（先构建再使用）。** 依赖写 `"@scope/core": "workspace:*"`，`exports` 里 `types` 放第一位：`{ ".": { "types": "./dist/index.d.ts", "default": "./dist/index.js" } }`。删掉指向其他包 `src` 的 `paths` 别名，这是整仓重查最常见的原因。
- **由打包器加载的包，在自己的配置里改一下模块设置。** 例如前端用 `"module": "preserve", "moduleResolution": "bundler", "lib": ["es2022","dom"]`。直接给 Node.js 加载的包继续用 `nodenext`。
- **`references` 要和依赖方向一致，不能有环。** 加一个 CI 检查脚本，比对 `package.json` 里的 workspace 依赖和 `references`，不一致就失败。
- **常用命令：**
  - `"typecheck": "tsc -b"`：日常检查，只重建过期的项目。
  - `"typecheck:clean": "tsc -b --clean && tsc -b"`：CI 每天至少跑一次全量。
  - 只查一个包：`pnpm exec tsc -b packages/api`，它会顺带检查该包的依赖，已经是最新的会跳过。

## 三、升级步骤

先确认最新大版本：`pnpm view typescript dist-tags`，并读对应的发布说明，不要凭记忆。据我所知，7.0 是 Go 写的原生编译器，**没有程序化 API**。所以按下面的顺序分几个 PR 做，每一步都要全绿再进下一步：

1. **PR 1：在 5.x 上改结构。** 做第二节的 references 改造，先不升版本。拿到全绿和耗时数据，作为后面对比的基线。
2. **盘点。** 跑 `pnpm ls -r typescript`，确认全仓只有一个版本，用根 devDependency 或 pnpm `catalog:` 固定。然后列出所有调用编译器 API 的工具：typescript-eslint、vue-tsc、ts-jest/ts-node、tsup/rollup-plugin-dts、api-extractor、TypeDoc、vitest typecheck 等，逐个查它们支持的 TS 版本范围。
3. **PR 2：升到 6.0。**
   - `moduleResolution: node`/`node10` 改成 `nodenext` 或 `bundler`。
   - 去掉 `baseUrl`，把前缀写进每条 `paths`。
   - 确认第二节已经显式写出 `types`、`rootDir`、`module`、`target`、`strict`、`noUncheckedSideEffectImports`。
   - 新出现的错误要么修掉，要么用带原因的 `// @ts-expect-error` 压住。
   - 最后 **不能留 `ignoreDeprecations`**。6.0 的废弃项到 7.0 会变成硬错误。
4. **PR 3：升到 7.x。**
   - 类型检查（`tsc -b`）改用 7。
   - 还需要 6.0 API 的工具，按 TypeScript 团队文档的方式让它们用 `@typescript/typescript6`（自带 `tsc6` 和 6.0 API）。
   - 在根 `package.json` 或 AGENTS.md 里写明哪些工具留在 6、什么时候切过去。不要因为依赖解析让两个版本意外共存。
   - 如果 typescript-eslint 还不支持 7，这一步要等，或者有意让它留在 6。
5. **PR 4：清理。** 删掉升级时加的 `@ts-expect-error`。升级 PR 里不夹带无关的类型重构。
