## 一、tsconfig 结构

```
tsconfig.base.json        # 共享选项，只写一份
tsconfig.json             # 根"汇总"配置：files: []，只引用各个包
packages/
  a/tsconfig.json         # 叶子包：composite + 引用它依赖的包
  a/tsconfig.test.json    # 测试/脚本单独一个配置（全局类型不同）
  b/ ...
```

**`tsconfig.base.json`**（把 6.0 改过默认值的选项全部显式写出来，不依赖默认值）：
```jsonc
{
  "compilerOptions": {
    "strict": true,
    "target": "es2022",            // 按最老的目标运行时填写，不要让它随版本自动变化
    "module": "nodenext",          // 由 Node 直接加载的代码/发布的库用这组；纯前端打包的包改成 esnext + bundler
    "moduleResolution": "nodenext",
    "verbatimModuleSyntax": true,
    "isolatedModules": true,
    "composite": true,             // 自动开启 declaration，并要求所有源文件都被 include 覆盖
    "declarationMap": true,
    "incremental": true,
    "types": [],                   // 6.0 起默认就是 []，各包按需显式列出
    "noUncheckedSideEffectImports": true,
    "skipLibCheck": true           // 有手写 .d.ts 时，另开一个 skipLibCheck:false 的配置专门检查它们
  }
}
```

**`packages/b/tsconfig.json`**（假设 b 依赖 a）：
```jsonc
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "rootDir": "src",
    "outDir": "dist",
    "types": ["node"]
  },
  "include": ["src"],
  "references": [{ "path": "../a" }]
}
```

**`packages/b/tsconfig.test.json`**：用 `extends` 继承 `./tsconfig.json`，`include` 改成 `["test"]`，`types` 加上测试框架的全局类型，`references` 指向 `{ "path": "." }`（也就是 b 自己）。

**根 `tsconfig.json`**：
```jsonc
{ "files": [], "references": [
  { "path": "packages/a" }, { "path": "packages/a/tsconfig.test.json" },
  { "path": "packages/b" }, { "path": "packages/b/tsconfig.test.json" }
  // ……五个包都列上，包括它们的 test 配置
]}
```

**要点：**
- **`references` 必须和 `package.json` 里的 `workspace:*` 依赖一一对应。** 少写一条，`tsc -b` 的构建顺序就会错；出现环形引用说明包的分层设计有问题，不能靠改配置绕过。建议在 CI 里加一个小脚本，对比 `package.json` 依赖和 `references`，不一致就失败。
- **各包的 `exports` 里，`types` 要放在第一位**，指向 `dist/*.d.ts`。用 `tsc -b` 时推荐先构建再使用：下游读的是上游生成的 `.d.ts`。如果改成直接用源码（`customConditions`），打包工具和测试运行器也必须认同一个条件，否则编辑器、CI、运行时看到的类型会不一致。
- **不要用 `baseUrl`/`paths` 做包之间的跳转**，直接走 pnpm workspace 链接加 `exports`。包内部的别名用 `package.json#imports`（`#internal/*`）。
- **增量收益的来源**：`tsc -b` 只重建过期的项目。如果上游改动后生成的 `.d.ts` 没变（只改了实现），下游会被跳过。所以导出函数要写明返回类型，否则推断结果一变，就会连带重新检查所有下游包。
- **CI 缓存**：把 `**/*.tsbuildinfo` 和 `dist` 一起缓存，缓存键用 lockfile 哈希加 TS 版本。只检查改动的包：`tsc -b packages/b`，它会顺带构建 b 的上游。如果要连下游一起检查，用 `pnpm --filter "...[origin/main]"` 选出受影响的包，再分别 `tsc -b`。合并前的门禁仍然在根目录跑完整的 `tsc -b`。

## 二、升级步骤

**0. 盘点所有用到编译器 API 的工具**：`pnpm why typescript -r`。重点看 typescript-eslint、vue-tsc、tsup/rollup-plugin-dts、api-extractor、ts-jest、ts-node、ts-morph、vitest typecheck。记下每个工具支持的 TS 版本范围；typescript-eslint 通常要在 TS 新版发布一段时间后才正式支持。

**1. 全仓只保留一个 TS 版本**：在 `pnpm-workspace.yaml` 用 `catalog:`，或在根 `package.json` 用 `pnpm.overrides` 把版本固定下来，提交 lockfile。

**2. 先升到 5.x 的最新版本**，`tsc -b` 全绿，作为基线（见第三节的步骤 1）。

**3. 升到 6.0：**
- 按上面的 base 配置，把 `strict`、`module`、`target`、`types`、`rootDir`、`noUncheckedSideEffectImports` 全部显式写出来。
- 迁移已弃用的写法：`moduleResolution: node`/`node10` 改成 `nodenext` 或 `bundler`；`baseUrl` 改成在每条 `paths` 里写全前缀。
- 新出现的错误逐条修。实在要暂时压住的，用 `// @ts-expect-error <原因>`，不要用 `@ts-ignore`，也不要关掉 `strict`。
- 退出条件：**不依赖 `ignoreDeprecations` 也能零错误通过**。

**4. 升到 7.0**（Go 写的原生编译器，没有编译器 API）：
- 安装 7.0。具体包名和可执行文件名以发布说明为准。
- 用 `tsc -b` 做类型检查门禁。
- 第 0 步里需要 API 的工具，按官方提供的并存方案（`@typescript/typescript6`，含 `tsc6` 和 6.0 的 API）逐个决定是否暂时留在 6.0 API 上。每个决定都记录下来，并写明什么条件下移除。
- 确认 7.0 对 project references / `tsc -b` / `.tsbuildinfo` 的支持情况，同样以发布说明为准。

**5. 收尾**：在后续的单独改动里清掉这次加的 `@ts-expect-error`。不要把类型重构和编译器升级混在同一个 PR 里。
