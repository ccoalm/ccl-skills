## 1. tsconfig 结构：用 project references 实现按包增量检查

```
tsconfig.base.json          # 共享选项，不放 include
tsconfig.json               # solution：files: []，references 列出全部 5 个包
packages/
  core/   tsconfig.json     # composite, 无 references
  utils/  tsconfig.json     # references: core
  api/    tsconfig.json     # references: core, utils
  web/    tsconfig.json     # references: core, utils（bundler 环境）
  cli/    tsconfig.json     # references: core, api
  */tsconfig.test.json      # 测试单独一个工程，types 里加测试框架
```

**`tsconfig.base.json`**：把会随大版本改变的默认值都显式写出来，下文第 2 节解释原因。

```jsonc
{
  "compilerOptions": {
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "noImplicitOverride": true,
    "noFallthroughCasesInSwitch": true,
    "verbatimModuleSyntax": true,
    "isolatedModules": true,
    "noUncheckedSideEffectImports": true,

    "target": "es2022",              // 按最老的运行环境定，不跟随默认值
    "lib": ["es2022"],
    "module": "nodenext",
    "moduleResolution": "nodenext",
    "types": [],                     // 各包按需显式列出全局类型

    "composite": true,               // 隐含 declaration，tsc -b 增量构建的前提
    "declarationMap": true,
    "incremental": true,
    "skipLibCheck": true             // 前提：第一方手写 .d.ts 另有 skipLibCheck:false 的检查
  }
}
```

**叶子包**，例如 `packages/api/tsconfig.json`：

```jsonc
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "rootDir": "src",
    "outDir": "dist",
    "tsBuildInfoFile": "dist/.tsbuildinfo",
    "types": ["node"]
    // 如果 JS 由 tsup/esbuild 产出，这里加 "emitDeclarationOnly": true
  },
  "include": ["src"],
  "references": [{ "path": "../core" }, { "path": "../utils" }]
}
```

浏览器包（`web`）单独写环境相关的选项：`"module": "preserve"`、`"moduleResolution": "bundler"`、`"lib": ["es2022", "dom"]`。

**根 `tsconfig.json`（solution）**：

```jsonc
{ "files": [], "references": [
  { "path": "packages/core" }, { "path": "packages/utils" },
  { "path": "packages/api" },  { "path": "packages/web" }, { "path": "packages/cli" },
  { "path": "packages/core/tsconfig.test.json" } /* …其余测试工程 */ ] }
```

**这样就不用整仓检查了：**

- 改了 `api`，就运行 `tsc -b packages/api`。它只会重建 `api` 本身，以及依赖链上已经过期的包。依赖没改的部分直接复用 `.tsbuildinfo` 和 `.d.ts`。
- 在根目录运行 `tsc -b` 也是增量的，只重建过期的包。CI 缓存 `**/dist/.tsbuildinfo` 和 `dist/**/*.d.ts` 就能享受同样的增量。
- 下游包读取上游包的 `.d.ts`，不会重新检查上游源码。这是提速的主要来源。

**有一个决策要定下来：包之间的引用指向哪里。**

- **推荐“先构建”：** 每个包的 `exports` 指向 `dist`，`types` 放在条件对象的第一位。这样编辑器、CI 和运行时看到的是同一份类型。
- 另一种是“源码优先”：用 `customConditions` 加上 `exports` 里的 `"source"` 条件。bundler 和测试运行器也必须认这个条件。两种方式混用，会导致编辑器、CI、运行时三处的类型不一致。

```jsonc
"exports": { ".": { "types": "./dist/index.d.ts", "default": "./dist/index.js" } }
```

`paths` 只在编译期生效，不要用它在包之间互相引用；包内的别名用 `package.json#imports`（`#internal/*`）。不要再用 `baseUrl`。

## 2. 升级步骤：5.x → 6.0 → 7.x，分两步，不要直接跳

TS 6.0 改了一批默认值：`strict`=true，`module`=esnext，`target` 跟随最新的 ES 版本，`types`=`[]`，`rootDir` 默认为 tsconfig 所在目录，`noUncheckedSideEffectImports`=true。它还废弃了 `moduleResolution: node`/`node10` 和把 `baseUrl` 当作查找根目录的用法。TS 7 是用 Go 重写的原生编译器：6.0 的废弃项在 7 里直接报错，而且**没有编译器 API**。官方提供 `@typescript/typescript6` 包，里面有 `tsc6` 和 6.0 的 API，供需要 API 的工具与 7 并存。下面的版本号请先用 `pnpm view` 和官方发布说明确认，不要凭记忆。

**每一步都单独提一个 PR，不要混入无关的类型重构。**

1. **PR 1：只改结构。** 在当前 5.x 上落地第 1 节的 references 结构，并把默认值写成显式选项。根目录 `tsc -b` 必须全绿，CI 改成运行 `tsc -b`。这样以后只要有新报错，就能确定是升级引起的。
2. **PR 2：升到 6.0。**
   - 在根 `package.json` 用 `pnpm.overrides`（或 catalog）统一版本，确保整个仓库只解析出一份 `typescript`。
   - 运行 `tsc -b`，逐条修复新报错。常见原因是 `types: []` 导致缺少 `node` 或测试框架的全局类型，`rootDir` 变化，以及副作用导入找不到。
   - 暂时没法修的，在出错处加 `// @ts-expect-error <原因>`，不要用 `@ts-ignore`，也不要关 `strict`。
   - 把 `moduleResolution: node` 改成 `nodenext` 或 `bundler`；把 `baseUrl` 去掉，前缀直接写进 `paths`。
   - 最终状态必须是：**零 `ignoreDeprecations`、零废弃项**。
   - 用 typescript-eslint 和其他调 API 的工具确认支持 6.0；版本范围不兼容时一起升级。
3. **PR 3：清理。** 删掉 PR 2 里加的 `@ts-expect-error`。
4. **PR 4：升到 7.x。**
   - 按第 0 步的清单，为每个调用编译器 API 的工具逐个决定：它是继续走 `@typescript/typescript6`，还是已有支持 7 的版本。重点是 typescript-eslint 的 typed rules、declaration bundler、ts-jest/vue-tsc。
   - 根目录的 `typescript` 升到 7，类型检查门禁用 7 的 `tsc -b`。
   - 仍需 6.0 API 的工具通过官方文档给出的别名方式拿到 6.0。把这次“有意保留两个版本”记在 `AGENTS.md` 或 README 里，并写明什么条件下可以移除。
   - 确认 7.x 对 `tsc -b`、`composite` 和 `--watch` 的支持状态（以当时的发布说明为准）；如果有缺口，这一部分先保留在 `tsc6`。

**门禁规则：**

- CI 的类型检查必须是 `tsc -b`，并覆盖源码、测试和脚本所在的全部 tsconfig。
- 只要有报错就失败。
- tsup/esbuild/vite/tsx 能跑通，**不能**当作类型检查已通过的证据。
- 用 `tsc -b --verbose` 的输出（只重建了被改动的包及其下游）来证明增量检查真的生效。

**剩余风险：**

- TS 7 没有 API，typed lint 和 declaration bundler 是最可能卡住的地方。
- 6.0 的默认值变化可能悄悄改变 `target` 或 `rootDir`，导致产物路径变化，需要比对 `dist` 的目录结构。
- 如果包之间有循环依赖，必须先在架构层面拆开，才能用 references。
