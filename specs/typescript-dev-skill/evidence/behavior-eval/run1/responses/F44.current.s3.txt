## 一、核心思路

整仓重新检查的原因，通常是各包靠 `paths` 或源码互相引用，TS 只能把整个仓库当成一个程序来检查。改成 **Project References + `tsc -b`** 之后：

- 每个包是一个独立的 `composite` 项目，有自己的 `.tsbuildinfo` 缓存；
- 下游包只读上游包生成的 `.d.ts`，不再重新检查上游源码；
- 改一个包时，只重新检查这个包。只有它导出的类型（`.d.ts`）真的变了，才会接着检查下游包。

**先改结构，再升级版本。** 两件事分开做，出问题时才分得清是哪一步引起的。

## 二、tsconfig 结构

```
tsconfig.base.json        # 公共选项
tsconfig.json             # 根配置，只列出各包，本身不检查文件
packages/core/tsconfig.json
packages/api/tsconfig.json   # references → core
...
```

**tsconfig.base.json**
```jsonc
{
  "compilerOptions": {
    "composite": true,
    "incremental": true,
    "declaration": true,
    "declarationMap": true,       // 编辑器里跳转到源码，而不是 .d.ts
    "sourceMap": true,
    "strict": true,
    "target": "es2022",
    "module": "nodenext",          // 前端包交给打包器处理的，改成 esnext + "moduleResolution": "bundler"
    "moduleResolution": "nodenext",
    "lib": ["es2023"],
    "types": ["node"],             // 显式写出来，不要依赖默认值（6.0 改了默认值）
    "verbatimModuleSyntax": true,
    "isolatedModules": true,
    "skipLibCheck": true,
    "forceConsistentCasingInFileNames": true
    // 不要用 baseUrl / paths 做包之间的引用：靠 pnpm 的 workspace 软链即可（baseUrl 在 6.0 已弃用）
  }
}
```

**根目录 tsconfig.json**
```jsonc
{
  "files": [],
  "references": [
    { "path": "packages/core" },
    { "path": "packages/api" }
    // 五个包都列上
  ]
}
```

**packages/api/tsconfig.json**
```jsonc
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "rootDir": "src",
    "outDir": "dist",
    "tsBuildInfoFile": "dist/.tsbuildinfo"
  },
  "include": ["src"],
  "references": [{ "path": "../core" }]   // 必须和 package.json 里的 workspace 依赖保持一致
}
```

**packages/core/package.json**
```jsonc
{
  "type": "module",
  "exports": { ".": { "types": "./dist/index.d.ts", "default": "./dist/index.js" } }
}
```
下游包这样声明依赖：`"@scope/core": "workspace:*"`。

**脚本**
- 根目录：`"typecheck": "tsc -b"`、`"typecheck:watch": "tsc -b -w"`
- 只检查单个包：`tsc -b packages/api`。它会先确认上游包是不是最新的，没变就跳过。

**几个要注意的地方**
- **用打包器出产物的包**（tsup/vite 等）：`composite` 不能和 `noEmit` 一起用。可以设置 `emitDeclarationOnly: true` 和 `outDir: "dist/types"`，让 tsc 只生成类型声明。
- **测试代码**：把包内的 tsconfig 拆成 `tsconfig.src.json` 和 `tsconfig.test.json`，测试配置引用源码配置，包里的 `tsconfig.json` 再引用这两个。这样测试文件不会打乱 `dist` 的目录结构。
- **防止依赖和 references 不一致**：在 CI 里加一个检查，对比 `package.json` 的 `workspace:` 依赖和 `references`，不一致就失败。可以自己写个小脚本，也可以用 `workspaces-to-typescript-project-references` 这类工具。
- **可选优化**：开启 `isolatedDeclarations`。它要求导出项写明类型，生成 `.d.ts` 会更快，也更稳定。

## 三、升级步骤

先运行 `npm view typescript versions --json` 确认当前最新的大版本。截至我的知识范围：6.0 是过渡版本，主要做弃用和默认值调整；7.x 是用 Go 重写的原生编译器（`tsgo`）。具体的弃用项和默认值以官方 release notes 为准。

1. **记录基线**（还在 5.x 上）：在新结构下运行 `tsc -b --clean && tsc -b --extendedDiagnostics`，保存错误数和耗时，同时把所有包的 `dist/**/*.d.ts` 复制一份留作对比。
2. **统一版本来源**：在 `pnpm-workspace.yaml` 里用 `catalog:` 写 `typescript: ^x`，各包写 `"typescript": "catalog:"`，或者只在根目录安装。之后用 `pnpm why typescript` 确认整个仓库只有一个版本。
3. **先升到最新的 5.x**，修完报错，再继续。
4. **升到 6.0**：
   - 把弃用项清理干净：`moduleResolution: node`（node10）、`baseUrl`、`target: es5`、`outFile`、amd/umd/system 模块格式等。
   - 显式写出所有改了默认值的选项，比如 `types`、`rootDir`、`strict`、`module`、`target`。
   - `ignoreDeprecations: "6.0"` 只能当临时开关用，合并前删掉。
5. **检查周边工具的兼容性**：
   - 依赖 TS 编译器 API 的工具要逐个确认支持的版本范围：typescript-eslint、ts-jest、ts-node、tsup/rollup-plugin-dts 的 dts 生成、vue-tsc 等。
   - vitest/esbuild 只是去掉类型，受影响小。
6. **升到 7.x**：
   - 先在 CI 里并行运行 `tsgo -b`（来自 `@typescript/native-preview` 或 7.x 的 `tsc`）和 6.x 的 `tsc -b`，对比两边的诊断结果。
   - 如果 lint、dts 等工具还需要 JS 版的编译器 API，就让它们继续用 `typescript@6`，类型检查交给 7.x。等工具链跟上之后，再移除 6.x。
7. **锁定版本**：`pnpm install` 更新 lockfile，CI 用 `pnpm install --frozen-lockfile`。
