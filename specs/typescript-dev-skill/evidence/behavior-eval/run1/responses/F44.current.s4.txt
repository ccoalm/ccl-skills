## 一、tsconfig 结构（project references + `tsc -b`）

要解决"改一个包就全仓重新检查"，做法是把每个包变成一个 composite 项目，用根目录的总配置文件串起来，然后用 `tsc -b` 增量构建：

- 没改的包会被跳过。
- 某个包内部改了、但对外的 `.d.ts` 没变时，依赖它的包也不会重新检查。

```
tsconfig.base.json          # 公共编译选项，不含 include/references
tsconfig.json               # 根总配置：files: []，只列 references
packages/
  core/tsconfig.json        # composite，无依赖
  utils/tsconfig.json       # references: core
  api/tsconfig.json         # references: core, utils
  ...
```

**tsconfig.base.json**
```jsonc
{
  "compilerOptions": {
    "composite": true,          // 隐含 incremental + declaration
    "declarationMap": true,     // 编辑器"跳转定义"能跳到源码
    "strict": true,
    "target": "es2022",
    "module": "nodenext",       // 显式写出来，不依赖默认值（TS 6 改了很多默认值）
    "moduleResolution": "nodenext",
    "types": ["node"],          // 显式写出来（TS 6 起默认值据我所知变成 []）
    "skipLibCheck": true,
    "verbatimModuleSyntax": true,
    "isolatedModules": true
    // 可选："isolatedDeclarations": true —— 声明文件生成会更快，但所有导出都要写显式类型
  }
}
```

**packages/api/tsconfig.json**
```jsonc
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "rootDir": "src",
    "outDir": "dist",
    "tsBuildInfoFile": "dist/.tsbuildinfo"
  },
  "include": ["src"],
  "references": [{ "path": "../core" }, { "path": "../utils" }]
}
```

**根 tsconfig.json**
```jsonc
{ "files": [], "references": [
  { "path": "packages/core" }, { "path": "packages/utils" },
  { "path": "packages/api" },  { "path": "packages/web" }, { "path": "packages/cli" }
]}
```

**要点：**
1. **不能有循环引用。** project references 不支持环。"互相引用"如果指的是 A↔B，就得把共享的部分抽成第六个包，或者合并成一个包。这是整套结构能成立的前提。
2. **references 要和 package.json 里的 `workspace:*` 依赖保持一致。** 漏写会导致构建顺序错，或者读到过期的 `.d.ts`。在 CI 里加一个检查（见第三节）。
3. **每个包的 `package.json` 用 `exports` / `types` 指向 `dist/*.d.ts`。** 编辑器默认会把引用重定向到源码，所以开发时不需要先构建。
4. **测试文件**可以单独放一个 `tsconfig.test.json`：设 `noEmit`，并 reference 同包的 `src` 项目。这样测试代码不会进入发布产物的声明文件。
5. **TypeScript 只在根目录装一份。** 用 pnpm catalog 统一版本：在 `pnpm-workspace.yaml` 写 `catalog: { typescript: ^x.y }`，各包里写 `"typescript": "catalog:"`。
6. **脚本：**
   - 全量：`"typecheck": "tsc -b"`
   - 单包：`tsc -b packages/api`，只构建 api 和它上游的包
   - CI 缓存 `packages/*/dist` 和 `**/.tsbuildinfo`，缓存 key 带上 lockfile 的哈希。

## 三、验证

**结构正确性**
```bash
pnpm install --frozen-lockfile
pnpm -r exec tsc -v          # 每个包解析到的都应该是同一个版本
pnpm why typescript          # 只能有一个版本
node scripts/check-refs.mjs  # references 和 workspace 依赖一致（脚本见下）
```

```js
// scripts/check-refs.mjs —— 在 CI 里跑，不一致就退出码 1
import fs from 'node:fs'; import path from 'node:path';
const dirs = fs.readdirSync('packages').map(d => path.join('packages', d));
const byName = Object.fromEntries(dirs.map(d => [JSON.parse(fs.readFileSync(`${d}/package.json`)).name, d]));
let bad = 0;
for (const d of dirs) {
  const pkg = JSON.parse(fs.readFileSync(`${d}/package.json`));
  const deps = Object.keys({ ...pkg.dependencies, ...pkg.devDependencies, ...pkg.peerDependencies }).filter(n => byName[n]).map(n => byName[n]).sort();
  const ts = JSON.parse(fs.readFileSync(`${d}/tsconfig.json`, 'utf8').replace(/\/\/.*$/gm, ''));
  const refs = (ts.references ?? []).map(r => path.join(d, r.path)).map(p => path.normalize(p)).sort();
  if (JSON.stringify(deps) !== JSON.stringify(refs)) { console.error(`${d}: deps=${deps} refs=${refs}`); bad = 1; }
}
process.exit(bad);
```

**增量是否真的生效**（用 `tsc -b --verbose` 看哪些项目被重新构建）：
1. 什么都不改，直接重跑：5 个项目都应该是 "up to date"。
2. 改某个叶子包（比如 `cli`）：只有它被重新构建。
3. 改 `core` 的内部实现，不动导出的类型：`core` 重新构建，下游的包不应该被重新检查。
4. 改 `core` 导出的类型签名：下游重新构建，并且能报出真实的类型错误。
5. 反向用例：在下游故意写一个类型错误，`tsc -b` 必须失败、返回非 0 退出码。确认门禁没有被缓存掩盖。

**升级前后对比**
- `.d.ts` 快照 diff：没有差异最好，有差异就逐条说明原因。这是对外 API 有没有变的直接证据。
- 跑 lint、单元测试、各包构建，再做一次运行时冒烟，比如 import 每个包的入口、启动服务或 CLI。
- 对比 `--extendedDiagnostics` 的耗时：全量、单包增量、空跑各一组数据，用来证明"不用再整仓检查"。
- CI 缓存命中时，空跑应该在秒级完成。

**回滚：** 每一步都是独立的 PR，回滚就是 revert 那个 PR（package.json 和 lockfile 一起回退）。tsbuildinfo 的缓存 key 包含了 TypeScript 版本，回滚后不会读到旧缓存。
