## 0. 先说明为什么不能只改 package.json

现在的配置有三个问题：

1. **`main` 指向的是 ESM 代码，但 package.json 没写 `type`。** 没有 `type` 时 Node 会把 `.js` 当 CommonJS，CJS 用户 `require` 后会直接报语法错误。ESM 用户从 Node 加载时，也会因为文件被当成 CJS 而出错。
2. **`moduleResolution: bundler` 允许 `import './foo'` 不写扩展名，tsc 也不会帮你补。** 打包工具能处理，Node 原生 ESM 会报 `ERR_MODULE_NOT_FOUND`。
3. **只有一份 `.d.ts`，TS 只能把它当成 ESM 或 CJS 中的一种。** 另一种用户就会遇到 "Masquerading as ESM/CJS" 这类类型错误，比如 `default` 导出的形状对不上。

所以思路是：用 tsc 编两遍，每种格式各配一份自己的 `.d.ts`，再用 `exports` 按 `import` / `require` 分别指过去。

## 1. package.json

```jsonc
{
  "type": "module",
  "main": "./dist/cjs/index.js",          // 给不认 exports 的老工具 / node10 解析用
  "module": "./dist/esm/index.js",
  "types": "./dist/cjs/index.d.ts",       // 给 moduleResolution: node10 的 TS 用户
  "exports": {
    ".": {
      "import":  { "types": "./dist/esm/index.d.ts", "default": "./dist/esm/index.js" },
      "require": { "types": "./dist/cjs/index.d.ts", "default": "./dist/cjs/index.js" }
    },
    "./package.json": "./package.json"
  },
  "files": ["dist"],
  "sideEffects": false,
  "scripts": {
    "clean": "node -e \"require('node:fs').rmSync('dist',{recursive:true,force:true})\"",
    "typecheck": "tsc -p tsconfig.json --noEmit",
    "build": "npm run clean && tsc -p tsconfig.esm.json && tsc -p tsconfig.cjs.json && node -e \"require('node:fs').writeFileSync('dist/cjs/package.json', JSON.stringify({type:'commonjs'}))\"",
    "check:package": "publint && attw --pack .",
    "prepack": "npm run build"
  },
  "devDependencies": {
    "@arethetypeswrong/cli": "^0.17",
    "publint": "^0.3"
  }
}
```

要点：
- **`types` 必须写在每个条件分支的第一位。** TS 是按顺序匹配条件的。
- **`dist/cjs/package.json` 里的 `{"type":"commonjs"}` 不能省。** Node 运行时和 TS 都靠离文件最近的 package.json 判断 `dist/cjs/*.js` 和 `*.d.ts` 是 CJS。少了它，CJS 的类型会被当成 ESM。`dist/esm` 沿用根目录的 `"type": "module"`。
- `"type": "module"` 会改变仓库根目录下其他 `.js` 文件的解释方式，比如 `eslint.config.js`、`jest.config.js`。如果它们是 CJS 写法，要改名为 `.cjs`。

## 2. tsconfig 拆成三份

**`tsconfig.json`**：基础配置，编辑器和类型检查用，ESM 构建也继承它。
```jsonc
{
  "compilerOptions": {
    "target": "es2020",
    "module": "nodenext",
    "moduleResolution": "nodenext",
    "rootDir": "src",
    "strict": true,
    "declaration": true,
    "declarationMap": true,
    "sourceMap": true,
    "skipLibCheck": true,
    "isolatedModules": true
  },
  "include": ["src"],
  "exclude": ["src/**/*.test.ts", "src/**/__tests__/**"]
}
```

**`tsconfig.esm.json`**
```jsonc
{ "extends": "./tsconfig.json", "compilerOptions": { "outDir": "dist/esm" } }
```

**`tsconfig.cjs.json`**
```jsonc
{
  "extends": "./tsconfig.json",
  "compilerOptions": {
    "outDir": "dist/cjs",
    "module": "commonjs",
    "moduleResolution": "node10"
    // TS 6.x 会对 node10 给出弃用告警；可加 "ignoreDeprecations": "6.0"
  }
}
```

为什么把 `bundler` 换成 `nodenext`：`nodenext` 会在编译阶段强制相对导入写扩展名。这样"Node ESM 里跑不起来"的问题在构建时就能发现，不会等到用户那边才暴露。

## 3. 源码需要配合的改动

- 相对导入都补上 `.js` 扩展名：`import { x } from './utils'` 改成 `'./utils.js'`。目录导入改成 `'./utils/index.js'`。不确定改全没有，跑一次 `tsc --noEmit` 就会全部列出来。
- **不要用 `export default`，统一用具名导出。** 否则 CJS 用户只能写 `require('pkg').default`，attw 也会报警。
- 不能出现 `import.meta`、顶层 `await`。CJS 构建会直接报错，这正是一道兜底检查。
- 不要开 `verbatimModuleSyntax`，它和 `module: commonjs` 的输出冲突。
- 如果依赖了只有 ESM 的包，CJS 产物里的 `require()` 在 Node 20.19 / 22.12 之前的版本会失败。要么换依赖，要么在 `engines` 里写明最低 Node 版本。
- **双包风险：** 同一个进程里可能同时加载 ESM 和 CJS 两份代码。如果库里有模块级状态，或者用户会用 `instanceof` 判断你的类，这两处要特别留意。

## 4. 兼容性影响

加了 `exports` 之后，用户就不能再深层导入 `pkg/dist/xxx`，这对他们是破坏性变更。要么发一个 major 版本，要么在 `exports` 里把公开的子路径逐个列出来。
