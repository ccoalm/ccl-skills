# TypeScript `strict` + `noUncheckedIndexedAccess` 一周迁移方案

## 先定清楚"打开"指什么

"一周内全部打开"有两种理解，需要团队先选一种：

- **A. 开关打开，旧错误按存量管理**：主 tsconfig 第 1 天就打开两个开关，新写的代码马上按严格模式检查；3000 多个旧错误记成一份基线，只许减少，不许增加。
- **B. 开关打开，且没有任何错误、没有任何压制**：真正的零错误。

**建议：以 A 为第 1 天的底线，以 B 为本周冲刺目标，第 3 天按实际修复速度决定能不能达到 B。** 一周修完 3000 个错误不是做不到，但最常见的失败方式是用 `!`、`as any`、`@ts-ignore` 把数字刷到零：开关开了，类型保护却没有。所以这个方案把"不许刷数字"当成和"错误数"同等重要的验证项。

前提假设：代码按 ES module 打包（Vite、webpack 等），打包工具本身不做类型检查，类型检查只靠 `tsc --noEmit`。如果实际情况不同，后面会指出要改哪几处。

## 核心机制

### 1. 错误基线（ratchet）
- 用 `tsc --noEmit --pretty false` 的输出，按"文件 + 错误码 → 数量"统计，存成 `strict-baseline.json` 提交进仓库。不按行号统计，否则改一行代码就会让后面的行号全部错位。
- CI 用这份基线比较，而不是要求零错误。任何文件的任何错误码数量变多、或者出现新的有错文件，CI 就失败。数量变少时，要求在同一个 PR 里更新基线，这样基线只能往下走。
- 例外：修好一个底层工具函数的类型后，下游文件可能冒出新错误。允许在同一个 PR 里把基线调高，但 CI 要把增加的部分打印出来，由 reviewer 确认。
- 现成工具可以用 betterer，也可以自己写一个约 50 行的脚本。

### 2. 编译产物对比：判断改动有没有影响运行时
这是整个方案最重要的验证。
- 类型注解、`!`、`as` 在编译时都会被擦掉；而 `?.`、`??`、`if` 判断、提前 throw 会留在编译出的 JS 里。
- 对 PR 改到的每个文件，用和正式构建相同的转译器（babel、esbuild、swc 或 tsc）分别编译改动前和改动后的版本，格式化后做 diff：
  - **diff 为空**：标记为 `type-only`，运行时不变，可以走轻量 review，随时合入。
  - **diff 不为空**：标记为 `runtime`，必须附带测试，走正常 QA 流程。
- 如果项目开了 `emitDecoratorMetadata`（Angular、class-validator、DI 框架常见），改类型注解会改变编译出的 `design:type` 元数据。这个检查正好能抓到，所以一定要用真实的转译配置，不能偷懒直接用 esbuild 的默认配置。

### 3. 刷数字监控
第 0 天先记下全仓库这几类写法的数量：
- 非空断言 `!`
- `as any`、`as unknown as`
- 显式写的 `any`
- `@ts-ignore`、`@ts-expect-error`
- `eslint-disable`

之后每个 PR 都报告这几项的增减。规则：
- `!` 只能用在有明确不变量的地方，旁边要写一行原因。批量新增的 `!` 会被 review 打回。
- 显式 `any` 和 `@ts-ignore` 默认不许新增。
- 可以用 `@typescript-eslint/no-non-null-assertion` 和 `no-explicit-any` 加同样的基线方式来自动检查。

## 日程与每一步的验证

### 第 1 天：建基线、搭工具、打开开关

1. **统计错误并分类**
   - 只开 `strict`：得到错误数 A。
   - 再加上 `noUncheckedIndexedAccess`：得到错误数 B。B − A 就是索引访问带来的部分。这个开关依赖 `strictNullChecks`，不开后者时它基本不起作用，所以必须分两次统计。
   - 再把 strict 拆成子开关逐个打开计数：`strictNullChecks`、`noImplicitAny`、`strictPropertyInitialization`、`strictFunctionTypes`、`useUnknownInCatchVariables`、`strictBindCallApply`、`noImplicitThis`、`alwaysStrict`。
   - 最后按"目录或 CODEOWNERS × 错误码"做成分配表。
   - **验证**：各分项加起来能对上总数；所有数字都附上命令和 commit SHA。
2. **检查所有 tsconfig 是否真的生效**
   - 对每个 tsconfig（应用、测试、storybook、scripts、各个 package）运行 `tsc --showConfig`，确认最终生效的配置里两个开关都是 true。子配置里写的 `"strict": false` 会覆盖父配置，必须 grep 清理掉。
   - **验证**：每个 tsconfig 的 `--showConfig` 输出都存档。
3. **确认 `alwaysStrict` 的运行时影响**
   - 打开它会在编译输出里加上 `"use strict"`。ES module 本来就是严格模式，不受影响；但如果有非 module 的脚本（老的全局 JS、注入页面的脚本），行为可能改变。
   - **验证**：用第 2 节的产物对比，对整个仓库跑一次，确认只有预期的文件出现 diff。
4. **合入开关和 CI 门禁**
   - 修改主 tsconfig，提交基线文件，CI 换成基线比较、产物对比和刷数字统计三项检查。如果构建脚本里有 `tsc && build` 这类要求零错误的写法，同步改掉。
   - **验证（反向用例必须做）**：在一个临时分支里故意写一个没标类型的参数、一个 `arr[0].x`，CI 必须失败；再修掉其中一个已有错误但不更新基线，CI 也必须失败。主分支在开关打开后 CI 必须保持绿色。
5. **对团队发规则**：修复规范见下文，PR 粒度为"一个目录 × 一个错误码"或不超过约 300 行，`type-only` 和 `runtime` 两类改动分开提 PR。

**第 1 天的退出条件**：开关已在主 tsconfig 生效，新代码不能再增加错误；基线数字、反向用例结果、刷数字统计的初始值都有记录。

### 第 2–4 天：分批清理

修复顺序：
1. **先修底层**：共享的 types、utils、API client、store。这里修好一个类型，往往能让下游一批错误一起消失。
2. **再做批量机械修复**（基本都是 `type-only`）：
   - 函数参数标类型。TS 的"根据用法推断类型"修复和 ts-migrate 可以生成初稿，但推断结果必须人工过一遍，推断出的 `any` 不算修好。
   - 给类成员加 `!` 声明（只限框架负责注入的字段，比如 `@Input`、`@ViewChild`、DI 注入的属性）。
3. **最后是需要改运行时逻辑的部分**，由各目录负责人处理，必须附测试：null 判断、默认值、catch 里的 `unknown` 处理。这类 PR 最晚第 4 天合完，留出 QA 时间，不要在周五合入。

每个 PR 的验证：
- 基线检查：错误数只减不增。若有增加，必须说明原因并由 reviewer 确认。
- 产物对比：确认 PR 被标对了类别。标成 `type-only` 但实际有 diff 的，直接打回。
- 刷数字统计：`!`、`any`、各类压制注释的增量在允许范围内。
- 现有的单测和构建必须通过。`runtime` 类 PR 还要附上针对这次修改的测试，并在关键页面跑一次 E2E 冒烟。
- 每天更新一次进度：错误总数、各开关和各目录的剩余数量、刷数字统计的变化趋势。

**第 3 天中午决策点**：按目前的修复速度推算第 5 天还会剩多少。
- 预计能清零：按 B 目标继续。
- 清不完：确定退出目标就是 A，剩下的错误保留在基线里（或者统一转成带 `TODO(strict-migration)` 标签的 `@ts-expect-error`，并计入统计），**禁止在最后两天用 `!` 或 `any` 突击刷数字**。

### 第 5 天：收尾验收

- **配置**：所有 tsconfig 的 `--showConfig` 输出里两个开关都生效，没有任何子配置把它们关掉。
- **错误数**：
  - B 目标：`tsc --noEmit` 对每个 project 都报 0 个错误，基线文件和对应的 CI 步骤可以删掉，改成直接要求零错误。
  - A 目标：剩余错误数与对应负责人列表存档，基线继续作为 CI 门禁。
- **质量**：刷数字统计的初始值和最终值并列展示。`!` 和 `any` 的净增量要逐条说明理由。
- **运行时**：本周所有 `runtime` 类 PR 列成清单，确认每一条都有测试和 QA 记录。
- **上线后**：在前端错误监控（Sentry 等）里，按新版本过滤 `TypeError` 和新增断言抛出的错误。回滚就是逐个 revert `runtime` 类的小 PR；`type-only` 类改动不影响运行时，不需要回滚。

## 各类错误的修复规范

| 开关 / 错误 | 正确的修法 | 禁止的修法 |
|---|---|---|
| `noImplicitAny`（TS7006、7031 等） | 标上真实类型，或从调用处推断出类型 | 一律写成 `any` |
| `strictNullChecks`（TS2531、2532、18047、18048、2322、2345） | 值确实可能为空：处理它（属于 `runtime` 改动，要测试）。值有不变量保证不为空：写 `assertDefined(x, 'reason')`，或带注释的 `!` | 不分情况加 `!` 或 `?.`。`?.` 会把原本的报错变成悄悄返回 undefined，等于藏起一个 bug |
| `noUncheckedIndexedAccess` | 循环改用 `for...of` 或 `entries()`；取数组第一个元素后做判断，或改成解构赋值再判断；正则的 `m[1]` 先判断再用；把 `Record<string, V>` 改成 `Map`，或明确写成 `Partial<Record<…>>` | `arr[i]!` 全仓库批量替换 |
| `strictPropertyInitialization`（TS2564） | 在构造函数里赋值；框架负责注入的字段用 `!:` 声明 | 给所有字段都加 `!` |
| `strictFunctionTypes` | 修正回调和事件处理函数的参数类型（这类错误通常说明真有问题） | 用 `as` 强转 |
| `useUnknownInCatchVariables`（TS18046） | 统一写一个 `toError(e)` 工具函数（属于 `runtime` 改动，要测试） | `catch (e: any)` |
| 第三方 `.d.ts` 报错 | 升级 `@types`，或在仓库里补本地的类型声明 | 去掉现有的 `skipLibCheck` 配置以外的任何"捷径" |

## 风险与应对

- **合并冲突**：大量小 PR 同时改代码，正在开发的功能分支会频繁冲突。应对：按目录分配负责人，PR 小步、快速合入；不提交几百个文件的大批量自动修复 PR，批量修复也按目录拆开。
- **把 bug 当成正确行为固化**：修复时发现某处的空值处理本来就是错的（真实存在的线上 bug），要单独提 PR 修，并写测试，不要用类型断言把它绕过去。
- **CI 变慢**：严格模式下 `tsc` 会更慢。可以开 `incremental` 加构建缓存，或按 project references 拆开并行检查；第 1 天先测出耗时。
