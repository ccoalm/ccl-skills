# 打开 `strict` 和 `noUncheckedIndexedAccess` 的迁移方案（一周）

我手上没有这个仓库，所以下面的命令和时间都按通用的单仓库前端项目来写。路径、脚本名请换成你们实际用的。

## 先对齐目标

一周内把三千多个错误全部改掉，风险很高：每天要修约 600 个，而且很多修改会改变运行时行为。我建议把目标定成两条：

1. **第 1–2 天：两个选项在整个仓库正式打开，CI 开始拦截。** 新写的代码和改过的代码马上按 strict 检查。还没修的老错误记进一份"错误基线"，这份基线只能减少，不能增加。
2. **第 2–5 天：分目录修复，把基线清零。** 到周五如果清零了，就删掉基线机制。如果没清零，剩下的错误按负责人和截止日期列出来，继续修。

这样不管周五清没清零，"一周内全部打开"都做到了，也不需要在代码里批量插 `@ts-ignore`。批量压制会让错误从视线里消失，等于没迁移。

## 第 0 步（半天）：摸清现状并统计错误

**要做的事：**
- 查清楚 TypeScript 版本（`npx tsc -v`），以及哪个工具做类型检查、哪个工具输出 JS（tsc、Babel、esbuild、SWC 或 Vite）。还要列出所有依赖编译器 API 的工具，比如 typescript-eslint、vue-tsc、类型测试工具。
- 列出所有 `tsconfig*.json`，包括 `extends` 和 `references` 引用的。确认 CI 现在的类型检查是不是覆盖了 src、测试、脚本、storybook 等每一个配置。**如果测试或脚本现在根本没有被检查，接进来后错误会远超 3000**，要提前算进总数。
- 按选项分别统计错误。`strict` 其实是一组检查，分开开才能看出错误集中在哪：
  ```bash
  for f in strictNullChecks noImplicitAny strictFunctionTypes strictPropertyInitialization \
           useUnknownInCatchVariables strictBindCallApply noImplicitThis noUncheckedIndexedAccess; do
    echo "$f $(npx tsc --noEmit --pretty false -p tsconfig.json --$f 2>/dev/null | grep -c 'error TS')"
  done
  ```
  通常 `strictNullChecks` 和 `noUncheckedIndexedAccess` 占大头。
- 按目录和错误码汇总，例如 TS18048、TS2532（可能是 undefined）、TS7006（参数隐式 any）、TS2564（类属性没初始化）、TS18046（catch 里的变量是 unknown）。

**怎么验证：** 产出一张"目录 × 错误码"的统计表。各选项单独统计的数字加起来，应该和两个选项一起开时的总数大致对得上（有少量重叠是正常的）。检查覆盖到的 tsconfig 清单要和仓库里实际的一一对上。

## 第 1 步（第 1 天）：打开选项，CI 只拦新增错误

**1. 改根 tsconfig**，所有子配置都继承它：
```jsonc
{ "compilerOptions": { "strict": true, "noUncheckedIndexedAccess": true } }
```
不要在子配置里把这两个选项关掉。

**2. 写一个基线脚本**（例如 `scripts/tsc-baseline.mjs`）。tsc 本身不支持基线，需要自己写：
- 运行 `tsc --noEmit --pretty false -p <config>`，解析每行 `file(line,col): error TSxxxx`，按"文件 + 错误码"计数。**不要按行号记**，否则别人改了上面几行代码，基线就对不上了。
- `check` 模式：只要某个"文件 + 错误码"的数量超过基线，就失败，并列出是哪些。数量比基线少也失败，提示运行 `update`，这样修掉的错误会被锁进基线，后面不会再长回来。
- `update` 模式：把当前结果写进 `tsc-baseline.json`。
- 如果 tsc 退出码非零，但一条错误都没解析出来（比如配置文件本身写错了），直接失败。不能把这种情况当成"没有错误"。
- 每个 tsconfig 各有一份基线。

**3. CI 里加两道检查：**
- 运行 `node scripts/tsc-baseline.mjs check`。
- 把 PR 里的基线总数和 `origin/main` 上的比较，只允许减少。另外给基线文件设置 CODEOWNERS，防止有人直接改大基线让 PR 通过。

**4. 用 lint 防止"用断言糊过去"：**
- `@typescript-eslint/ban-ts-comment`：禁用 `ts-ignore`；`ts-expect-error` 只在写明原因时允许。
- 统计 `!`（非空断言）、`as` 和 `@ts-expect-error` 的总数，作为 CI 指标，只允许持平或下降。

**怎么验证：**

| 检查项 | 怎么确认 |
|---|---|
| 新错误会被拦住 | 在试验分支里故意写一个 `arr[0].foo`，CI 必须失败 |
| 修复会被锁定 | 修掉一个错误但不更新基线，CI 必须失败并提示 update |
| 基线不能被改大 | 手工把基线里某个计数改大，和 main 比较那一步必须失败 |
| 所有配置都在检查范围内 | CI 日志里能看到每个 tsconfig 都跑了 |
| 运行时行为没变 | 改配置前后各构建一次，对比产物哈希，应该完全一致（这两个选项只影响类型）。**唯一要注意的是**：如果由 tsc 输出 JS，并且有非 ESM 的脚本文件，`alwaysStrict` 会加上 `"use strict"`，可能改变运行行为，要对比 tsc 的输出 |
| 回滚 | 只需要撤掉 tsconfig 这一处改动 |

## 第 2 步（第 2–5 天）：分目录修复

**修复顺序：**
1. **先修公共的类型源头**：API 响应类型、公共工具函数的返回类型、全局状态和 store 的类型、第三方库的 `.d.ts` 补丁。一个源头类型改对了，下游几十上百个错误会一起消失。每天开工前重新统计一次，按"错误多的文件"重新排序。
2. **再处理大量重复、模式固定的错误**，按错误码分批：
   - `noUncheckedIndexedAccess` 带来的错误：
     - 下标循环 `for (let i…) arr[i]` 改成 `for…of`。
     - 记录查找 `record[key]` 加判空。键的范围固定时，把 `Record<string, T>` 改成 `Record<'a'|'b', T>`。键是有限的字面量联合时，访问结果不会多出 `undefined`。
     - 数组首元素 `arr[0]`，用解构加守卫处理。
   - catch 里的变量（TS18046）：统一写一个 `toError(e: unknown)` 辅助函数来收窄类型。
   - 参数隐式 any（TS7006）：从调用方或类型定义里补上参数类型，**不要写 `any`**。
   - 类属性没初始化（TS2564）：在构造函数里初始化，或者把类型改成可选的。只有确实由框架注入的属性，才用 `!:`，并写注释说明原因。
3. **最后是零散、需要逐个判断的错误**，交给对应目录的负责人。

**每个 PR 的规则：** 只改一个目录，或者只处理一类错误。不要顺手做无关的重构。不要用 `!` 或 `as` 来消除错误。

**这一步的风险在运行时，不在类型。** 原来是 `x!.foo`，代码默认 x 一定存在。改成 `if (!x) return` 之后，以前会直接报错崩掉的地方，现在会悄悄跳过，行为变了。所以凡是加了守卫或默认值、改变了执行分支的地方，都要补测试，或者在 PR 里说明为什么行为是等价的。

**每个 PR 都要验证：**
1. 对相关项目运行 `tsc --noEmit -p <config>`，基线已经更新，而且只减不增。
2. 带类型信息的 lint 通过，断言和压制的计数没有上升。
3. 改动目录的单元测试和组件测试通过。改变了行为的守卫有对应的新测试。
4. 构建成功。打包工具构建成功不能代替类型检查。
5. 涉及关键页面的改动，跑一遍现有的 E2E 冒烟测试。

**进度跟踪：** 第 2 天结束时，用实际修复速度推算周五能不能清零。如果明显清不完，第 3 天就告诉团队调整预期，不要等到周五。

## 第 3 步（第 5 天）：收尾

- **基线清零：** 删掉基线脚本和 CI 里的比较步骤，改回普通的 `tsc --noEmit`，任何错误都直接失败。检查全仓库没有剩下关闭严格选项的子配置。
- **没有清零：** 选项保持打开，基线继续生效。剩下的错误按目录列出负责人和截止日期。每个保留的 `@ts-expect-error` 都要写原因，等错误修掉后它会自己报错，提醒删除。
- **最终验证：** 全量类型检查、lint、单元测试、E2E 冒烟测试、构建产物对比，都在 main 上跑一遍并通过。

## 风险和应对

| 风险 | 应对 |
|---|---|
| 修复时改坏了运行时行为 | 行为变化必须有测试；PR 尽量小；每个 PR 可以单独撤回 |
| 大家用 `!` 或 `as` 快速"消灭"错误 | lint 规则加计数指标拦截，代码评审时重点看 |
| 编辑器里老文件满屏红线 | 这是预期内的，能推动大家去修；需要的话可以按目录排期 |
| 漏检的 tsconfig 让错误总数暴涨 | 第 0 步先把覆盖范围补齐，再定排期 |
| 和 TypeScript 升级混在一起做 | 本周不升级编译器版本；升级 6.0 及以后版本要单独作为一次迁移来做 |
