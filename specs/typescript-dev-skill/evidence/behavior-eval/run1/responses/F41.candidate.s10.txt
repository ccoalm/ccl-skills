## 方案

用 tsc 编译两次：ESM 输出到 `dist/esm`，CJS 输出到 `dist/cjs`。每个目录配一套自己的 `.d.ts`，再用 `exports` 的 `import` / `require` 条件分别指过去。

单份 `dist/index.d.ts` 不够用。TypeScript 根据同目录 `.js` 是 ESM 还是 CJS 来理解对应的 `.d.ts`，两种格式共用一份声明，总有一方的类型是错的。

现在的 `moduleResolution: bundler` 也不适合发 npm。它默认用户都用打包器，所以允许不带扩展名的相对导入。Node 直接加载 ESM 时，这种导入会失败。库应该用 `nodenext` 来检查。

## 1. 源码要改的地方

- 所有相对导入都加上 `.js` 后缀：`import { x } from './util.js'`（源文件仍是 `util.ts`）。目录导入要写成 `./dir/index.js`。
- 同一份源码要编出 CJS，所以不能用顶层 `await` 和 `import.meta`，也不能依赖 `__dirname`。
- 不要开 `verbatimModuleSyntax`。开了以后，ESM 语法编译成 CJS 会报 TS1286。

## 2. tsconfig 拆成四个

**`tsconfig.base.json`**
```json
{
  "compilerOptions": {
    "target": "es2022",
    "lib": ["es2022"],
    "strict": true,
    "declaration": true,
    "declarationMap": true,
    "sourceMap": true,
    "esModuleInterop": true,
    "rootDir": "src"
  }
}
```

**`tsconfig.esm.json`**（以它为准，按 Node 的真实规则检查）
```json
{
  "extends": "./tsconfig.base.json",
  "compilerOptions": { "module": "nodenext", "moduleResolution": "nodenext", "outDir": "dist/esm" },
  "include": ["src"]
}
```

**`tsconfig.cjs.json`**
```json
{
  "extends": "./tsconfig.base.json",
  "compilerOptions": { "module": "commonjs", "moduleResolution": "bundler", "outDir": "dist/cjs" },
  "include": ["src"]
}
```
`module: commonjs` 搭配 `moduleResolution: bundler` 需要 TypeScript 6.0 及以上。我没有在本机核实过。如果用的是 5.x，或者 tsc 报 TS5095，就改成 `"moduleResolution": "node10"`。这个值在 6.0 已废弃，以后要换掉。

**`tsconfig.json`**（给编辑器和 CI 做类型检查用，覆盖测试和脚本）
```json
{
  "extends": "./tsconfig.esm.json",
  "compilerOptions": { "noEmit": true, "rootDir": "." },
  "include": ["src", "test", "scripts"]
}
```

## 3. `package.json`

```json
{
  "type": "module",
  "main": "./dist/cjs/index.js",
  "types": "./dist/cjs/index.d.ts",
  "module": "./dist/esm/index.js",
  "exports": {
    ".": {
      "import":  { "types": "./dist/esm/index.d.ts", "default": "./dist/esm/index.js" },
      "require": { "types": "./dist/cjs/index.d.ts", "default": "./dist/cjs/index.js" }
    },
    "./package.json": "./package.json"
  },
  "files": ["dist"],
  "scripts": {
    "clean": "node -e \"require('fs').rmSync('dist',{recursive:true,force:true})\"",
    "typecheck": "tsc -p tsconfig.json",
    "build:esm": "tsc -p tsconfig.esm.json",
    "build:cjs": "tsc -p tsconfig.cjs.json && node -e \"require('fs').writeFileSync('dist/cjs/package.json', JSON.stringify({type:'commonjs'}))\"",
    "build": "npm run clean && npm run build:esm && npm run build:cjs",
    "check:pack": "attw --pack . && publint",
    "prepublishOnly": "npm run typecheck && npm run build && npm run check:pack"
  },
  "devDependencies": { "@arethetypeswrong/cli": "*", "publint": "*" }
}
```

这样配的原因：
- **`dist/cjs/package.json` 里的 `{"type":"commonjs"}` 必须有。** 根目录是 `"type": "module"`。没有这个文件，Node 和 TypeScript 都会把 `dist/cjs` 下的 `.js` 和 `.d.ts` 当成 ESM，CJS 用户拿到的类型和运行结果都会出错。
- **`types` 要写在每个条件对象的第一位。** 条件按顺序匹配，排在 `default` 后面的 `types` 永远不会被读到。
- **顶层的 `main` 和 `types`** 只是给老的 `node10` 解析方式兜底，指向 CJS 那套。
- 公开类型里引用到的第三方包必须放在 `dependencies` 或 `peerDependencies` 里，不能只放在 `devDependencies`。
- 以后新增子路径导出（比如 `./utils`）时，也要按同样的 `import` / `require` 结构各配一套类型。

**5) 在临时项目里装真实的 tarball 测试。** 直接对源码目录跑检查，不能证明发出去的包是对的。

```bash
TARBALL=$(npm pack | tail -1); PKG=$(node -p "require('./package.json').name")
for kind in esm cjs bundler; do
  d=$(mktemp -d); cp "$TARBALL" "$d"; cd "$d"
  npm init -y >/dev/null && npm i ./"$TARBALL" typescript >/dev/null
  case $kind in
    esm)     npm pkg set type=module
             echo '{"compilerOptions":{"module":"nodenext","moduleResolution":"nodenext","strict":true,"noEmit":true}}' > tsconfig.json
             echo "import * as m from '$PKG'; const k: string[] = Object.keys(m); console.log('esm', k);" > index.ts ;;
    cjs)     npm pkg set type=commonjs
             echo '{"compilerOptions":{"module":"nodenext","moduleResolution":"nodenext","strict":true,"noEmit":true}}' > tsconfig.json
             echo "import m = require('$PKG'); console.log('cjs', Object.keys(m));" > index.ts ;;
    bundler) echo '{"compilerOptions":{"module":"esnext","moduleResolution":"bundler","strict":true,"noEmit":true}}' > tsconfig.json
             echo "import * as m from '$PKG'; console.log('bundler', Object.keys(m));" > index.ts ;;
  esac
  npx tsc -p . && echo "$kind types OK"
  cd - >/dev/null
done
# 运行时冒烟
node --input-type=module -e "import('$PKG').then(m=>console.log(Object.keys(m)))"  # 在 esm 临时目录执行
node -e "console.log(Object.keys(require('$PKG')))"                                 # 在 cjs 临时目录执行
```

通过标准：
- `attw` 四列全绿。
- 三个临时项目都 `tsc` 通过，并且有一处真实调用的类型不是 `any`。可以在 `index.ts` 里写一句 `const r: <预期类型> = m.someFn(...)` 来确认。
- 两种运行方式导出的名字一致。

## 剩下的风险
- **同一个包被加载两次。** 同一个进程里，ESM 和 CJS 用户各自加载时会得到两份模块实例。如果库里有模块级状态、单例，或者靠 `instanceof` 判断的类，两边会对不上。要么把状态做成无状态，要么让 ESM 入口只是一层包装，内部 re-export CJS 那份。
- **确认还要不要支持 CJS。** Node 20.19+ 和 22.12+ 已经能 `require()` 不含顶层 await 的 ESM。如果你要支持的 Node 版本都在这之上，只发 ESM 会简单很多。你已经明确要两边都支持，所以上面按双格式配置。
- **CJS 构建的模块解析设置**取决于你的 TypeScript 版本，见第 2 节。
