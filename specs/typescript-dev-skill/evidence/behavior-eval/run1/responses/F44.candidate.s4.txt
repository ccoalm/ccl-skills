## 一、tsconfig 结构：用 project references，改一个包只检查受影响的包

```
tsconfig.base.json          # 只放共享的编译选项
tsconfig.json               # 根配置：自身不编译文件，只列出 5 个包
packages/
  core/   tsconfig.json  tsconfig.test.json
  utils/  tsconfig.json  tsconfig.test.json
  api/    tsconfig.json  ...
```

**tsconfig.base.json**：把 6.0 改过的默认值全部写明，换版本时不受默认值变化影响。

```jsonc
{
  "compilerOptions": {
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "noImplicitOverride": true,
    "verbatimModuleSyntax": true,
    "isolatedModules": true,
    "module": "nodenext",            // 浏览器/打包器的包改成 esnext + bundler
    "moduleResolution": "nodenext",
    "target": "es2022",              // 按最老的目标运行时来定，别让它随版本变
    "lib": ["es2022"],
    "types": [],                     // 6.0 起默认就是 []；需要的全局类型在各包里写明
    "noUncheckedSideEffectImports": true,
    "composite": true,               // 会隐含 declaration: true
    "declarationMap": true,
    "incremental": true,
    "skipLibCheck": true             // 如果有手写 .d.ts，要另跑一遍 skipLibCheck:false 检查
  }
}
```

**packages/api/tsconfig.json**：`references` 必须和 `package.json` 里的 `workspace:*` 依赖一一对应。

```jsonc
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "rootDir": "src",
    "outDir": "dist",
    "tsBuildInfoFile": "dist/.tsbuildinfo",
    "types": ["node"]
  },
  "include": ["src"],
  "references": [{ "path": "../core" }, { "path": "../utils" }]
}
```

**packages/api/tsconfig.test.json**：测试代码单独一个工程，不然测试永远没人检查。

```jsonc
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": { "noEmit": false, "emitDeclarationOnly": true, "outDir": "dist-test", "types": ["node", "vitest/globals"] },
  "include": ["test"],
  "references": [{ "path": "." }]
}
```

**根目录 tsconfig.json**：

```jsonc
{ "files": [], "references": [
  { "path": "packages/core" }, { "path": "packages/utils" }, { "path": "packages/api" },
  { "path": "packages/api/tsconfig.test.json" } /* 每个包的 test 工程都列上 */ ] }
```

为什么这样就不用每次整仓重查：
- `tsc -b` 拿 `.tsbuildinfo` 判断哪些工程过期，只重建改动的包和依赖它的包。
- 下游包读的是上游生成的 `.d.ts`，不会再把上游源码检查一遍。
- 如果上游的改动没让 `.d.ts` 变化，下游只更新时间戳，不重新检查。

**包之间按源码还是按产物引用，二选一，不要混用**：
- 推荐：先构建再用。每个包的 `exports` 指向 `dist`，并且 `types` 写在每个条件的第一位。
- 或者：直接引用源码。用自定义的 export 条件加 `customConditions`，同时 vitest、打包器和编辑器都必须认这个条件。
- 混用的结果是编辑器、CI 和运行时看到的类型各不相同。

**还要做两件事**：
- 删掉指向其他包的 `paths` 别名，改用 workspace 依赖或 `package.json#imports`。`baseUrl` 在 6.0 已经弃用。
- 加一个脚本，校验 `references` 和 `package.json` 的依赖是否一致，在 CI 里跑。

## 二、升级步骤：5.x → 6.0 → 7.0，每一步单独一个 PR

我没法查实时发布信息。先跑 `pnpm view typescript dist-tags versions --json`，确认最新大版本是不是 7.0 正式版，再看一下 7.0 的 release notes。

1. **记录基线**（还在 5.x 上）：
   - 先完成上面的 references 改造，跑通 `tsc -b`。
   - 把错误列表、每个包生成的 `.d.ts`、`tsc -b` 的耗时存档。
   - 跑 `pnpm why typescript`，确认整个仓库只有一个 typescript 版本。
2. **列出所有调用编译器 API 的工具**：typescript-eslint、vue-tsc、ts-jest、tsup/rollup 的 dts 插件、api-extractor、ts-morph、编辑器插件等。逐个查它们支持的 TypeScript 版本范围。7.0 是 Go 写的原生编译器，不提供 JS API，这些工具都受影响。
3. **升到 6.0**：
   - 在根目录 `devDependencies` 固定版本，用 `pnpm.overrides` 保证全仓只有一个版本。
   - 修复 6.0 的弃用项：`moduleResolution: node/node10` 改成 `nodenext` 或 `bundler`；去掉 `baseUrl`；补上 `types`。
   - 新出现的错误要么修掉，要么用 `// @ts-expect-error <原因>` 加上原因做局部抑制。
   - 这一步结束时，仓库里不能有 `ignoreDeprecations`。
4. **升到 7.0**：
   - `typescript` 改成 7.x，用它的 `tsc` 做类型检查和构建。
   - 第 2 步里还需要 API 的工具，按官方文档用 `@typescript/typescript6`（提供 `tsc6` 和 6.0 API）和 7.0 并存。这个拆分要在仓库里写明原因，不能是依赖装着装着自己变成这样的。
   - 确认 7.0 对 `tsc -b` 和 project references 的支持程度。如果某个功能还不支持，那部分暂时留在 `tsc6`。
5. **清理**：等工具链都支持 7.0 后，在后续 PR 里逐步删掉第 3 步加的抑制和 `tsc6`。升级 PR 里不要夹带其他类型重构。
