## 一、tsconfig 结构：用 Project References 做增量检查

慢的原因：每个包各自从源码检查全部依赖，或者根目录用一个大 `tsconfig` 一次检查全部。改用 project references 后，每个包检查完会生成 `.d.ts` 和 `.tsbuildinfo`。下游包只读上游的 `.d.ts`，上游没变化就直接跳过。

```
tsconfig.base.json      # 共享编译选项，不含 include
tsconfig.json           # 根：files: []，只列出 references
packages/core/tsconfig.json
packages/utils/tsconfig.json   # references → core
packages/api/tsconfig.json     # references → core, utils
...
```

**`tsconfig.base.json`**（所有选项都写明，不依赖默认值，因为 6.0 改了不少默认值）

```jsonc
{
  "compilerOptions": {
    "composite": true,            // 启用 references 必需，同时隐含 incremental 和 declaration
    "declarationMap": true,       // 编辑器里跳转能直接到源码
    "emitDeclarationOnly": true,  // JS 由 tsup/vite 等打包器产出时用；如果由 tsc 产出 JS，删掉这一行
    "target": "es2022",
    "module": "nodenext",
    "moduleResolution": "nodenext",   // 打包器项目改成 "bundler" + "module": "esnext"
    "verbatimModuleSyntax": true,
    "isolatedModules": true,
    "strict": true,
    "skipLibCheck": true,
    "types": ["node"]             // 6.0 起 types 默认为 []，需要显式写上
  }
}
```

**`packages/api/tsconfig.json`**

```jsonc
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "rootDir": "src",
    "outDir": "dist",
    "tsBuildInfoFile": "dist/.tsbuildinfo"
  },
  "include": ["src"],
  "references": [{ "path": "../core" }, { "path": "../utils" }]
}
```

**根 `tsconfig.json`**

```jsonc
{ "files": [], "references": [
  { "path": "packages/core" }, { "path": "packages/utils" },
  { "path": "packages/api" }, { "path": "packages/web" }, { "path": "packages/cli" }
]}
```

**命令**

| 场景 | 命令 | 检查范围 |
|---|---|---|
| 全仓 | `tsc -b` | 只重新检查有变化的包，以及公开 `.d.ts` 变了的下游包 |
| 只看某个包 | `tsc -b packages/api` | api 加上它的上游；已是最新的上游会跳过 |
| 开发时 | `tsc -b -w` | 增量 watch |
| 查看跳过原因 | `tsc -b --verbose` | 每个项目是否 up to date 以及原因 |

需要注意：

1. **包之间不能有循环引用。** 你说"互相引用"，如果确实存在 A↔B 的循环，`tsc -b` 会直接报错。必须把共用部分抽到 `core`，或者合并这两个包。这一步是这套方案能落地的前提。
2. **`references` 要和 `package.json` 的 `workspace:*` 依赖保持一致。** 漏写 reference 时会读到旧的 `.d.ts`，或者报找不到模块。建议 CI 加一个检查，可以用 `workspaces-to-typescript-project-references --check`，或者写一个几十行的脚本对比两边。
3. `package.json` 里 `exports.types` 指向 `dist/*.d.ts`。
4. CI 缓存 `packages/*/dist` 和 `*.tsbuildinfo`，跨次运行也能增量。
5. 测试 / 脚本文件如果要单独配置，可以加 `tsconfig.test.json`，引用本包后再挂到根 references 上，不要混进主项目。

## 二、升级步骤（每一步单独提交，可以单独回滚）

0. **记录基线**（在 5.x 上）：
   - 运行 `tsc -b --clean && tsc -b`，确认零错误。
   - 保存 `tsc -b --extendedDiagnostics` 输出的耗时。
   - 把当前生成的 `dist/**/*.d.ts` 复制到 `/tmp/dts-before`，供后面对比。
   - 跑一遍全量测试和 lint，保存结果。
1. **统一版本源**：在 `pnpm-workspace.yaml` 用 `catalog:` 管理 typescript，各包写 `"typescript": "catalog:"`，或者只在根 devDependencies 安装一份。用 `pnpm why typescript` 确认只有一个版本。
2. **先做结构改造，再升级**：在 5.x 上完成第一节的 references 改造并通过验证。这样后面出问题时，能分清是结构引起的还是版本引起的。
3. **升到 5.x 的最新补丁版**（5.9）并修掉新报错。
4. **升到 6.0**（这是 5 和 7 之间的过渡版本，主要做弃用清理）：
   - 删掉或替换已弃用的选项：
     - `baseUrl` 改成 `paths` 写相对路径
     - `moduleResolution: node` / `node10` / `classic` 改成 `nodenext` 或 `bundler`
     - `target: es5`
     - `outFile`
     - `downlevelIteration`
     - `module: amd/umd/system`
     - `esModuleInterop: false`
   - 不要用 `"ignoreDeprecations": "6.0"` 长期压住警告。它最多作为临时过渡，因为 7.0 会直接删掉这些选项。
   - 默认值变了的选项（`strict`、`types`、`rootDir`、`module`/`target`）已经在 base 里写明，应该不受影响。
5. **升到 7.x（如果已是 latest）**：编译器改成了原生实现，速度明显更快。但依赖 TS JS API 的工具要逐个确认兼容，包括 typescript-eslint、ts-jest、vue-tsc、ts-node、API Extractor 等。不兼容的话有两条路：
   - 等它们发布适配版本；
   - 让类型检查用 7（`tsc -b`），工具链暂时继续使用 6.x 的 API 包，两者都锁定在 catalog 里。
6. **同步升级周边**：`@types/node`、typescript-eslint（检查 peer 版本范围）、IDE 的 workspace TS 版本（`.vscode/settings.json` 里的 `typescript.tsdk`）。
