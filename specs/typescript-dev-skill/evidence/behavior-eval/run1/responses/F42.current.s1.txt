## 结论

一周把 `strict` 和 `noUncheckedIndexedAccess` 打开可以做到，前提是先定清楚"打开"指什么。我建议这样定义：

- **第 1 天：** 两个开关写进主 `tsconfig.json`，CI 立即对新增错误卡关（基线棘轮）。
- **第 5 天：** 存量错误清零。实在修不完的，用带工单号的 `@ts-expect-error` 显式登记，并设上限。

不建议的做法：
- 把"一周内 0 错误、0 抑制"当硬目标。最后两天容易靠大量 `!`、`as any` 硬凑，开关开了，类型保护却没有。
- 等全部修完再开开关。修复期间新代码还会继续产生错误，数字一直降不下来。

这只是方案，我手上没有这个仓库，下面的数字和工具链都是假设，落地前需要在你们仓库里核实。

## 开工前要知道的几件事

1. **3000 只是下限。** 补上 `noImplicitAny` 的参数类型后，原本是 `any` 的值会开始参与空值检查，错误数会先涨再降。按 1.3–2 倍预估工作量。
2. **`strict` 里只有 `alwaysStrict` 会改变运行时行为**：它会给非 ES module 文件加 `"use strict"`。tsc、esbuild、swc 都会读这个选项。其余子开关只影响类型检查。
3. **修复分两类，风险完全不同：**
   - **纯类型修复**：加注解、`!`、`as`、收窄类型声明。产物 JS 不变，可以机械验证。
   - **行为修复**：加 `if` 守卫、`?? 默认值`、`?.`、改循环写法。会改变运行时行为，要走测试和正常发布。
4. **不报错的检查器也要处理。** vite/esbuild/babel 构建不做类型检查，开关打开不会让构建失败。但如果用了 `fork-ts-checker`、`vite-plugin-checker`、`ts-loader`，打开开关当天构建就会红，要提前把它们指向基线检查，或者关掉它们、只保留 CI 那一步。
5. **生成代码也要处理**（OpenAPI、GraphQL codegen 等）。它们会被类型检查（`skipLibCheck` 只跳过 `.d.ts`），应该改生成器配置后重新生成，而不是手改产物。

安全检查：这次迁移只改编译配置和类型，不涉及身份、计费、权限、租户隔离，没有安全敏感输入。

## 分步方案

### 第 0 天（半天）：度量与准备

| 动作 | 验证 |
|---|---|
| 锁定 TypeScript 版本（精确版本号，不用 `^`），同时锁定 `@types/*` | 两台机器跑同一命令，错误数完全一致 |
| 分开测每个子开关的错误数：`strictNullChecks`、`noImplicitAny`、`strictPropertyInitialization`、`useUnknownInCatchVariables`、`strictFunctionTypes`、`noImplicitThis`、`strictBindCallApply`、`noUncheckedIndexedAccess`，再按目录、按错误码统计 | 得到一张"开关 × 目录 × 错误码"表，用来分配人和排优先级 |
| 记录现状：单测、E2E 通过情况，构建产物的哈希或快照，线上前端错误率（如 Sentry） | 后面所有"没有回归"的判断都和这份基线比 |
| 把错误按目录分给负责人，先排被依赖最多的底层模块（`types/`、`api/`、`utils/`） | 每个目录都有负责人，没有无人认领的错误 |

工作量粗估（假设，需要用第 0 天的统计校准）：约 60% 是机械修复，每个约 1 分钟；约 40% 需要判断，每个 3–10 分钟。合计约 130–150 人时，再加上评审，大约要 4–5 名工程师全职投入一周。人手不够就延期，不要压缩质量标准。

### 第 1 天：打开开关，同时上线基线棘轮

1. **先单独提交只改配置的 PR**：主 `tsconfig.json` 加上 `"strict": true, "noUncheckedIndexedAccess": true`。这样 IDE 里所有人都能直接看到新错误。
2. **基线文件**：按"文件 + 错误码 + 数量"记录，不记行号（行号一动基线就失效）。可以直接用 betterer，也可以自己写一个约 50 行的脚本：

```ts
// scripts/ts-baseline.ts —— 思路示例
// 运行 tsc --noEmit --pretty false，解析每行 "file(line,col): error TSxxxx: ..."
// 按 `${file}|${code}` 统计数量，和 ts-baseline.json 比较：
//   当前数量 > 基线 → 失败（新增错误）
//   当前数量 < 基线 → 失败并提示执行 `--update`（强制基线只降不升）
//   基线里有、当前已没有的 key → 同样要求更新
```

3. CI 增加 `ts-baseline check` 并设为必过检查；把构建期的类型检查插件改为调用它，或者关掉插件。
4. **验证：**
   - 配置 PR 的构建产物，和第 0 天快照逐文件对比。差异只允许出现在非 ESM 文件新增的 `"use strict"` 上。如果有这类文件，单独过一遍：它们是否依赖非严格模式下的 `this` 或给未声明变量赋值。
   - 测试和 E2E 结果与基线一致。
   - 故意构造一个带新错误的 PR，确认 CI 拦下；再构造一个修掉一个错误但没更新基线的 PR，确认 CI 要求更新。
   - 提前通知所有人：从今天起，功能分支 rebase 后，自己改动里新出现的错误要自己修。

### 第 1–4 天：分批清零

**先跑批量工具，再手工修：**
- `noImplicitAny`（7006/7031）：用 TS 自带的"根据用法推断参数类型"代码修复批量处理，例如 Microsoft 的 `ts-fix`（`-e 7006` 等），然后人工抽查推断结果。推断成 `any` 的不算修好。
- `useUnknownInCatchVariables`：常见写法用 codemod 改成 `catch (e) { const err = toError(e) ... }`，统一一个 `toError` 工具函数。
- `strictPropertyInitialization`：确实由框架注入的字段用 `!:`，其他的补初始化。
- `noUncheckedIndexedAccess`，按以下优先级处理：
  1. 按下标遍历的 `for (let i...)` 改成 `for...of` 或 `.entries()`（行为修复，通常安全）。
  2. 键集合固定的 `Record<string, T>` 改成 `Record<'a' | 'b', T>` 或映射类型（纯类型修复，最好）。
  3. `arr[0]` 这类访问补显式判断（行为修复）。
  4. 实在能证明不会越界的才用 `!`，并加一句为什么。
- `strictNullChecks`：先修底层类型定义。接口字段是否可选要以后端契约为准，不能凭感觉，否则会把空值问题推给下游。

**PR 规则（这是验证的核心）：**

| PR 类型 | 内容限制 | 验证 | 评审 |
|---|---|---|---|
| **纯类型修复 PR** | 只改类型、`!`、`as`、注解 | 自动做产物等价检查：对改动文件的改前、改后版本分别跑 `ts.transpileModule`（`removeComments: true`）或 esbuild 去掉类型，输出必须逐字节相同。不同就说明混进了行为改动，打回去拆 PR | 快速评审，看类型是否真实，不能 `any` 了事 |
| **行为修复 PR** | 守卫、默认值、`?.`、循环改写 | 改动的代码路径要有单测；没有的先补一条覆盖"空值或越界"的测试。跑全量单测和相关 E2E | 正常评审，重点看兜底值有没有在业务上把错误吞掉（比如 `?? 0` 让金额静默变成 0） |

**全程生效的约束：**
- ESLint 加 `@typescript-eslint/ban-ts-comment`（禁止 `@ts-ignore`，允许带说明的 `@ts-expect-error`）和 `no-explicit-any`。`no-non-null-assertion` 设为 warn，每天统计 `!` 的新增数量，有明显暴涨就叫停复查。
- PR 按目录拆小，每个最好不超过 300 行，当天合入，减少和功能开发的冲突。

**每天的验证：**
- 看板记录基线剩余错误数（按开关、按目录）、当天新增的 `!` / `as` / `@ts-expect-error` 数量、测试通过率。
- 第 2 天和第 3 天结束时检查进度：如果剩余数量的下降速度撑不到第 5 天清零，就加人或启用第 5 天的兜底，不要等到最后一天才发现。

### 第 5 天：收尾，删掉基线机制

1. 剩余错误先评估能否当天修完。修不完的用脚本批量插入 `// @ts-expect-error TODO(strict-migration): <工单号>`，每条都对应工单和负责人。`@ts-expect-error` 比 `@ts-ignore` 好在：错误修掉后它自己会报错，不会留下失效的抑制。
2. 删除 `ts-baseline.json` 和棘轮脚本，CI 改为直接跑 `tsc --noEmit`，0 错误才算通过。
3. **验证：**
   - `tsc --noEmit` 退出码为 0。
   - `grep -rn "TODO(strict-migration)"` 的数量等于已登记的工单数，并且公布出来。
   - 统计本周新增 `!` / `as any` 的总数（和第 0 天比），作为类型质量的诚实指标。
   - 全量单测、E2E 与第 0 天基线一致。

### 第 6 天之后：上线与观察

- 行为修复会跟着正常发布上线。如果有灰度就走灰度，观察前端错误监控里 `TypeError` 和 `Cannot read properties of undefined` 的变化。预期它们应该减少。如果出现新的错误或业务指标异常，优先排查本周的兜底默认值。
- 剩余的 `@ts-expect-error` 列入后续迭代，每次迭代复查一次数量。
