## 1. 为什么每次都要整仓重查

常见原因有三个，通常同时存在：
- 根目录用一个 `tsc -p` 把所有包一起检查，没有增量；
- 用 `paths` 把 `@scope/core` 指到兄弟包的 `src`，每个包都会把依赖包的源码当成自己的一部分再查一遍；
- 没有开启 `composite` 和 project references，也就没有 `.tsbuildinfo`，TS 不知道哪些包没变。

解决办法是改用 **project references 加 `tsc -b`**。包之间只通过各自生成的 `.d.ts` 依赖。改动没碰到对外 API 时，只重查改动的那个包；对外 API 变了，才会连带重查依赖它的包。

## 2. tsconfig 结构

```
tsconfig.base.json          # 只放共享 compilerOptions
tsconfig.json               # solution：files: []，只列 references
packages/core/tsconfig.json
packages/utils/tsconfig.json   → references core
packages/api/tsconfig.json     → references core, utils
...
```

**tsconfig.base.json**
```jsonc
{
  "compilerOptions": {
    "target": "es2022",
    "module": "nodenext",           // 前端包可改 "preserve" + moduleResolution "bundler"
    "strict": true,
    "composite": true,              // 隐含 declaration + incremental
    "declarationMap": true,         // 编辑器跳转能直接跳到兄弟包源码
    "sourceMap": true,
    "isolatedModules": true,
    "verbatimModuleSyntax": true,
    "skipLibCheck": true,
    "types": ["node"],              // 显式写；TS 6 起默认值变了（见下）
    "forceConsistentCasingInFileNames": true
  }
}
```

**根 tsconfig.json**（只负责编排，自己不编译任何文件）
```jsonc
{
  "files": [],
  "references": [
    { "path": "packages/core" }, { "path": "packages/utils" },
    { "path": "packages/api" },  { "path": "packages/web" }, { "path": "packages/cli" }
  ]
}
```

**packages/api/tsconfig.json**
```jsonc
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": { "rootDir": "src", "outDir": "dist" },
  "include": ["src"],
  "references": [{ "path": "../core" }, { "path": "../utils" }]
}
```

**packages/core/package.json**：兄弟包从 `dist` 拿类型，不用 `paths`
```jsonc
{
  "name": "@scope/core",
  "type": "module",
  "exports": { ".": { "types": "./dist/index.d.ts", "default": "./dist/index.js" } }
}
```
使用方写 `"@scope/core": "workspace:*"`。

要点：
- 删掉指向兄弟包 `src` 的 `paths` 别名，否则 references 不起作用。
- 如果 JS 由 tsup、vite 等打包，tsc 只负责类型时，在对应包里加 `"emitDeclarationOnly": true`。
- 测试文件要单独做类型检查的话，给 `tsconfig.test.json` 再建一个 project，用 references 指向本包的 src project，不要把 test 混进 src 的 `include`。
- 把 `*.tsbuildinfo` 和 `dist/` 加进 `.gitignore`。CI 想要增量，就缓存这两类产物。
- 可选：加上 `"isolatedDeclarations": true`。它要求导出项写显式类型，好处是 `.d.ts` 生成更快，也更利于并行。

脚本：
```jsonc
// 根 package.json
"scripts": {
  "typecheck": "tsc -b",
  "typecheck:clean": "tsc -b --clean && tsc -b"
}
```

## 3. 统一 TypeScript 版本

在 `pnpm-workspace.yaml` 里用 catalog 锁定唯一版本，所有包都写 `"typescript": "catalog:"`：
```yaml
catalog:
  typescript: <目标版本>
```

## 4. 升级步骤（每一步单独提交）

**版本前提**：我不确定你们现在的"最新大版本"指 6.x 还是 7.x，请先跑 `pnpm view typescript dist-tags` 确认。下面按"6.0 是最后一个 JS 实现的版本，7.0 是 Go 原生实现"来安排，具体弃用项以官方 release notes 为准。

0. **先在 5.x 上完成第 2 节的改造**，不和升级混在一起。保存基线：
   ```bash
   tsc -b --pretty false > diag-5x.txt
   cp -r packages/*/dist ../dts-5x/
   ```
   同时用 `--extendedDiagnostics` 记录冷启动和增量各花多少时间。
1. **升到 5.9.x**（5.x 的最后一个小版本），修掉新出现的报错。
2. **升到 6.0**，逐项处理弃用配置，不要长期依赖 `"ignoreDeprecations": "6.0"`：
   - `moduleResolution: node` / `node10` / `classic` 改为 `nodenext` 或 `bundler`；
   - 去掉 `baseUrl`，`paths` 改用相对路径；
   - `target: es5`、`outFile`，以及 `amd` / `umd` / `system` 模块格式都要迁走；
   - 6.0 起几个默认值变了，例如 `strict`、`types`、`rootDir`。按上面的写法把它们都显式写在配置里，就不会因为默认值变化而出问题。
3. **试 7.x（原生实现）**：先在 CI 里加一个并行任务（7.0 正式发布前用 `@typescript/native-preview` 的 `tsgo -b`），对比两边的报错列表和 `.d.ts` 产物。
   - 要注意依赖 TS 编译器 API 的工具，比如 typescript-eslint、ts-morph、vue-tsc、ts-jest。它们可能还不支持 7。确认之前，可以让 `tsc -b` 用 7，同时保留 6.x 给这些工具用（用 npm alias 并存）。
4. 更新 lockfile，确认 `pnpm install --frozen-lockfile` 能通过，并且 `pnpm why typescript` 只显示一个版本。

## 5. 验证

| 要证明的事 | 怎么验证 |
|---|---|
| 依赖图正确 | `tsc -b --verbose` 不报 TS6305/TS6307；`tsc -p packages/api --explainFiles` 里看不到兄弟包的 `src/**` |
| 只改内部实现时只重查一个包 | 改 `core` 里一个没导出的函数体后跑 `tsc -b --verbose`：只有 `core` 被重查，其余显示 *up to date* |
| 改对外 API 时连带重查依赖方 | 改 `core` 导出的类型：`core` 和依赖它的包被重查，和它无关的包被跳过 |
| 增量结果可信 | `pnpm typecheck:clean` 的结果必须和增量构建一致；CI 至少跑一次干净构建 |
| 真的变快了 | 用 `--extendedDiagnostics` 对比第 0 步的基线 |
| 升级没有改变行为 | 报错列表和 `diag-5x.txt` 的差异逐条解释；`dist/**/*.d.ts` 和基线的差异逐条确认（这对外部使用者是公开 API）；单测、lint、构建、启动全部通过 |
| references 和实际依赖不脱节 | CI 加一个小脚本，检查每个包的 `workspace:*` 依赖和 `references` 一一对应，防止以后有人加了依赖却忘了加 reference |
