## 1. 先确认 4 件事（会影响下面的写法）

1. 当前 TypeScript 精确版本（`pnpm -r exec tsc -v`），以及整仓是否只有一个 `typescript`（`pnpm why typescript`）。
2. 哪些工具直接调用编译器 API：typescript-eslint、vue-tsc、tsup 或 rollup 的 dts 插件、api-extractor、ts-jest、ts-morph、vitest 的 typecheck 等。**TS 7.0 没有编程 API，这份清单决定你能不能升到 7。**
3. 分工：谁做类型检查，谁产出 JS，谁产出 `.d.ts`。下面假设 `tsc -b` 只产出声明和做检查，JS 仍由现有打包器产出。
4. 每个包运行在哪：Node 直接加载用 `nodenext`，打包器加载用 `bundler`。

## 2. tsconfig 结构

改一个包要整仓重查，通常有三个原因：没用 project references、`tsc -p` 一次检查全部源码、没有保留 `.tsbuildinfo`。改成 `tsc -b` 后，只重建过期的项目。下游包只有在上游的公开 `.d.ts` 变了时才会重查。

```
tsconfig.base.json          # 共享选项，不含 include
tsconfig.json               # 根 solution：files: []，引用所有叶子项目
tsconfig.tooling.json       # 根目录脚本和配置文件（eslint.config.ts、vite.config.ts）
packages/<pkg>/
  tsconfig.json             # 包级 solution，让编辑器同时认到 lib 和 test
  tsconfig.lib.json         # src，composite
  tsconfig.test.json        # 测试，引用 lib
```

**tsconfig.base.json**：把 TS 6.0 改了默认值的选项全部写明，不依赖默认值。

```jsonc
{
  "compilerOptions": {
    "strict": true,
    "target": "es2022",               // 按最老的运行环境定，不按开发机定
    "lib": ["es2022"],                // 需要 dom 的包自己加
    "module": "nodenext",             // 打包器加载的包改成 esnext + bundler
    "moduleResolution": "nodenext",
    "types": [],                      // 6.0 起默认就是 []，每个项目自己声明
    "verbatimModuleSyntax": true,
    "isolatedModules": true,
    "noUncheckedSideEffectImports": true,
    "composite": true,
    "declaration": true,
    "declarationMap": true,
    "emitDeclarationOnly": true,
    "skipLibCheck": true              // 前提：仓库里没有手写或提交的 .d.ts；有的话见第 4 节
  }
}
```

**packages/api/tsconfig.lib.json**

```jsonc
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "rootDir": "src",                 // 6.0 默认改成 tsconfig 所在目录，要写明
    "outDir": "dist",
    "tsBuildInfoFile": ".tsbuild/lib.tsbuildinfo",
    "types": ["node"]
  },
  "include": ["src"],
  "exclude": ["src/**/*.test.ts"],
  "references": [{ "path": "../shared/tsconfig.lib.json" }]
}
```

**packages/api/tsconfig.test.json**：被引用的项目必须是 composite，所以测试项目把声明输出到一个忽略目录，不用 `noEmit`。

```jsonc
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "rootDir": ".",
    "outDir": ".tsbuild/test",
    "tsBuildInfoFile": ".tsbuild/test.tsbuildinfo",
    "types": ["node", "vitest/globals"]
  },
  "include": ["src/**/*.test.ts", "test"],
  "references": [{ "path": "./tsconfig.lib.json" }]
}
```

**packages/api/tsconfig.json**

```jsonc
{ "files": [], "references": [{ "path": "./tsconfig.lib.json" }, { "path": "./tsconfig.test.json" }] }
```

**根 tsconfig.json**：列出每个包的 lib、test，再加上 `tsconfig.tooling.json`。

```jsonc
{ "files": [], "references": [
  { "path": "packages/shared/tsconfig.lib.json" }, { "path": "packages/shared/tsconfig.test.json" },
  { "path": "packages/api/tsconfig.lib.json" },    { "path": "packages/api/tsconfig.test.json" },
  { "path": "tsconfig.tooling.json" }
] }
```

几条规则：

- **`references` 要和 `package.json` 里的 `workspace:*` 依赖一致。** 依赖方向属于架构决策，出现循环引用是设计问题，不能靠改配置绕过去。CI 里加一个小脚本比对两边，例如：

  ```js
  // scripts/check-refs.mjs：每个 workspace 依赖都必须出现在 tsconfig.lib.json 的 references 里
  import fs from "node:fs"; import path from "node:path";
  const pkgs = fs.readdirSync("packages").map(d => path.join("packages", d));
  const byName = Object.fromEntries(pkgs.map(p => [JSON.parse(fs.readFileSync(`${p}/package.json`)).name, p]));
  let bad = 0;
  for (const p of pkgs) {
    const pj = JSON.parse(fs.readFileSync(`${p}/package.json`));
    const deps = Object.entries({ ...pj.dependencies, ...pj.peerDependencies, ...pj.devDependencies })
      .filter(([, v]) => String(v).startsWith("workspace:")).map(([n]) => byName[n]).filter(Boolean);
    const refs = new Set((JSON.parse(fs.readFileSync(`${p}/tsconfig.lib.json`)).references ?? [])
      .map(r => path.dirname(path.normalize(path.join(p, r.path)))));
    for (const d of deps) if (!refs.has(path.normalize(d))) { console.error(`${p} 缺少对 ${d} 的引用`); bad = 1; }
  }
  process.exit(bad);
  ```

  （tsconfig 里如果有注释，要换成支持 JSONC 的解析器。）
- **包之间统一用 build-first。** 每个包的 `exports` 指向 `dist`，`types` 写在每个条件的第一位，例如 `"exports": { ".": { "types": "./dist/index.d.ts", "default": "./dist/index.js" } }`。有了 references，编辑器跳转时会自动定位到源码。不要一部分包走源码、一部分包走 dist，否则编辑器、CI 和运行时看到的类型会不一样。
- **路径别名**：去掉 `baseUrl`（6.0 已弃用）。包内别名改用 `package.json#imports`（`#internal/*`），包之间直接用包名导入。
- **TypeScript 只保留一个版本**：只在根 `devDependencies` 安装，或用 pnpm catalog 统一，并加 `pnpm.overrides` 锁住版本，避免某个包悄悄用上别的版本。
- **CI 缓存** `**/.tsbuild`、`**/dist` 和 `*.tsbuildinfo`，缓存键里带上锁文件哈希。不缓存的话，CI 每次都等于整仓重查，本地增量的收益到不了 CI。

## 3. 升级步骤（按版本一步一步来，每步单独提交、单独合并）

截至今天，最新大版本应该是 **7.0**（Go 写的原生编译器）。它沿用 6.0 的默认值，把 6.0 里弃用的选项变成硬错误，并且**没有编程 API**。所以路线是 5.x → 6.0 → 7.0，不要直接跳。具体版本号和包名以官方发布说明为准，动手前请再核对一次。

**第 0 步：在 5.x 上重构结构（不升级版本）**
- 先记录基线：`tsc` 的错误数（应为 0）、构建产物的 `.d.ts`（保存到 `/tmp/dts-5x`），以及 CI 类型检查耗时。
- 按第 2 节改成 references，跑通 `tsc -b`，检查 `.d.ts` 和基线没有差异。
- 这一步只改结构，不改选项，也不修类型。

**第 1 步：在 5.x 上把隐式默认值写明**
- 在 base 里写明 `strict`、`module`、`target`、`types`、`rootDir`、`noUncheckedSideEffectImports`。最后这个选项在 5.x 上就要打开，并修掉它报的错。
- `moduleResolution: node`/`node10` 改成 `nodenext` 或 `bundler`，`baseUrl` 改成 `paths` 里写全前缀，或者改用 `imports`。
- 完成后，升级到 6.0 时就不会因为默认值变化而产生意外。

**第 2 步：升到 6.0**
- 执行 `pnpm add -Dw typescript@^6`，确认 typescript-eslint 等 API 消费方声明支持 6.0。
- 跑 `tsc -b`。每个新报错要么修掉，要么加 `// @ts-expect-error <原因>`，并另开一个后续任务把它们清掉。**不要加 `ignoreDeprecations`**，那样到 7.0 会直接报错。
- 不要顺带做和升级无关的类型重构。

**第 3 步：升到 7.0**
- 前提：6.0 下零错误，没有 `ignoreDeprecations`，API 消费方清单已经完成。
- 用 7.0 的 `tsc` 跑 CI 类型检查门。需要编程 API 的工具，按官方文档的方式解析到 `@typescript/typescript6`（它带 `tsc6` 和 6.0 API）。typescript-eslint 是否支持、怎么配置，查它当时的版本支持范围。
- 用 `pnpm why typescript` 和各工具的 `--version` 确认两个版本是**有意并存**，并写进仓库的 AGENTS.md 或 README。
- 如果关键工具（比如 vue-tsc）还不能和 7.0 配合，**就先停在 6.0**。6.0 是合理的停靠点；为了凑最新版本而关掉检查不值得。
- 确认 7.0 的 `tsc -b` 对 project references 和增量构建的支持程度，以发布说明为准。不支持的话，第 2 节的增量收益就要靠 6.0 的 `tsc6 -b` 来拿。
