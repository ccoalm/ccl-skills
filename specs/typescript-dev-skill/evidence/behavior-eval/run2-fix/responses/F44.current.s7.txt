## 一、tsconfig 结构：用项目引用（project references）+ `tsc -b`

整仓重新检查的原因，通常是根目录只有一个大 `tsconfig`，或者每个包各跑一次 `tsc --noEmit`，每次都从头检查。改法是：每个包是一个 `composite` 项目，根目录放一个只负责列引用的总配置（下文叫"汇总配置"），用 `tsc -b` 做增量构建。

- 没改过的项目直接跳过。
- 改了一个包，只有它对外的 `.d.ts` 变了，依赖它的包才会重新检查。只改内部实现时，依赖它的包也跳过。

```
tsconfig.base.json        # 共享选项
tsconfig.json             # 汇总配置：files: []，引用所有项目
packages/core/tsconfig.json        # 源码项目
packages/core/tsconfig.test.json   # 测试项目，引用 ./tsconfig.json
packages/api/tsconfig.json         # references: core
...
```

**`tsconfig.base.json`**：6.0 改过默认值的选项全部显式写出，以后换版本行为也不会悄悄变。

```jsonc
{
  "compilerOptions": {
    "composite": true,
    "declaration": true,
    "declarationMap": true,
    "sourceMap": true,
    "strict": true,
    "target": "es2022",          // 按支持的最老 Node 版本定
    "lib": ["es2022"],
    "module": "nodenext",
    "moduleResolution": "nodenext",
    "verbatimModuleSyntax": true,
    "isolatedModules": true,
    "noUncheckedSideEffectImports": true,
    "skipLibCheck": true,        // 如果有手写的 .d.ts，另起一个 skipLibCheck:false 的检查
    "types": []                  // 每个包按需自己声明
    // 仓库里现有的严格选项（noUncheckedIndexedAccess 等）原样保留，不要借这次升级改
  }
}
```

**`packages/api/tsconfig.json`**

```jsonc
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": { "rootDir": "src", "outDir": "dist", "types": ["node"] },
  "include": ["src"],
  "references": [{ "path": "../core" }]
}
```

**`packages/api/tsconfig.test.json`**：测试和脚本也要纳入检查。

```jsonc
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "rootDir": ".", "outDir": "../../node_modules/.cache/tsc/api-test",
    "emitDeclarationOnly": true, "types": ["node", "vitest/globals"]
  },
  "include": ["test", "scripts"],
  "references": [{ "path": "./tsconfig.json" }]
}
```

**根目录 `tsconfig.json`**

```jsonc
{ "files": [], "references": [
  { "path": "packages/core" }, { "path": "packages/core/tsconfig.test.json" },
  { "path": "packages/api" },  { "path": "packages/api/tsconfig.test.json" }
  // …五个包都列上
]}
```

**包之间怎么引用**：统一采用"先构建"。依赖写 `"@scope/core": "workspace:*"`，`exports` 指向构建产物，并且把 `types` 放在第一位：

```json
"exports": { ".": { "types": "./dist/index.d.ts", "default": "./dist/index.js" } }
```

不要一部分包走源码、一部分包走 `dist`，否则编辑器、CI 和运行时看到的类型会不一样。

几条约束：

- `references` 必须和 `package.json` 里的 workspace 依赖一一对应。出现循环引用是架构问题，不能靠改配置绕过。
- `paths`/`baseUrl` 只对编译器生效，运行时不认。包内别名改用 `package.json#imports`（`#internal/*`）。

**脚本**

```jsonc
// 根 package.json
"typecheck": "tsc -b",            // 增量构建，没变的项目直接跳过
"typecheck:clean": "tsc -b --clean && tsc -b"
// 包内
"typecheck": "tsc -b tsconfig.test.json"   // 检查本包及上游，上游有缓存
```

CI 里要缓存 `**/*.tsbuildinfo` 和 `dist`。这两样没缓存，CI 每次仍然是全量检查。

## 二、升级步骤（5.x → 6.0 → 7.x）

1. **先盘点，不改版本**
   - 用 `pnpm ls -r typescript` 和 `pnpm why typescript` 确认整个仓库只解析出一个 `typescript`。
   - 找出所有调用编译器 API 的工具：typescript-eslint、ts-jest、ts-node、vue-tsc、api-extractor、rollup-plugin-dts、typedoc、编辑器插件等。
   - 用 `pnpm view typescript version` 和官方发布说明确认当前最新的大版本。我手头的记录是 7.0 已发布，但请以发布说明为准。
2. **先把上面的项目引用改造合进去，提交独立**：在当前 5.x 上完成，`tsc -b` 全绿后再开始升级。升级和结构改造不要放在一个提交里。
3. **升到 6.0（过渡版本）**：在根目录固定版本（pnpm `catalog:` 或 `overrides`，保证只有一份）。然后处理废弃项：
   - `moduleResolution: node`/`node10` 改成 `nodenext` 或 `bundler`。
   - 去掉作为查找根目录的 `baseUrl`，把前缀写进每条 `paths`。
   - 每个包显式写 `types`。
   - 新增的报错要么修掉，要么用 `// @ts-expect-error <原因>` 临时压住。
   - 验收标准是：不靠 `ignoreDeprecations` 也能编译通过。
4. **升到 7.x（Go 实现的原生编译器）**：7.0 把 6.0 的废弃项变成了硬错误，而且**不提供编译器 API**。
   - 要用 API 的工具（typescript-eslint 等）改用官方的 `@typescript/typescript6`（提供 `tsc6` 和 6.0 API），具体怎么指过去按官方公告写法来。这类"两个版本并存"的情况要写进仓库文档。
   - 先确认 typescript-eslint 当前支持的 TS 版本范围。
   - 再确认 7.x 当前版本是否完整支持 `-b`/增量构建。如果不支持，构建先留在 6.0，等支持了再切。
5. **收尾**：在后续提交里逐条清掉临时的 `@ts-expect-error`。


- 只改 `core` 的内部实现，`--verbose` 里只有 `core`（和它的测试项目）重新构建，下游显示 up to date。
- 改 `core` 的导出类型，它的下游会重新检查。
- 把这两个结果和改造前的耗时一起记下来，作为"不再整仓重检"的证据。
