## 一、tsconfig 结构：用 project references 只重查改过的包

改一个包就整仓重查，原因通常是只有一个大 tsconfig，或者每个包用 `paths` 直接引用别的包的源码。改成每个包是一个独立的 `composite` 项目，再用 `tsc -b` 增量构建。`tsc -b` 会跳过已是最新的项目；被依赖的包如果生成的 `.d.ts` 没变，依赖它的包也不会重查。

```
tsconfig.base.json          # 共享选项，不包含任何文件
tsconfig.json               # 根配置：只列出所有包，自己不编译文件
packages/core/tsconfig.json
packages/core/tsconfig.test.json   # 测试用的全局类型不同，单独一个项目
packages/utils/...
```

**tsconfig.base.json**：把 6.0 改了默认值的选项都写明，升级时就不会被悄悄改掉。

```jsonc
{
  "compilerOptions": {
    "composite": true,              // 隐含 declaration；include 必须覆盖所有源文件
    "incremental": true,
    "declarationMap": true,         // 编辑器跳转到源码
    "strict": true,
    "target": "es2022",             // 按最老的运行时定，别让它跟着版本变
    "module": "nodenext",           // Node 直接加载的包；前端包在自己的配置里改成 esnext + bundler
    "moduleResolution": "nodenext",
    "verbatimModuleSyntax": true,
    "isolatedModules": true,
    "noUncheckedSideEffectImports": true,
    "types": [],                    // 每个项目自己写明需要的全局类型
    "skipLibCheck": true            // 前提：仓库里没有手写或提交进来的 .d.ts
  }
}
```

**packages/api/tsconfig.json**（依赖 core 和 utils）：

```jsonc
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "rootDir": "src",
    "outDir": "dist",
    "tsBuildInfoFile": "dist/.tsbuildinfo",
    "types": ["node"]
  },
  "include": ["src"],
  "references": [{ "path": "../core" }, { "path": "../utils" }]
}
```

**packages/api/tsconfig.test.json**：

```jsonc
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": { "noEmit": false, "emitDeclarationOnly": true, "outDir": "dist-test",
                       "rootDir": ".", "types": ["node", "vitest/globals"] },
  "include": ["test"],
  "references": [{ "path": "." }]
}
```

**根 tsconfig.json**：

```jsonc
{ "files": [], "references": [
  { "path": "packages/core" }, { "path": "packages/core/tsconfig.test.json" },
  { "path": "packages/utils" }, /* …五个包和各自的 test 配置都列上 */ ] }
```

几个必须定下来的点：

- **`references` 必须和 `package.json` 里的 `workspace:*` 依赖一致**。在 CI 里加一个脚本比对两者，不一致就失败。项目之间出现循环引用说明架构有问题，不要靠改配置绕过去。
- **包之间按"先构建再引用"的方式消费**。每个包的 `exports` 指向 `dist`，`types` 条件写在最前面；把跨包的 `paths` 删掉。要是想直接引用源码，就得用 `customConditions`，而且打包器和测试运行器都要支持同一个条件。两种方式混着用，编辑器、CI 和运行时看到的类型会不一样。
- **如果 JS 由 tsup、esbuild、Vite 等工具产出**，`tsc -b` 用 `emitDeclarationOnly` 只负责类型检查和生成 `.d.ts`。
- **常用命令**：
  - 根目录：`"typecheck": "tsc -b"`
  - 只检查某个包及它的依赖：`tsc -b packages/api`
  - 开发时：`tsc -b -w`
  - CI 缓存 `**/*.tsbuildinfo` 和 `dist`，缓存 key 带上 lockfile 的哈希。

## 二、升级步骤：5.x → 6.0 → 7.0，每步单独一个 PR

到 2026-11，"最新大版本"应该是 7.0，也就是用 Go 写的原生编译器。动手前先查一下官方 release notes 确认版本状态，以及 `--build` / project references 是否已经完全支持。

**第 0 步：拆 references（还在 5.x 上做）**
- 先记录基线：`tsc -b --extendedDiagnostics`，并把现在的报错输出保存成 `before.txt`。
- 列出所有直接调用编译器 API 的工具：typescript-eslint、vitest 的类型检查、ts-jest/ts-node、api-extractor/rollup-plugin-dts、vue-tsc 等。
- 结构调整和版本升级分开提交，否则出了新报错分不清是哪一步引起的。

**第 1 步：升级到 6.0**
1. 整个仓库只保留一个 `typescript` 版本，用 pnpm catalog 或在根 `devDependencies` 固定，并用 `pnpm why -r typescript` 确认没有第二个版本。
2. 修掉所有弃用告警：
   - `moduleResolution: node`/`node10` 改成 `nodenext` 或 `bundler`；
   - 删掉 `baseUrl`，把前缀直接写进每个 `paths` 条目，或者改用 `package.json#imports`；
   - 测试和 Node 用到的全局类型都写进各项目的 `types`。
3. 新出现的类型错误：能改就改；暂时改不了的，用 `// @ts-expect-error <原因>` 压住。不要降低 `strict`。
4. `"ignoreDeprecations": "6.0"` 只能作为临时过渡，**必须删掉之后才能进入下一步**，因为 7.0 会把这些弃用直接变成错误。
5. 确认 typescript-eslint 等工具的支持版本范围已经包含 6.0。

**第 2 步：升级到 7.0**
1. 前提：6.0 下没有任何报错，也没有 `ignoreDeprecations`。
2. 命令行的 `tsc -b` 换成 7.0。
3. 7.0 没有编程 API，所以第 0 步列出的那些工具要继续跑在 6.0 的 API 上。TypeScript 团队为此发布了 `@typescript/typescript6`（自带 `tsc6` 命令和 6.0 的 API）。按官方文档给出的别名方式，对每个工具分别指定用哪一版，并把这个双版本安排写进仓库文档。不要无意中混出两个版本。
4. 回滚方式：直接 revert 改版本号和 lockfile 的那个提交。
