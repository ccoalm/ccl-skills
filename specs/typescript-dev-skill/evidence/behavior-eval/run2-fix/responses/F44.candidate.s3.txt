## 一、为什么每次都要整仓重查

常见原因有三个：

1. **没用 project references**。每个包各跑一遍 `tsc --noEmit`，不会增量。
2. **包之间通过 `exports` 或 `paths` 直接引用对方的 `src/*.ts`**。这样每个包都会把依赖包的源码再检查一遍，等于整仓重查。
3. **CI 或本地脚本按包循环跑 `tsc -p`**，而不是在根目录跑一次 `tsc -b`。

## 二、tsconfig 结构

```
tsconfig.base.json          # 共享选项，不含 include
tsconfig.json               # solution：files: []，引用所有叶子项目
packages/a/tsconfig.json    # composite，只含 src
packages/a/tsconfig.test.json  # 测试，引用 ./tsconfig.json
...
```

**tsconfig.base.json**：选项都写成显式值，不依赖默认值，因为 6.0 改了一批默认值。

```jsonc
{
  "compilerOptions": {
    "composite": true,
    "declaration": true,
    "declarationMap": true,
    "incremental": true,
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "verbatimModuleSyntax": true,
    "isolatedModules": true,
    "module": "nodenext",            // 打包器负责解析的前端包改成 esnext + bundler
    "moduleResolution": "nodenext",
    "target": "es2023",              // 按最老的目标运行时填，不要用默认值
    "lib": ["es2023"],
    "types": [],                     // 6.0+ 默认就是 []，每个包自己声明需要的全局类型
    "noUncheckedSideEffectImports": true,
    "skipLibCheck": true             // 如果有手写的 .d.ts，另外加一道 skipLibCheck:false 的检查
  }
}
```

**根目录 tsconfig.json（solution）**

```jsonc
{
  "files": [],
  "references": [
    { "path": "packages/a" }, { "path": "packages/b" }, { "path": "packages/c" },
    { "path": "packages/d" }, { "path": "packages/e" },
    { "path": "packages/a/tsconfig.test.json" }
    // …每个包的 test 项目都要列上，否则测试代码不会被检查
  ]
}
```

**packages/b/tsconfig.json**（假设 b 依赖 a）

```jsonc
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "rootDir": "src",
    "outDir": "dist",
    "tsBuildInfoFile": "dist/.tsbuildinfo",
    "types": ["node"]
  },
  "include": ["src"],
  "references": [{ "path": "../a" }]   // 必须和 package.json 里的 workspace 依赖一一对应
}
```

**packages/b/tsconfig.test.json**

```jsonc
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "rootDir": ".",
    "outDir": "dist-test-types",
    "emitDeclarationOnly": true,
    "types": ["node", "vitest/globals"]
  },
  "include": ["test"],
  "references": [{ "path": "./tsconfig.json" }]
}
```

**最关键的一点：包之间引用构建产物。** `packages/a/package.json` 这样写：

```jsonc
"exports": { ".": { "types": "./dist/index.d.ts", "default": "./dist/index.js" } }
```

`types` 要放在每个条件对象的第一位。这样 b 只读 a 的 `.d.ts`，不会去检查 a 的源码。之后改 a 的内部实现，只要 a 的公开 `.d.ts` 不变，b 到 e 都不会重查；只有公开类型变了，才会重查下游。

如果想让编辑器直接跳到源码，可以改用 `customConditions` 走源码，但打包器和测试运行器也必须认这个条件。这两种方式不要混用，否则编辑器、CI 和运行时看到的类型会不一致。

**脚本**

```jsonc
"typecheck": "tsc -b",
"typecheck:clean": "tsc -b --clean && tsc -b"
```

## 三、升级步骤（5.x → 6.0 → 7.0，不要一步跳过去）

整个升级过程中都不要顺手做无关的类型重构。

**第 0 步：先只改结构，不换编译器版本。**
在当前的 5.x 上落地上面的 references 结构，确认 `tsc -b` 零错误。这一步单独提交，这样后面出错时能分清是结构问题还是版本问题。

**第 1 步：列出所有依赖编译器 API 的工具。**

```bash
pnpm why typescript -r
```

查出所有用到 `typescript` 包 API 的工具，常见的有 typescript-eslint、vue-tsc、tsup 和 rollup 的 dts 插件、api-extractor、ts-jest、ts-node、编辑器插件。TS 7.0 **没有编程 API**，这些工具要逐个决定怎么处理。typescript-eslint 还要核对它支持的 TS 版本范围。

**第 2 步：升到 6.0，作为过渡。**

```bash
pnpm add -Dw typescript@^6
```

- 修掉弃用项。`moduleResolution: node`/`node10` 改成 `nodenext` 或 `bundler`。`baseUrl` 不要再当查找根，前缀写进每条 `paths`，最好改用 `package.json#imports`。
- 处理默认值变化带来的新报错：`types: []`、`rootDir`、`noUncheckedSideEffectImports`、`strict`。
- 需要临时压制时，源码里的报错用 `// @ts-expect-error <原因>`。弃用选项的报错（TS5101、TS5107）报在 tsconfig 上，只能临时加 `"ignoreDeprecations": "6.0"`。**必须清空 `ignoreDeprecations` 之后才能进入下一步**，因为 7.0 会把这些弃用项变成硬错误。

**第 3 步：升到 7.0。**

- 根目录只保留一份 `typescript` 解析，用 `pnpm.overrides` 固定版本，lockfile 要提交。
- 第 1 步里需要编译器 API 的工具，继续用 TypeScript 团队发布的 `@typescript/typescript6`（提供 `tsc6` 和 6.0 的 API）跑在旁边。具体的别名写法以官方文档为准。这个分拆是刻意的，要写进仓库说明，不能是装依赖时意外混进去的。
- 确认 7.0 的 `--build` 和 project references 在你实际用的版本上可用（看 release notes）。不可用的话，这一步先暂停。

**第 4 步：收尾。** 在后续的提交里逐个移除 `@ts-expect-error`，并删掉 `tsc6` 依赖里已经不需要的部分。

## 四、验证

| 验证什么 | 命令和通过标准 |
|---|---|
| 全量零错误 | 在干净环境里执行 `tsc -b --clean && tsc -b`，退出码为 0 |
| 增量生效 | 改 c 的一个内部函数实现，不改导出类型，再跑 `tsc -b --verbose`：只有 c 和 c 的测试项目被重建，其他项目显示 up to date |
| 公开类型变化会传给下游 | 改 a 的一个导出签名：依赖 a 的项目被重建，并在使用处报错 |
| 依赖关系一致 | 写个小脚本，对比每个包 `package.json` 里的 `workspace:*` 依赖和 `references`，不一致就失败。顺便确认引用没有环 |
| 测试和脚本也被检查 | 在 `test/` 里故意写一个类型错误，`tsc -b` 必须失败 |
| 升级前后对比 | 每一步都记录 `tsc -b --extendedDiagnostics` 的耗时和错误数 |
| 类型化 lint | typescript-eslint 用 `recommendedTypeChecked` 加 `projectService: true`，在 CI 里设为 error 级别，跑在它支持的 TS 版本上 |
| 运行时和构建 | 跑单测和各包构建。注意 tsx、esbuild、Vite 能跑通**不代表类型检查通过** |
| 对外发布的包 | `pnpm pack` 后执行 `attw --pack .`，再在一个临时项目里用 `nodenext` 和 `bundler` 两种方式导入每个入口做类型检查 |

CI 门禁是根目录跑一次 `tsc -b`，任何错误都算失败。CI 可以缓存 `.tsbuildinfo`，但每周至少跑一次不带缓存的全量检查，防止缓存掩盖问题。
