## 一、为什么每次都要整仓检查

通常是用一个根 `tsconfig` 用 `include` 把所有包都包进来，或者各包通过 `paths` 直接引用别的包的源码。这样 tsc 只看到一个大程序，改一个文件就得全部重新检查。

改法是用 **project references（项目引用）+ `tsc -b`**。每个包是一个 `composite` 项目，各自有构建缓存（`.tsbuildinfo`）。改一个包时：
- 只重新检查这个包；
- 只有它对外的 `.d.ts` 变了，才重新检查依赖它的下游包；
- 只改了函数内部、对外类型不变时，下游直接跳过。

## 二、tsconfig 结构

```
repo/
├─ tsconfig.base.json        # 共享选项，不含 include/references
├─ tsconfig.json             # 根配置：files: []，引用所有包
└─ packages/
   ├─ core/
   │  ├─ tsconfig.json       # 源码：composite，输出到 dist
   │  └─ tsconfig.test.json  # 测试：引用 ./tsconfig.json，不输出
   ├─ utils/ ...
   └─ app/   ...
```

**tsconfig.base.json**：把 6.0 改了默认值的选项都写明，不依赖默认值。

```jsonc
{
  "compilerOptions": {
    "target": "es2023",            // 按实际支持的最老 Node 版本定
    "lib": ["es2023"],
    "module": "nodenext",
    "moduleResolution": "nodenext",
    "strict": true,                // 保持现有严格度，升级时不顺手加新 flag
    "verbatimModuleSyntax": true,
    "isolatedModules": true,
    "noUncheckedSideEffectImports": true,
    "types": [],                   // 6.0 起默认就是 []，各包自己声明需要的全局类型
    "composite": true,
    "declaration": true,
    "declarationMap": true,        // 编辑器跳转定义能到源码，而不是 .d.ts
    "sourceMap": true,
    "skipLibCheck": true           // 只跳过第三方；手写 .d.ts 要单独用 false 检查
  }
}
```

**packages/core/tsconfig.json**（源码）

```jsonc
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "rootDir": "src",              // 6.0 默认值改了，必须写明
    "outDir": "dist",
    "types": ["node"]
  },
  "include": ["src"],
  "references": [{ "path": "../utils" }]   // 必须和 package.json 里的 workspace 依赖一一对应
}
```

**packages/core/tsconfig.test.json**（测试和脚本也要检查，但不能输出到 dist）

```jsonc
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "rootDir": ".",
    "noEmit": true,
    "types": ["node", "vitest/globals"]
  },
  "include": ["test", "scripts"],
  "references": [{ "path": "./tsconfig.json" }]
}
```

如果你用的版本拒绝 `composite` 项目设 `noEmit`，就改成 `emitDeclarationOnly` 加独立的 `outDir`。

**根 tsconfig.json**

```jsonc
{
  "files": [],
  "references": [
    { "path": "packages/utils" }, { "path": "packages/utils/tsconfig.test.json" },
    { "path": "packages/core" },  { "path": "packages/core/tsconfig.test.json" }
    // ...五个包都列上
  ]
}
```

**各包 package.json**：采用先构建、再从 dist 消费类型的方式，`types` 放在第一位。

```jsonc
{
  "type": "module",
  "exports": { ".": { "types": "./dist/index.d.ts", "default": "./dist/index.js" } },
  "dependencies": { "@scope/utils": "workspace:*" }
}
```

几个必须定下来的点：
- **不要再用 `paths` 指向别的包的 `src`**。另外 6.0 已经弃用 `baseUrl`。
- 如果测试工具或打包工具要直接读源码，就统一用 `customConditions`，再加一个自定义 export 条件，让 tsc、vitest、打包工具都认同一个条件。不要一部分走源码、一部分走 dist，否则编辑器、CI 和运行时看到的类型会不一样。
- 加一个 CI 小脚本，比对 `package.json` 的 `workspace:*` 依赖和 `references`，不一致就失败。包之间如果出现循环引用，那是包怎么拆分的设计问题，不是改配置能解决的。

**脚本**

```jsonc
// 根 package.json
"typecheck": "tsc -b",
"typecheck:watch": "tsc -b -w",
"typecheck:clean": "tsc -b --clean"
```

本地改了某个包，直接跑 `pnpm typecheck` 就行，没过期的项目会自动跳过。如果只想检查某个包加它的下游，用 `pnpm --filter "...@scope/core" exec tsc -b`。

## 三、升级步骤（三个阶段，各自一个 PR，不和别的类型重构混在一起）

先确认最新版本：`pnpm view typescript dist-tags`。到 2026 年最新的大版本应该是 7.0，也就是 Go 写的原生编译器。它会把 6.0 的弃用项变成硬错误，而且**没有编程 API**。所以不能从 5.x 直接跳到 7，要走 5.x → 6.0 → 7.0。

**阶段 0：在当前 5.x 上改成 references 结构，并记录基线**
1. 按第二节改结构，确认 `tsc -b` 零错误。
2. 记录基线：
   - `tsc -b --extendedDiagnostics` 的耗时；
   - 把所有 `dist/**/*.d.ts` 复制一份作为快照（`cp -r` 到 `/tmp/dts-baseline`）。
3. 列出所有调用 TypeScript 编程 API 的工具：typescript-eslint、vue-tsc、ts-jest/ts-node、api-extractor、rollup-plugin-dts（tsup 的 dts）、typedoc、ts-morph 等，可以用 `pnpm why typescript` 查。

**阶段 1：升级到 6.0**
1. 在根 `package.json` 写死 `typescript` 版本，用 `pnpm.overrides` 保证整仓只解析出一个版本。
2. `tsc -b --clean && tsc -b`，逐条处理报错：
   - `moduleResolution: node`/`node10` 改成 `nodenext`（Node 加载的包）或 `bundler`（打包工具处理的包）；
   - 去掉 `baseUrl`，把前缀写进每条 `paths`；
   - 默认的 `types: []` 会让 `node`、测试框架的全局类型消失，在各 tsconfig 里显式写上；
   - 把 `rootDir`、`target`、`module` 写成显式值。
   - 其他弃用项以官方 6.0 release notes 为准。
3. 源码上的新报错先修。修不了的用 `// @ts-expect-error <原因>` 压住，不要用 `@ts-ignore`。tsconfig 上的弃用报错（TS5101/TS5107）只能用 `"ignoreDeprecations": "6.0"` 临时压住，必须在下一个 PR 里清掉。
4. 确认 typescript-eslint 等工具的支持范围已经包含 6.0。

**阶段 2：升级到 7.0**
1. 进入条件：
   - 仓库里搜不到 `ignoreDeprecations`（`grep -r ignoreDeprecations` 结果为空）；
   - 6.0 下零错误；
   - 所有调用编程 API 的工具都有处理方案。
2. 类型检查和构建用 7.0 的 `tsc`。仍然需要编程 API 的工具（主要是 typescript-eslint）继续用 6.0 的 API，具体按官方文档说的 `@typescript/typescript6` 别名方式接入。这个双版本并存要写进仓库文档，不能是无意中混进来的。
3. 确认你装的 7.x 已经完整支持 `--build`/`composite`/增量构建。早期预览版在这方面不全，以 release notes 为准。

## 四、验证（每个阶段都跑一遍）

| 检查项 | 命令或方法 | 通过标准 |
|---|---|---|
| 版本唯一 | `pnpm why typescript`、`pnpm -r exec tsc -v` | 只有一个 `typescript`；如果有 6.0 API 别名，必须是有意保留并记录过的 |
| 全量类型检查 | `tsc -b --clean && tsc -b` | 零错误，并且根配置覆盖了每个包的源码、测试和脚本 |
| 增量生效 | 改一个叶子包内部实现，跑 `tsc -b --verbose` | 只重建这个包，下游显示 up to date |
| 下游会重查 | 改一个导出的类型，再跑 `tsc -b --verbose` | 这个包和它的下游都重新检查 |
| 类型没变 | 把新 `dist/**/*.d.ts` 和基线快照做 `diff -r` | 没有差异；有差异要能逐条解释 |
| 手写声明 | `tsc --noEmit --skipLibCheck false -p <含 types/ 的配置>` | 零错误 |
| 类型 lint | `eslint .`（`*TypeChecked` 规则集 + `projectService`） | 零 error |
| 运行时 | 测试和构建 | 全部通过。注意：打包工具或 tsx 跑通**不算**类型检查通过 |
| 发布包（如果有） | `pnpm pack` 后跑 `attw --pack .` | 每个入口都没有类型问题 |
| 性能 | 再跑 `tsc -b --extendedDiagnostics` 和基线对比 | 记录全量和增量耗时 |
