## 一、为什么每次都要整仓检查

通常是下面三种情况之一：

1. 根目录只有一个 `tsconfig.json`，`include` 了所有包。
2. 包之间用 `paths` 别名直接引用对方的源码，所以编辑器和 CI 每次都要从头编整个程序。
3. 没开 `composite`，也没用 `tsc -b`，所以没有增量信息，也不知道包之间的依赖顺序。

解决办法是改成 **project references（项目引用）+ `tsc -b`**。改了一个包，只重新检查这个包；只有它导出的 `.d.ts` 变了，才会继续检查依赖它的包。

## 二、tsconfig 结构

```
repo/
├─ tsconfig.base.json        # 共享编译选项，不含 include/references
├─ tsconfig.json             # 总入口：files: []，引用全部五个包
└─ packages/
   ├─ a/ tsconfig.json       # 叶子包，不引用其他包
   ├─ b/ tsconfig.json       # references: [a]
   └─ ...
```

**`tsconfig.base.json`**：所有默认值都显式写出来，这样升级到 6/7 时行为不会因为默认值变化而悄悄改变。

```jsonc
{
  "compilerOptions": {
    "strict": true,
    "target": "es2022",              // 按最老的目标运行时填写
    "lib": ["es2022"],               // 浏览器包在自己的 tsconfig 里加 "dom"
    "module": "nodenext",            // Node 直接加载的代码用 nodenext；全部由打包器处理的包用 esnext + "moduleResolution": "bundler"
    "moduleResolution": "nodenext",
    "verbatimModuleSyntax": true,
    "isolatedModules": true,
    "noUncheckedIndexedAccess": true,
    "noImplicitOverride": true,
    "noUncheckedSideEffectImports": true,
    "types": [],                     // 每个包自己列出需要的全局类型，比如 ["node"]
    "composite": true,               // 会自动打开 declaration，并要求源码都被 include 覆盖
    "declarationMap": true,
    "sourceMap": true,
    "skipLibCheck": true             // 如果有手写的 .d.ts，需要另外用 skipLibCheck: false 单独检查（见第四节）
  }
}
```

**各包的 `packages/b/tsconfig.json`**：

```jsonc
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "rootDir": "src",
    "outDir": "dist",
    "tsBuildInfoFile": "dist/.tsbuildinfo",
    "types": ["node"]
  },
  "include": ["src"],
  "references": [{ "path": "../a" }]   // 必须和 package.json 里的 workspace:* 依赖一一对应
}
```

测试代码的全局类型和源码不同，所以单独建一个 `packages/b/tsconfig.test.json`：`include: ["test"]`，`types: ["node", "<测试框架>"]`，`references: [{ "path": "." }]`，并且也要加进总入口的 `references`。否则测试代码根本不会被类型检查。

**根目录 `tsconfig.json`（总入口）**：

```jsonc
{ "files": [], "references": [
  { "path": "packages/a" }, { "path": "packages/b" }, /* …c d e，以及各包的 tsconfig.test.json */
]}
```

**包与包之间怎么取类型**：两种方式只能选一种，混用会导致编辑器、CI 和运行时看到的类型不一样。我建议**先构建再使用**：

```jsonc
// packages/a/package.json
"exports": { ".": { "types": "./dist/index.d.ts", "default": "./dist/index.js" } }
```

- `types` 必须写在每个条件对象的第一位，否则不会被读到。
- 不要再用 `paths` 去指向其他包的 `src`。
- 只有你确实需要"直接读源码"时，才改用 `customConditions` 方案，而且打包器和测试运行器也必须支持同一个条件。

**另外两点**：

- 包之间不能形成环形引用。出现环说明包的边界划分有问题，得拆分包，而不是去改配置。
- 在 CI 里加一个小脚本，比对每个包的 `workspace:*` 依赖和它的 `references`，不一致就失败，防止两边慢慢对不上。

## 三、升级步骤（每一步单独提交）

**第 0 步：盘点**
- 运行 `pnpm why typescript`，确认整个仓库只解析到一个版本。用 pnpm `catalog:` 或根目录的 `overrides` 固定版本。
- 列出所有调用 TypeScript 编译器 API 的工具：typescript-eslint、vue-tsc、api-extractor 或 rollup-plugin-dts、ts-jest、ts-node、各种 IDE 插件。**TS 7.0 不提供编译器 API**，这些工具决定了后面怎么切换。

**第 1 步：在当前 5.x 上改结构**
- 按第二节改成项目引用，不升级版本。
- 运行 `tsc -b`，确保零错误，并且错误数和改之前一样。重构结构和升级编译器绝不混在同一次提交里。

**第 2 步：5.x → 6.0（过渡版）**
- 6.0 改了不少默认值：`strict` 变为 true、`module` 变为 esnext、`types` 变为 `[]`、`rootDir` 默认是 tsconfig 所在目录、`noUncheckedSideEffectImports` 变为 true。上面的 base 已经把这些都显式写出来了。
- 6.0 废弃了几项写法，需要逐个改掉：
  - `moduleResolution: node`/`node10` 改成 `nodenext` 或 `bundler`；
  - 删掉把 `baseUrl` 当查找根目录的用法，把前缀直接写进每一条 `paths`；能用 `package.json#imports`（`#internal/*`）的地方优先用它。
- 新出现的错误，要么修好，要么加 `// @ts-expect-error <原因>`。**不要用 `ignoreDeprecations`**，否则到 7.0 会直接报错。
- 完成标准：6.0 下零错误、零废弃警告，然后再清理掉那些 `@ts-expect-error`。

**第 3 步：6.0 → 7.x（原生编译器）**
- 编译器 API 的使用方先检查各自的版本支持范围。不支持 7 的，继续通过官方发布的 `@typescript/typescript6`（自带 `tsc6` 命令和 6.0 API）运行，具体别名写法以 TypeScript 团队文档为准。在 pnpm overrides 里明确记录哪些工具留在 6，不要让两个版本意外混用。
- 核对 7.x 发布说明里关于 `--build`（项目引用构建）和增量模式的支持情况，再把类型检查命令切到 7。
- typescript-eslint 的类型感知规则需要编译器 API。如果它还不支持 7，lint 这一步就固定用 6 的 API；类型检查本身用 7。

## 四、验证

| 检查项 | 命令 | 通过标准 |
|---|---|---|
| 全量类型检查 | `pnpm exec tsc -b`（在根目录） | 退出码 0；错误数和上一步记录的基线一致 |
| 增量只查受影响的包 | 改叶子包 `a` 的私有实现后运行 `tsc -b --verbose` | 只有 `a` 重新构建，`b`～`e` 显示为已是最新 |
| 改动沿依赖向下传 | 改 `a` 的导出类型后运行 `tsc -b --verbose` | `a` 以及依赖它的包都重新检查，无关的包不动 |
| 性能 | 改造前后各跑一次 `tsc -b --extendedDiagnostics` | 记录全量耗时和单包增量耗时 |
| 手写的 `.d.ts` | `tsc --noEmit --skipLibCheck false -p <只包含 types/ 的配置>` | 零错误 |
| 类型感知 lint | `eslint .`（`projectService: true`，关键规则设为 `error`） | 零错误 |
| 运行时测试和构建 | 仓库现有的 test/build 脚本 | 全部通过 |
| 对外发布的包 | `pnpm pack` → `attw <tarball>` → 在临时项目里按 nodenext 和 bundler 两种方式导入每个入口并检查类型 | 每个入口都能解析到类型，且模块格式正确 |
| CI 门禁 | CI 运行 `tsc -b`，覆盖源码、测试和脚本的所有 tsconfig | 有任何错误就失败 |

注意：用 tsx、esbuild、SWC 或打包器能跑通，只说明语法能被转换，**不能当作类型检查通过的证据**。
