### Review round 8: two P1s accepted, fixed by DELETING the enumeration

`codex` returned two P1s on the obligation-pinned candidate. Both are accepted as real, but the remediation deliberately differs from the one proposed, and the reason is the convergence signal rather than a preference.

**(a)** The protected condition listed permission/authorization, data-safety, and finality controls; abuse/rate-limit, financial, security, and availability obligations fall outside it, so those could still be abandoned on a self-recorded acceptance. **(b)** The fixture pinned the operative fragments but not the condition that binds them, so narrowing the condition keeps every assertion green.

The proposed fix for (a) was to extend the list. That is the fourth consecutive round of the same class — each round names a class the previous list omitted — and this repository's own rule says same-class recurrence across rounds is a design signal, not a cue to patch again. An enumeration of protected risk classes is permanently one unlisted class away from letting a real control out, and (b) is only exploitable *because* a condition exists to narrow.

So the enumeration is deleted rather than extended. The unconditional scope is itself pinned, because the most likely future edit is a well-meaning "clarification" back into a list — exactly what round 8 proposed. It required a named owner and a stated cost, but no approval of the deferral, no end, and no consequence for reaching the end — so a landing could write "pending, owner X, cost Y", ship, and the dead claim would keep charging rent forever, which is precisely the tax the firing point exists to stop. An unbounded exception to a rule against unbounded enforcement is the failure wearing the fix's clothes.

Fixed: `pending` is now an accepted risk with an end, not a note. The named accountable risk owner accepts the **deferral itself**; the record states the cost being paid meanwhile and the event that ends it — at the latest, the next landing that touches the mechanism; and arriving there without a disposition escalates through `feature-risk-router` rather than renewing quietly. The bound is an observable event rather than a date, because this repository has no scheduler to fire a date and a date nobody reads is another silent renewal. All four obligations are pinned and each was mutation-tested individually.

**P1 (b), half accepted — the same request round 9 declined, re-verified rather than re-declined by reflex.** The comparator half is declined again on the same two legs, now checked twice against the current candidate rather than inherited: an author who adds "except availability controls" to the section edits this fixture in the same commit, so a normative-block comparator buys no detection against them (`trust-model fit`), and it reds on every legitimate wording edit to a clause this round has already reworded four times (`marginal cost`).

But the finding's second half is right and costs nothing: *stop treating fragment presence as evidence that the semantics survived*. The plan's own wording ("one assertion per obligation") did read as a semantic guarantee. The fixture now states its limits in place — these assertions catch deletion, rewording-away, and relocation, and they do **not** catch a weakening sentence added beside them; a green run is not evidence the rule still means what it meant, and catching a deliberate weakening is the dual-track review's job. Naming the limit is the honest version of what a comparator would only pretend to provide.

### Review round 11: three findings, all accepted

**P1 (a) — the deferral bound named the wrong actor.** Round 10's fix ended a pending retirement at "the next landing that touches the mechanism". But nobody has to touch it: the mechanism keeps running and charging every landing that *invokes* it, while the bound waits for an edit that may never come. The tax is paid by the callers, so the bound now ends at **the first landing that pays the cost** — the next one that invokes or modifies it. Two rounds in a row on this same clause, and the pattern is worth naming: an escape hatch attracts exactly the errors the main rule was written to prevent, so it deserves the same adversarial attention as the rule, not less.

**P1 (b) — one deferral obligation was stated but never pinned.** The rule requires recording the per-change cost being paid meanwhile; no assertion covered it, so it could be deleted with the fixture green, contradicting this plan's own claim that each obligation is pinned. Anchor added, deletion mutation reds it.

**P2 (c) — the prose co-location check was brittle in the legitimate direction.** `assert_same_line` on the sibling paragraph would red if a formatter wrapped the destination path onto the next physical line, even though rendered routing is unchanged. A false red on a shared gate is a real cost — the `marginal cost` leg applied to this round's own fixture. Prose now uses `assert_same_paragraph` (blank-line-delimited block). Verified in both directions, because loosening a check is the change that most needs proof it did not go blind: a legitimate rewrap passes, and deleting the pointer from that same paragraph still reds.

### Review round 12: one P1 accepted, resolved by stating what the packet cannot prove

The only finding: at release depth, the sole evidence that the fixture, the repository checker, and the full suite pass is text authored inside the candidate itself, so a reviewer cannot tell a real green from a false one.

Accepted, and it is correct about the packet. The remedy is not to embed self-attesting outputs — a candidate that certifies itself is the same shape, one indirection deeper, and this repository already rules on it: CI authority comes from the protected platform, never from candidate-local text. So the verification section now labels its rows as implementer-run evidence rather than proof, and carries an explicit `pending` row for the authoritative CI execution, which cannot exist while the branch is unpushed. That is what the finding asked for — keep the release verdict pending until those executions are available — stated in the repository's own terms.

### Adversarial challenge on the landing candidate: one P1, accepted

The challenge found the hole in the branch I never guarded. The rule offers two dispositions — re-base or retire — but the obligation walk was written as "*Retiring* one is not a deletion either", so it was grammatically scoped to retirement alone. A re-base rewrites the enforcement surface just as thoroughly: it can drop an independent live obligation the mechanism also carried, or keep enforcing the withdrawn claim under a new name, and every pinned clause in the rule would still be satisfied. Both failure modes are the ones this round exists to prevent, reachable through the disposition it recommends first.

Accepted. The walk now binds both paths explicitly, and a re-base additionally has to show that no component still enforces the withdrawn claim — otherwise the tax has only moved rather than gone. Two anchors added, each mutation-tested: scoping the walk back to retirement alone reds, and dropping the carry-forward check reds.

Worth recording as the round's own lesson, since it is the third instance of one shape: **the escape routes and the secondary branches of a rule attract the exact failures the main clause was written to prevent** — the unbounded `pending`, the self-accepted loss, and now the unwalked re-base. All three read as harmless while the headline rule reads as strict.

One note on my own verification: fixing this broke a fixture anchor, because the rewrite moved a pinned sentence to the start of a sentence and capitalised its first word while the anchor matched the lowercase form. The fixture caught it immediately, which is the behaviour these pins exist for — the anchor is now written to match independently of sentence position.

### Staging defect: the commits lagged the reviewed content

Recorded because it invalidated real evidence, not as a footnote.

Each round's candidate was rebuilt with `git reset --soft <base>` followed by a commit. `reset --soft` **keeps the index**, and edits made after the last `git add` were never staged — so every rebuild committed the previously-staged state while the newest fixes stayed in the working tree. The defect compounded silently across rounds: by the time the branch was pushed, the committed tree was missing the loss-acceptance clause, the bounded deferral, the re-base walk, the section-bound anchors, and the paragraph-scoped helper.

What this did and did not invalidate, established by reading the harness rather than assuming:

- **The reviews and the challenge remain valid.** `review_gate.py` builds its packet from `git diff --no-color <base>` — the **working tree**, not `HEAD` — so every reviewer saw the complete content. This is confirmed behaviourally too: round 7 raised findings about the loss-acceptance clause, which existed only in the working tree at that moment.
- **`make test` and the fixture runs remain valid** for the same reason: they read files from disk.
- **The first CI run and the committed-diff-scoped gates were invalid.** CI run `32406950446` was green on an incomplete tree, and `check-ccl-skills.sh`'s impact-chain gate scopes to the committed diff, so its verdict covered content that was not the reviewed content. Both were re-run after the history was rebuilt.

The recurrence control is mechanical, not a resolution to be careful: every candidate rebuild now ends with `git status --porcelain` asserted empty and `git diff <base>` compared byte-for-byte against `git diff <base> HEAD`. A candidate whose committed tree differs from the tree that was reviewed is not a candidate.
