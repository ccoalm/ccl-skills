# 拆分通知服务 技术设计

## 领域模型与不变量

1. 同一事件同一渠道至多通知一次：订单服务重复投递同一事件时，用户在同一渠道也只收到一次通知。保证方式：deliveries 表以 (event_id, channel) 为唯一键，插入成功才发送；集成测试 duplicate_event_sends_once。
2. 通知偏好只有一个写入方：各渠道开关和联系方式归通知服务所有，只有通知服务写；订单服务和客服后台不再直接改这些数据，改为调通知服务的接口。保证方式：数据迁到通知服务自己的库，回收订单库上这几列的写权限；契约测试 preferences_only_written_through_notify_api。
3. 关闭渠道后不再发送：用户关闭某个渠道之后，该渠道不再发出任何通知，包括已经在队列里的。保证方式：发送前一刻重新读取偏好再决定是否发送，而不是入队时判断；单测 queued_notification_dropped_after_opt_out。
4. 下单不受通知影响：下单不等待通知发送，也不会因为通知失败而失败。保证方式：订单服务在本地事务里写 outbox，由后台投递事件；故障注入测试 order_succeeds_when_notify_is_down。

## 分层与依赖方向

入口适配器（事件消费者、HTTP 路由）调用领域服务；供应商适配器实现领域层定义的发送接口。依赖只朝里指：领域层不 import Fastify、数据库驱动或供应商 SDK。

## 运行时

- 进入通知服务的事件和请求在边界上用运行时 schema 校验，TypeScript 类型在运行时不存在，不能当作校验。
- 对供应商的出站调用有上限：每次调用 3 秒超时，每个供应商并发不超过 20，重试最多 3 次，队列长度超限时拒绝新任务。
